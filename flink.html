三层防线处理迟到数据

  • Watermark：允许一定延迟（如 3 秒），Watermark 到达后才触发窗口计算
  • Allowed Lateness：窗口触发后再等一段时间（如 1 分钟），期间新到的数据会重新计算
  • Side Output：超过 Allowed Lateness 的数据输出到侧输出流，不丢弃

Checkpoint 配置要点

  • 间隔：Checkpoint 间隔（如 1 分钟），太频繁影响性能，太稀疏恢复慢
  • 超时：Checkpoint 超时时间，防止卡住
  • 最小间隔：两次 Checkpoint 之间的最小间隔
  • 并发数：同时进行的 Checkpoint 数量（默认 1）
  • 模式：EXACTLY_ONCE（Barrier 对齐）或 AT_LEAST_ONCE（不对齐，更快）

1.7 背压与内存管理

背压 (Backpressure)

当下游算子处理速度跟不上上游时，网络缓冲区满，上游被阻塞。Flink 基于信用-based 流控：下游告诉上游自己还能接收多少数据。

排查：Flink Web UI → 反压面板，红色表示高背压。解决：增加并行度、优化算子逻辑、增加内存。

2.6 性能调优

调优要点

  • 并行度：算子并行度 = min(Partition 数, Slot 数)
  • 算子链：相邻算子合并为一个 Task，减少网络开销（startNewChain / disableChain）
  • Slot Sharing：同一 Job 的不同算子共享 Slot，提高资源利用率
  • 内存配置：TaskManager 内存 = 框架堆 + Task 堆 + 网络缓冲 + 管理内存 + RocksDB
  • 反压处理：增加并行度、优化算子逻辑、增加网络缓冲区

🎤第三部分：模拟面试

Flink 和 Spark Streaming 最本质的区别？
计算模型不同。Flink 是真正的流处理，数据逐条到达逐条处理，延迟 ms 级。Spark Streaming 是微批处理，把流数据切成小批次（如 1 秒一批），本质上还是批处理。这导致 Flink 天然支持 Event Time、Watermark、完善的 State 管理和 Exactly-Once Checkpoint。
什么是 Watermark？为什么需要它？
Watermark 是一个时间戳，表示"在此之前的数据基本到齐了"。网络传输可能导致数据乱序到达，Watermark 告诉 Flink "可以触发窗口计算了"。设置 Watermark 延迟（如 3 秒）可以容忍乱序，但会增加端到端延迟。配合 Allowed Lateness + Side Output 处理迟到数据。
Flink 的 Checkpoint 机制？
基于 Chandy-Lamport 分布式快照算法。JobManager 定期向 Source 注入 Barrier，Barrier 随数据流向下游传播。当算子收到所有输入的 Barrier 后，快照自己的 State 到 State Backend（如 HDFS/RocksDB）。故障恢复时从最近的 Checkpoint 恢复 State，重放 Source 数据。
如何保证端到端 Exactly-Once？
需要 Source 和 Sink 都支持——① Source：可重放（如 Kafka，记录 offset）；② 算子：Checkpoint 保证 State 一致性；③ Sink：两阶段提交（2PC）或幂等写入。Flink 的 TwoPhaseCommitSinkFunction 在 Pre-commit 写入临时文件，Checkpoint 完成后 Commit 真正写入。
Flink 的 Window 有哪些类型？
Tumbling（固定不重叠）、Sliding（固定有滑动）、Session（按活跃间隔）、Count（按数量）、Global（所有数据进同一窗口，配合 Trigger）。按驱动方式分为 Time Window 和 Count Window。最常用的是 Tumbling + Event Time + Watermark。
什么是 State？有哪些类型？
State 是算子在处理数据过程中需要记住的信息。Keyed State 绑定在 KeyedStream 的每个 Key 上：ValueState（单值）、ListState（列表）、MapState（映射）、ReducingState（聚合）、AggregatingState（聚合，输入输出不同）。Operator State 绑定在算子实例上，如 Source 的 offset。
State Backend 怎么选？
HashMap State Backend：State 存 JVM Heap，最快但受 GC 影响，适合小 State（<100MB）。EmbeddedRocksDB State Backend：State 存本地磁盘 + 内存，不受 GC 影响，支持增量 Checkpoint，适合大 State（GB~TB 级）。生产环境推荐 RocksDB。
什么是背压？Flink 怎么处理？
下游算子处理速度跟不上上游，缓冲区满导致上游阻塞。Flink 基于信用-based 流控：下游告诉上游自己还能接收多少数据。排查：Web UI 反压面板。解决：① 增加并行度；② 优化算子逻辑（减少外部调用）；③ 增加网络缓冲区；④ 检查是否有数据倾斜。
Flink CDC 是什么？
基于 Debezium 的 Change Data Capture 组件，读取 MySQL Binlog 实现全量+增量一体化同步。2.x 版本：单并行度读取全量快照，无缝切换到增量 Binlog。优势：无需 Canal/Debezium 等额外组件，Flink 直接消费 CDC 数据流。
如何处理迟到数据？
三层防线——① Watermark：设置允许延迟（如 3 秒），Watermark 到达后才触发窗口；② Allowed Lateness：窗口触发后再等一段时间（如 1 分钟），新到数据重新计算；③ Side Output：超过 Allowed Lateness 的数据输出到侧输出流，不丢弃，可后续处理。
Checkpoint 和 Savepoint 的区别？
Checkpoint：Flink 自动触发，定期保存，Job 取消后默认删除，用于故障恢复。Savepoint：用户手动触发，不会自动删除，用于版本升级（改代码后从 Savepoint 恢复）、A/B 测试、集群迁移。Savepoint 本质上也是一种 Checkpoint，但更"持久"。
