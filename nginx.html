第一部分：技术原理

1. 整体架构 — Master-Worker 进程模型

Nginx 进程模型
Nginx 主进程 (Master Process)
负责：读取配置文件、管理 Worker 进程、支持热部署（reload）
▼ fork
Worker 进程 1
epoll/kqueue
Worker 进程 2
epoll/kqueue
Worker 进程 N
epoll/kqueue
每个 Worker 是单线程，通过 IO 多路复用处理数千并发连接

Master 进程职责

  • 读取并验证配置：启动时读取 nginx.conf，检查语法正确性
  • 管理 Worker 进程：接收信号（如 SIGHUP 热重载、SIGTERM 停止），向 Worker 发送对应信号
  • 热部署：通过 nginx -s reload 实现不停机更新配置——先启动新的 Worker，再优雅关闭旧 Worker
  • 创建 / 回收 Worker：Worker 异常退出后，Master 会自动重新 fork 新的 Worker

Worker 进程工作原理

  • 单线程 + 事件驱动：每个 Worker 进程运行在单线程中，避免了线程上下文切换和锁竞争
  • IO 多路复用：Linux 下使用 epoll，macOS/FreeBSD 下使用 kqueue，通过非阻塞 IO 处理海量连接
  • 连接处理：一个 Worker 可同时处理数千个连接，适合高并发、IO 密集型场景
  • Worker 数量：一般设置为 CPU 核心数（worker_processes auto;），充分利用多核
💡 为什么 Nginx 性能高？
核心在于 Master-Worker 架构 + 事件驱动 + 非阻塞 IO。传统 Apache 的 prefork 模型每个请求一个进程/线程，而 Nginx 的单个 Worker 可以处理数千连接，内存占用极低。

重点阶段详解

阶段核心指令说明
rewrite rewrite、return 对 URI 进行重写或重定向；会循环执行直到不再变化（最多 10 次，防止死循环）
access allow/deny、auth_basic、limit_req 访问控制：IP 黑白名单、HTTP 基础认证、限流等；任一模块拒绝则返回 403/401
content proxy_pass、root、fastcgi_pass 生成响应内容：静态文件服务、反向代理转发、FastCGI 处理等
post-read realip 获取客户端真实 IP（通过 X-Forwarded-For 等头）
log access_log、error_log 记录访问日志和错误日志，不影响请求结果
⚠️ 面试要点：每个阶段的模块是按顺序执行的，同一阶段内多个模块的执行顺序取决于模块类型和加载顺序。rewrite 阶段在 access 阶段之前，所以 return 301 的重定向会优先于 allow/deny 的访问控制。

配置块层级关系

location
# main 块：全局配置
worker_processes auto;
error_log /var/log/nginx/error.log;

events {
    worker_connections 65535;
}

http {
    # http 块：HTTP 全局配置
    include       mime.types;
    default_type  application/octet-stream;
    sendfile      on;
    keepalive_timeout 65;

    server {
        # server 块：虚拟主机配置
        listen 80;
        server_name example.com;

        location / {
            # location 块：请求路径匹配
            root /var/www/html;
            index index.html;
        }

        location /api/ {
            proxy_pass http://backend;
        }
    }
}

Location 匹配优先级

当一个请求匹配多个 location 块时，Nginx 按以下优先级选择：

符号匹配方式优先级说明
= 精确匹配 最高 URI 必须完全相同，匹配成功立即停止搜索
^~ 前缀匹配（禁止正则） 高 匹配最长前缀，匹配成功后不再检查正则
~ 正则匹配（区分大小写） 中 按配置文件中的顺序，第一个匹配的正则生效
~* 正则匹配（不区分大小写） 中 同上，但忽略大小写
/path 普通前缀匹配 低 匹配最长前缀，如果有正则匹配则被覆盖
/ 通用匹配 最低 所有请求都会匹配，兜底规则
💡 匹配记忆口诀：精确 = 优先，前缀 ^~ 禁正则，正则 ~/~* 按序匹配，普通前缀找最长，通用 / 兜底。
实际案例：= /api/health 健康检查精确匹配 > ^~ /static/ 静态资源 > ~ \.php$ PHP 处理 > / 默认处理。

配置继承规则

  • 子块会继承父块的配置，但可以在子块中覆盖
  • http 块中设置的 gzip on 会被所有 server/location 继承
  • 某些指令（如 proxy_set_header）在子块中设置后会覆盖父块的全部同类配置（而非合并）
  • location 中使用 include 可以引入外部配置片段，便于模块化管理

4. 反向代理原理 — proxy_pass 机制

反向代理基本流程

Client
→
Nginx (反向代理)
→
Backend Server

Nginx 接收客户端请求，将请求转发给后端服务器，获取响应后返回给客户端。客户端不知道后端服务器的存在。

proxy_pass 配置详解

# 基本反向代理
location /api/ {
    proxy_pass http://backend_server;
}

# 注意尾部斜杠的区别：
# location /api/ + proxy_pass http://backend/  → /api/test → /test （路径替换）
# location /api/ + proxy_pass http://backend    → /api/test → /api/test （路径保留）
⚠️ proxy_pass 尾斜杠陷阱：当 proxy_pass 的 URL 包含 URI（如 http://backend/）时，Nginx 会用该 URI 替换匹配的 location 前缀；不包含 URI 时，整个原始请求路径会被原样传递。

请求头传递

# 设置转发给后端的请求头
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

# 超时设置
proxy_connect_timeout 60s;   # 连接后端超时
proxy_read_timeout 60s;      # 读取响应超时
proxy_send_timeout 60s;      # 发送请求超时

# 缓冲设置
proxy_buffering on;
proxy_buffer_size 4k;
proxy_buffers 8 16k;

WebSocket 代理配置

# WebSocket 升级
location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;  # WebSocket 长连接需要较长超时
}

WebSocket 通过 HTTP Upgrade 机制升级协议，Nginx 需要显式设置 Upgrade 和 Connection 头才能正确转发握手请求。

第二部分：场景化讲解

1. 负载均衡策略

upstream 配置与负载均衡策略

# 定义上游服务器组
upstream backend {
    # 负载均衡策略（默认轮询）
    server 192.168.1.1:8080;
    server 192.168.1.2:8080;
    server 192.168.1.3:8080;
}

各负载均衡策略对比

策略配置原理适用场景
轮询 默认（无需配置） 按请求顺序依次分配到后端服务器 后端服务器性能一致、无状态服务
加权轮询 server x weight=3; 按权重比例分配请求，权重越高分配越多 后端服务器性能不同，按能力分配流量
IP Hash ip_hash; 根据客户端 IP 的 hash 值分配，同一 IP 总是访问同一后端 需要 session 粘性，保持会话状态
最少连接 least_conn; 将请求分配给当前活跃连接数最少的后端 后端请求处理时间差异大（如长连接场景）
一致性哈希 hash $request_uri consistent; 对指定变量做一致性哈希，相同请求总是路由到同一后端 缓存场景，减少缓存失效，后端扩缩容影响小

后端服务器高级配置

upstream backend {
    least_conn;

    server 192.168.1.1:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 192.168.1.2:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 192.168.1.3:8080 weight=1 backup;   # 备用服务器
    server 192.168.1.4:8080 down;              # 标记为不可用

    keepalive 32;  # 保持的长连接数
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";  # keepalive 需要清除 Connection 头
    }
}
  • max_fails：允许失败次数，超过后标记为不可用
  • fail_timeout：失败检测的时间窗口 + 标记不可用后的恢复等待时间
  • backup：仅在主服务器全部不可用时才接收请求
  • down：永久标记为不可用（维护时使用）

2. 缓存机制

proxy_cache 配置

# 在 http 块中定义缓存区域
proxy_cache_path /var/cache/nginx levels=1:2
    keys_zone=my_cache:10m max_size=10g
    inactive=60m use_temp_path=off;

server {
    location / {
        proxy_pass http://backend;

        # 启用缓存
        proxy_cache my_cache;
        proxy_cache_valid 200 302 10m;   # 200/302 缓存 10 分钟
        proxy_cache_valid 404 1m;        # 404 缓存 1 分钟
        proxy_cache_valid any 5m;        # 其他状态码缓存 5 分钟

        # 缓存 key
        proxy_cache_key $scheme$proxy_host$request_uri;

        # 添加缓存状态头
        add_header X-Cache-Status $upstream_cache_status;
    }
}

缓存命中流程

客户端请求
→
Nginx 检查缓存
→
命中 → 直接返回
未命中
→
请求后端
→
响应写入缓存
→
返回客户端

$upstream_cache_status 状态值：HIT（命中）、MISS（未命中）、EXPIRED（已过期）、STALE（使用过期缓存）、UPDATING（正在更新缓存）。

缓存穿透与击穿解决方案

# 缓存锁：防止缓存击穿（同一资源失效时只允许一个请求穿透到后端）
proxy_cache_lock on;
proxy_cache_lock_timeout 5s;
proxy_cache_lock_age 5s;

# 缓存穿透：对空结果也缓存（配合后端返回合理的空响应）
proxy_cache_valid 200 10m;
proxy_cache_valid 404 1m;

# 后端不可用时使用过期缓存
proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
  • 缓存穿透：请求的数据不存在，每次请求都穿透到后端。解决：对 404 结果也缓存短时间
  • 缓存击穿：热点 key 过期瞬间大量请求涌向后端。解决：proxy_cache_lock 只放行一个请求去后端更新缓存，其他请求等待
  • 缓存雪崩：大量缓存同时过期。解决：在 proxy_cache_valid 中使用 random 指令让过期时间分散

3. 性能优化

核心性能优化配置

# === 进程与连接 ===
worker_processes auto;              # 自动匹配 CPU 核心数
worker_rlimit_nofile 65535;         # 每个 Worker 最大打开文件数
events {
    worker_connections 65535;        # 每个 Worker 最大连接数
    multi_accept on;                 # 一次 accept 多个连接
    use epoll;                       # 使用 epoll 事件模型
}

# === 传输优化 ===
http {
    sendfile on;                     # 零拷贝传输，内核直接发送文件
    tcp_nopush on;                   # 配合 sendfile，数据包累积到一定大小再发送
    tcp_nodelay on;                  # 小数据包立即发送（keepalive 连接下）

    keepalive_timeout 65;            # 长连接超时时间
    keepalive_requests 1000;         # 单个长连接最大请求数

    # === Gzip 压缩 ===
    gzip on;
    gzip_min_length 1k;              # 最小压缩文件大小
    gzip_comp_level 4;               # 压缩级别 1-9
    gzip_types text/plain text/css application/json application/javascript text/xml;
    gzip_vary on;                    # 添加 Vary: Accept-Encoding
    gzip_proxied any;                # 代理请求也压缩

    # === 文件缓存 ===
    open_file_cache max=10000 inactive=20s;  # 缓存文件句柄和元信息
    open_file_cache_valid 30s;       # 多久重新检查缓存有效性
    open_file_cache_min_uses 2;      # inactive 期间最少访问次数
    open_file_cache_errors on;       # 缓存文件查找错误
}
💡 优化要点总结
① sendfile：避免内核态和用户态之间的数据拷贝，显著提升静态文件传输速度
② tcp_nopush：配合 sendfile，将响应头和数据打包发送，减少网络包数量
③ tcp_nodelay：在 keepalive 连接下，小数据不等缓冲区满就立即发送，降低延迟
④ open_file_cache：缓存已打开文件的句柄和 stat 信息，避免频繁的文件系统调用

4. 限流与安全

limit_req — 请求限流（漏桶算法）

# 在 http 块中定义限流区域
# rate=10r/s 表示每秒 10 个请求
limit_req_zone $binary_remote_addr zone=req_limit:10m rate=10r/s;

server {
    location /api/ {
        # burst=20：允许突发 20 个请求排队
        # nodelay：突发请求立即处理，不排队等待
        limit_req zone=req_limit burst=20 nodelay;
        limit_req_status 429;       # 自定义限流返回状态码
        proxy_pass http://backend;
    }
}
  • 漏桶算法：请求以固定速率流出，超出速率的请求被排队或拒绝
  • rate=10r/s：每秒允许 10 个请求（底层以毫秒级精度：100ms 一个）
  • burst=20：突发队列大小，最多排队 20 个请求
  • nodelay：不排队等待，突发请求直接处理（但仍受 burst 数量限制）

limit_conn — 连接数限制

# 按客户端 IP 限制并发连接数
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

server {
    limit_conn conn_limit 10;       # 每个 IP 最多 10 个并发连接
    limit_conn_status 429;

    # 按请求带宽限速
    limit_rate_after 1m;            # 下载 1M 后开始限速
    limit_rate 100k;                # 限速 100KB/s
}

SSL/TLS 安全配置

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/cert.pem;
    ssl_certificate_key /etc/nginx/ssl/key.pem;

    # 协议与加密套件
    ssl_protocols TLSv1.2 TLSv1.3;

    add_header Strict-Transport-Security "max-age=63072000" always;

    add_header X-Content-Type-Options nosniff;

    # HTTP → HTTPS 跳转
}

server {

}

防盗链配置

# 基于 Referer 的防盗链
location ~* \.(jpg|jpeg|png|gif|mp4)$ {
    valid_referers none blocked server_names *.example.com;
    if ($invalid_referer) {
        return 403;
        # 或返回防盗链提示图片：rewrite ^ /images/hotlink-denied.png break;
    }
}
  • none：允许无 Referer 的请求（直接访问）
  • blocked：允许被防火墙/代理去除 Referer 的请求
  • server_names：允许本域名的引用
  • *.example.com：允许指定域名的子域名引用

第三部分：模拟面试

高频面试 Q&A

Q1：请解释 Nginx 的 Master-Worker 架构，为什么 Nginx 能处理高并发？
参考：Nginx 采用 Master-Worker 多进程架构。Master 进程负责读取配置、管理 Worker 生命周期；Worker 进程负责实际处理请求。每个 Worker 是单线程 + 事件驱动 + 非阻塞 IO，通过 epoll/kqueue 实现 IO 多路复用，单个 Worker 可以同时处理数千个连接。这避免了传统多线程模型的上下文切换和锁开销，内存占用极低。
追问：Worker 进程数应该设置为多少？ 一般设置为 CPU 核心数（worker_processes auto;），让每个核心运行一个 Worker。过多的 Worker 会导致 CPU 缓存抖动和上下文切换，反而降低性能。如果是 IO 密集型场景，可以适当增加，但通常不超过核心数的 2 倍。
Q2：Nginx 的 location 匹配规则是什么？优先级如何？请举例说明。
参考：Nginx location 匹配优先级从高到低为：
① = /path（精确匹配）> ② ^~ /path（前缀匹配，禁止正则）> ③ ~ pattern（区分大小写正则）/~* pattern（不区分大小写正则）> ④ /path（普通前缀匹配）> ⑤ /（通用匹配）

例如请求 /api/user：= /api/user 命中精确匹配直接返回；如果没有精确匹配，检查 ^~ /api；如果没有 ^~，按顺序匹配正则 ~ /api/.*；都没有则使用最长前缀匹配 /api。
追问：精确匹配和前缀匹配有什么实际应用区别？ = 精确匹配常用于健康检查路径（= /health），性能最好（直接查 hash 表）。^~ 前缀匹配常用于静态资源目录（^~ /static/），避免被后续正则覆盖。
Q3：Nginx 如何实现负载均衡？有哪些策略？各自的适用场景是什么？
参考：通过 upstream 模块定义后端服务器组，主要有 5 种策略：
① 轮询（默认）：适合服务器性能一致的无状态服务
② 加权轮询（weight）：适合服务器性能不均的场景
③ IP Hash（ip_hash）：同一 IP 固定路由到同一后端，适合需要 session 粘性的场景
④ 最少连接（least_conn）：适合请求处理时间差异大的场景
⑤ 一致性哈希（hash ... consistent）：适合缓存场景，后端增减时缓存失效最少
追问：IP Hash 有什么缺点？ 如果客户端经过代理或 NAT，大量客户端共享同一个出口 IP，会导致流量分配不均。解决方案是使用 hash $remote_addr consistent 或在代理层获取真实 IP 后再 hash。
Q4：请解释 proxy_cache 的工作原理，如何防止缓存穿透和击穿？
参考：proxy_cache 将后端响应缓存到本地磁盘。当请求到达时，先根据 proxy_cache_key 计算 key 查找缓存：命中则直接返回（HIT），未命中则请求后端并将响应写入缓存。proxy_cache_valid 可按状态码设置不同缓存时间。

防止缓存穿透：对查询结果为空（404）的请求也缓存短时间（proxy_cache_valid 404 1m），避免每次请求都打到后端。
防止缓存击穿：proxy_cache_lock on 在缓存未命中时只放行一个请求到后端更新缓存，其他请求等待锁释放后读取新缓存。
追问：缓存雪崩怎么处理？ 使用 proxy_cache_valid 结合不同的 inactive 时间，或在后端响应中设置随机的 Cache-Control max-age，让缓存过期时间分散。
Q5：Nginx 的 limit_req 和 limit_conn 有什么区别？漏桶算法和令牌桶算法有什么区别？
参考：limit_req 限制请求速率（单位时间内的请求数），基于漏桶算法；limit_conn 限制并发连接数（同一时刻的连接数）。两者可以同时使用。

漏桶算法：请求像水一样注入桶中，桶以固定速率漏水（处理请求）。桶满时新请求被丢弃。特点：输出速率恒定，平滑流量。
令牌桶算法：系统以固定速率生成令牌放入桶中，请求需要拿到令牌才能处理。桶满时令牌丢弃。特点：允许突发流量（桶中积累的令牌）。

Nginx 的 limit_req burst=n 实际上是对漏桶的扩展——burst 相当于桶的大小，nodelay 让突发请求直接通过但消耗桶中位置。
追问：如何对整个 server 而非单个 location 限流？ 将 limit_req_zone 和 limit_req 指令放在 server 块级别即可。
Q6：Nginx 如何实现 WebSocket 代理？为什么需要特殊的配置？
参考：WebSocket 通过 HTTP Upgrade 机制从 HTTP 协议升级为 WebSocket 协议。默认情况下，Nginx 作为 HTTP/1.0 代理，不会转发 Upgrade 和 Connection 头。需要配置：
① proxy_http_version 1.1; — 升级到 HTTP/1.1 协议代理
② proxy_set_header Upgrade $http_upgrade; — 传递 Upgrade 头
③ proxy_set_header Connection "upgrade"; — 设置 Connection 为 upgrade
④ proxy_read_timeout 设置较长超时，因为 WebSocket 是长连接
追问：如果后端有多个 WebSocket 实例，如何做负载均衡？ 可以使用 ip_hash 或一致性哈希，确保同一客户端的 WebSocket 连接始终路由到同一后端实例，避免消息路由问题。
Q7：如何优化 Nginx 的性能？请从进程、网络、缓存、压缩等角度分析。
参考：
进程优化：worker_processes auto 匹配 CPU 核心数；worker_connections 65535 提高单 Worker 最大连接数；worker_rlimit_nofile 提高文件描述符上限。
网络优化：sendfile on 实现零拷贝传输；tcp_nopush on + tcp_nodelay on 优化数据包发送策略；keepalive_timeout 和 keepalive_requests 复用 TCP 连接。
缓存优化：open_file_cache 缓存文件元信息避免重复 stat 调用；proxy_cache 缓存后端响应减少后端压力。
压缩优化：gzip on 压缩文本资源；gzip_min_length 避免压缩过小的文件；gzip_comp_level 4 在压缩率和 CPU 消耗间取得平衡。
追问：如何判断 Nginx 是否成为瓶颈？ 监控 worker_connections 使用率（stub_status 模块）、CPU 使用率、连接等待队列（SYN backlog）。如果 Worker 的活跃连接数接近 worker_connections，需要增加 Worker 数或连接数上限。
