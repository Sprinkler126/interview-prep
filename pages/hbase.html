1.1 数据模型

HBase 数据模型
RowKey → Column Family:Qualifier → Timestamp → Value

示例：
RowKey: "user:1001"
  cf:info     name        t3  → "张三"
  cf:info     email       t2  → "zhangsan@example.com"
  cf:info     age         t1  → "28"
  cf:action   login       t5  → "2026-06-01 10:00"
  cf:action   browse      t4  → "/product/123"

数据模型核心概念

概念说明
RowKey行键，表的唯一标识，按字典序排列，决定数据分布和查询性能
Column Family列族，表的 Schema 需预先定义，存储时物理上按列族分组
Qualifier列限定符（列名），不需要预先定义，可在写入时动态添加
Timestamp版本号，默认为写入时间戳，每个 Cell 可存储多个版本
Value单元格的值，存储为字节数组
Cell最小存储单元，由 RowKey + CF + Qualifier + Timestamp 唯一确定

1.3 Region 管理

Region 基础

  • Region：表按 RowKey 范围水平拆分的分片，是 HBase 分布和负载均衡的基本单位
  • Region 的组成：多个 Store（每个 Column Family 一个 Store）+ WAL
  • Store：一个 MemStore（内存）+ 多个 HFile（磁盘）

Region 分裂 (Split)

Region 大小超过阈值
默认 10GB
触发
找到分裂点
中间 RowKey
执行
生成两个子 Region
各持有原 Region 一半数据
  • 预分区：创建表时预先定义 Region 数量和边界，避免热点和频繁分裂
  • 分裂策略：SteppingSplitPolicy、DisabledRegionSplitPolicy 等

Region 合并 (Merge)

  • 相邻小 Region 可合并，减少 Region 数量
  • 过多小 Region 会增加 ZooKeeper 和 HMaster 的负担
  • 通常在分裂过于频繁或数据删除导致 Region 变小时触发

Region 迁移

  • 负载均衡：HMaster 定期检查 RegionServer 负载，将 Region 从高负载节点迁移到低负载节点
  • 故障转移：RegionServer 故障后，HMaster 将其上的 Region 重新分配到其他 RegionServer
  • 下线迁移：RegionServer 下线前先 Unassign 其上的 Region

Flush（MemStore 满）

有序 KV 存储（HDFS 上） / 多层 HFile / 支持布隆过滤器

HFile 结构

  • Data Block：存储实际的 KV 数据，默认 64KB，按 RowKey 排序
  • Index Block：Data Block 的索引，加速定位
  • Bloom Filter Block：布隆过滤器，快速判断某个 RowKey 是否存在
  • Trailer：指向各 Block 的指针
  • 多层索引：Data Block Index 可分层，支持快速二分查找

Compaction 对比

特性Minor CompactionMajor Compaction
触发条件自动（HFile 数量达到阈值）默认 7 天自动或手动触发
合并范围相邻的小 HFile一个 Store 中所有 HFile
删除数据不清理 TTL 过期或标记删除的数据物理删除过期和标记删除的数据
IO 影响小，可频繁执行大，建议低峰期执行
Major Compaction 期间会产生大量 IO，可能导致读写延迟升高。生产环境建议关闭自动 Major Compaction，改为低峰期手动触发。

设计动机：为什么 HBase 用 LSM-Tree 而不是 B+Tree？

设计起点：HBase 定位是海量数据的高吞吐写入（如 IoT 时序、用户行为日志，每秒百万级写入）。B+Tree 的写入是随机写（要找到对应页再改），数据量大了之后随机 IO 是磁盘杀手。LSM-Tree 把写入变成顺序写内存 + 顺序写磁盘，写入吞吐比 B+Tree 高 1~2 个数量级。

B+Tree (MySQL) — 读写均衡

  • 写入：找页（随机 IO）→ 改页 → 落盘，写放大=1
  • 读取：3-4 次 IO 定位，读放大=树高
  • 适合：读写均衡的 OLTP
  • 痛点：海量写入时随机 IO 瓶颈

✅ LSM-Tree (HBase) — 写优读次

  • 写入：写 MemStore（内存）→ Flush HFile（顺序写），无随机 IO
  • 读取：合并 MemStore + 多 HFile + BlockCache，读放大高
  • 适合：写多读少 + 海量数据
  • 代价：Compaction 写放大、读放大
面试金句：HBase 选 LSM 是因为定位"写多读少海量数据"。B+Tree 随机写在 SSD 上也有上限（磁头/FTL 映射），LSM 顺序写能把 SSD 写吞吐吃满。代价是读取需合并多 HFile——所以 HBase 不擅长复杂查询，只擅长按 RowKey 读写 + 范围扫。
易错点：LSM 不是"读慢"而是"读有放大"——点查（按 RowKey）配合 BlockCache + Bloom Filter 仍很快。慢的是扫描多个 HFile 合并，Compaction 后 HFile 数减少，读性能会回升。

1.4b 二级索引方案 — HBase 的查询短板与解法

设计起点：HBase 只能按 RowKey 查，怎么办？

HBase 只支持按 RowKey 的 GET 和 Scan，没有 MySQL 那样的二级索引。但业务经常要按非 RowKey 列查询（如按手机号查用户）。HBase 社区给出了几种二级索引方案，各有取舍。

方案原理优势劣势
协处理器维护索引表Observer 在写入时同步写一张"索引表"（索引列值作 RowKey → 原表 RowKey）实时一致写放大（写两次），RegionServer 崩溃可能索引不一致
Phoenix 二级索引Apache Phoenix 在 HBase 之上提供 SQL + 二级索引（底层就是协处理器）SQL 接口，易用依赖 Phoenix，全局索引写慢，本地索引有限制
Elasticsearch 异步索引写 HBase 后异步同步到 ES，查询走 ES 拿 RowKey 再回 HBaseES 搜索能力强，灵活最终一致，需维护 ES 集群
二级索引 HBase (Lily/华为)用独立索引 RegionServer 维护索引解耦主表架构复杂
面试要点：HBase 二级索引是它的痛点，没有官方标准方案。生产常见做法是HBase + ES 组合——HBase 存海量明细，ES 存索引做检索，查到 RowKey 后回 HBase 取详情。这也是 HBase 不适合替代 MySQL 的根本原因。

1.5 读写流程

写入流程 (Write Path)

Client 发送 Put 请求
v
写入 WAL（预写日志）
v
写入 MemStore（内存）
v
返回客户端成功
v
MemStore 满 -> Flush 为 HFile
  • 先写 WAL 再写 MemStore（崩溃可从 WAL 恢复）
  • MemStore 按 RowKey 排序，达到阈值（128MB）Flush 为 HFile
  • 写入性能极高：顺序写 WAL + 内存写 MemStore

读取流程 (Read Path)

Client 发送 Get/Scan 请求
v
定位 Region（元数据查询）
v
扫描 Block Cache（读缓存）
v
扫描 MemStore（内存）
v
扫描 HFile（磁盘，布隆过滤器过滤）
v
合并结果返回客户端
  • 需要合并 Block Cache + MemStore + 多个 HFile 的结果
  • 布隆过滤器可快速跳过不包含目标 RowKey 的 HFile
  • 读取性能比写入差（多处查找 + 合并），Compaction 可改善

读取优化手段

  • Block Cache：读缓存，LRU 淘汰，热点数据常驻内存
  • Bloom Filter：Row 级别或 Row+Column 级别布隆过滤器，减少无效 HFile 扫描
  • Compaction：减少 HFile 数量，减少合并次数
  • 列族设计：将查询时一起访问的列放在同一 Column Family

1.6 RowKey 设计

RowKey 设计原则

原则说明
唯一性RowKey 必须唯一，相同 RowKey 的数据被视为更新
散列性避免单调递增 RowKey 导致写热点集中到一个 Region
长度建议 10~100 字节，过长浪费存储和内存
业务相关将查询条件中常用的字段编码进 RowKey

热点避免策略

加盐 (Salting)

// 原始 RowKey: 001, 002, 003
// 加盐后: a001, b001, c001
//         a002, b002, c002
prefix = hash(rowkey) % N

优点：打散效果好。缺点：范围查询需要扫描 N 个 Region。

反转 (Reversing)

// 原始: 192.168.1.1
// 反转: 1.1.168.192
// 时间戳反转: Long.MAX - ts

适合前缀变化少、后缀变化多的场景（如 IP 地址、时间戳）。

哈希 (Hashing)

// 原始 RowKey: user_1001
// MD5 前 8 位: a3f2b1c8
// 新 RowKey: a3f2b1c8_user_1001

优点：均匀分布。缺点：失去原始 RowKey 的有序性。

预分区

// 创建表时指定 split points
create 'table', 'cf', SPLITS => ['a', 'b', 'c', 'd']

提前规划 Region 边界，避免初期写入集中。

RowKey 设计示例

场景RowKey 设计说明
用户行为日志reversed_ts_userId时间反转 + 用户 ID，支持按时间范围查询
订单表hash(userId)_userId_orderId用户 ID 哈希前缀打散 + 按用户查询
时序数据metric_ts_deviceId指标 + 时间 + 设备，支持多维查询

2.1 过滤器 (Filter)

HBase 过滤器类型
过滤器用途示例
RowFilter按 RowKey 过滤new RowFilter(CompareOp.EQUAL, new BinaryComparator(Bytes.toBytes("row1")))
PrefixFilter按 RowKey 前缀过滤new PrefixFilter(Bytes.toBytes("user:"))

PageFilter分页过滤new PageFilter(100) 每页 100 行

过滤器使用示例

Scan scan = new Scan();

// 过滤条件：age > 25
SingleColumnValueFilter filter = new SingleColumnValueFilter(
    Bytes.toBytes("cf"),
    Bytes.toBytes("age"),
    CompareOperator.GREATER,
    Bytes.toBytes("25")
);
filter.setFilterIfMissing(true);
scan.setFilter(filter);

ResultScanner scanner = table.getScanner(scan);

2.2 协处理器 (Coprocessor)

Observer（观察者）

类似触发器，在特定事件前后执行自定义逻辑。

  • RegionObserver：Region 级别的 get/put/scan 前后
  • MasterObserver：Master 级别的 DDL 操作前后
  • WALObserver：WAL 写入前后

场景：数据校验、权限控制、二级索引维护、审计日志

Endpoint（终端）

类似存储过程，在 RegionServer 上执行自定义计算。

  • 将计算逻辑下推到数据所在节点
  • 减少网络传输，提高聚合性能
  • 实现 CoprocessorService 接口

场景：服务端聚合（SUM/COUNT/AVG）、数据统计、复杂查询

2.4 适用场景

适用场景

场景说明示例
时序数据按时间写入，RowKey 反转时间戳IoT 传感器数据、监控指标
用户画像用户 ID 作为 RowKey，动态列存储标签广告推荐、精准营销
日志存储海量写入、按时间范围查询应用日志、操作审计
消息/Feed 流消息 ID 有序写入社交 Feed、消息存档
时空数据GeoHash + 时间戳作为 RowKey地理位置轨迹、出行数据

不适合的场景

  • OLTP 事务：HBase 不支持跨行事务
  • 复杂关系查询：不支持 JOIN，需应用层实现
  • 小数据量：分布式系统有额外开销，小规模数据用 MySQL 更合适
  • 实时随机更新：LSM Tree 写入性能好但读取需合并，频繁更新单条记录效率低

🎤第三部分：模拟面试

HBase 的数据模型是怎样的？和关系型数据库有什么区别？
参考：HBase 是列族存储模型，数据由 RowKey + Column Family + Qualifier + Timestamp + Value 五维定位。区别：① 列族需预定义但 Qualifier 可动态添加；② 空值不占空间（稀疏矩阵）；③ 每个 Cell 可存储多版本；④ RowKey 按字典序排列决定数据分布。
HBase 的读写流程是怎样的？为什么写入比读取快？
参考：写入：先写 WAL（顺序写）再写 MemStore（内存），返回成功后异步 Flush 为 HFile。读取：需合并 Block Cache + MemStore + 多个 HFile 的结果。写入快因为：① 顺序写 WAL；② 内存写 MemStore；③ 异步 Flush。读取慢因为：① 需要多处查找；② 多 HFile 合并；③ 布隆过滤器可优化但仍有磁盘 IO。
LSM Tree 是什么？Compaction 有什么作用？
参考：LSM Tree 是日志结构合并树，写入先进内存（MemStore），满后 Flush 为有序文件（HFile）。Compaction 分两种：Minor 合并相邻小 HFile（自动），Major 合并所有 HFile 并物理删除过期数据（建议手动低峰期执行）。Compaction 可减少 HFile 数量、回收空间，但消耗大量 IO。
HBase 的 RowKey 怎么设计？如何避免写热点？
参考：RowKey 设计原则：唯一性、散列性、长度合理、业务相关。避免热点策略：① 加盐（hash 分前缀打散）；② 反转（时间戳/ID 反转）；③ 哈希（MD5 前缀）；④ 预分区（创建表时定义 Region 边界）。生产中常组合使用，如 hash(userId) + userId + orderId。
HBase 的架构是怎样的？各组件的职责？
参考：ZooKeeper（Master 选举、RegionServer 注册、meta 表位置）、HMaster（DDL 操作、Region 分配、负载均衡）、RegionServer（处理读写、管理 Region）、HDFS（底层存储 HFile 和 WAL）。Client 直接连接 RegionServer 读写数据，不经过 HMaster。
HBase 的协处理器是什么？Observer 和 Endpoint 有什么区别？
参考：Observer 类似触发器，在 get/put/scan 前后执行自定义逻辑（如数据校验、二级索引维护）。Endpoint 类似存储过程，在 RegionServer 上执行计算逻辑（如服务端聚合），减少网络传输。Observer 是事件驱动，Endpoint 是主动调用。
HBase 和 Cassandra 怎么选？
参考：HBase（CP）适合强一致性场景、Hadoop 生态、大数据量。Cassandra（AP）适合高可用、去中心化、多数据中心。HBase 依赖 HDFS 和 ZooKeeper，架构重；Cassandra 无中心节点，部署简单。如果有 Hadoop 生态选 HBase，需要高可用和多数据中心选 Cassandra。
HBase 适合什么场景？不适合什么场景？
参考：适合：海量数据写入、时序数据、用户画像、日志存储、需要水平扩展。不适合：OLTP 事务、复杂关系查询（无 JOIN）、小数据量、需要实时随机更新。核心优势是大数据量下的高吞吐写入和按 RowKey 快速查询。
