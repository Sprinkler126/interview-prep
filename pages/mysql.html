连接层详解

  • 选择索引：决定使用哪个索引、是否走索引下推（ICP）
  • JOIN 顺序：多表 JOIN 时决定表的连接顺序，减少中间结果集

Buffer Pool 工作机制

  • 页管理：以 16KB 数据页为单位管理，使用改进的 LRU 算法（young 区 + old 区，比例 63:37）
  • LRU 优化：新读入的页先放 old 区头部，只有再次被访问（超过 1 秒innodb_old_blocks_time）才移入 young 区，防止全表扫描冲刷热点数据
  • 脏页刷新：Buffer Pool 中被修改但未写入磁盘的页，通过后台线程异步刷盘（innodb_io_capacity 控制刷盘速度）
  • Change Buffer：当修改非唯一二级索引页且该页不在 Buffer Pool 时，先缓存到 Change Buffer，后台合并（merge）到磁盘，减少随机 IO

1.2b Change Buffer 设计动机

为什么需要 Change Buffer？

设计起点：聚簇索引的修改通常是顺序且局部的（按主键定位页），而非唯一二级索引的修改往往是随机 IO——更新一条记录可能命中磁盘上任意位置的索引页。

DML 修改二级索引列
→
目标索引页不在 Buffer Pool？
→
随机读磁盘（costly!）

Change Buffer 的解法：先在内存缓存这次变更，不立即读磁盘，等该页因其他查询被读入 Buffer Pool 时再"合并"（merge），把多次随机 IO 合并成一次顺序写。

DML 命中不在内存的二级索引页
→
变更记录存入 Change Buffer
→
该页被读入 / 后台 merge
→
合并变更一次性落盘

为什么只对"非唯一"二级索引生效？

✅ 非唯一二级索引

  • 插入新值时不需要检查唯一性
  • 变更可以"延迟合并"——记录追加到索引页任意位置即可
  • 因此可以安全缓存，后台 merge

❌ 唯一索引 / 聚簇索引

  • 必须立即读磁盘判断是否违反唯一约束
  • 不能延迟——否则并发插入可能写入重复值
  • 聚簇索引还要更新完整数据行，必须即时落盘定位
面试易错点：Change Buffer 不是缓存"数据"，而是缓存"对索引页的修改操作"。merge 发生在该页被读入内存时，或后台线程定期触发。崩溃恢复靠 redo log 保证不丢失。
适用场景：写多读少的非唯一二级索引。若索引页很快被读（读多写少），Change Buffer 几乎用不上反而有合并开销，可通过 innodb_change_buffering 调整策略。

WAL 机制（Write-Ahead Logging）

事务修改数据
→
写 Buffer Pool（脏页）
→
写 Log Buffer
→
刷 redo log 到磁盘
→
提交完成
  • 核心思想：先写日志再写数据页，保证事务的持久性
  • redo log 刷盘策略（innodb_flush_log_at_trx_commit）：
    • 0：每秒刷盘 → 速度快，最多丢 1 秒数据
    • 1（默认）：每次提交刷盘 → 数据最安全
    • 2：每次提交写 OS 缓存，每秒 fsync → 速度和安全性居中
  • checkpoint 机制：当 redo log 空间不足时，将脏页刷盘并推进 checkpoint，释放已刷盘的 redo log 空间

两阶段提交（2PC）— 保证 Redo Log 和 Binlog 一致性

InnoDB 写 redo log（prepare）
→
Server 写 binlog
→
InnoDB redo log（commit）
崩溃场景状态恢复策略
redo log prepare，无 binlog不一致回滚事务
redo log prepare，有 binlog一致提交事务
redo log commit已完成无需处理

判断 binlog 是否完整：binlog 末尾有 XID event 表示写入完整。MySQL 5.7+ 引入 binlog_group_commit 优化，批量刷盘减少 IO。

1.4 索引原理

B+ 树结构

InnoDB B+ 树索引结构
                     ┌──────────────────────┐
                     │   [20]  [40]  [60]   │  ← 非叶子节点（只存 key + 指针）
                     └──┬─────┬─────┬──────┘
                        │     │     │
              ┌─────────┤     │     ├──────────┐
              ▼         ▼     ▼     ▼          ▼
         ┌─────────┐ ┌───────┐ ┌───────┐ ┌─────────┐
         │10,15,20 │ │25,30,40│ │45,50,60│ │65,70,80 │  ← 叶子节点（存完整数据行）
         └────┬────┘ └───┬───┘ └───┬───┘ └────┬────┘
              │          │         │          │
              ←──────────←────────←──────────←─────── 双向链表（支持范围查询）
  • 非叶子节点：只存储索引键值和子节点指针，不存数据，扇出高（单页可存更多 key）
  • 叶子节点：存储完整数据行（聚簇索引）或主键值（二级索引），叶子节点间用双向链表连接
  • 树高度：通常 2~4 层，千万级数据只需 3~4 次磁盘 IO（每层一次 IO）
  • 页大小：默认 16KB，按 bigint 主键（8B）计算，单页约存 1170 个 key，三层可存约 2000 万行

聚簇索引 vs 非聚簇索引（二级索引）

🔑 聚簇索引（主键索引）

  • 叶子节点存储完整数据行
  • 每张表只有一个聚簇索引
  • 默认使用主键，无主键则使用 UNIQUE NOT NULL 列，都没有则生成隐藏 row_id
  • 数据按主键顺序物理存储

📋 二级索引（辅助索引）

  • 叶子节点存储索引列值 + 主键值
  • 查询非索引列需要回表：先查二级索引得到主键，再查聚簇索引得到完整行
  • 每张表可建多个二级索引
  • 二级索引越多，写入成本越高（需维护索引页）
SELECT * WHERE name='Tom'
→
查 idx_name 二级索引
→
得到主键 id=5
→
回表查聚簇索引 id=5
→
返回完整行

覆盖索引 & 联合索引 & 前缀索引

覆盖索引（Covering Index）

查询列全部在索引中，无需回表。EXPLAIN 中 Extra 显示 Using index

-- idx_name_age(name, age)
SELECT name, age FROM user WHERE name = 'Tom';
-- 索引已包含 name 和 age，无需回表

联合索引（Composite Index）

多列组合索引，遵循最左前缀原则

-- idx_a_b_c(a, b, c) 可匹配：
WHERE a=1               -- ✅ 用 a
WHERE a=1 AND b=2       -- ✅ 用 a,b
WHERE a=1 AND b=2 AND c=3  -- ✅ 用 a,b,c
WHERE b=2               -- ❌ 跳过 a
WHERE a=1 AND c=3       -- ⚠️ 只用 a

索引失效的常见场景

场景示例原因
函数操作WHERE YEAR(create_time)=2024对索引列使用函数，破坏 B+ 树有序性
隐式类型转换WHERE phone=13800138000（phone 是 varchar）MySQL 自动对列做 CAST，等同于函数
隐式字符集转换JOIN 两表字符集不同（utf8 vs utf8mb4）驱动表的索引列被隐式转换
前导模糊查询WHERE name LIKE '%tom'前缀不确定，无法利用索引有序性
OR 连接非索引列WHERE indexed_col=1 OR non_indexed=2必须全表扫描 non_indexed
违反最左前缀联合索引 (a,b,c)，WHERE b=2跳过了最左列 a
不等于查询WHERE status != 0优化器可能判断全扫更优
IS NULL / IS NOT NULLWHERE col IS NULL取决于 NULL 值比例，比例高则放弃索引
强制/忽略索引：SELECT * FROM t FORCE INDEX(idx_name) 可强制使用指定索引；IGNORE INDEX(idx_name) 忽略索引。生产慎用，先用 EXPLAIN 分析。

1.4b B+树设计动机 与 索引下推 ICP

为什么数据库索引用 B+ 树而不是 B 树 / Hash / 红黑树？

设计起点：数据库索引存在磁盘上，核心瓶颈是磁盘 IO 次数 ≈ 树高。一切设计都围绕"降低树高 + 适配磁盘页"展开。

数据结构每个节点存储树高(千万级)范围查询磁盘友好度
红黑树1 个 key + 2 指针约 23 层❌ 需中序遍历回溯❌ 二叉，每层只存 1 个 key，树太高
Hash哈希桶O(1) 一次❌ 不支持范围/排序⚠️ 仅等值查询，无法 ORDER BY
B 树key + data + 指针约 4 层⚠️ 中序遍历，跨节点回溯⚠️ 节点存数据→扇出低→树偏高
B+ 树非叶子只存 key+指针约 3 层✅ 叶子双向链表顺序扫✅ 扇出极高，树矮，IO 少
三个关键优势：① 非叶子节点不存数据 → 单页存更多 key → 扇出大 → 树更矮 → IO 更少；② 叶子链表 → 范围查询只需定位起点后顺序扫描，无需回溯父节点；③ 数据按页组织 → 完美匹配磁盘预读。

B 树 vs B+ 树：数据存放位置对比

B 树（每个节点都存数据）

    [20|data] [40|data] [60|data]
     /      |       |        \
[10|d][15|d] [25|d][30|d] [45|d] [65|d][70|d]

↑ 单页既存 key 又存 data → 存 key 数量少
↑ 范围查询要在树上来回跳转回溯

B+ 树（数据只存叶子）

    [20]  [40]  [60]     ← 只存 key
   /     |      |      \
[10,15,20]→[25,30,40]→[45,50,60]→[65,70,80]

↑ 非叶子腾出空间存更多 key → 扇出大
↑ 叶子链表 → 范围扫描一气呵成
面试追问：为什么 InnoDB 选 B+ 树而 Memory 引擎选 Hash？Memory 是内存引擎无磁盘 IO，Hash 的 O(1) 等值查询优势放大；而 InnoDB 面向磁盘，B+ 树的"低树高 + 范围查询 + 顺序 IO"才是关键。

索引下推（Index Condition Pushdown, ICP）

设计起点：5.6 之前，二级索引回表前只能用索引的"最左匹配"部分过滤，剩余 WHERE 条件要回表后才能判断，导致大量无谓回表。ICP 把索引覆盖部分的 WHERE 条件下推到存储引擎层，在回表前先过滤。

场景：联合索引 idx_name_age(name, age)，查询 SELECT * FROM user WHERE name LIKE '张%' AND age = 20;

❌ 无 ICP（5.6 之前）

用 name LIKE '张%' 取二级索引
→
全部回表（含 age≠20 的）
→
Server 层再过滤 age=20

问题 匹配"张X"的有 1000 条，但 age=20 只有 5 条 → 浪费 995 次回表

✅ 有 ICP（5.6+）

用 name LIKE '张%' 取二级索引
→
引擎层用索引里的 age 过滤
→
仅 5 条回表

优化 age 在联合索引里 → 回表前就过滤 → 回表次数 1000→5

EXPLAIN 判断：启用 ICP 时 Extra 显示 Using index condition；未启用则显示 Using where。ICP 对联合索引 + 范围/模糊查询场景收益最大。
ICP 限制：仅适用于二级索引；条件必须能用到索引列；对子查询的 condition 不下推；name LIKE '张%' 用到了范围扫描所以 age 部分原本无法用索引定位，但 ICP 让它在回表前过滤。

1.5 事务与 MVCC

ACID 特性

特性含义InnoDB 实现机制
A 原子性事务要么全部成功，要么全部回滚undo log（回滚日志）
C 一致性事务前后数据满足完整性约束由 AID 共同保证
I 隔离性并发事务互不干扰MVCC + 锁机制
D 持久性提交后数据不丢失redo log（WAL）

四种隔离级别

隔离级别脏读不可重复读幻读说明
READ UNCOMMITTED ❌ 有❌ 有❌ 有最低级别，几乎不用
READ COMMITTED (RC) ✅ 无❌ 有❌ 有每次 SELECT 生成新 ReadView，Oracle 默认
REPEATABLE READ (RR) ⭐ ✅ 无✅ 无 ⚠️ InnoDB 通过 MVCC + Next-Key Lock 解决 InnoDB 默认级别
SERIALIZABLE ✅ 无✅ 无✅ 无 串行执行，性能最差
脏读：读到未提交事务的数据
不可重复读：同一事务两次读同一行结果不同（被其他事务 UPDATE）
幻读：同一事务两次同样条件查询结果行数不同（被其他事务 INSERT）

MVCC 实现原理

事务 BEGIN
→
获取 Read View
→

→

→

Read View 结构
字段含义
m_ids生成 Read View 时，所有活跃（未提交）事务 ID 列表
min_trx_id活跃事务中最小的事务 ID
max_trx_id系统应分配的下一个事务 ID（最大事务 ID + 1）

可见性判断规则
条件判断
trx_id == creator_trx_id自己修改的 → 可见
trx_id < min_trx_id在 Read View 前已提交 → 可见
trx_id ≥ max_trx_id在 Read View 后才开始 → 不可见

trx_id 不在 m_ids 中生成 Read View 前已提交 → 可见

  • 当前读 vs 快照读：普通 SELECT 是快照读（读历史版本）；INSERT/UPDATE/DELETE/SELECT ... FOR UPDATE/LOCK IN SHARE MODE 是当前读（读最新数据，加锁）

InnoDB 行锁详解

锁类型锁定范围作用触发条件
Record Lock（记录锁） 锁定索引上的一条记录 防止其他事务修改或删除 等值查询命中唯一索引
Gap Lock（间隙锁） 锁定索引记录之间的间隙 防止其他事务在间隙中插入新记录（防幻读） 等值查询未命中，或范围查询
Next-Key Lock（临键锁） Record Lock + Gap Lock 锁定记录本身和前面的间隙 RR 级别下的默认行锁类型
Insert Intention Lock（插入意向锁） 间隙中等待插入 多个事务插入同一间隙不同位置时互不阻塞 INSERT 被 Gap Lock 阻塞时

加锁规则（RR 隔离级别下）

查询类型唯一索引非唯一索引
等值查询（命中） Record Lock Next-Key Lock + 右侧 Gap Lock
等值查询（未命中） Gap Lock Gap Lock
范围查询 Next-Key Lock（遍历到不满足条件为止） Next-Key Lock + 右侧 Gap Lock
⚠️ 死锁：两个事务互相等待对方持有的锁。InnoDB 自动检测死锁（innodb_deadlock_detect=ON），回滚代价较小的事务。
避免死锁：① 固定加锁顺序 ② 缩短事务 ③ 使用低隔离级别 ④ 合理设计索引减少锁范围

2.3 分库分表

垂直拆分 vs 水平拆分

📐 垂直拆分

垂直分库：按业务模块拆分（用户库、订单库、商品库）

垂直分表：大表拆分为 主表（常用字段）+ 扩展表（不常用字段）

  • ✅ 降低单库/单表复杂度
  • ✅ 业务解耦，便于独立扩展
  • ❌ 无法解决单表数据量过大
  • ❌ 跨库 JOIN 复杂

📊 水平拆分

水平分库：同一业务数据分散到多个库

水平分表：同一张大表拆分为多张结构相同的小表（如 order_0 ~ order_9）

  • ✅ 解决单表数据量过大
  • ✅ 分散 IO 压力
  • ❌ 分布式事务复杂
  • ❌ 跨片查询困难

分片策略

策略原理优点缺点
Range 范围分片 按 ID 范围分（0~100 万 → 分片 1） 扩容简单，新增分片即可 容易数据不均，热点问题
Hash 取模分片 shard = hash(id) % N 数据均匀分布 扩容时数据大规模迁移
一致性 Hash 哈希环 + 虚拟节点 扩容只迁移部分数据 实现复杂，需要虚拟节点

分布式 ID 生成 — 雪花算法（Snowflake）

Snowflake 64 位 ID 结构
  0 │ 00000000 00000000 00000000 00000000 00000000 0 │ 00000 00000 │ 000000000000
    │←──────────── 41 位时间戳 ──────────────────→│←─ 10位机器 →│←── 12位序列 ─→│
    │        毫秒级（69 年）                        │   ID（1024） │  每 ms 4096 个 │
  • 优点：趋势递增（对 B+ 树友好）、高性能（纯内存计算）、不依赖 DB
  • 时钟回拨问题：NTP 校时可能导致时间戳回退，需特殊处理（等待或抛异常）
  • 常见变种：美团 Leaf、百度 UidGenerator、滴滴 TinyID

跨库 JOIN 解决方案

方案说明适用场景
全局表（字典表）小表在每个分片都存一份配置表、字典表
冗余字段常用关联字段冗余到业务表查询频率高、数据变化少
应用层组装多次查询后在内存组装数据量不大
ER 分片关联数据分到同一分片（如按 user_id 分片）关联关系明确
中间件ShardingSphere / MyCat 等中间件聚合复杂场景

2.4 主从复制与高可用

主从复制原理

Master 写 binlog
→
Slave IO 线程拉取 binlog
→
写入 relay log
→
Slave SQL 线程重放
  • 异步复制（默认）：Master 提交后不等 Slave 确认，主从可能数据不一致
  • 半同步复制（Semi-sync）：Master 等待至少一个 Slave 确认收到 binlog 再提交，rpl_semi_sync_master_wait_for_slave_count=1
  • 组复制 MGR（MySQL 5.7.17+）：基于 Paxos 协议，多数节点确认即提交，强一致性

主从延迟原因与解决方案

原因说明解决方案
大事务一个大事务在 Master 执行很久拆分大事务，批量提交
单线程重放Slave SQL 线程单线程回放 binlog开启并行复制（slave_parallel_workers）
网络延迟主从之间网络抖动同机房部署，专线网络
机器性能差异Slave 配置低于 MasterSlave 配置不低于 Master
从库压力大大量查询拖慢 SQL 线程读写分离，专用从库做备份
并行复制（MySQL 5.7+）：slave_parallel_type=LOGICAL_CLOCK + slave_parallel_workers=8，同一组提交的事务可并行重放，大幅减少延迟。

读写分离实现方式

应用层路由

代码中配置多个数据源，写操作走 Master，读操作走 Slave

  • ✅ 简单直接，无额外中间件
  • ✅ 无中间件性能损耗
  • ❌ 代码侵入性强
  • ❌ 切换数据源逻辑重复

中间件代理

使用 ProxySQL / MySQL Router / ShardingSphere-Proxy 等中间件

  • ✅ 应用无感知，SQL 自动路由
  • ✅ 支持负载均衡和故障转移
  • ✅ 统一管理连接池
  • ❌ 增加网络跳数和延迟
⚠️ 主从延迟下的读写分离问题：写入 Master 后立即读 Slave 可能读不到最新数据。
解决方案：① 关键读走 Master ② 判断 Seconds_Behind_Master 延迟超过阈值则读 Master ③ 使用半同步复制保证一致性

2.5 "双一"配置与 MySQL 8.0 新特性

"双一"配置 — 金融级可靠性的基线

设计起点：默认配置下，MySQL 在崩溃时可能丢数据（redo log 不强制刷盘、binlog 不强制落盘）。"双一"指两个参数都设为 1，是金融场景的最低可靠性要求。

参数默认"双一"值含义代价
innodb_flush_log_at_trx_commit11每次事务提交都 fsync redo log 到磁盘每次提交多一次 fsync，TPS 下降
sync_binlog11每次事务提交都 fsync binlog 到磁盘每次提交多一次 fsync

❌ 非双一的丢数据场景

  • innodb_flush_log_at_trx_commit=0：每秒刷盘，崩溃丢 1 秒数据
  • sync_binlog=0：OS 决定刷盘，崩溃丢 binlog → 从库丢数据
  • 非双一组合：崩溃恢复时 redo/binlog 不一致，需两阶段提交回滚

✅ 双一配置的收益

  • redo log + binlog 都强制落盘，崩溃不丢已提交事务
  • 配合半同步复制 + min.insync.replicas，主从都不丢
  • 性能优化：用组提交 (group commit) 把多个事务的 fsync 合并成一次，缓解双一的性能损失
面试金句：双一是"宁可慢也不丢"的取舍。组提交 (binlog_group_commit_sync_delay) 是缓解双一性能损失的关键——把并发事务的 fsync 合并，N 个事务一次 fsync。

MySQL 8.0 关键新特性

特性解决的问题价值
原子 DDL5.7 DDL 中途崩溃留下脏元数据DDL 写入 binlog 一个原子事务，崩溃可回滚
Instant DDL (8.0.12+)加列要重建表，小时级锁表只改元数据，秒级完成（仅限加列末尾/重命名列）
隐藏列 / 不可见索引想测试索引效果又怕影响生产索引可设 invisible，优化器忽略但结构保留
函数索引WHERE f(col) 无法走索引对 (LOWER(name)) 建索引，函数查询可命中
降序索引5.7 降序索引实际仍正向存储8.0 真正反向存储，ORDER BY ... DESC 加速
并行查询 (8.0.14+)单 SQL 单线程，OLAP 慢set 语句可并行扫描分区
caching_sha2_passwordmysql_native_password 弱默认更强的认证插件，SHA-256 + cache

易错点：8.0 移除了 Query Cache（5.7 已 deprecated）。不要再说"开 Query Cache 优化"——高并发下其锁竞争反而拖累性能，这是 8.0 移除它的根本原因。

在线 DDL 三种算法

算法锁级别原理典型耗时
COPY (旧)EXCLUSIVE（表级写锁）建临时表 → 拷数据 → 改名小时级，阻塞写
INPLACE (5.6+)SHARED（可读不可写）原表上修改，不拷全表（部分操作）分钟级

使用：ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INSTANT, LOCK=NONE;

大表 DDL 推荐用 pt-online-schema-change 或 gh-ost（GitHub 开源）——通过 binlog 增量同步+影子表，实现零锁表在线变更，8.0 INSTANT 不能覆盖的场景靠它们兜底。

🎤第三部分：模拟面试

MySQL 的索引为什么使用 B+ 树而不是 B 树、红黑树或 Hash？
参考：① B+ 树叶子节点用链表连接，支持高效范围查询，B 树不支持；② B+ 树非叶子节点不存数据，扇出更高，树更矮，IO 次数更少；③ 红黑树是二叉树，数据量大时树过高导致大量 IO；④ Hash 索引不支持范围查询和排序，且存在哈希冲突。
追问：Hash 索引在什么场景下有用？InnoDB 的自适应哈希索引（AHI）自动对热点等值查询建立 Hash 索引，O(1) 查找。Memory 引擎也支持显式 Hash 索引，适合纯等值查询场景。
MVCC 是怎么实现的？RC 和 RR 的区别是什么？
参考：InnoDB 在每行记录后面隐藏两个字段：trx_id（最近修改的事务 ID）和 roll_pointer（指向 undo log 版本链）。读取数据时，根据 Read View 判断哪个版本对当前事务可见。
RC vs RR：RC 每次 SELECT 都生成新的 Read View，所以能看到其他已提交事务的最新修改；RR 只在第一次 SELECT 时生成 Read View，后续复用，所以能看到一致的快照。
追问：RR 级别下真的完全不会幻读吗？快照读通过 MVCC 避免幻读；当前读（SELECT ... FOR UPDATE）通过 Next-Key Lock 阻止其他事务插入，从而避免幻读。但如果先快照读再当前读，可能出现"幻象"。
什么是覆盖索引和索引下推（ICP）？
参考：覆盖索引：查询所需的所有列都在索引中，不需要回表查询聚簇索引，EXPLAIN 显示 Using index。
索引下推 ICP（Index Condition Pushdown，5.6+）：将 WHERE 条件中索引列的过滤下推到存储引擎层，在索引遍历时直接过滤，减少回表次数。EXPLAIN 显示 Using index condition。
追问：idx_name_age(name, age)，WHERE name LIKE 'T%' AND age=20，没有 ICP 时只能用 name 前缀查出所有 'T%' 开头的记录再回表过滤 age；有 ICP 后，在 idx_name_age 索引上直接同时判断 name LIKE 'T%' AND age=20，减少回表。
MySQL 有哪些锁？什么场景下会触发行锁升级为表锁？
参考：MySQL 有全局锁（FTWRL）、表锁（表锁、MDL 锁、意向锁、AUTO-INC 锁）、行锁（Record Lock、Gap Lock、Next-Key Lock）。InnoDB 的行锁是加在索引上的，如果 SQL 没有走索引，行锁会退化为表锁（锁住所有行，因为扫描全表）。
追问：MDL 锁是什么？元数据锁（Metadata Lock），DML 操作自动加 MDL 读锁，DDL 操作加 MDL 写锁。长事务持有 MDL 读锁不释放时，DDL 会被阻塞，且后续所有查询都会被 DDL 的 MDL 写锁请求阻塞，可能导致连接耗尽。
如何优化一个慢 SQL？说说你的排查思路。
参考：① 开启慢查询日志，用 pt-query-digest 定位 Top N 慢 SQL；② EXPLAIN 分析执行计划，重点看 type（是否 ALL）、key（是否用索引）、rows（扫描行数）、Extra（filesort/temporary）；③ 检查是否缺少索引或索引失效；④ 优化 SQL 写法（避免 SELECT *、子查询改 JOIN、分页优化）；⑤ 考虑表结构优化（拆大字段、分表）。
追问：type=ref 和 type=range 哪个好？const 最好（主键/唯一索引等值查询），eq_ref（JOIN 时主键匹配），ref（非唯一索引等值），range（索引范围扫描）。一般来说 ref 优于 range，因为 ref 是精确匹配。
分库分表后有哪些问题？怎么解决？
参考：① 分布式事务：XA 事务（性能差）或 TCC/SAGA 模式；② 跨库 JOIN：全局表冗余、应用层组装、ER 分片；③ 排序分页：各分片查询后归并排序，深分页性能差；④ 全局唯一 ID：雪花算法；⑤ 扩容迁移：一致性 Hash 或成倍扩容。
追问：什么时候该分库分表？单表超过 1000 万行或超过 10GB 考虑分表；单库写 QPS 持续超过 5000 或数据量超过 1TB 考虑分库。优先考虑读写分离、缓存、SQL 优化，分库分表是最后手段。
MySQL 主从复制有哪些模式？半同步复制是什么？
参考：① 异步复制（默认）：Master 提交即返回，不等 Slave 确认，可能丢数据；② 半同步复制（Semi-sync）：Master 等至少一个 Slave 确认收到 binlog 才返回客户端，保证至少有一个 Slave 有最新数据；③ 组复制 MGR：基于 Paxos 的多节点一致性协议，多数节点确认即提交，支持多主模式。
追问：半同步的退化问题？如果所有 Slave 都超时未确认，半同步自动退化为异步复制，不阻塞 Master 写入。可通过 rpl_semi_sync_master_timeout 设置超时时间（默认 10 秒）。
InnoDB 的 Buffer Pool 如何工作？LRU 有什么优化？
参考：Buffer Pool 以 16KB 数据页为单位缓存数据和索引。传统 LRU 的问题是全表扫描会把热点数据冲刷掉。InnoDB 使用改进 LRU：将 LRU 列表分为 young 区（热数据，约 63%）和 old 区（冷数据，约 37%）。新读入的页放在 old 区头部，只有在 old 区停留超过 1 秒（innodb_old_blocks_time）后再次被访问，才移到 young 区。
追问：Buffer Pool 多大合适？专用数据库服务器建议设置为物理内存的 70%~80%。用 SHOW ENGINE INNODB STATUS 查看 Buffer Pool 命中率，正常应 > 99%。
