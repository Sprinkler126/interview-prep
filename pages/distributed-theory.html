第一部分：技术原理

CAP 定理

CAP 三大特性

C - Consistency（一致性）

所有节点在同一时刻看到的数据是相同的。即写操作完成后，后续的读操作都能读到最新值。

A - Availability（可用性）

每个请求都能在合理时间内得到响应（不保证是最新数据）。即系统不能返回错误或超时。

P - Partition Tolerance（分区容错）

网络分区（节点间通信中断）时，系统仍能继续运行。分布式系统中网络分区是不可避免的。

核心结论

P 是必选项，所以实际选择是 CP 或 AP。CA 在分布式环境中不存在（无分区时退化为单机）。

CP vs AP 系统对照

类型代表系统特点适用场景
CP 系统ZooKeeper、etcd、HBase、Consul强一致性，分区时可能拒绝服务配置中心、分布式锁、选主
AP 系统Eureka、Cassandra、DynamoDB、CouchDB高可用，数据可能短暂不一致服务发现、社交信息流
混合系统Nacos（AP+CP）不同场景使用不同策略注册中心+配置中心

CAP 定理的证明（简述）

假设两个节点 N1、N2，数据初始为 V0：

  1. 客户端向 N1 写入新值 V1
  2. N1 需要将 V1 同步给 N2（但此时发生网络分区，N1 和 N2 通信中断）
  3. 选择 C（一致性）：N2 拒绝读请求（因为无法确认数据是最新的），牺牲了 A
  4. 选择 A（可用性）：N2 返回旧值 V0，牺牲了 C
CAP 定理的更精确表述：在网络分区发生时，系统只能在 C 和 A 之间二选一。没有分区时，可以同时满足 CA。

BASE 理论

BASE 三要素

要素全称含义
BABasically Available（基本可用）系统出现故障时，允许损失部分功能或响应时间变长，但保证核心功能可用
SSoft State（软状态）允许系统存在中间状态，该状态不影响系统的整体可用性。如数据同步中的"同步中"状态
EEventually Consistent（最终一致性）经过一段时间的同步后，系统最终能达到数据一致的状态

BASE 理论是 CAP 中 AP 方案的延伸，核心思想是：牺牲强一致性，换取系统的高可用和高性能。这是大多数互联网系统的设计哲学。

最终一致性的几种变体

  • 因果一致性（Causal Consistency）：有因果关系的操作保证顺序一致，无因果关系的操作不做保证
  • 读己之所写（Read Your Writes）：用户总能读到自己最新写入的数据
  • 会话一致性（Session Consistency）：在同一个会话内保证读己之所写
  • 单调读一致性（Monotonic Read）：用户不会读到比之前更旧的数据

一致性哈希

传统哈希的问题

传统取模哈希 hash(key) % N 在节点数 N 变化时，几乎所有 key 的映射都会改变，导致大规模数据迁移。

// 传统哈希：节点数变化影响全部数据
// 3个节点时：key="user1" → hash("user1") % 3 = 1
// 4个节点时：key="user1" → hash("user1") % 4 = 3  （映射变了！）
// 变化率 ≈ (N-1)/N，几乎全量迁移

一致性哈希原理

将哈希值空间组织成一个环（0 ~ 2^32-1），节点和数据都映射到环上。数据沿顺时针方向找到第一个节点存储。

// 一致性哈希：节点增减只影响相邻区间
// 环空间：0 ──────────────── 2^32-1
//         |   Node A   |   Node B   |   Node C   |
//
// 新增 Node D：只影响 Node D 到其前一个节点之间的数据
// 变化率 ≈ 1/N（只迁移 1/N 的数据）
一致性哈希的数据倾斜问题：当节点较少时，数据分布可能极不均匀（某个节点承担大部分数据）。

虚拟节点解决数据倾斜

每个物理节点对应多个虚拟节点（如 100~200 个），虚拟节点均匀分布在哈希环上，使数据分布更加均匀。

// 虚拟节点示例
// 物理节点 Node A → 虚拟节点 A#0, A#1, A#2, ..., A#99
// 物理节点 Node B → 虚拟节点 B#0, B#1, B#2, ..., B#99
//
// 数据映射到虚拟节点后，再映射到物理节点
// 虚拟节点越多，数据分布越均匀
方案节点增减时迁移比例数据分布适用场景
传统取模(N-1)/N（几乎全量）均匀节点数固定
一致性哈希（无虚拟节点）1/N可能倾斜节点数多且均匀
一致性哈希（有虚拟节点）1/N均匀通用推荐

分布式 ID 方案

分布式 ID 方案对比

方案实现方式优点缺点
UUID128位随机数简单、无网络开销无序、存储大、不适合做主键
数据库自增单库 AUTO_INCREMENT简单有序单点瓶颈、扩展性差
号段模式批量获取 ID 段（如 Leaf）高性能、减少 DB 交互需要额外服务
Snowflake时间戳+机器ID+序列号趋势递增、高性能依赖时钟、机器ID需管理

Snowflake 算法详解

// Snowflake ID 结构（64位）
// ┌─────────┬───────────┬───────────┬──────────────┐
// │ 符号(1) │ 时间戳(41) │ 机器ID(10) │ 序列号(12)  │
// └─────────┴───────────┴───────────┴──────────────┘
//
// 符号位：0（正数）
// 时间戳：41位，毫秒级，可用约69年
// 机器ID：10位，支持1024个节点（5位数据中心+5位机器）
// 序列号：12位，同一毫秒内支持4096个ID

public class SnowflakeIdGenerator {
    private long epoch = 1609459200000L; // 2021-01-01
    private long datacenterId;  // 5位
    private long workerId;      // 5位
    private long sequence = 0;  // 12位
    private long lastTimestamp = -1;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis() - epoch;
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & 0xFFF; // 4096
            if (sequence == 0) timestamp = waitNextMillis();
        } else {
            sequence = 0;
        }
        lastTimestamp = timestamp;
        return (timestamp << 22) | (datacenterId << 17) |
               (workerId << 12) | sequence;
    }
}
Snowflake 的核心优势：趋势递增（按时间排序）、高性能（纯内存计算、无网络开销）、全局唯一。缺点是依赖机器时钟，时钟回拨可能导致 ID 重复。

  • 每次从数据库批量获取一段 ID（如 1~1000），缓存在内存中分发

幂等性设计

什么是幂等性

幂等性是指同一个操作执行一次和执行多次的效果完全相同。在分布式系统中，由于网络超时、重试机制等原因，同一请求可能被多次发送，幂等性设计可以保证数据不会重复处理。

天然幂等的操作：SELECT、DELETE（删除同一个记录）、SET key=value

非幂等的操作：INSERT（可能插入多条）、UPDATE balance = balance + 100

幂等性实现方案

方案实现原理适用场景
Token 机制请求前获取唯一 Token，服务端消费 Token 后删除，重复请求因 Token 已消费而拒绝表单防重复提交
唯一索引在数据库中对业务字段建唯一索引，重复插入会报唯一键冲突创建订单等写入操作
乐观锁使用版本号 UPDATE SET ... WHERE version=old_version更新操作
状态机限制状态流转方向，如"已支付"不能再次支付订单状态流转
去重表将请求的唯一标识存入去重表，处理前先查询消息消费去重

分布式事务理论

分布式事务方案全景

方案一致性性能复杂度适用场景
2PC（两阶段提交）强一致低（阻塞）中数据库层面分布式事务
3PC（三阶段提交）强一致中高理论模型，实际少用
TCC最终一致高高资金、库存等核心业务
Saga最终一致高中长事务、跨多服务

2PC（两阶段提交）原理

阶段1: Prepare
协调者询问所有参与者
是否可以提交
→
参与者响应
YES/NO
→
阶段2: Commit/Abort
全部YES→提交
任一NO→回滚

问题：1）同步阻塞：参与者在 Prepare 后需等待 Commit/Abort，期间资源被锁定；2）单点故障：协调者宕机，参与者会一直阻塞；3）数据不一致：Commit 消息丢失导致部分提交、部分未提交。

TCC 模式详解

三个阶段

  • Try：资源检查与预留（如冻结库存、冻结余额）
  • Confirm：确认执行，使用预留资源（如扣减冻结的库存）
  • Cancel：取消执行，释放预留资源（如解冻库存）

三大难题

  • 空回滚：Try 未执行就收到 Cancel，需要识别并跳过
  • 幂等：Confirm/Cancel 可能被重试，需要保证幂等
  • 悬挂：Cancel 先于 Try 到达，需防止后续 Try 执行

Saga 模式

Saga 将长事务拆分为一系列本地事务，每个本地事务有对应的补偿操作：

T1: 创建订单
→
T2: 扣减库存
→
T3: 扣减余额

如果 T3 失败，执行补偿：C2（恢复库存）→ C1（取消订单）

编排式（Orchestration）

中央协调器控制执行流程，类似指挥者模式。适合复杂流程，易于监控。

协调式（Choreography）

各服务通过事件驱动自行协调，无中央控制器。适合简单流程，松耦合。

Raft 协议简述

Raft 三大子问题

子问题说明关键机制
Leader 选举集群中选出唯一 Leader随机选举超时、多数派投票
日志复制Leader 将日志复制到 FollowerAppendEntries RPC、多数派确认
安全性保证所有节点最终一致选举限制、提交规则

Leader 选举流程

  1. 所有节点初始为 Follower 状态
  2. Follower 在选举超时（150~300ms 随机）内未收到 Leader 心跳，转变为 Candidate
  3. Candidate 自增任期号（Term），向所有节点发起 RequestVote 请求
  4. 获得多数派（N/2+1）投票的 Candidate 成为 Leader
  5. Leader 周期性向所有节点发送心跳（AppendEntries）维持权威
  6. 如果多个 Candidate 同时竞选导致票数分裂，等待随机超时后重新选举
随机选举超时是 Raft 避免活锁的关键设计。通过随机化，大概率只有一个 Candidate 先超时发起选举。

日志复制流程

  1. 客户端向 Leader 发送写请求
  2. Leader 将请求作为日志条目追加到本地日志
  3. Leader 通过 AppendEntries RPC 将日志复制到所有 Follower
  4. 当多数节点确认收到日志后，Leader 将该条目标记为已提交（committed）
  5. Leader 通知所有 Follower 提交该条目，各节点应用到状态机
  6. Leader 返回客户端写入成功

分布式系统常见问题

脑裂（Split Brain）

网络分区导致集群出现多个 Leader，各自接受写入，造成数据不一致。

  • 解决方案：多数派机制（Quorum），只有获得 N/2+1 节点投票才能成为 Leader
  • Fencing 机制：旧 Leader 的写入通过 epoch/term 号被拒绝
  • 实践中：Raft/ZAB 通过任期号（Term）+ 选举限制天然防脑裂

拜占庭问题（Byzantine Failure）

节点可能发送任意错误消息（包括恶意行为），不仅仅是宕机或超时。

  • 非拜占庭故障（CFT）：节点只会宕机或超时，Raft/Paxos 可处理
  • 拜占庭故障（BFT）：节点可能发送错误信息，需要 PBFT 等算法处理
  • 实际场景：大多数内部系统只需 CFT；区块链等开放环境需要 BFT
  • 容错数：CFT 需要 N/2+1 正常节点；BFT 需要 2N/3+1 正常节点

网络分区（Network Partition）

网络分区是指集群中部分节点之间无法通信，形成多个孤立的子网络。

  • 影响：可能导致数据不一致、服务不可用
  • 检测：通过心跳超时检测节点是否可达
  • 处理：CAP 权衡——选择 CP 则少数派分区不可用，选择 AP 则少数派分区可能数据不一致
  • 恢复：分区恢复后，通过日志复制或数据同步恢复一致性

第三部分：模拟面试

什么是 CAP 定理？为什么不能同时满足 CA？
参考：CAP 定理指出分布式系统中一致性（C）、可用性（A）、分区容错（P）最多同时满足两个。分布式系统中网络分区是不可避免的（P 是必选），所以在分区发生时，只能选择 C（拒绝服务保证一致性）或 A（返回旧数据保证可用性）。不存在分区时可以同时满足 CA，但那本质上是单机系统。实际系统多选择 AP + 最终一致性（BASE）。
一致性哈希是什么？为什么需要虚拟节点？
参考：一致性哈希将哈希空间组织成环，节点和数据都映射到环上，数据沿顺时针找到最近节点存储。当节点增减时，只影响相邻区间的数据，迁移比例为 1/N。虚拟节点是为了解决数据倾斜问题：当物理节点较少时，数据分布可能极不均匀。通过为每个物理节点创建多个虚拟节点（如 100 个），使其均匀分布在环上，从而实现数据的均匀分布。Redis Cluster 使用哈希槽（16384 个）而非一致性哈希，本质思路类似。
分布式 ID 有哪些方案？Snowflake 算法的原理是什么？
参考：常见方案：UUID（简单但无序）、数据库自增（简单但单点）、号段模式（Leaf，批量获取减少 DB 压力）、Snowflake（趋势递增、高性能）、ULID（有序兼容 UUID）。Snowflake 将 64 位 ID 分为：1 位符号 + 41 位毫秒时间戳（约 69 年）+ 10 位机器 ID（1024 节点）+ 12 位序列号（每毫秒 4096 个 ID）。核心优势是趋势递增（利于 B+Tree 索引）和纯内存生成（高性能）。缺点是依赖时钟，时钟回拨可能重复。
什么是幂等性？如何保证接口幂等？
参考：幂等性是指同一操作执行多次效果与执行一次相同。在分布式系统中，网络超时重试可能导致请求重复发送。保证幂等的方案：1）Token 机制：请求前获取唯一 Token，服务端消费后删除；2）唯一索引：数据库对业务字段建唯一索引，重复插入报冲突；3）乐观锁：使用版本号控制更新；4）状态机：限制状态流转方向（如"已支付"不能再次支付）；5）去重表：记录已处理的请求标识。
2PC 和 TCC 有什么区别？各适用于什么场景？
参考：2PC 是数据库层面的分布式事务：Prepare 阶段参与者锁定资源，Commit 阶段统一提交。问题是同步阻塞、单点故障、数据不一致风险。TCC 是业务层面：Try 阶段预留资源（如冻结库存），Confirm 阶段确认扣减，Cancel 阶段释放。区别：2PC 在数据库层实现，对业务侵入小但性能差；TCC 在业务层实现，侵入大但性能好。2PC 适合对一致性要求极高的数据库操作；TCC 适合资金、库存等核心业务场景。
Raft 协议是如何选举 Leader 的？如何防止脑裂？
参考：Raft 选举流程：1）Follower 在随机选举超时（150-300ms）内未收到心跳，转变为 Candidate；2）自增 Term，向所有节点发 RequestVote；3）获得多数派投票成为 Leader；4）Leader 定期发心跳维持权威。防脑裂：1）多数派机制——只有获得 N/2+1 投票才能成为 Leader；2）Term 机制——旧 Leader 的 Term 小于新 Leader，Follower 会拒绝旧 Leader 的请求；3）选举限制——Candidate 的日志必须足够新（至少和多数节点一样新）。
分布式系统中的数据分片有哪些策略？如何选择？
参考：三种策略：1）Range 分片：按数据范围划分（如 ID 1-100万在分片1），范围查询高效但可能热点集中，适合时间序列数据；2）Hash 分片：hash(key) % N 确定分片，分布均匀但扩容需全量迁移；3）一致性哈希：哈希环 + 虚拟节点，扩容只迁移 1/N 数据，适合缓存分片。选择依据：需要范围查询用 Range，通用场景用 Hash，需要弹性扩缩容用一致性哈希。分库分表通常结合使用：按 user_id Hash 分库，按时间 Range 分表。
什么是 Saga 模式？编排式和协调式有什么区别？
参考：Saga 将长事务拆为一系列本地事务，每个有对应补偿操作。正向流程 T1→T2→T3，若 T3 失败则执行 C2→C1 补偿回滚。编排式（Orchestration）：由中央协调器控制流程，类似指挥者模式，适合复杂流程，易于监控和调试。协调式（Choreography）：各服务通过事件驱动自行协调，无中央控制器，松耦合但流程难以追踪。实际中编排式更常用（如 Seata Saga），因为业务流程更直观，便于管理补偿逻辑。
