第一部分：技术原理

分布式锁需求场景

为什么需要分布式锁

在单机环境中，JVM 内的锁（synchronized、ReentrantLock）可以保证线程安全。但在分布式系统中，多个进程分布在不同机器上，JVM 内的锁无法跨进程生效，需要一个全局的锁机制来协调。

  • 秒杀防超卖：多个请求同时扣减库存，需要互斥访问
  • 定时任务防重复执行：集群中多个实例同时触发定时任务，只需一个执行
  • 订单防重复提交：用户快速点击导致同一订单被创建多次
  • 分布式缓存更新：多节点同时更新缓存导致数据不一致
  • 全局序列号生成：保证序列号不重复

分布式锁的核心特性

特性说明
互斥性同一时刻只有一个客户端能持有锁
防死锁持有锁的客户端崩溃后，锁能自动释放（超时机制）
容错性锁服务节点故障时，系统仍能正常工作
加锁/解锁原子性加锁和解锁操作必须是原子的，不能出现中间状态
可重入性同一线程可以重复获取同一把锁（可选特性）

Redis 实现分布式锁

基础实现：SET NX EX

# 加锁：SET key value NX EX seconds
# NX = 仅当 key 不存在时设置（互斥性）
# EX = 过期时间秒（防死锁）
SET lock:order:123 "uuid-client-1" NX EX 30

# 返回 OK 表示加锁成功
# 返回 nil 表示锁已被其他客户端持有
必须使用 SET NX EX 一条命令（原子操作），不能先 SETNX 再 EXPIRE，否则 SETNX 成功后客户端崩溃，EXPIRE 未执行导致死锁。

安全释放：Lua 脚本

-- 释放锁的 Lua 脚本（原子操作）
-- 先检查锁的 value 是否是自己的，再删除
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

-- KEYS[1] = lock key
-- ARGV[1] = 客户端唯一标识（UUID）
-- 只有加锁的客户端才能释放自己的锁
不能直接 DEL key 来释放锁！因为锁可能已过期被其他客户端获取，直接删除会误删别人的锁。必须用 Lua 脚本先检查 value 再删除（保证原子性）。

锁续期机制

锁的过期时间设置是一个两难问题：太短可能导致业务未执行完就释放，太长会导致故障恢复时间长。

  • WatchDog 看门狗：后台线程定期检查锁是否仍被持有，如果是则自动续期
  • Redisson 默认：锁过期时间 30 秒，每 10 秒续期一次（续期到 30 秒）
  • 手动续期：业务代码中主动检查并续期（不推荐，侵入性大）

RedLock 算法

单节点 Redis 锁的问题

单节点 Redis 锁存在以下风险：

  • 主从切换：主节点加锁成功后宕机，从节点升主后锁丢失，其他客户端可再次加锁
  • 单点故障：Redis 节点宕机，锁服务不可用

RedLock 算法流程

RedLock 由 Redis 作者 Antirez 提出，使用 N 个独立的 Redis 节点（建议 5 个，奇数个）：

  1. 获取当前时间 T1（毫秒级）
  2. 依次向 N 个节点请求加锁：使用相同的 key 和随机 value，设置较短的超时时间（如 50ms）
  3. 计算加锁耗时：T2 = 当前时间 - T1，加锁耗时应小于锁的有效时间
  4. 判断加锁成功：当且仅当多数派（N/2+1）节点加锁成功，且总耗时小于锁有效时间
  5. 锁有效时间 = 初始有效时间 - 加锁耗时
  6. 如果加锁失败：向所有节点发送释放锁请求
// RedLock 伪代码
bool redlock_acquire(key, ttl):
    T1 = current_time_ms()
    success_count = 0
    for node in redis_nodes:
        if node.SET(key, uuid, NX, EX=ttl):
            success_count += 1
    T2 = current_time_ms()
    elapsed = T2 - T1

    if success_count >= N/2 + 1 AND elapsed < ttl:
        lock_ttl = ttl - elapsed
        return true  // 加锁成功
    else:
        // 加锁失败，释放所有已获取的锁
        for node in acquired_nodes:
            release_lock(node, key, uuid)
        return false

Redisson 看门狗机制

Redisson 分布式锁

Redisson 是 Java 实现的 Redis 客户端，内置了完善的分布式锁实现：

// Redisson 使用示例
RLock lock = redissonClient.getLock("myLock");
try {
    // 尝试加锁，等待 10 秒，锁有效期 30 秒
    boolean acquired = lock.tryLock(10, 30, TimeUnit.SECONDS);
    if (acquired) {
        // 执行业务逻辑
    }
} finally {
    // 只有持有锁的线程才能解锁
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}

  • 客户端宕机后，WatchDog 随之停止，锁在 30 秒后自动过期
  • 如果指定了 leaseTime，不会启动 WatchDog（手动控制过期时间）

Zookeeper 实现分布式锁

基于临时顺序节点的公平锁

Zookeeper 利用临时顺序节点（Ephemeral Sequential）和Watcher 机制实现分布式锁：

  1. 客户端在 /locks/mylock 下创建临时顺序节点 /locks/mylock/lock-0001
  2. 获取 /locks/mylock 下所有子节点，判断自己是否是编号最小的
  3. 如果是最小的，获取锁成功
  4. 如果不是最小的，对前一个节点注册 Watcher，监听其删除事件
  5. 前一个节点删除时（锁释放），ZooKeeper 通知当前客户端，检查自己是否是最小节点
只监听前一个节点而非所有节点，避免"惊群效应"（大量 Watcher 同时被触发）。

Zookeeper 锁的特性

公平锁

  • 临时顺序节点保证 FIFO 顺序
  • 先到先得，避免饥饿
  • 通过 Watcher 机制通知下一个等待者

读写锁

  • 读锁：创建 /lock/read- 节点
  • 写锁：创建 /lock/write- 节点
  • 读锁之间不互斥，读写互斥
  • 判断前面是否有写锁节点

临时节点自动释放

Zookeeper 临时节点的关键特性：创建临时节点的客户端会话结束时，临时节点自动删除。

  • 客户端正常释放锁：主动删除临时节点
  • 客户端崩溃：会话超时后（默认 30 秒），临时节点自动删除，锁自动释放
  • 不需要设置过期时间，天然防死锁
  • 缺点：会话超时期间（30 秒）锁仍被占用

第二部分：场景化讲解

数据库实现分布式锁

三种数据库锁方案

唯一索引

CREATE TABLE distributed_lock (
  lock_key VARCHAR(128) PRIMARY KEY,
  owner VARCHAR(128),
  expire_at DATETIME
);

-- 加锁
INSERT INTO distributed_lock
VALUES ('order:123', 'client-1', NOW()+30);

-- 释放锁
DELETE FROM distributed_lock
WHERE lock_key='order:123'
AND owner='client-1';

悲观锁 SELECT FOR UPDATE

-- 加锁（行锁）
BEGIN;
SELECT * FROM locks
WHERE lock_key='order:123'
FOR UPDATE;

-- 业务逻辑...

-- 释放锁
COMMIT;

乐观锁方案

-- 乐观锁：使用版本号
UPDATE resource
SET value = 'new_value', version = version + 1
WHERE id = 123 AND version = 5;

-- 如果 affected_rows = 0，说明被其他客户端修改，重试

RedLock 争议

Martin Kleppmann vs Antirez 辩论

Martin Kleppmann 的批评

  • 时钟问题：RedLock 依赖各节点时钟大致同步，但 NTP 可能导致时钟跳变
  • GC 停顿：客户端获取锁后 GC 停顿，锁已过期但客户端不知道，导致两个客户端同时认为持有锁
  • 结论：RedLock 不能提供真正的互斥保证，推荐使用 Zookeeper（基于共识算法）

Antirez 的回应

  • 时钟跳变：可以通过关闭自动 NTP 同步、使用单调时钟来规避
  • GC 问题：这是所有基于超时的分布式锁共有的问题，不仅限于 RedLock
  • 实用性：在合理配置下，RedLock 的安全性足够满足大多数业务场景
面试加分点：了解 RedLock 争议说明你对分布式系统有深入理解。实际使用中，如果对互斥性要求极高（如金融交易），应使用 Zookeeper 或 etcd 等基于共识算法的锁；一般业务场景使用 Redis 单节点锁即可。

分布式锁最佳实践

锁粒度设计

# 粗粒度锁（不推荐）- 锁住整个资源
SET lock:orders NX EX 30

# 细粒度锁（推荐）- 锁住具体资源
SET lock:order:123 NX EX 30

# 更细粒度 - 锁住具体操作
SET lock:order:123:pay NX EX 30
  • 锁粒度越细，并发性越高
  • 锁粒度越粗，实现越简单
  • 需要在并发性和复杂度之间取舍

最佳实践清单

实践说明
设置合理的超时时间根据业务执行时间设置，留有余量。使用 WatchDog 自动续期
使用唯一标识锁的 value 使用 UUID，释放时先检查再删除
保证加锁/解锁原子性加锁用 SET NX EX，解锁用 Lua 脚本
业务幂等设计即使锁失效导致重复执行，业务层也能正确处理

可重入设计同一客户端/线程可重复获取同一把锁

第三部分：模拟面试

如何用 Redis 实现分布式锁？需要注意哪些问题？
参考：基本实现：用 SET key uuid NX EX 30 加锁（NX 保证互斥，EX 防死锁），用 Lua 脚本释放锁（先检查 value 是否是自己的再删除）。需要注意：1）必须用 SET NX EX 原子命令，不能分开 SETNX 和 EXPIRE；2）释放锁必须先检查再删除，防止误删别人的锁；3）value 使用 UUID 标识客户端身份；4）锁的过期时间要合理，长时间任务需续期机制；5）单节点 Redis 主从切换可能丢锁，对可靠性要求高可用 RedLock 或 Zookeeper。
什么是 RedLock 算法？有什么争议？
参考：RedLock 使用 N 个独立 Redis 节点（建议 5 个），客户端依次向所有节点请求加锁，当且仅当多数派（N/2+1）加锁成功且总耗时小于锁有效期时才算加锁成功。争议：Martin Kleppmann 批评 RedLock 依赖时钟同步，NTP 时钟跳变可能导致安全问题；GC 停顿可能导致客户端持有过期锁而不自知。Antirez 回应时钟问题可通过单调时钟规避，GC 问题是所有超时锁的共性问题。实际使用中，一般业务用 Redis 单节点锁足够，高可靠场景选 Zookeeper。
Redisson 的看门狗机制是如何工作的？
参考：Redisson 在客户端加锁时（不指定 leaseTime 的情况下），会启动一个后台 WatchDog 定时任务。默认锁过期时间 30 秒，WatchDog 每 10 秒（lockWatchdogTimeout/3）检查一次：如果锁仍被当前线程持有，则重新将锁的 TTL 设置为 30 秒（续期）。客户端正常释放锁时 WatchDog 自动停止；客户端崩溃时 WatchDog 随之停止，锁在 30 秒后自动过期释放。如果指定了 leaseTime 参数，则不启动 WatchDog，由用户自行控制过期时间。
Zookeeper 是如何实现分布式锁的？和 Redis 有什么区别？
参考：Zookeeper 利用临时顺序节点实现公平锁：客户端在锁目录下创建临时顺序节点，判断自己是否是最小节点（是则获取锁），否则 Watcher 前一个节点的删除事件。核心优势：1）公平性（FIFO 顺序）；2）防死锁（临时节点会话结束自动删除）；3）强一致性（ZAB 协议保证）。与 Redis 的区别：Redis 性能更高（毫秒级 vs 十毫秒级），Zookeeper 可靠性更强（基于共识算法）。Redis 非公平锁可能饥饿，Zookeeper 公平锁不会。大多数场景推荐 Redis（Redisson），高可靠场景选 Zookeeper。
分布式锁的锁粒度如何设计？
参考：锁粒度取决于业务场景。粗粒度（如 lock:orders）：实现简单但并发性差，所有订单操作串行化。细粒度（如 lock:order:123）：不同订单可并行处理，提高并发性。更细粒度（如 lock:order:123:pay）：同一订单的不同操作可并行。设计原则：1）能用细粒度就不用粗粒度；2）锁粒度要与业务数据匹配；3）避免锁嵌套导致死锁；4）考虑锁的管理成本。实际中通常以业务 ID 作为锁的粒度（如订单 ID、用户 ID）。
如何避免分布式锁导致的死锁？
参考：避免死锁的方法：1）设置过期时间——Redis 的 EX 参数、Zookeeper 的临时节点都能在客户端崩溃后自动释放锁；2）锁续期——Redisson 的 WatchDog 机制自动续期，防止业务未执行完锁就过期；3）超时获取——tryLock 设置等待时间，避免无限等待；4）避免锁嵌套——多个锁按固定顺序获取（如按 key 字典序），防止循环等待；5）业务幂等——即使锁失效导致重复执行，业务层也能正确处理。
分布式锁如何保证可重入性？
参考：Redis 可重入锁实现：使用 Hash 结构存储（key=锁名，field=客户端标识+线程标识，value=重入次数）。加锁时判断 field 是否存在：不存在则新增并设 count=1；存在（当前线程）则 count+1。解锁时 count-1，count=0 时删除整个 Hash。Redisson 的 RLock 天然支持可重入。Zookeeper 可重入锁：客户端在内存中记录已持有的锁信息，重复加锁时检查当前节点是否已创建，是则增加重入计数。数据库可重入锁：在锁表中增加重入次数字段。
