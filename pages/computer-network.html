1.1 网络模型

OSI 七层 vs TCP/IP 四层

OSI 七层TCP/IP 四层协议/设备数据单位
应用层应用层HTTP、FTP、SMTP、DNS、WebSocket数据
表示层SSL/TLS、JPEG、ASCII数据
会话层RPC、NetBIOS数据
传输层传输层TCP、UDP段（Segment）
网络层网络层IP、ICMP、ARP、路由器包（Packet）
数据链路层网络接口层以太网、交换机、MAC帧（Frame）
物理层光纤、双绞线、集线器比特（Bit）

TCP vs UDP

TCP

  • 面向连接，三次握手
  • 可靠传输，有序、不丢失
  • 流量控制、拥塞控制
  • 全双工，字节流
  • 适用：HTTP、FTP、邮件

UDP

  • 无连接，直接发送
  • 不可靠，可能丢包、乱序
  • 无流量/拥塞控制
  • 报文，有边界
  • 适用：DNS、视频、游戏、直播

1.2 TCP 三次握手与四次挥手

三次握手（建立连接）

客户端 → SYN(seq=x) → 服务端
→
服务端 → SYN+ACK(seq=y, ack=x+1) → 客户端
→
客户端 → ACK(ack=y+1) → 服务端
  • 第一次握手：客户端发送 SYN，进入 SYN_SENT 状态
  • 第二次握手：服务端收到后回复 SYN+ACK，进入 SYN_RCVD 状态
  • 第三次握手：客户端收到后发送 ACK，双方进入 ESTABLISHED 状态
  • 为什么三次？：① 确认双方的收发能力；② 防止历史重复连接的初始化（两次握手无法防止服务端建立过期连接）；③ 同步双方的初始序列号

四次挥手（断开连接）

客户端 → FIN → 服务端
→
服务端 → ACK → 客户端
→
服务端 → FIN → 客户端
→
客户端 → ACK → 服务端
  • 为什么四次？：TCP 是全双工，每个方向需要单独关闭。服务端收到 FIN 后可能还有数据要发送，先回 ACK 确认收到，等数据发完再发 FIN
  • TIME_WAIT：客户端发送最后一个 ACK 后等待 2MSL（约 60 秒），原因：① 确保 ACK 能到达服务端（若丢失，服务端会重发 FIN）；② 让旧连接的数据包在网络中消亡，防止影响新连接
  • 大量 TIME_WAIT：短连接场景（如 HTTP）常见，可通过 SO_REUSEADDR 或调整内核参数解决
  • 大量 CLOSE_WAIT：通常是服务端程序没有正确关闭连接（代码 bug）

1.3 TCP 可靠传输

可靠传输机制

机制原理说明
序列号/确认号每个字节都有序列号，接收方通过 ACK 确认保证数据有序、不丢失
超时重传发送后启动定时器，超时未收到 ACK 则重传RTO 动态计算（RTT 估算）
滑动窗口发送窗口内的数据可以连续发送，无需等待 ACK提高吞吐量
流量控制接收方通过窗口大小（rwnd）告知发送方自己的接收能力防止发送方淹没接收方
拥塞控制发送方维护拥塞窗口（cwnd），根据网络状况调整防止网络拥塞
校验和对 TCP 首部和数据计算校验和检测传输错误

1.4 TCP 拥塞控制

拥塞控制四阶段

慢启动
→
拥塞避免
→
快重传
→
快恢复
阶段cwnd 变化触发条件
慢启动每 RTT 翻倍（指数增长），从 1 MSS 开始连接开始或超时
拥塞避免每 RTT 增加 1 MSS（线性增长）cwnd ≥ ssthresh
快重传收到 3 个重复 ACK 立即重传丢失段收到 3 个重复 ACK
快恢复ssthresh = cwnd/2，cwnd = ssthresh + 3，进入拥塞避免快重传后
超时重传：ssthresh = cwnd/2, cwnd = 1 MSS，重新慢启动。快重传/快恢复避免了从慢启动重新开始，减少了性能损失。

1.6 HTTPS 与 TLS

TLS 握手过程（RSA 握手）

Client Hello（支持的加密套件、随机数）
→
Server Hello（选定加密套件、随机数 + 证书）
→
客户端验证证书 → 生成预主密钥 → 用服务端公钥加密发送
→
双方用三个随机数生成会话密钥 → 加密通信
  • 三个随机数：Client Random + Server Random + Pre-Master Secret → 生成对称会话密钥
  • 证书验证：浏览器检查证书链（服务器证书 → 中间 CA → 根 CA）、有效期、域名匹配、吊销状态
  • TLS 1.3：1-RTT 握手（0-RTT 恢复），废弃 RSA 密钥交换（前向安全性），仅支持 ECDHE

🎯第二部分：场景化讲解

2.1 HTTP 缓存机制

强缓存 vs 协商缓存

强缓存（不请求服务器）

  • Cache-Control：max-age=3600（秒）、no-cache（协商缓存）、no-store（不缓存）、public/private
  • Expires：过期的绝对时间（HTTP/1.0，受客户端时间影响）
  • Cache-Control 优先级高于 Expires
  • 命中时返回 200（from memory/disk cache）

协商缓存（请求服务器验证）

  • Last-Modified / If-Modified-Since：基于文件修改时间，精度为秒
  • ETag / If-None-Match：基于文件内容哈希，精度更高
  • ETag 优先级高于 Last-Modified
  • 命中时返回 304 Not Modified
浏览器发起请求
→
检查强缓存（Cache-Control/Expires）
→
未命中 → 携带 If-None-Match/If-Modified-Since
→
服务端验证 → 304 或 200

2.2 DNS 解析

DNS 解析过程

浏览器缓存
→
OS 缓存（hosts 文件）
→
本地 DNS 服务器
→
递归/迭代查询
  • 递归查询：客户端只需问一次，本地 DNS 服务器负责完整解析
  • 迭代查询：本地 DNS 依次向根 DNS → 顶级域 DNS → 权威 DNS 查询
  • 解析顺序：浏览器缓存 → OS 缓存 → 路由器缓存 → ISP DNS 缓存 → 根 DNS → 顶级域 → 权威 DNS
  • DNS 记录类型：A（IPv4）、AAAA（IPv6）、CNAME（别名）、MX（邮件）、NS（域名服务器）、TXT

2.3 WebSocket

WebSocket 协议

  • 特点：全双工通信，服务端可主动推送，低延迟
  • 握手：基于 HTTP 升级协议（Upgrade: websocket），状态码 101 Switching Protocols
  • 帧格式：轻量级帧头（2~14 字节），比 HTTP 头小得多
  • 心跳机制：Ping/Pong 帧保持连接活跃
  • 适用场景：实时聊天、在线游戏、股票行情、协同编辑

WebSocket vs HTTP 轮询

  • 轮询：客户端定时请求，浪费资源，有延迟
  • 长轮询：服务端 hold 住请求直到有数据，有延迟
  • WebSocket：真正的实时双向通信

WebSocket vs SSE

  • SSE（Server-Sent Events）：服务端单向推送
  • SSE 基于 HTTP，自动重连，文本格式
  • WebSocket：双向，二进制支持，不自动重连

2.4 Cookie / Session / Token

认证方式对比

特性CookieSessionToken（JWT）
存储位置浏览器服务端（内存/Redis）客户端（localStorage/Cookie）
安全性易 CSRF 攻击较安全（ID 在 Cookie 中）无 CSRF 问题（不自动携带）
跨域受同源策略限制需要共享 Session 存储天然支持跨域
扩展性4KB 限制服务端有状态，难扩展无状态，易水平扩展
适用场景简单状态管理传统 Web 应用前后端分离、微服务
JWT 结构：Header（算法）.Payload（声明）.Signature（签名）。服务端不存储状态，通过签名验证 token 合法性。注意：JWT 无法主动失效，可通过黑名单或短过期时间 + Refresh Token 解决。

🎤第三部分：模拟面试

TCP 三次握手的过程是什么？为什么不是两次或四次？
参考：① 客户端发 SYN；② 服务端回 SYN+ACK；③ 客户端发 ACK。两次握手不行：服务端无法确认客户端收到了 SYN+ACK，也无法防止历史连接。四次没必要：三次已经能确认双方收发能力，四次浪费资源。
追问：如果第三次 ACK 丢失会怎样？服务端处于 SYN_RCVD 状态，会重发 SYN+ACK，超时后关闭连接。客户端已进入 ESTABLISHED 状态，发数据时服务端会返回 RST。
HTTP/1.1 和 HTTP/2.0 有什么区别？HTTP/2.0 解决了什么问题？
参考：HTTP/1.1 的问题：① 队头阻塞（管道化前面的请求阻塞后面）；② 每个连接一次只能处理一个请求；③ 头部冗余。HTTP/2.0 解决方案：① 二进制分帧，多路复用（同一连接并行多个流）；② HPACK 头部压缩；③ 服务器主动推送；④ 流优先级。
追问：HTTP/2.0 仍有 TCP 层队头阻塞，HTTP/3.0 用 QUIC（基于 UDP）彻底解决。
HTTPS 的 TLS 握手过程？为什么需要三个随机数？
参考：Client Hello → Server Hello（证书）→ 客户端验证证书，生成 Pre-Master Secret 用服务端公钥加密发送 → 双方用三个随机数生成会话密钥。三个随机数的作用：Client Random 和 Server Random 是明文传输的，如果只用它们生成密钥不够安全。Pre-Master Secret 是加密传输的，三者结合确保密钥的随机性和安全性。
TCP 的 TIME_WAIT 状态是什么？为什么需要等待 2MSL？
参考：主动关闭方发送最后一个 ACK 后进入 TIME_WAIT，等待 2MSL（约 60 秒）。原因：① 确保最后一个 ACK 能到达对方（若丢失，对方会重发 FIN）；② 让网络中残余的旧连接数据包过期，防止影响新连接。
追问：大量 TIME_WAIT 怎么办？短连接场景常见，可通过连接池复用连接、SO_REUSEADDR、调整内核参数 tcp_tw_reuse 解决。
浏览器输入 URL 到页面展示，经历了哪些过程？
参考：① DNS 解析域名得到 IP；② TCP 三次握手建立连接（HTTPS 还需 TLS 握手）；③ 发送 HTTP 请求；④ 服务器处理请求，返回响应；⑤ 浏览器解析 HTML，构建 DOM 树；⑥ 解析 CSS，构建 CSSOM；⑦ 合并为渲染树；⑧ 布局（计算位置大小）；⑨ 绘制（GPU 光栅化）；⑩ 加载子资源（JS/CSS/图片），JS 可能阻塞解析和渲染。
TCP 拥塞控制的慢启动和拥塞避免有什么区别？
参考：慢启动：cwnd 从 1 MSS 开始，每收到一个 ACK 就增加 1 MSS（即每 RTT 翻倍），指数增长。拥塞避免：当 cwnd ≥ ssthresh 时切换，每 RTT 增加 1 MSS，线性增长。发生超时重传时：ssthresh = cwnd/2, cwnd = 1 MSS，重新慢启动。快重传/快恢复：收到 3 个重复 ACK 时，ssthresh = cwnd/2, cwnd = ssthresh + 3，进入拥塞避免（不从 1 开始）。
Cookie、Session、Token 各自的优缺点？什么时候用 JWT？
参考：Cookie 存在浏览器，有 4KB 限制，易 CSRF；Session 存在服务端，安全但有状态，分布式环境需要共享存储；Token（JWT）无状态，天然跨域，适合前后端分离和微服务。
JWT 适用场景：① 前后端分离架构；② 微服务间认证；③ 第三方授权（OAuth）。不适用：需要即时吊销的场景（JWT 无法主动失效）。
DNS 解析过程是怎样的？什么是递归查询和迭代查询？
参考：浏览器输入域名后，先查浏览器缓存 → OS 缓存 → hosts 文件 → 本地 DNS 服务器。本地 DNS 服务器如果没有缓存，会进行递归查询或迭代查询。递归查询：客户端只问一次，本地 DNS 负责完整解析过程。迭代查询：本地 DNS 依次向根 DNS（返回顶级域地址）→ 顶级域 DNS（返回权威 DNS 地址）→ 权威 DNS（返回最终 IP）查询。
追问：DNS 用 TCP 还是 UDP？通常用 UDP（端口 53），数据量小、速度快。但区域传送（AXFR）和响应超过 512 字节时用 TCP。
HTTP 状态码 301 和 302 有什么区别？304 是什么意思？
参考：301：永久重定向，浏览器会缓存，下次直接访问新地址。SEO 权重转移到新 URL。302：临时重定向，浏览器不缓存，每次仍请求原地址。304：Not Modified，协商缓存命中，资源未变化，使用浏览器缓存的版本。
追问：301 和 307 的区别？307 保证不会把 POST 改为 GET（301/302 在某些浏览器中会改变方法）。
