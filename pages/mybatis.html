Executor 三种类型

类型说明特点
SimpleExecutor简单执行器（默认）每次执行都创建新的 Statement
ReuseExecutor复用执行器复用 Statement 对象（Map 缓存）
BatchExecutor批处理执行器批量执行 SQL，减少网络往返
默认使用 SimpleExecutor，开启二级缓存后会用 CachingExecutor 装饰（装饰器模式）。BatchExecutor 适合批量插入/更新场景，注意需要手动 flushStatements()。

一级缓存 vs 二级缓存

缓存对比

一级缓存（Local Cache）

  • 作用域：SqlSession 级别
  • 默认：开启（SESSION 级别）
  • 实现：HashMap（PerpetualCache）
  • 生命周期：与 SqlSession 相同
  • 同一个 SqlSession 中相同查询直接返回缓存
  • 执行 insert/update/delete 后清空
  • 可设置为 STATEMENT 级别（每次查询后清空）

二级缓存（Global Cache）

  • 作用域：Mapper（namespace）级别
  • 默认：关闭
  • 实现：装饰器模式（多个 Cache 实现）
  • 生命周期：与应用相同
  • 多个 SqlSession 共享同一 Mapper 的缓存
  • SqlSession 关闭或提交后才写入二级缓存
  • 需要手动开启：<cache/>

缓存失效场景

场景一级缓存二级缓存
执行写操作（insert/update/delete）清空当前 SqlSession 缓存清空整个 namespace 缓存
调用 clearCache()清空不清空
SqlSession 关闭缓存销毁缓存写入二级缓存
配置 flushCache="true"每次查询前清空每次查询前清空
配置 localCacheScope=STATEMENT每次查询后清空不受影响
二级缓存的坑：1）多表关联查询时，A 表的修改不会清空 B 表 Mapper 的缓存，导致脏读；2）分布式环境下二级缓存默认是本地的，节点间不同步。解决方案：1）避免多表关联查询使用二级缓存；2）使用 Redis 等外部缓存作为二级缓存（如 mybatis-redis-cache）。

装饰器模式实现缓存

// MyBatis 缓存装饰器链
// 最底层：PerpetualCache（HashMap 实现）
// 装饰器层：
LruCache → FifoCache → SoftCache/WeakCache → LoggingCache → SerializedCache → SynchronizedCache → TransactionalCache

// 装饰顺序（从外到内）：
TransactionalCache
  → SynchronizedCache（线程安全）
    → LoggingCache（日志记录）

intercept() 方法
// 自定义插件示例：SQL 执行耗时统计
@Intercepts({
    @Signature(
        type = StatementHandler.class,     // 拦截的目标对象
        method = "query",                  // 拦截的方法
        args = {Statement.class, ResultHandler.class}  // 方法参数
    )
})
public class SlowSqlInterceptor implements Interceptor {

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();  // 执行原方法
        } finally {
            long cost = System.currentTimeMillis() - start;
            if (cost > 1000) {
                StatementHandler handler = (StatementHandler) invocation.getTarget();
                BoundSql boundSql = handler.getBoundSql();
                log.warn("慢 SQL [{}ms]: {}", cost, boundSql.getSql());
            }
        }
    }

    @Override
    public Object plugin(Object target) {
        return Plugin.wrap(target, this);  // 创建代理
    }
}
插件执行顺序与注册顺序相反（后注册的先执行，类似洋葱模型）。MyBatis 插件本质是 JDK 动态代理 + 责任链模式。

延迟加载

延迟加载原理

延迟加载（Lazy Loading）是指在查询主对象时不立即加载关联对象，只有在访问关联对象时才发送 SQL 查询。

<!-- 开启延迟加载 -->
<settings>
    <setting name="lazyLoadingEnabled" value="true"/>
    <setting name="aggressiveLazyLoading" value="false"/>  <!-- 按需加载 -->
    <setting name="lazyLoadTriggerMethods" value="equals,clone,hashCode,toString"/>
</settings>

<!-- association 延迟加载 -->
<resultMap id="orderWithUser" type="Order">
    <id property="id" column="id"/>
    <result property="orderNo" column="order_no"/>
    <association property="user" javaType="User"
                 select="com.example.mapper.UserMapper.selectById"
                 column="user_id" fetchType="lazy"/>
</resultMap>

<!-- collection 延迟加载 -->
<resultMap id="userWithOrders" type="User">
    <id property="id" column="id"/>
    <result property="name" column="name"/>
    <collection property="orders" ofType="Order"
                select="com.example.mapper.OrderMapper.selectByUserId"
                column="id" fetchType="lazy"/>
</resultMap>

实现原理：MyBatis 通过 CGLIB 为关联对象创建代理。当访问关联属性时，代理对象拦截 getter 方法，发送额外的 SQL 查询并填充数据。

第二部分：场景化讲解

#{} vs ${}

区别对比

#{}（预编译参数）

  • 使用 PreparedStatement 的 ? 占位符
  • 参数会被转义，防止 SQL 注入
  • 自动进行类型转换
  • 适合传递参数值
  • 默认会对字符串加引号
-- 生成的 SQL
SELECT * FROM user WHERE name = ?
-- 参数：'张三'

${}（字符串拼接）

  • 直接拼接到 SQL 字符串中
  • 不做转义，有 SQL 注入风险
  • 不做类型转换
  • 适合传递表名、列名、ORDER BY
  • 不会自动加引号
-- 生成的 SQL
SELECT * FROM user WHERE name = '张三'
-- 字符串直接拼接
-- #{} 的使用（推荐）
SELECT * FROM user WHERE id = #{id} AND name = #{name}

-- ${} 的使用场景（必须用时）
SELECT * FROM ${tableName} ORDER BY ${columnName} ${order}
-- 注意：使用 ${} 时必须在代码层做参数校验，防止 SQL 注入
原则：能用 #{} 就用 #{}，只有在动态表名、列名、ORDER BY 等无法使用占位符的场景才用 ${}。使用 ${} 时必须在代码层做白名单校验。

常见问题与优化

N+1 查询问题

问题：查询 N 个主对象后，每个主对象的关联对象需要单独发一次 SQL，总共 N+1 次查询。

解决方案：

  • 嵌套结果映射：使用 JOIN 查询，一次 SQL 获取所有数据（推荐）
  • 批量查询：先查主表 ID 列表，再用 IN 批量查关联表
  • 延迟加载：只在访问关联属性时才查询（适合不总是需要关联数据的场景）
  • MyBatis-Plus：使用 Wrapper 组装查询条件

MyBatis 常见性能优化

优化项说明
避免 SELECT *只查询需要的字段，减少网络传输和内存占用
批量操作使用 foreach 批量插入/更新，减少数据库交互次数
合理使用缓存一级缓存默认开启；二级缓存按需开启，注意多表关联的脏读问题
避免 N+1 查询使用 JOIN 或批量查询替代嵌套查询
分页查询大数据量使用物理分页（LIMIT），避免全表查询
索引优化确保 WHERE/JOIN 条件的字段有索引
使用 PreparedStatement使用 #{} 而非 ${}，利用预编译和计划缓存

第三部分：模拟面试

MyBatis 的整体架构是怎样的？一次 SQL 查询经历了哪些步骤？
参考：MyBatis 架构分为三层：1）接口层（SqlSession），提供 CRUD API；2）核心处理层（配置解析、SQL 解析、SQL 执行、结果映射）；3）基础支撑层（连接管理、事务管理、缓存、类型处理）。一次查询流程：SqlSession → Executor（检查缓存 → 执行查询） → StatementHandler（创建 Statement、设置参数、执行 SQL） → ResultSetHandler（将 ResultSet 映射为 Java 对象）。期间插件可以在四大对象（Executor、StatementHandler、ParameterHandler、ResultSetHandler）上进行拦截增强。
参考：一级缓存是 SqlSession 级别的，默认开启。同一个 SqlSession 中执行相同查询会直接返回缓存结果，执行写操作后清空。实现是 HashMap。二级缓存是 Mapper（namespace）级别的，默认关闭，需要在 XML 中加 <cache/> 开启。SqlSession 关闭或提交后，数据才写入二级缓存。二级缓存使用装饰器模式，底层也是 HashMap，外层包装了 LruCache、SerializedCache、SynchronizedCache 等。注意：二级缓存在多表关联查询时可能导致脏读（A 表修改不会清空 B 表的缓存），分布式环境下默认是本地缓存，建议使用 Redis 替代。
参考：#{} 使用 PreparedStatement 的参数占位符（?），参数会被预编译和转义，可以防止 SQL 注入。${} 是字符串直接拼接，不做任何转义，有 SQL 注入风险。推荐使用 #{} 因为：1）安全，防止 SQL 注入；2）性能好，PreparedStatement 可以复用执行计划；3）自动类型转换。${} 的使用场景：动态表名、动态列名、ORDER BY 子句（因为这些无法用占位符）。使用 ${} 时必须在代码层做白名单校验。
MyBatis 的插件机制是如何实现的？如何自定义插件？
参考：MyBatis 插件基于 JDK 动态代理 + 责任链模式。核心是 Interceptor 接口，通过 @Intercepts 注解声明要拦截的目标对象和方法（四大对象：Executor、StatementHandler、ParameterHandler、ResultSetHandler）。在 Configuration 创建四大对象时，MyBatis 会遍历所有注册的 Interceptor，通过 Plugin.wrap() 用动态代理包装目标对象。多个插件按注册顺序的逆序层层代理，执行时按责任链顺序调用 intercept() 方法。自定义插件步骤：1）实现 Interceptor 接口；2）用 @Intercepts 声明拦截目标；3）在 intercept() 中实现增强逻辑，调用 invocation.proceed() 执行原方法；4）注册到 MyBatis 配置。典型应用：分页插件 PageHelper、SQL 性能监控插件。
参考：延迟加载通过 CGLIB 动态代理实现。查询主对象时，MyBatis 为关联属性创建代理对象。当访问关联属性时，代理对象拦截 getter 方法，发送额外的 SQL 查询填充数据。配置：lazyLoadingEnabled=true 开启，aggressiveLazyLoading=false 设置按需加载。使用场景：1）关联数据不是每次都需要（如订单详情可能不需要查看用户信息）；2）避免 N+1 查询的权衡方案。注意事项：延迟加载在 SqlSession 关闭后无法工作（因为需要发送 SQL），所以要么在 SqlSession 生命周期内访问关联属性，要么使用嵌套结果映射替代。
参考：MyBatis-Plus 增强：1）通用 CRUD：BaseMapper 和 IService 提供单表增删改查，无需写 XML；2）条件构造器：QueryWrapper/LambdaQueryWrapper 链式构建查询条件；3）分页插件：物理分页，自动拼接 LIMIT；4）代码生成器：一键生成 Entity/Mapper/Service/Controller；5）逻辑删除：@TableLogic 注解实现软删除；6）自动填充：@TableField(fill=FieldFill.INSERT) 自动填充创建时间等；7）乐观锁：@Version 注解。LambdaQueryWrapper 好处：1）使用方法引用（User::getName），编译期检查字段名，避免拼写错误；2）重构友好，字段改名时编译报错；3）代码可读性更好。
参考：association 用于一对一关联映射（如订单关联用户），collection 用于一对多关联映射（如用户关联多个订单）。两种实现方式：1）嵌套结果映射（推荐）：使用 JOIN 查询一次获取所有数据，在 ResultMap 中用 association/collection 定义映射关系；2）嵌套查询：association/collection 的 select 属性指向另一个查询方法，有 N+1 问题。避免 N+1 的方式：优先使用嵌套结果映射（JOIN）；如果关联数据不需要每次加载，使用延迟加载（fetchType="lazy"）；或者先查主表 ID 列表，再用 IN 批量查关联表。
