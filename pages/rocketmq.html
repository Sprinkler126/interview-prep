组件职责详解

  • NameServer：几乎无状态的注册中心，各 NameServer 节点互不通信，Broker 向所有 NameServer 注册路由信息，Producer/Consumer 从任意 NameServer 拉取 Topic 路由。相比 ZooKeeper 更轻量，无单点瓶颈。
  • Broker：消息存储的核心节点。每个 Broker 启动时向所有 NameServer 注册，定期发送心跳。Broker 分为 Master（可读写）和 Slave（只读、备份），通过 BrokerName + BrokerId 标识。
  • Producer：消息生产者，通过 NameServer 获取 Topic 的 Broker 列表，选择 MessageQueue 发送消息。支持同步、异步、单向（Oneway）三种发送方式。
  • Consumer：消息消费者，支持集群模式（一条消息只被组内一个消费者消费）和广播模式（所有消费者都收到）。默认 Pull 模式，封装为 Push 模式（长轮询）。

设计取舍：为什么 RocketMQ 自研 NameServer 而不用 ZooKeeper？

设计起点：RocketMQ 早期版本其实依赖 ZooKeeper，但 Alibaba 团队在生产实践中发现 ZK 的几个硬伤，遂自研轻量级 NameServer。这体现了"不为了用成熟组件而用，按实际痛点取舍"的工程思想。

ZooKeeper 的痛点

  • CP 系统，选举时不可用：ZK Leader 选举期间整个集群无法服务，对 MQ 这种 AP 倾向系统是痛点
  • Watch 机制重：每次节点变化触发 Watch，海量 Topic + Broker 时回调风暴
  • 运维复杂：要单独维护一套 ZK 集群（JVM 调优、ZAB 协议、数据快照）
  • 写入瓶颈：所有写都过 Leader，元数据频繁更新时压力大

✅ NameServer 的解法

  • 完全无状态：节点互不通信，每个节点独立存全量路由，挂了用别的
  • AP 倾向：Broker 注册是推给所有 NS，NS 间不复制；短暂不一致靠心跳过期收敛
  • 极简实现：就是一个内存 HashMap + 定时清理过期 Broker，几 MB 内存
  • 客户端容错：Producer/Consumer 拉路由时轮询所有 NS，任一可用即可
权衡代价：NameServer 牺牲了强一致性——某 NS 可能短暂持有过期路由（Broker 已宕机但心跳未过期），客户端可能拿到失效地址，需配合发送失败重试 + 客户端定时刷新路由弥补。这是用"最终一致"换"轻量+高可用"的典型取舍。
面试加分：能说出"RocketMQ 放弃 ZK 是因为 ZK 是 CP 系统与 MQ 的 AP 需求冲突"会非常加分。Kafka 早期也用 ZK，4.0 起用 KRaft 替代，思路与 RocketMQ 不谋而合——都是"去外部元数据依赖"。

Topic 与 MessageQueue

一个 Topic 对应多个 MessageQueue（类似 Kafka 的 Partition），分布在不同的 Broker 上。MessageQueue 是消息路由和负载均衡的最小单位。Producer 通过轮询或哈希选择 Queue 发送，Consumer 以 Queue 为单位分配消费。

2. 消息类型

RocketMQ 六种消息类型
普通消息 — 同步/异步/单向发送，不保证顺序，最基础的消息类型
顺序消息 — 全局有序或分区有序，通过 MessageQueueSelector 实现
延迟消息 — 指定延迟投递，4.x 有 18 个固定级别，5.0 支持任意时间
事务消息 — Half Message + 本地事务 + 事务回查，实现最终一致性
批量消息 — 将多条消息合并发送，提高吞吐量，要求同一 Topic、同一 WaitStoreMsgOK
广播消息 — 所有消费者都收到同一消息，用于配置广播、缓存刷新等

3. 顺序消息

顺序消息：全局有序 vs 分区有序

全局有序

  • 只使用 1 个 MessageQueue
  • 所有消息串行发送和消费
  • 吞吐量低，适合严格顺序场景
  • 如：数据库 Binlog 同步

分区有序（推荐）

  • 同一业务 Key 的消息发到同一 Queue
  • 同一 Queue 内有序
  • 不同 Queue 可并行，吞吐量高
  • 如：同一订单的消息有序

实现原理

发送端：使用 MessageQueueSelector，根据业务 Key（如订单 ID）选择固定的 MessageQueue。例如对订单 ID 取模，保证同一订单的消息始终发送到同一个 Queue。

消费端：使用 MessageListenerOrderly（而非 MessageListenerConcurrently），它会对每个 Queue 加锁，保证单 Queue 内串行消费。

订单ID=1001
→ hash % QueueNum
Queue-2
→
Consumer 串行消费 Queue-2

顺序消息的代价：消费端单 Queue 串行，消费并行度降低。如果某条消息消费失败会一直重试，阻塞后续消息。需要做好超时和死信兜底。

4. 延迟消息

4.x 版本：18 个固定延迟级别

RocketMQ 4.x 不支持任意时间延迟，只支持 18 个固定级别，通过 messageDelayLevel 配置：

级别延迟时间级别延迟时间

发送时设置 message.setDelayTimeLevel(3) 即表示延迟 10 秒投递。

实现原理（4.x）

延迟消息不是在 Broker 端定时扫描，而是改 Topic 投递：

Producer 发送延迟消息
→
Broker 改写 Topic 为 SCHEDULE_TOPIC_XXXX
→
TimerTask 到期后投递到原 Topic
→
Consumer 正常消费

延迟消息被投递到内部 Topic SCHEDULE_TOPIC_XXXX 的 18 个 Queue（对应 18 个级别），每个 Queue 有自己的定时任务，到期后投递回原 Topic 的 ConsumeQueue。

5.0 版本：任意时间延迟

RocketMQ 5.0 引入任意时间延迟，支持秒级精度的任意延迟时间。使用 message.setDeliveryTimestamp(timestamp) 设置投递时间戳。底层基于时间轮（TimingWheel）实现，精度更高、资源消耗更少。

时间轮算法是延迟消息的核心数据结构。相比优先级队列，时间轮在大量延迟任务场景下插入和删除都是 O(1)。

5. 事务消息

事务消息三阶段流程
1. 发送 Half Message
对 Consumer 不可见
→
2. 执行本地事务
DB 操作
→
3. Commit / Rollback
提交或回滚

详细流程

  • Step 1：Producer 发送 Half Message 到 Broker，消息写入 RMQ_SYS_TRANS_HALF_TOPIC，Consumer 看不到。
  • Step 2：Broker 返回 Half Message 发送成功，Producer 执行本地事务。
  • Step 3：根据本地事务结果，Producer 发送 Commit（消息投递到目标 Topic）或 Rollback（消息标记为删除）。
  • Step 4（回查）：如果 Broker 长时间没收到 Commit/Rollback（Producer 宕机、网络异常），Broker 会定时回查 Producer 的本地事务状态（最多 15 次，可配置）。

事务回查机制

Broker 在 transactionTimeout（默认 6s）后未收到二次确认，会发起回查。回查间隔由 transactionCheckInterval（默认 60s）控制，最多回查 15 次（transactionCheckMax）。Producer 需实现 TransactionListener.checkLocalTransaction() 来处理回查。

事务消息只保证最终一致性，不保证实时性。Half Message 在 Commit 前对 Consumer 不可见，Rollback 的消息只做标记不物理删除。

6. 消费模式

Push vs Pull、集群 vs 广播

Push 模式（推荐）

  • 底层是长轮询 Long Polling
  • Broker 有消息立即通知 Consumer
  • 使用 MessageListenerConcurrently
  • 开发简单，实时性好

Pull 模式

  • Consumer 主动调用 pull()
  • 可自定义拉取频率和批量大小
  • 适合批处理、流控场景
  • 需要自行管理 offset

集群消费 vs 广播消费

模式特点适用场景
CLUSTERING（默认）一条消息只被组内一个消费者消费大多数业务场景
BROADCASTING所有消费者都收到同一条消息配置广播、本地缓存刷新

Long Polling 长轮询

Push 模式的底层实现是长轮询：Consumer 发起 Pull 请求，如果 Broker 没有新消息，不会立即返回空，而是hold 住请求（默认 5s），期间有新消息到达立即返回。这样既避免了短轮询的无效请求，又保证了实时性。

Consumer Pull 请求
→
Broker hold 5s
→
有消息立即返回
无消息超时返回空

7. 死信队列（DLQ）

重试与死信流程

消息消费失败后会进入重试队列，按梯度时间重试（默认 16 次：10s, 30s, 1min, 2min, ... 2h）。重试次数耗尽后，消息进入死信队列 %DLQ%ConsumerGroup。

消费失败
→
重试队列（最多 16 次）
→
死信队列 DLQ

死信队列特点

  • 每个 ConsumerGroup 有独立的死信 Topic：%DLQ%ConsumerGroupA
  • 死信消息不会再被消费者自动消费
  • 需要专门的消费者订阅死信 Topic 进行人工处理或告警
  • 死信消息默认保留 72 小时（与普通消息一致）

8. 消息存储

RocketMQ 存储结构：CommitLog + ConsumeQueue + IndexFile
CommitLog
所有消息顺序写入
单个文件 1GB
所有 Topic 混合存储
⬇️ 异步构建（ReputMessageService）
ConsumeQueue
逻辑队列，每个 Topic-Queue 一个
20 字节/条（offset + size + tag hash）
消费时的索引
IndexFile
哈希索引，支持按 Key 查询
Key Hash + 时间范围
默认 2000W 条/文件

写入流程

  • 顺序写 CommitLog：所有消息追加写入 CommitLog（顺序写磁盘，性能极高）
  • 异步构建索引：后台线程 ReputMessageService 从 CommitLog 异步构建 ConsumeQueue 和 IndexFile
  • 消费查询：Consumer 先查 ConsumeQueue（很小，可全内存缓存）拿到 CommitLog 物理偏移量，再从 CommitLog 读取完整消息
  • Key 查询：通过 IndexFile 的哈希索引定位消息

这种设计类似于数据库的"堆表 + 二级索引"：CommitLog 是堆表（按写入顺序存储），ConsumeQueue 和 IndexFile 是二级索引（按查询需求构建）。

设计动机：为什么 RocketMQ 用"CommitLog 混合存储"而 Kafka 用"Partition 独立存储"？

设计起点：消息存储的核心矛盾是"写入要快（顺序写）"和"消费要快（按 Topic-Queue 定位）"。Kafka 和 RocketMQ 给出了截然不同的解法，体现了各自的定位差异。

Kafka：Partition 独立存储

  • 每个 Partition 一个独立日志文件，写入直接落在对应 Partition
  • 优势：消费时直接顺序读对应 Partition 文件，无需中间索引，零开销
  • 劣势：Topic+Partition 数量多时，并发写多个文件，磁盘随机写严重（多个 Partition 抢磁头）
  • 定位：Kafka 单集群 Topic 数通常少（数十个），每个 Partition 流量大，随机写影响小

RocketMQ：CommitLog 混合存储

  • 所有 Topic 的消息混在一个 CommitLog 文件，写入永远只 append 一个文件
  • 优势：无论多少 Topic，写入都是单文件顺序写，吞吐稳定不退化
  • 劣势：消费时需先查 ConsumeQueue 拿到 CommitLog 偏移量，多一次索引查找
  • 定位：阿里电商场景 Topic 数动辄上万（每业务线多个），混合存储保证 Topic 多时写入不退化
面试要点：这是 RocketMQ 与 Kafka 在海量 Topic 场景下性能差异的关键。Kafka 在 Topic 数 <100 时吞吐无敌；RocketMQ 在 Topic 数 >1000 时仍稳定。ConsumeQueue 的 20 字节小条目设计让索引几乎全内存，消费端额外开销极小。
易错点：CommitLog 混合存储意味着删除某个 Topic 的消息很麻烦——消息物理上和其他 Topic 混在一起，只能靠文件过期整体删除，不能单独清理某 Topic。这是 RocketMQ 不擅长"按 Topic 精细控制保留"的根因。

刷盘策略

策略配置特点
同步刷盘flushDiskType=SYNC_FLUSH消息写入 Page Cache 后立即刷盘，可靠性高，性能较低
异步刷盘（默认）flushDiskType=ASYNC_FLUSH后台线程定时刷盘，性能高，极端情况（掉电）可能丢少量消息

9. 高可用机制

Broker 主从复制模式

同步复制（SYNC_MASTER）

  • Master 写入后等待 Slave 同步完成才返回 ACK
  • 数据可靠性高
  • 写入延迟较高
  • 适合金融场景

异步复制（ASYNC_MASTER，默认）

  • Master 写入成功即返回 ACK
  • Slave 异步拉取同步
  • 性能高，Master 宕机可能丢少量消息
  • 适合大多数业务场景

DLedger 多副本模式（4.5+）

基于 Raft 协议的多副本方案，替代传统 Master-Slave。至少 3 个节点组成 Raft Group，Leader 选举和数据复制由 DLedger 自动管理。

  • 自动选主：Master 宕机后自动从 Follower 中选举新 Leader，无需人工干预
  • 多数派写入：消息写入多数节点后才返回 ACK，数据不丢失
  • 原 Master-Slave 模式下 Master 宕机需要人工切换，DLedger 解决了这个痛点

推荐生产配置：同步刷盘 + 同步复制（SYNC_FLUSH + SYNC_MASTER），配合 BrokerRole.SLAVE，做到"绝对不丢消息"。

2.2 金融交易场景

金融级消息可靠性保障

  • 同步刷盘 + 同步复制：保证消息写入磁盘且 Slave 同步完成后才返回 ACK

🎤第三部分：模拟面试

RocketMQ 的整体架构是什么？
四组件架构——NameServer（无状态注册中心，管理 Topic 路由信息，节点间不通信）；Broker（消息存储与转发，Master-Slave 架构，CommitLog 存储）；Producer（消息生产者，支持同步/异步/单向发送）；Consumer（消息消费者，Push/Pull 模式）。NameServer 比 ZooKeeper 更轻量，无单点瓶颈。
RocketMQ 如何保证消息顺序？
两种方案——① 全局有序：只使用 1 个 MessageQueue，吞吐量低，适合 Binlog 同步；② 分区有序（推荐）：同一业务 Key（如订单 ID）通过 MessageQueueSelector 发到同一 Queue。消费端用 MessageListenerOrderly 对每个 Queue 加锁串行消费。代价是单 Queue 并行度降低，需配合死信队列兜底。
RocketMQ 事务消息的原理？
三阶段——① 发送 Half Message（写入 HALF_TOPIC，Consumer 不可见）；② 执行本地事务；③ 根据结果发送 Commit（投递到目标 Topic）或 Rollback（标记删除）。如果 Broker 长时间未收到确认（Producer 宕机），会定时回查 Producer 的本地事务状态（最多 15 次）。只保证最终一致性，不保证实时性。
RocketMQ 延迟消息的实现原理？
4.x 版本有 18 个固定延迟级别（1s~2h），发送时设置 DelayTimeLevel。原理：延迟消息被改写 Topic 为 SCHEDULE_TOPIC_XXXX，存入对应级别的 Queue，由定时任务到期后投递回原 Topic。5.0 版本支持任意时间延迟，使用 DeliveryTimestamp + 时间轮算法。
RocketMQ 的消息存储结构？
三层结构——① CommitLog：所有消息顺序追加写入（单文件 1GB），所有 Topic 混合存储；② ConsumeQueue：逻辑队列索引（每条 20 字节：offset + size + tag hash），每个 Topic-Queue 一个文件；③ IndexFile：哈希索引，支持按 Key 查询。消费流程：先查 ConsumeQueue 拿偏移量，再从 CommitLog 读完整消息。类似于"堆表 + 二级索引"。
RocketMQ 和 Kafka 怎么选？
RocketMQ：业务消息首选，原生支持事务消息、延迟消息、消息轨迹、消息回溯，金融级可靠性，国内阿里系广泛使用。Kafka：大数据首选，吞吐量更高（百万级/s），与 Flink/Spark/Hadoop 生态深度集成。简单原则：业务消息选 RocketMQ，大数据管道选 Kafka。
RocketMQ 的死信队列机制？
消息消费失败后进入重试队列，默认重试 16 次（梯度时间：10s, 30s, 1min, ... 2h）。重试耗尽后消息进入死信队列 %DLQ%ConsumerGroup。死信消息不会被自动消费，需要专门消费者订阅 DLQ Topic 进行人工处理或告警。
RocketMQ 的高可用方案？
两种——① Master-Slave：同步复制（SYNC_MASTER，数据不丢但延迟高）或异步复制（ASYNC_MASTER，性能高但可能丢少量数据），Master 宕机需人工切换；② DLedger（4.5+）：基于 Raft 协议的多副本，至少 3 节点，自动选主、多数派写入，解决手动切换痛点。金融场景推荐同步刷盘 + 同步复制。
Push 模式和 Pull 模式的区别？
Push（底层是长轮询 Long Polling）：Broker 有消息立即返回，开发简单、实时性好。Pull：Consumer 主动拉取，可自定义频率和批量大小，适合批处理和流控。长轮询原理：Consumer 发 Pull 请求，Broker 没消息时 hold 住请求（默认 5s），期间有新消息立即返回，兼顾实时性和效率。
RocketMQ 的刷盘策略？
两种——① 同步刷盘（SYNC_FLUSH）：消息写入 Page Cache 后立即刷盘，可靠性高，性能较低；② 异步刷盘（ASYNC_FLUSH，默认）：后台线程定时刷盘，性能高，极端情况（掉电）可能丢少量消息。金融场景建议同步刷盘 + 同步复制，做到"绝对不丢"。
如何处理 RocketMQ 消息积压？
紧急：增加消费者实例数（≤ Queue 数）、临时增加 Queue 数量。消费端：批量消费、异步处理、数据库批量写入、调整 consumeThreadMin/Max。根本：优化消费逻辑耗时、异步化非关键操作。预防：Dashboard 监控 Consumer Lag，设告警阈值。
