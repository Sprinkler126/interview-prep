@SpringBootApplication 注解拆解

@SpringBootApplication
// 等价于以下三个注解
@SpringBootConfiguration    // 标记为配置类（本质是 @Configuration）
@EnableAutoConfiguration    // 开启自动配置
@ComponentScan              // 包扫描（默认扫描主类所在包及子包）

// @EnableAutoConfiguration 的核心
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@AutoConfigurationPackage   // 将主类所在包注册到 AutoConfigurationPackages
@Import(AutoConfigurationImportSelector.class)  // 导入自动配置类
public @interface EnableAutoConfiguration { }

Spring Boot 3.x 改用 imports 文件替代 spring.factories，解析效率更高，因为 spring.factories 是全量加载再过滤，而 imports 文件支持条件化按需加载。

自动配置类示例分析

@Configuration
@ConditionalOnClass(DataSource.class)           // classpath 有 DataSource 类才生效
@ConditionalOnMissingBean(DataSource.class)     // 容器中没有 DataSource Bean 才生效
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public DataSource dataSource(DataSourceProperties properties) {
        // 根据配置自动创建 DataSource
        return DataSourceBuilder.create()
            .url(properties.getUrl())
            .username(properties.getUsername())
            .password(properties.getPassword())
            .build();
    }
}

自动配置的核心思想：约定优于配置。引入 Starter 依赖后，Spring Boot 自动检测 classpath 上的类和已有的 Bean，通过条件注解决定是否创建默认的 Bean。用户可以通过自定义 Bean 或修改配置属性来覆盖默认行为。

条件注解

@Conditional 系列注解

注解生效条件典型用途
@ConditionalOnClassclasspath 中存在指定类引入某依赖后自动配置
@ConditionalOnMissingClassclasspath 中不存在指定类排除特定依赖时的配置
@ConditionalOnBean容器中存在指定 Bean依赖其他 Bean 的配置
@ConditionalOnMissingBean容器中不存在指定 Bean提供默认实现，允许用户覆盖
@ConditionalOnProperty配置属性满足条件@ConditionalOnProperty(prefix="app", name="cache", havingValue="redis")
@ConditionalOnResourceclasspath 中存在指定资源存在某个配置文件时生效
@ConditionalOnWebApplication当前是 Web 应用Web 相关自动配置
@ConditionalOnNotWebApplication当前不是 Web 应用非 Web 环境的配置
@ConditionalOnExpressionSpEL 表达式为 true复杂条件判断
@ConditionalOnMissingBean 是自动配置"可被覆盖"的关键：Spring Boot 先提供默认 Bean，如果用户自己定义了同类型的 Bean，自动配置的 Bean 就不会生效。

自定义 Starter 步骤

// 1. 创建属性配置类
@ConfigurationProperties(prefix = "app.greeting")
public class GreetingProperties {
    private String prefix = "Hello";
    private String suffix = "!";
    // getter/setter
}

// 2. 创建自动配置类
@Configuration
@EnableConfigurationProperties(GreetingProperties.class)
@ConditionalOnClass(GreetingService.class)
public class GreetingAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public GreetingService greetingService(GreetingProperties properties) {
        return new GreetingService(properties.getPrefix(), properties.getSuffix());
    }
}

// 3. 创建业务类
public class GreetingService {
    private final String prefix;
    private final String suffix;

    public GreetingService(String prefix, String suffix) {
        this.prefix = prefix;
        this.suffix = suffix;
    }

    public String greet(String name) {
        return prefix + " " + name + suffix;
    }
}

// 4. 注册自动配置
// resources/META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  com.example.starter.GreetingAutoConfiguration

// 5. 使用（引入 starter 依赖后）
// application.yml
app:
  greeting:
    prefix: "Hi"
    suffix: "!!"

@Autowired
private GreetingService greetingService;

Actuator 监控

常用 Actuator 端点

端点说明默认暴露
/actuator/health健康检查（UP/DOWN/UNKNOWN）是
/actuator/info应用信息是
/actuator/metrics指标数据（JVM/HTTP/自定义）否
/actuator/env环境变量和配置属性否
/actuator/beans容器中所有 Bean 信息否
/actuator/configprops@ConfigurationProperties 配置否
/actuator/mappingsURL 映射（RequestMapping）否
/actuator/loggers日志级别查看/修改否
/actuator/threaddump线程 dump否
/actuator/heapdump堆 dump 文件下载否
/actuator/prometheusPrometheus 格式指标否
 
# Actuator 配置
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,env  # 暴露的端点
        exclude: shutdown                  # 排除的端点
  endpoint:
    health:
      show-details: always  # 显示详细健康信息（磁盘/DB/Redis）
    shutdown:
      enabled: true         # 开启优雅停机端点
生产环境不要暴露所有端点，特别是 /actuator/env（可能泄露密码）和 /actuator/heapdump（内存快照）。建议只暴露 health、info、metrics。

配置加载顺序

Spring Boot 配置优先级（从高到低）

1. 命令行参数 --server.port=9090
2. Java 系统属性 -Dserver.port=9090
3. 操作系统环境变量 SERVER_PORT=9090
4. application-{profile}.yml（profile 特定配置）
5. application.yml（主配置文件）
6. @PropertySource 引入的配置
7. 默认属性 SpringApplication.setDefaultProperties()
同级目录下，YAML 优先于 Properties。jar 包外的配置文件优先于 jar 包内的。配置查找路径：file:./config/ > file:./ > classpath:/config/ > classpath:/。

Profile 机制

多环境配置

# application.yml（公共配置）
spring:
  profiles:
    active: dev  # 激活的 Profile

---
# application-dev.yml（开发环境）
spring:
  config:
    activate:
      on-profile: dev
server:
  port: 8080
logging:
  level:
    com.example: debug

---
# application-prod.yml（生产环境）
spring:
  config:
    activate:
      on-profile: prod
server:
  port: 80
logging:
  level:
    com.example: info

激活方式（优先级从高到低）：

  1. 命令行：--spring.profiles.active=prod
  2. Java 系统属性：-Dspring.profiles.active=prod
  3. 环境变量：SPRING_PROFILES_ACTIVE=prod
  4. 配置文件：spring.profiles.active=dev
  5. 代码方式：SpringApplication.setAdditionalProfiles("prod")

启动流程关键步骤

@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        // SpringApplication.run() 内部流程
        SpringApplication app = new SpringApplication(Application.class);

        // 1. 推断应用类型（SERVLET / REACTIVE / NONE）
        // 2. 加载 META-INF/spring.factories 中的 ApplicationContextInitializer
        // 3. 加载 META-INF/spring.factories 中的 ApplicationListener

        app.run(args);
        // 4. 创建并配置 Environment（加载配置文件）
        // 5. 创建 ApplicationContext
        // 6. 准备 Context（加载 BeanDefinition）
        // 7. 刷新 Context（refresh()，核心：Bean 实例化、依赖注入、AOP）
        // 8. 调用 ApplicationRunner 和 CommandLineRunner
        // 9. 发布 ApplicationReadyEvent
    }
}

ApplicationRunner vs CommandLineRunner

CommandLineRunner

  • 接收 String[] args 原始参数
  • 可使用 @Order 排序
  • 在容器启动完成后执行

ApplicationRunner

  • 接收 ApplicationArguments 对象
  • 支持解析 optional/non-optional 参数
  • 可使用 @Order 排序

第三部分：模拟面试

Spring Boot 的自动配置原理是什么？
参考：@SpringBootApplication 包含 @EnableAutoConfiguration，它通过 @Import(AutoConfigurationImportSelector.class) 加载 META-INF/spring.factories（Spring Boot 2.x）或 AutoConfiguration.imports（3.x）中定义的自动配置类。每个自动配置类通过 @Conditional 系列注解进行条件判断（如 @ConditionalOnClass、@ConditionalOnMissingBean），只有满足条件时才会生效。用户自定义的 Bean 优先级高于自动配置（@ConditionalOnMissingBean 保证）。核心思想是"约定优于配置"——引入 Starter 后自动提供合理默认值，用户可按需覆盖。
参考：自定义 Starter 需要两个模块：1）autoconfigure 模块：创建 @ConfigurationProperties 属性类、@Configuration 自动配置类（使用 @Conditional 注解控制条件）、@Bean 定义默认实现；2）starter 模块：空模块，仅引入 autoconfigure 和必要的第三方依赖。注册：在 autoconfigure 模块的 META-INF/spring.factories 中注册自动配置类。命名规范：官方 spring-boot-starter-xxx，第三方 xxx-spring-boot-starter。最佳实践：自动配置类使用 @ConditionalOnMissingBean 保证可被覆盖；属性类使用 @ConfigurationProperties 绑定配置；提供 spring-configuration-metadata.json 支持 IDE 提示。
参考：优先级从高到低：1）命令行参数（--key=value）；2）Java 系统属性（-Dkey=value）；3）操作系统环境变量（大写下划线格式）；4）application-{profile}.yml；5）application.yml；6）@PropertySource 注解引入的配置；7）默认属性。同级目录下 jar 包外的配置优先于 jar 包内。查找路径优先级：file:./config/ > file:./ > classpath:/config/ > classpath:/。配置属性支持松散绑定（server.port = SERVER_PORT = server_port 都可以绑定）。
参考：@ConditionalOnMissingBean 表示"当容器中不存在指定类型的 Bean 时才生效"。自动配置中大量使用是因为 Spring Boot 的设计理念是"提供默认实现，允许用户覆盖"。如果用户没有自定义 Bean，自动配置提供默认实现；如果用户自己定义了同类型的 Bean，自动配置就不会生效。例如 DataSourceAutoConfiguration 使用 @ConditionalOnMissingBean(DataSource.class)，当用户自己配置了数据源时，Spring Boot 的默认数据源配置就会被跳过。这保证了 Starter 的开箱即用同时又足够灵活。
参考：Spring Boot 通过 ServletWebServerFactory 创建内嵌的 Tomcat 实例。TomcatServletWebServerFactory 在 refresh() 阶段创建 Tomcat 实例、配置 Connector（端口/线程池/协议）、部署 Web 应用（DispatcherServlet）。自定义配置方式：1）application.yml 中通过 server.tomcat.* 配置线程池、连接数等；2）实现 WebServerFactoryCustomizer<TomcatServletWebServerFactory> 编程式自定义；3）注册 TomcatConnectorCustomizer 自定义 Connector。切换容器：排除 spring-boot-starter-tomcat，引入 spring-boot-starter-undertow 或 jetty。
参考：Profile 是 Spring 提供的多环境配置机制。Spring Boot 扩展了它：1）通过 spring.profiles.active 激活指定 Profile；2）加载对应的 application-{profile}.yml 配置文件；3）@Profile 注解控制 Bean 只在特定 Profile 下创建。激活方式：命令行参数（最高优先级）、环境变量、配置文件、代码方式。Spring Boot 2.4+ 支持 Profile 分组（spring.profiles.group）和多文档 YAML（---分隔）。Spring Profiles 与 @Conditional 不同：Profile 控制"环境"，@Conditional 控制"条件"。
参考：实现 HealthIndicator 接口或继承 AbstractHealthIndicator：重写 doHealthCheck() 方法，检查自定义资源（如数据库连接、Redis 连接、外部 API 可用性），返回 Builder.up() 或 down() 状态。复合健康检查使用 CompositeHealthContributor。可通过 management.endpoint.health.show-details=always 显示详细信息。禁用默认健康检查：management.health.defaults.enabled=false。自定义健康状态码映射：management.endpoint.health.status.http-mapping.down=503。
