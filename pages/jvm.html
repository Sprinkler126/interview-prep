  • 方法区由永久代实现
  • 位于 JVM 堆内存中

  • 容易出现 OOM: PermGen space
  • 字符串常量池在永久代

  • 方法区由元空间实现
  • 位于本地内存（Native Memory）
  • 大小由 -XX:MaxMetaspaceSize 控制
  • 默认不限制大小（受物理内存限制）
  • 字符串常量池移到堆中

内存分配方式

指针碰撞（Bump the Pointer）

堆内存绝对规整时使用。已用和空闲内存中间有一个指针，分配时将指针向空闲方向移动对象大小的距离。

适用：Serial、ParNew 等带压缩整理的收集器

空闲列表（Free List）

堆内存不规整时使用。JVM 维护一个列表记录哪些内存块可用，分配时从列表中找到足够大的空间划分给对象。

适用：CMS 等不带压缩整理的收集器

并发场景下的线程安全问题：JVM 采用 CAS + 失败重试 或 TLAB（Thread Local Allocation Buffer）解决。TLAB 为每个线程在 Eden 区预先分配一小块内存，避免多线程竞争。

垃圾收集算法

对象存活判定

引用计数法

  • 每个对象维护引用计数器
  • 引用 +1，取消引用 -1
  • 计数为 0 则可回收
  • 缺点：无法解决循环引用
  • JVM 不使用此算法

可达性分析（GC Roots）

  • 从 GC Roots 出发遍历引用链
  • 不可达的对象即为可回收
  • GC Roots 包括：
  • 虚拟机栈中引用的对象
  • 方法区中静态属性/常量引用
  • Native 方法引用的对象
  • synchronized 持有的对象

四种 GC 算法

标记-复制存活对象复制到另一块，清除原区域无碎片；效率高空间浪费 50%新生代（Eden+S0→S1）

Humongous 对象

  • 大小超过 Region 50% 的对象被判定为 Humongous 对象
  • Humongous 对象直接分配在连续的 Humongous Region 中
  • Humongous Region 不会被 Mixed GC 回收，只在 Full GC 时回收
  • 应尽量避免创建 Humongous 对象（大数组、大字符串等）

JIT 编译

C1 与 C2 编译器

C1 编译器（Client Compiler）

  • 编译速度快，优化较少
  • 简单可靠的优化（方法内联、去虚拟化）
  • 适用于客户端程序

1.9 Java 内存模型 (JMM) — 并发编程的灵魂

JMM 是什么？为什么需要它？

设计出发点：JVM 把内存划分成"堆/栈/方法区"是物理视角；而 JMM（Java Memory Model）是并发抽象视角——它规定多线程之间如何通过共享内存交互。没有 JMM，不同 CPU、不同编译器重排序规则各异，Java 程序在不同机器上行为不可预测。

JMM 是 JSR-133 规范（JSR-133 重写了原 JMM）。它解决三个核心问题：可见性（一个线程的写何时对其他线程可见）、原子性（哪些操作不可分割）、有序性（指令能否重排序）。

JMM 的抽象结构

JMM — 主内存与工作内存模型
主内存
所有共享变量
（堆中的实例字段、静态字段）
⬌
线程 A 工作内存
本地副本 + CPU 缓存
⬌
线程 B 工作内存
本地副本 + CPU 缓存
8 种原子操作：read / load / use / assign / store / write / lock / unlock
  • 主内存：所有共享变量存于此（对应堆中实例字段、静态字段；局部变量是私有的，不归 JMM 管）
  • 工作内存：每线程一份，对应 CPU 寄存器 + 缓存。线程对变量的操作都在工作内存中进行
  • 同步规则：线程不能直接读写主内存，必须通过 read/load、store/write 等原子操作

三大特性 与 实现机制

特性含义保证方式
可见性一个线程修改共享变量，其他线程能立刻看到volatile / synchronized / final（正确构造后）
原子性操作不可分割，不会被中断基本类型读写天然原子；synchronized / Lock 保证更大粒度原子性
有序性程序执行顺序符合预期（防止指令重排）volatile（禁止重排）/ synchronized（锁内串行）/ happens-before 规则
易错点：volatile 不保证原子性。i++ 是"读-改-写"三步，volatile 只保证每步可见，仍可能丢失更新。要原子性用 AtomicInteger 或 synchronized。

happens-before 规则 — 有序性的核心

设计思想：与其让程序员记忆复杂的重排序规则，JMM 提供"如果 A happens-before B，则 A 的结果对 B 可见，且 A 的操作不会被重排到 B 之后"。这是面向程序员的宽松但易用的保证。

规则说明
程序顺序规则同一线程内，前一个操作 happens-before 后一个（前面的代码先于后面执行）
管程锁定规则unlock 操作 happens-before 后续对同一把锁的 lock
volatile 变量规则对 volatile 的写 happens-before 后续对它的读
线程启动规则Thread.start() happens-before 该线程的所有操作
线程终止规则线程所有操作 happens-before Thread.join() 返回
线程中断规则interrupt() 调用 happens-before 被中断线程检测到中断
对象终结规则构造方法执行完 happens-before finalizer() 开始
传递性A happens-before B，B happens-before C → A happens-before C
关键理解：happens-before 不是说"时间上先发生"，而是可见性 + 有序性的保证。即使时间上 B 先执行，只要符合 happens-before，编译器/硬件必须保证 A 的结果对 B 可见。

volatile 底层 — 内存屏障

volatile 的内存屏障插入策略
普通写    → StoreStore 屏障 → volatile 写 → StoreLoad 屏障
                ⬆禁止前面普通写重排到后面   ⬆禁止后续读重排到前面（最昂贵）
LoadLoad 屏障 → volatile 读 → LoadStore 屏障 → 普通读/写
 ⬆禁止后续读重排到前面                ⬆禁止后续写重排到前面
  • StoreStore：确保前面的普通写已对其他处理器可见，再执行 volatile 写
  • StoreLoad：最昂贵的屏障，确保 volatile 写对后续读可见，并禁止读重排到写之前
  • LoadLoad：确保 volatile 读完成后才执行后续读
  • LoadStore：确保 volatile 读完成后才执行后续写
DCL 单例为何要 volatile：instance = new Singleton() 分三步：①分配内存 ②初始化 ③引用指向内存。步骤②③可能重排，导致其他线程拿到"非 null 但未初始化"的对象。volatile 的 StoreStore 屏障禁止了②③重排。

指令重排序 的三种来源

层次谁在做重排举例
编译器重排javac / JIT 优化调整语句顺序提升性能（如把不相关的赋值提前）
指令级重排CPU 乱序执行（Out-of-Order）多条无依赖指令并行执行
内存重排CPU 缓存 + 写缓冲区写操作先入 Store Buffer，对其他核暂时不可见
JMM 通过内存屏障在编译器和处理器两个层面插入限制，保证 happens-before 语义。x86 是强内存模型（TSO），重排较少；ARM 是弱内存模型，更依赖屏障。

as-if-serial 与重排序的边界

as-if-serial 语义：无论怎么重排序，（单线程）程序的执行结果不能改变。编译器/处理器只对无数据依赖的操作重排。

// 单线程：data 依赖 flag，重排不会改变结果
int a = 1;      // 操作 1
int b = 2;      // 操作 2（与 1 无依赖，可重排）
int c = a + b;  // 操作 3（依赖 1、2，不能重排到前面）

// 多线程：flag 与 data 无依赖，可能被重排，导致问题
// 线程1            线程2
data = 1;        if (flag)
flag = true;       print(data); // 可能打印 0！
单线程下重排安全（as-if-serial），但多线程下重排会破坏可见性/有序性——这就是 JMM 要规范重排序的原因。volatile/synchronized 划定"不可重排"的边界。

第三部分：模拟面试

请介绍一下 JVM 的内存模型，各个区域分别存储什么？
参考：JVM 运行时数据区分为线程共享和线程私有两部分。线程共享：1）堆（Heap）存储对象实例和数组，是 GC 的主要管理区域；2）方法区（JDK 8+ 为元空间 Metaspace）存储类信息、常量、静态变量、JIT 编译产物。线程私有：1）虚拟机栈存储栈帧（局部变量表、操作数栈、动态链接、返回地址）；2）本地方法栈服务 Native 方法；3）程序计数器记录当前执行的字节码行号。此外还有直接内存（Direct Memory），不属于 JVM 管理但常被 NIO 使用。
一个对象从创建到被 GC 回收，经历了怎样的完整生命周期？
参考：1）类加载：JVM 检查类是否已加载，未加载则执行类加载过程；2）内存分配：在 Eden 区通过指针碰撞或空闲列表分配，使用 CAS 或 TLAB 保证线程安全；3）零值初始化：将分配的内存初始化为默认值（int=0, boolean=false 等）；4）设置对象头：填充 Mark Word（HashCode、GC 年龄、锁状态）和类型指针；5）执行 init 方法：执行构造方法和实例初始化块；6）使用阶段：对象被引用使用；7）不可达判定：通过可达性分析判定对象不可达；8）GC 回收：经过至少两次标记后被回收（第一次标记调用 finalize()，第二次真正回收）。
请对比 G1 和 CMS 两个收集器的区别。
参考：主要区别：1）算法不同：CMS 使用标记-清除算法，有内存碎片；G1 整体看是标记-整理，Region 间是复制算法，无碎片；2）范围不同：CMS 只回收老年代（需配合 ParNew 回收新生代）；G1 可同时管理新生代和老年代；3）停顿可控：G1 可通过 -XX:MaxGCPauseMillis 设置目标停顿时间，G1 会根据每个 Region 的回收价值排序，优先回收价值高的 Region；4）内存模型：CMS 使用连续内存空间；G1 将堆划分为多个等大的 Region，更灵活；5）大对象处理：CMS 大对象直接进入老年代；G1 有专门的 Humongous Region。JDK 9 将 G1 设为默认收集器，CMS 在 JDK 14 被移除。
什么是双亲委派模型？为什么要使用它？如何打破？
参考：双亲委派模型：类加载请求先委托给父加载器，父加载器无法加载时才自己尝试。层次为 Bootstrap → Extension → Application → Custom。好处：1）避免类重复加载；2）保护核心类安全（防止篡改 java.lang.String 等）。打破方式：1）重写 loadClass() 方法（Tomcat 的 WebAppClassLoader 优先加载自己 lib 的类）；2）Thread Context ClassLoader（SPI 机制，如 JDBC Driver 加载）；3）OSGi 的网状类加载模型。Tomcat 打破双亲委派是因为不同 Web 应用可能依赖同一库的不同版本，需要隔离加载。
线上服务频繁 Full GC，如何排查？
参考：排查步骤：1）通过 jstat -gcutil PID 1000 观察 GC 频率和各区域占用比例；2）确认是老年代满了还是元空间满了；3）添加 -XX:+HeapDumpOnOutOfMemoryError 参数或手动 jmap -dump:format=b,file=heap.hprof PID 获取堆转储；4）使用 MAT 或 VisualVM 分析 Heap Dump，查看 Dominator Tree 找到占用内存最大的对象；5）分析 GC Root 引用链，定位到代码中的持有引用位置；6）常见原因：集合类只添加不删除、缓存未设置过期、ThreadLocal 未 remove、大对象（大数组/大集合）；7）修复后进行压测验证。
JVM 中对象在内存中的布局是怎样的？什么是 Mark Word？
参考：对象在内存中由三部分组成：1）对象头（Object Header）：包含 Mark Word（8 字节，存储 HashCode、GC 分代年龄、锁状态标志、线程 ID 等）和类型指针 Klass Pointer（4 字节，指向方法区的类元数据）；2）实例数据（Instance Data）：对象各字段的实际值；3）对齐填充（Padding）：保证对象大小为 8 字节的整数倍。Mark Word 是实现 synchronized 锁升级的关键：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，不同锁状态下 Mark Word 存储的内容不同。
什么是逃逸分析？JVM 如何利用它进行优化？
参考：逃逸分析是 JIT 编译器的一种分析技术，判断对象是否会逃逸出方法或线程。如果对象不会逃逸，JVM 可以进行三种优化：1）栈上分配：对象在栈帧中分配，方法结束自动销毁，减少 GC 压力；2）标量替换：将对象拆解为基本类型变量（如 Point 对象拆解为 int x, y），避免对象分配；3）锁消除：如果对象不会被多线程访问，消除 synchronized 锁。逃逸分析由 C2 编译器执行，JDK 8 默认开启（-XX:+DoEscapeAnalysis）。
请介绍一下 ZGC 的工作原理和适用场景。
参考：ZGC（Z Garbage Collector）是 JDK 11 引入的超低延迟收集器。核心特性：1）使用染色指针（Colored Pointer）在指针中存储 GC 状态信息（Marked0/Marked1/Remapped/Finalizable）；2）使用读屏障（Load Barrier）保证并发整理阶段的正确性；3）所有阶段几乎都与用户线程并发执行，STW 时间不超过 1ms；4）支持 TB 级堆内存；5）不区分新生代和老年代（无分代设计）。适用场景：对延迟极度敏感的服务、大内存应用。缺点：吞吐量略低于 G1。JDK 15 生产就绪，JDK 21 引入分代 ZGC（Generational ZGC）。
什么是 TLAB？为什么需要它？
参考：TLAB（Thread Local Allocation Buffer）是 JVM 为每个线程在 Eden 区预先分配的一小块私有内存。对象创建时优先在 TLAB 中分配，避免多线程竞争同一块内存。当 TLAB 耗尽时，再通过 CAS 分配新的 TLAB。TLAB 默认开启（-XX:+UseTLAB），大小由 -XX:TLABSize 控制，默认为 Eden 区的 1%。TLAB 解决了并发内存分配的线程安全问题，比全局 CAS 更高效。
JVM 的类初始化时机是什么？什么情况下会触发类的初始化？
参考：类初始化会执行 <clinit> 方法（静态变量赋值 + static 代码块）。触发初始化的场景（主动引用）：1）new 实例化对象；2）读取/设置类的静态字段（final 常量除外）；3）调用类的静态方法；4）反射调用（Class.forName()）；5）初始化子类时先初始化父类；6）包含 main 方法的主类。不会触发初始化的场景（被动引用）：1）子类引用父类的静态字段（只初始化父类）；2）通过数组定义引用类（如 MyClass[] arr）；3）引用类的 final 常量（编译期已放入常量池）。
