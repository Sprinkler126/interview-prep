核心组件

  • Connection：TCP 长连接，一个连接可复用多个 Channel
  • Channel：轻量级会话，多线程共用一个 Connection
  • Exchange：路由引擎，根据 type 和 binding key 决定消息去哪个 Queue
  • Queue：消息存储缓冲，消费者从 Queue 订阅
  • Binding：Exchange 和 Queue 之间的绑定关系，携带 routing key
  • Virtual Host：虚拟隔离空间，类似 namespace

设计动机：为什么 AMQP 要把 Exchange 和 Queue 分开？

设计起点：传统消息队列（如 JMS）是"生产者直接发到 Queue"的直连模型——生产者必须知道目标 Queue 名字。这带来两个痛点：① 新增消费者要改生产者代码；② 同一条消息想发给多个不同规则的消费者，生产者要写多份发送逻辑。AMQP 的解法是把"路由"和"存储"拆成两个独立组件，用 Binding 解耦。

Producer
只关心"发到哪个 Exchange"
不关心消息最终去哪
→
Exchange
路由引擎
按 type + binding 决定去向
→
Queue
消息缓冲
消费者订阅

JMS 直连模型的痛点

  • 新增消费者要改生产者代码（硬编码 Queue 名）
  • 同一消息多规则分发，生产者写 N 份逻辑
  • 路由规则和发送代码耦合，难灵活调整

✅ AMQP 解耦的收益

  • 生产者零感知消费者：只发到 Exchange，新增 Queue 绑定即可
  • 路由规则可热配：改 Binding 不重启生产者
  • 4 种 Exchange 覆盖典型场景：Direct 点对点、Fanout 广播、Topic 通配、Headers 属性
  • 多级路由：Exchange 可绑到 Exchange 形成路由拓扑
面试要点：Exchange/Queue 分离的本质是"关注点分离"——生产者关注"发什么"，Exchange 关注"怎么路由"，Queue 关注"怎么缓冲、谁消费"。对比 Kafka 的"Topic+Partition 直连"模型：Kafka 牺牲了路由灵活性换取高吞吐（写入直接落 Partition，无中间路由层），RabbitMQ 牺牲吞吐换取路由灵活性。这是两者定位差异的根源。

设计动机：为什么 RabbitMQ 用 Erlang 而不是 Java/C++？

设计起点：RabbitMQ 诞生于 2007 年，作者选择 Erlang 不是赶时髦，而是 Erlang 的三大特性恰好匹配消息中间件的需求。

Erlang 特性对应 MQ 需求
Actor 模型 + 轻量进程每个连接/Queue 一个进程，百万级并发不爆内存
消息传递天然异步进程间通信就是发消息，与 MQ 语义同构
OTP 的 Supervisor 树进程崩溃自动重启，let it crash 哲学适合高可用
BEAM 虚拟机软实时毫秒级 GC 暂停，消息投递延迟稳定
热代码升级不停机打补丁，运维友好
代价：① Erlang 人才稀缺，二次开发门槛高；② BEAM 调度是单 Erlang VM 多核，水平扩展靠多节点镜像，不如 JVM 生态成熟；③ 与大数据生态（Flink/Spark）集成不如 Kafka 顺畅。这也是为什么"大数据场景选 Kafka，业务消息选 RabbitMQ"。

Dead Letter Exchange 完整配置示例

// 声明死信 Exchange 和死信队列
channel.exchangeDeclare("dlx.exchange", "direct");
channel.queueDeclare("dlx.queue", true, false, false, null);
channel.queueBind("dlx.queue", "dlx.exchange", "dlx");

// 声明业务队列时绑定 DLX
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "dlx.exchange");
args.put("x-dead-letter-routing-key", "dlx");
args.put("x-message-ttl", 60000);           // 队列级别 TTL 60s
args.put("x-max-length", 10000);            // 队列最大长度
channel.queueDeclare("order.queue", true, false, false, args);

Alternate Exchange（备用交换机）

当消息无法路由到任何队列时（无匹配 binding），会被发送到 Alternate Exchange，避免消息"静默丢失"。

// 声明 Exchange 时设置备用交换机
Map<String, Object> args = new HashMap<>();
args.put("alternate-exchange", "ae.exchange");
channel.exchangeDeclare("order.exchange", "direct", true, false, args);

// 备用交换机绑定一个兜底队列
channel.exchangeDeclare("ae.exchange", "fanout");
channel.queueDeclare("unrouted.queue", true, false, false, null);
channel.queueBind("unrouted.queue", "ae.exchange", "");

Alternate Exchange 兜底了路由失败的消息，配合监控可及时发现配置错误。

Publisher Confirm 三种模式

模式实现方式吞吐量适用场景
同步确认 channel.waitForConfirms()，逐条等待 低 简单场景、少量消息
批量确认 channel.waitForConfirmsOrDie()，批量等待 中 批量发送，一条失败全部重发
异步回调 channel.addConfirmListener(ackCallback, nackCallback) 高 生产推荐，高性能 + 可精确处理失败 
// 异步 Confirm（推荐）
channel.confirmSelect();
channel.addConfirmListener(
    (deliveryTag, multiple) -> {
        // ACK：消息已到达 Broker 并持久化
        if (multiple) {
            confirmSet.headSet(deliveryTag + 1).clear();
        } else {
            confirmSet.remove(deliveryTag);
        }
    },
    (deliveryTag, multiple) -> {
        // NACK：Broker 处理失败，需重发
        log.error("消息 {} 被 NACK", deliveryTag);
    }
);

Consumer ACK 模式

模式行为可靠性
auto收到即确认，不管是否处理成功可能丢消息
manual业务代码中手动调用 basicAck/basicNack最可靠
auto（ prefetch ）处理完一条再推下一条较好

Prefetch（QoS）设置

channel.basicQos(prefetchCount) 控制 Broker 向 Consumer 推送的未确认消息数量上限。

  • prefetchCount=1：处理完一条才推下一条，公平分发，但吞吐低
  • prefetchCount=10~100：批量预取，吞吐高，但可能不均匀
  • 推荐：根据消费速率调整，一般 10~50。消费慢设小，消费快设大
  • prefetchSize：按字节限制（部分客户端不支持）
  • global=true：整个 Channel 级别限制；false（默认）：每个 Consumer 级别

basic.ack vs basic.reject vs basic.nack

方法作用requeue批量
basicAck确认消息处理成功无（已确认）multiple 参数支持批量
basicReject拒绝单条消息requeue=true/false❌ 仅单条
basicNack拒绝消息（可批量）requeue=true/false✅ multiple 参数

requeue=true 的陷阱：消息被拒绝后重新入队，再次投递给消费者，如果消费逻辑本身有 bug，会导致消息反复重试 → 队列积压 → 内存告警。生产环境必须 requeue=false，失败消息进死信队列。

生产推荐：手动 ACK + basicNack(requeue=false) 失败消息进入死信队列，不要 requeue=true（会反复重试导致消息堆积）。

1.4 持久化

三层持久化

  • Exchange 持久化：durable=true，Broker 重启后 Exchange 还在
  • Queue 持久化：durable=true，Broker 重启后 Queue 还在（但消息会丢）
  • Message 持久化：deliveryMode=2，消息写入磁盘

三者缺一不可！Exchange 和 Queue 不持久化，重启后结构丢失；消息不持久化，重启后内容丢失。

持久化性能影响

  • 消息持久化需要写磁盘，比纯内存操作慢 10~100 倍
  • RabbitMQ 使用 journal + lazy free 优化：先写 WAL 日志再异步刷盘
  • 可选 queueDeclare(x-queue-mode=lazy)：消息尽量存磁盘，减少内存占用（适合大量堆积场景）

1.6 延迟队列

方案一：TTL + DLX（原生实现）

Producer
设置消息 TTL=30min
→
业务队列
无消费者
→
TTL 过期
成为死信
→
DLX 死信队列
消费者处理

典型：订单 30 分钟未支付自动取消。下单时发消息到业务队列（TTL=30min），超时后进入死信队列，消费者检查订单状态并取消。

// TTL + DLX 延迟队列完整配置
// 1. 声明死信交换机和队列
channel.exchangeDeclare("delay.dlx", "direct");
channel.queueDeclare("delay.process.queue", true, false, false, null);
channel.queueBind("delay.process.queue", "delay.dlx", "delay");

// 2. 声明延迟队列（绑定 DLX，不消费）
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "delay.dlx");
args.put("x-dead-letter-routing-key", "delay");
channel.queueDeclare("delay.queue.30min", true, false, false, args);

// 3. 发送消息时设置 TTL
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
    .expiration("1800000")  // 30 分钟
    .build();
channel.basicPublish("", "delay.queue.30min", props, body);
// 消息 30min 后过期 → 进入 delay.process.queue → 消费者处理

方案二：延迟插件（rabbitmq_delayed_message_exchange）

安装插件后，Exchange 类型变为 x-delayed-message，消息携带 x-delay header 指定延迟时间，Broker 到时间后才投递。

优势：支持任意延迟时间（不局限于队列级别 TTL），实现更灵活。劣势：需要安装插件，社区维护。

1.7 流控与内存告警

Credit-Based Flow Control

RabbitMQ 使用信用流控：Producer 发送消息消耗 Credit，Broker 处理完后返还 Credit。Credit 用完时 Producer 阻塞，防止 Broker 被压垮。

内存 / 磁盘告警

  • 内存告警：内存使用超过阈值（默认 40%），Broker 阻塞所有连接的写入
  • 磁盘告警：磁盘剩余空间低于阈值（默认 50MB），Broker 阻塞写入
  • 告警解除后自动恢复

关键配置参数

参数默认值说明
vm_memory_high_watermark0.4（40%）内存使用超此比例触发告警，阻塞生产者
vm_memory_high_watermark_paging_ratio0.5达到此比例开始将消息换页到磁盘
disk_free_limit50MB磁盘剩余低于此值触发告警
disk_free_limit relative1.0相对内存的倍数（如 1.5 表示磁盘至少留 1.5 倍内存）

内存告警触发时，所有连接（不仅是触发告警的那个连接）的生产者都会被阻塞。消费者不受影响，可继续消费以释放内存。

投递计数（Delivery Count）

Quorum Queue 会记录每条消息的投递次数。当消费者 nack 后，delivery_count 递增。可结合 x-delivery-limit 设置最大重试次数，超过后消息直接进入死信队列，避免无限重试。

// 声明 Quorum Queue
Map<String, Object> args = new HashMap<>();
args.put("x-queue-type", "quorum");
args.put("x-delivery-limit", 3);  // 最多重试 3 次
channel.queueDeclare("order.quorum.queue", true, false, false, args);

🆕 Stream Queue（3.9+）

Stream Queue 是 RabbitMQ 3.9 引入的日志型队列，类似 Kafka 的设计理念，消息持久化到磁盘日志中，消费后不删除。

核心特点

  • 消息保留：消费后不删除，可按时间或大小策略保留
  • 消息回溯：消费者可从任意位置（offset）开始消费
  • 多消费者：同一消息可被多个消费者独立消费
  • 高吞吐：底层使用顺序写日志，吞吐量远超经典队列
  • 只追加：不支持消息删除和 nack（只能 ack 或忽略）
// 声明 Stream Queue
Map<String, Object> args = new HashMap<>();
args.put("x-queue-type", "stream");
args.put("x-max-length-bytes", 1073741824);  // 保留 1GB 数据
args.put("x-stream-max-segment-size-bytes", 134217728);  // 每段 128MB
channel.queueDeclare("events.stream", true, false, false, args);

// 消费时指定 offset
Map<String, Object> consumerArgs = new HashMap<>();
consumerArgs.put("x-stream-offset", "first");  // 从头消费
// 也可以用 "last" 或具体 offset 数值
channel.basicConsume("events.stream", false, consumerArgs, consumer);

Stream Queue vs Kafka

特性Stream QueueKafka

分区单队列（不支持分区）多 Partition
生态AMQP 协议兼容丰富的 Connectors、Streams API
适用场景中等规模、需要回溯大规模日志/事件流

2.2 削峰填谷

秒杀场景

瞬时 10 万 QPS，数据库 5000 QPS。RabbitMQ 先承接流量到队列，消费者按 5000 QPS 匀速消费。队列起缓冲作用，保护下游。

注意：RabbitMQ 消息存内存，大量堆积会影响性能。如果预估堆积量大（>百万），考虑用 Kafka 替代。

2.3 延迟任务

典型场景

  • 订单超时取消：下单 → 发 TTL=30min 消息 → 超时检查并取消
  • 会议提醒：创建会议 → 发 TTL=提前15min 消息 → 到时推送通知
  • 重试机制：失败消息 → 发递增 TTL 消息（1s→5s→30s）→ 延迟重试

任何一步失败都有兜底：Confirm 失败 → Producer 重发；持久化失败 → 配合 Confirm 重发；消费失败 → DLX 死信队列收集异常消息。

消息幂等性

网络抖动可能导致消息重复投递。解决方案：Producer 发送时携带全局唯一 ID（如 UUID），Consumer 处理前查询去重表，已处理则跳过。

2.5 高可用方案

普通集群

元数据同步，Queue 数据只在声明节点上

其他节点访问时从声明节点拉取

Queue 所在节点宕机 → 数据丢失

镜像队列 (Mirror)

Queue 数据在所有节点都有镜像

写入同步到所有镜像，读从 Master

节点宕机自动切换，数据不丢

Quorum Queue（3.8+ 推荐）

基于 Raft 协议的分布式队列，替代镜像队列。优势：① 更好的数据一致性；② 更高的吞吐量；③ 支持消息确认的多数派提交。劣势：不支持消费者优先级、不支持 TTL 消息的即时过期检测。

2.6 消息积压处理

  • 紧急：增加消费者数量、提高 prefetch 数量
  • 根本：优化消费逻辑、批量处理、异步写入
  • 预防：监控队列长度，设置告警
  • 极端：临时将消息转发到更大的队列，消费者从新队列消费

🎤第三部分：模拟面试

RabbitMQ 的 Exchange 有哪些类型？分别什么场景？
Direct：精确匹配 routing key，点对点任务分发。Fanout：广播到所有绑定队列，日志分发。Topic：通配符匹配（*一个词，#零或多词），按规则订阅。Headers：按 header 属性匹配（少用）。此外还有 Alternate Exchange 兜底路由失败的消息。
如何保证消息不丢失？
三个环节——① Producer：开启 Publisher Confirm，异步回调确认 Broker 已收到；② Broker：Exchange + Queue + Message 三者都持久化（durable + deliveryMode=2）；③ Consumer：手动 ACK，处理完再确认；失败用 basicNack(requeue=false) 进死信队列。推荐使用 Quorum Queue 进一步保障数据一致性。
如何保证消息顺序性？
单 Queue 单 Consumer 有序。如果需要并行消费但保证部分有序：将同一业务 key 的消息发到同一 Queue（用 key hash 路由）。注意：Consumer ACK 失败后 requeue 可能导致乱序，建议失败进死信队列。
什么是死信队列？怎么用？
消息在三种情况下成为死信：① 被 reject/nack（requeue=false）；② TTL 过期；③ 队列满。死信会路由到指定的 DLX（Dead Letter Exchange）绑定的队列。用途：延迟任务（TTL+DLX）、失败消息重试、异常消息告警。配置时在队列声明参数中设置 x-dead-letter-exchange 和 x-dead-letter-routing-key。
RabbitMQ 如何实现延迟队列？
两种方案——① TTL + DLX：消息设 TTL 发到无消费者的队列，过期后进死信队列被消费。② 延迟插件：安装 delayed_message_exchange，消息带 x-delay header，Broker 到时间才投递。方案一简单但只能队列级别设 TTL；方案二灵活支持任意延迟时间。
镜像队列和 Quorum Queue 有什么区别？
镜像队列：主从模式，写入 Master 后同步到 Slave，Master 宕机从 Slave 选新 Master。问题：同步是异步的，可能丢消息。Quorum Queue（3.8+）：基于 Raft，多数派确认才算成功，数据一致性更好，吞吐量更高。推荐用 Quorum Queue 替代镜像队列。但 Quorum Queue 不支持消费者优先级和消息级别的 TTL。
消息幂等性怎么保证？
Producer 发送时携带全局唯一 ID（如 UUID）。Consumer 处理前查去重表（Redis Set 或 DB 表），已处理则跳过。注意：去重表要设过期时间（如 24h），防止无限增长。
RabbitMQ 和 Kafka 的区别？什么场景用哪个？
RabbitMQ：传统消息代理，灵活路由（4 种 Exchange），低延迟（μs 级），消息消费后删除，适合业务消息。Kafka：分布式流平台，高吞吐（百万级/s），消息保留可回溯，Pull 模式，适合大数据/日志。简单说：业务消息选 RabbitMQ，大数据选 Kafka。RabbitMQ 3.9+ 的 Stream Queue 在尝试缩小差距。
消息积压怎么处理？
紧急：① 增加消费者数量；② 提高 prefetch 值；③ 临时跳过非关键消息。根本：① 优化消费逻辑（减少 DB 调用、批量处理）；② 异步化非关键操作。预防：监控队列长度和消费速率，设置告警阈值。
Quorum Queue 的 Raft 机制是怎么工作的？
Quorum Queue 使用 Raft 共识协议：① 集群中一个节点选举为 Leader，其余为 Follower；② Producer 发送消息到 Leader，Leader 将消息写入 Raft 日志；③ Leader 将日志复制到 Follower 节点；④ 多数派（N/2+1）节点确认后，消息才被标记为已提交；⑤ Consumer 从 Leader 消费已提交的消息。如果 Leader 宕机，Follower 重新选举新 Leader。消息确认（ACK）也走 Raft 共识，确保 ACK 不丢失。
Stream Queue 是什么？适合什么场景？
Stream Queue 是 RabbitMQ 3.9 引入的日志型队列，类似 Kafka 设计：① 消息消费后不删除，持久化在磁盘日志中；② 支持消息回溯，消费者可从任意 offset 开始消费；③ 支持多消费者独立消费同一消息流；④ 吞吐量远超经典队列。适合场景：事件溯源、审计日志、需要回溯的高吞吐场景。限制：不支持 nack（只支持 ack）、不支持消息优先级。
prefetch 怎么设置？设多少合适？
channel.basicQos(prefetchCount) 设置 Broker 向每个 Consumer 推送的未确认消息上限。prefetchCount=1 最公平但吞吐最低；10~50 是常见范围。设置原则：① 消费处理快（如内存操作）→ 设大（50~200）；② 消费处理慢（如调外部 API）→ 设小（1~5）；③ global=false（默认）是每个 Consumer 级别，global=true 是整个 Channel 级别。经验值：从 10 开始，根据监控数据调整。
消息堆积时 RabbitMQ 和 Kafka 表现差异？
RabbitMQ：消息堆积到一定量后，内存告警触发，生产者被阻塞。即使使用 lazy queue（消息写磁盘），大量堆积仍影响路由性能。Kafka：消息天然写磁盘（顺序写），堆积只是多占磁盘空间，对性能几乎无影响。结论：大量堆积场景（百万级）首选 Kafka；RabbitMQ 适合消费速率接近生产速率的场景。RabbitMQ 3.9+ 的 Stream Queue 改善了堆积能力，但仍不如 Kafka。
Publisher Confirm 的异步模式怎么实现？为什么推荐？
异步模式通过 channel.addConfirmListener(ackCallback, nackCallback) 实现。Broker 确认消息后回调 ackCallback（包含 deliveryTag），失败回调 nackCallback。优势：① 不阻塞发送线程，吞吐量最高；② 可按 deliveryTag 精确定位失败消息并重发；③ 配合 ConcurrentSkipListSet 记录未确认消息，定期重发超时消息。注意：要处理 multiple=true 的情况（Broker 批量确认）。
RabbitMQ 的版本演进方向是什么？
三条主线：① 高可用：镜像队列（异步复制）→ Quorum Queue（Raft 强一致），镜像队列已在 3.10+ 标记为弃用；② 高吞吐：Stream Queue（日志型队列）对标 Kafka 的流处理能力；③ 元数据存储：Khepri（3.9+）逐步取代 Mnesia，提升集群扩展性和稳定性。面试能讲清这条演进线，说明你对 RabbitMQ 有深度理解。
