第一部分：技术原理

线程模型

三种 Reactor 线程模型

单线程 Reactor

  • 一个线程处理所有 IO
  • Accept + Read + Write + 业务
  • 简单但性能差
  • 不适合高并发

多线程 Reactor

  • 一个 Acceptor 线程
  • 多个 Worker 线程处理 IO
  • Reactor + Worker 线程池
  • 大多数场景适用
Netty 主从 Reactor 模型（默认）

1 个线程，负责 Accept 新连接

Netty 服务端启动模板

EventLoopGroup bossGroup = new NioEventLoopGroup(1);      // Accept 线程
EventLoopGroup workerGroup = new NioEventLoopGroup();    // Worker 线程（默认 CPU*2）
try {
    ServerBootstrap bootstrap = new ServerBootstrap();
    bootstrap.group(bossGroup, workerGroup)
        .channel(NioServerSocketChannel.class)           // 通道类型
        .option(ChannelOption.SO_BACKLOG, 128)           // 连接队列大小
        .childOption(ChannelOption.SO_KEEPALIVE, true)   // TCP 保活
        .childOption(ChannelOption.TCP_NODELAY, true)    // 禁用 Nagle 算法
        .childHandler(new ChannelInitializer<SocketChannel>() {
            @Override
            protected void initChannel(SocketChannel ch) {
                ChannelPipeline pipeline = ch.pipeline();
                pipeline.addLast(new IdleStateHandler(60, 0, 0));  // 心跳检测
                pipeline.addLast(new LengthFieldBasedFrameDecoder(1024, 0, 4));
                pipeline.addLast(new MessageDecoder());
                pipeline.addLast(new MessageEncoder());
                pipeline.addLast(new BusinessHandler());
            }
        });
    ChannelFuture future = bootstrap.bind(8080).sync();
    future.channel().closeFuture().sync();
} finally {
    bossGroup.shutdownGracefully();
    workerGroup.shutdownGracefully();
}

EventLoopGroup 与 EventLoop

核心概念

概念说明
EventLoop一个线程 + 一个 Selector + 一个任务队列，处理 IO 事件和普通任务
EventLoopGroupEventLoop 的集合，负责分配 EventLoop 给新 Channel
NioEventLoopNIO 实现的 EventLoop，基于 Selector 多路复用
任务队列每个 EventLoop 有三个任务队列：普通任务、定时任务、尾部任务

NioEventLoop 执行流程

select()
轮询 IO 事件（有超时时间）
→
processSelectedKeys()
处理就绪的 IO 事件
→
runAllTasks()
处理任务队列中的任务
  • 每个 NioEventLoop 绑定一个线程，一个 Channel 只会被一个 EventLoop 处理（线程安全保证）
  • IO 事件处理和任务队列处理在同一个线程，避免线程切换
  • 默认不执行用户自定义的定时任务（需要设置 -Dio.netty.eventLoop.executePendingTasks=true）
Channel 与 EventLoop 的绑定是永久的（在 Channel 生命周期内不变），确保了 Channel 上的所有 IO 操作都是线程安全的，无需额外加锁。

Inbound vs Outbound Handler

Inbound Handler（入站）

  • 处理入站数据（从网络读取）
  • 从 Head → Tail 方向执行
  • channelRead() / channelActive()
  • 典型：Decoder、业务 Handler
  • 继承 ChannelInboundHandlerAdapter

Outbound Handler（出站）

  • 处理出站数据（写出到网络）
  • 从 Tail → Head 方向执行
  • write() / flush() / connect()
  • 典型：Encoder、压缩 Handler
  • 继承 ChannelOutboundHandlerAdapter

责任链模式

Pipeline 本质是一个双向链表，每个节点是一个 ChannelHandlerContext（包装了 Handler）。数据在 Pipeline 中按方向逐个经过 Handler 处理：

入站数据
Socket → Head → Decoder → Business → Tail
出站数据
Tail → Encoder → Head → Socket
HeadContext 既是 Inbound 又是 Outbound Handler，负责实际的 Socket 读写。TailContext 负责处理未被消费的事件和资源释放。

零拷贝

Netty 零拷贝实现方式

方式说明适用场景
FileRegion底层使用 transferTo()，数据直接从文件缓冲区到 Socket 缓冲区文件传输
CompositeByteBuf组合多个 ByteBuf，逻辑上合并但不复制数据协议头+消息体组合
slice()切片 ByteBuf，共享底层内存但有独立的读写索引拆分数据包
wrap()包装已有 byte[]，不复制数据包装已有数据
堆外内存使用 DirectBuffer，减少堆内到堆外的拷贝IO 读写

传统 IO vs 零拷贝

传统 IO（4 次拷贝）

  • 磁盘 → 内核缓冲区（DMA 拷贝）
  • 内核缓冲区 → 用户缓冲区（CPU 拷贝）
  • 用户缓冲区 → Socket 缓冲区（CPU 拷贝）
  • Socket 缓冲区 → 网卡（DMA 拷贝）
  • 4 次上下文切换

零拷贝（2 次拷贝）

  • 磁盘 → 内核缓冲区（DMA 拷贝）
  • 内核缓冲区 → 网卡（DMA 拷贝）
  • 数据不经过用户空间
  • 2 次上下文切换
  • Linux: sendfile() / transferTo()

ByteBuf

ByteBuf 分类

维度类型说明
内存位置堆内（HeapByteBuf）分配在 JVM 堆上，受 GC 管理，读写需拷贝到堆外
堆外（DirectByteBuf）分配在堆外，不受 GC 管理，IO 读写性能好（推荐）
内存管理池化（PooledByteBuf）内存复用，减少分配/释放开销（推荐）
非池化（UnpooledByteBuf）每次分配新内存，用完释放

Netty 默认使用 PooledDirectByteBuf（池化堆外内存）。

ByteBuf 核心特性

  • 读写分离：readerIndex（读指针）和 writerIndex（写指针）独立维护，0 ≤ readerIndex ≤ writerIndex ≤ capacity
  • 自动扩容：写入时如果空间不足，ByteBuf 自动扩容（最大 Integer.MAX_VALUE）
  • 引用计数：通过 retain()/release() 管理生命周期，计数归零时释放内存
  • 三种指针区域：discardable bytes（已读）、readable bytes（可读）、writable bytes（可写）
// ByteBuf 使用示例
ByteBuf buf = Unpooled.buffer(256);  // 堆内缓冲区
ByteBuf buf2 = Unpooled.directBuffer(256);  // 堆外缓冲区

// 写入数据
buf.writeInt(1);
buf.writeLong(100L);
buf.writeBytes("hello".getBytes());

// 读取数据
int a = buf.readInt();
long b = buf.readLong();

// 引用计数（必须在 finally 中释放）
buf.retain();  // 引用计数 +1
buf.release(); // 引用计数 -1，归零时释放

// 切片（零拷贝，共享底层内存）
ByteBuf slice = buf.slice(0, 4);  // 包含前 4 个字节

// 组合 ByteBuf（零拷贝）
CompositeByteBuf composite = Unpooled.compositeBuffer();
composite.addComponents(true, header, body);  // true 自动调整 writerIndex

// 自定义编码器
public class MessageEncoder extends MessageToByteEncoder<Message> {
    @Override
    protected void encode(ChannelHandlerContext ctx, Message msg, ByteBuf out) {
        out.writeInt(msg.getLength());       // 4 字节长度头
        out.writeShort(msg.getType());       // 2 字节消息类型
        out.writeBytes(msg.getBody());       // 消息体
    }
}

// 自定义解码器
public class MessageDecoder extends ByteToMessageDecoder {
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        if (in.readableBytes() < 4) return;  // 不够读长度字段
        in.markReaderIndex();                 // 标记读位置
        int length = in.readInt();
        if (in.readableBytes() < length) {
            in.resetReaderIndex();            // 重置，等待更多数据
            return;
        }
        short type = in.readShort();
        byte[] body = new byte[length - 2];
        in.readBytes(body);
        out.add(new Message(type, body));
    }
}

粘包拆包

粘包拆包产生原因

TCP 是面向字节流的协议，没有消息边界的概念。发送方多次 write 的数据可能被合并成一次发送（粘包），也可能被拆分成多次发送（拆包）。

原因说明
发送端合并Nagle 算法将小包合并发送
接收端缓冲区TCP 接收缓冲区积累数据，一次 read 读到多条消息
MSS/MTU 分片数据包超过 MSS 被拆分成多个 TCP 段

四种解决方案

方案解码器原理适用场景
固定长度FixedLengthFrameDecoder每条消息固定长度，不足补零消息长度固定
分隔符DelimiterBasedFrameDecoder用特殊分隔符标记消息边界文本协议（如 HTTP）
长度字段LengthFieldBasedFrameDecoder消息头包含消息体长度二进制协议（最常用）
行分隔LineBasedFrameDecoder以 \n 或 \r\n 分隔行文本协议
 
// LengthFieldBasedFrameDecoder 参数详解
// maxFrameLength: 最大帧长度
// lengthFieldOffset: 长度字段偏移量
// lengthFieldLength: 长度字段大小（字节数）
// lengthAdjustment: 长度调整值（长度字段值 + adjustment = 内容长度）
// initialBytesToStrip: 跳过的字节数（去掉消息头）

// 示例：协议格式 [消息长度(4字节)][消息类型(2字节)][消息体]
pipeline.addLast(new LengthFieldBasedFrameDecoder(
    1024 * 1024,  // maxFrameLength: 1MB
    0,            // lengthFieldOffset: 0
    4,            // lengthFieldLength: 4 字节
    -2,           // lengthAdjustment: 减去消息类型 2 字节
    0             // initialBytesToStrip: 不跳过
));

// 示例：直接去掉长度头
pipeline.addLast(new LengthFieldBasedFrameDecoder(
    1024 * 1024, 0, 4, 0, 4  // 跳过 4 字节长度头
));

心跳机制

IdleStateHandler 心跳检测

// IdleStateHandler 参数
// readerIdleTime: 读空闲超时（多久没收到数据触发）
// writerIdleTime: 写空闲超时（多久没发送数据触发）
// allIdleTime: 读写空闲超时
// unit: 时间单位

pipeline.addLast(new IdleStateHandler(60, 30, 0, TimeUnit.SECONDS));

// 心跳处理 Handler
public class HeartbeatHandler extends ChannelInboundHandlerAdapter {
    private int lossCount = 0;
    private static final int MAX_LOSS = 3;  // 最大丢失次数

    @Override
    public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
        if (evt instanceof IdleStateEvent) {
            IdleStateEvent event = (IdleStateEvent) evt;
            switch (event.state()) {
                case READER_IDLE:
                    lossCount++;
                    if (lossCount >= MAX_LOSS) {
                        ctx.close();  // 超过最大丢失次数，关闭连接
                    }
                    break;
                case WRITER_IDLE:
                    ctx.writeAndFlush(heartbeatPacket());  // 发送心跳包
                    break;
            }
        } else {
            super.userEventTriggered(ctx, evt);
        }
    }

    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        lossCount = 0;  // 收到数据，重置丢失计数
        super.channelRead(ctx, msg);
    }
}
心跳机制的作用：1）检测连接是否存活（读空闲超时 → 关闭连接）；2）保持连接不被中间设备（如 NAT、防火墙）断开（定期发送心跳包）；3）服务端及时释放不活跃的连接资源。

第三部分：模拟面试

Netty 的线程模型是怎样的？什么是主从 Reactor？
参考：Netty 默认使用主从 Reactor 多线程模型。Boss EventLoopGroup（通常 1 个线程）负责 Accept 新连接，Worker EventLoopGroup（默认 CPU 核心数 * 2 个线程）负责 IO 读写和业务处理。每个 EventLoop 是一个线程 + 一个 Selector + 一个任务队列，一个 Channel 绑定到一个 EventLoop（保证线程安全）。Boss 线程接收新连接后，将 Channel 注册到 Worker 的某个 EventLoop 上，后续该 Channel 的所有 IO 操作都由这个 EventLoop 处理。这种模型避免了多线程竞争，同时通过多 Worker 线程实现高并发。
参考：Netty 的零拷贝是指减少数据在内存中的拷贝次数，提高 IO 效率。实现方式：1）FileRegion：底层使用 Linux 的 sendfile() 系统调用，数据直接从文件缓冲区传输到 Socket 缓冲区，不经过用户空间；2）CompositeByteBuf：逻辑上组合多个 ByteBuf，不拷贝底层数据；3）slice()：将 ByteBuf 切分成多个逻辑视图，共享底层内存；4）wrap()：包装已有 byte[]，不复制数据；5）堆外内存（DirectBuffer）：减少堆内到堆外的数据拷贝。传统 IO 需要 4 次拷贝（磁盘→内核→用户空间→Socket→网卡）和 4 次上下文切换，零拷贝只需 2 次拷贝和 2 次上下文切换。
参考：Pipeline 是一个双向链表，每个节点是一个 ChannelHandlerContext，包装了 ChannelHandler。数据在 Pipeline 中按方向流动：入站数据从 Head → Tail 方向经过 Inbound Handler（如解码器、业务 Handler），出站数据从 Tail → Head 方向经过 Outbound Handler（如编码器）。Inbound Handler 处理接收到的数据（channelRead），Outbound Handler 处理要发送的数据（write）。HeadContext 是实际进行 Socket 读写的 Handler，TailContext 处理未被消费的事件。一个 Handler 可以同时是 Inbound 和 Outbound（实现两个接口）。Pipeline 支持动态添加和删除 Handler。
什么是粘包拆包？Netty 提供了哪些解决方案？
参考：TCP 是面向字节流的协议，没有消息边界。多次发送的数据可能被合并接收（粘包），一次发送的数据也可能被分多次接收（拆包）。Netty 提供四种解决方案：1）FixedLengthFrameDecoder：固定长度帧，不足补零；2）DelimiterBasedFrameDecoder：分隔符（如 \n、\r\n 或自定义分隔符）；3）LengthFieldBasedFrameDecoder：消息头包含长度字段（最常用），需要配置 lengthFieldOffset、lengthFieldLength、lengthAdjustment、initialBytesToStrip 四个参数；4）LineBasedFrameDecoder：行分隔符。生产环境推荐使用 LengthFieldBasedFrameDecoder，设计自定义协议时在消息头中包含长度字段。
参考：区别：1）读写指针：ByteBuffer 用 position 和 limit，切换读写模式需要 flip()，容易出错；ByteBuf 有独立的 readerIndex 和 writerIndex，无需切换；2）扩容：ByteBuffer 固定大小，写满需要手动扩容；ByteBuf 支持自动扩容；3）池化：ByteBuffer 无池化机制；ByteBuf 支持对象池化复用；4）引用计数：ByteBuf 有引用计数机制，计数归零自动释放；5）API：ByteBuf 提供丰富的 readXxx/writeXxx 方法和零拷贝操作（slice、composite）。Netty 重新设计的原因是 ByteBuffer 的 API 太底层且难用，容易出错（flip/compact），且不支持池化和零拷贝等高级特性。
参考：心跳检测：使用 IdleStateHandler 监测读/写/全部空闲。配置 readerIdleTime（读空闲超时）、writerIdleTime（写空闲超时），当超时触发时会调用 userEventTriggered() 方法。在自定义 Handler 中处理 IdleStateEvent：读空闲超过阈值 → 关闭连接；写空闲 → 发送心跳包。断线重连：在客户端的 ChannelHandler 的 channelInactive() 方法中触发重连逻辑，使用定时任务延迟执行重连（避免频繁重连），重连成功后重新初始化 Channel Pipeline。注意使用指数退避策略（如 1s、2s、4s、8s...），避免服务端压力过大。
参考：1）使用池化的 DirectBuffer：减少 GC 和内存拷贝（默认已开启）；2）合理设置线程数：Boss 线程 1 个即可，Worker 线程默认 CPU*2；3）减少对象分配：使用 ByteBuf 池化、对象池化、ThreadLocal 缓存；4）避免在 EventLoop 中执行阻塞操作：使用 DefaultEventExecutorGroup 处理耗时业务；5）TCP 参数优化：SO_BACKLOG、SO_SNDBUF、SO_RCVBUF、TCP_NODELAY；6）使用 CompositeByteBuf 和 slice 实现零拷贝；7）减少系统调用：批量写（gather write）；8）使用 Protobuf 等高效序列化替代 JSON。
参考：好处：1）线程安全：一个 Channel 的所有 IO 操作都在同一个 EventLoop 线程中执行，无需加锁，避免了多线程竞争；2）减少线程切换：同一个连接的读写和业务处理在同一线程完成；3）简化编程模型：开发者无需关心 Channel 上的并发问题。实现原理：Channel 注册到 EventLoop 时建立绑定关系，后续该 Channel 的所有事件（读/写/连接/断开）都由绑定的 EventLoop 线程处理。如果在非 EventLoop 线程中调用 Channel 的方法（如 write），Netty 会将操作封装成任务提交到对应的 EventLoop 任务队列中。
