🗺️全景定位

可观测性三大支柱
支柱 定义 核心工具 典型场景
📈 Metrics（指标） 可聚合的数值型时间序列数据 Prometheus · Zabbix · Datadog CPU / 内存 / QPS / 延迟 / 错误率
🔭 Tracing（链路追踪） 单个请求在分布式系统中的完整路径 SkyWalking · Zipkin · Jaeger 跨服务调用链、慢请求定位、依赖分析
📝 Logging（日志） 离散的事件记录，包含详细上下文 ELK · Loki · ClickHouse 错误排查、审计记录、业务分析

三者关系

  • Metrics 回答"什么出了问题"（What）—— 通过指标异常发现系统问题
  • Tracing 回答"问题在哪里"（Where）—— 通过链路追踪定位具体服务和方法
  • Logging 回答"为什么出问题"（Why）—— 通过日志详情分析根因
  • 三者相互关联：Metrics 告警触发 → 通过 TraceId 关联链路 → 通过 TraceId 关联日志

面试话术：Prometheus 是云原生监控标准（CNCF 毕业项目），适合 K8s 和微服务场景，开源免费但需自运维。Zabbix 适合传统运维（服务器、网络设备），功能全面但对云原生支持较弱。Datadog 是 SaaS 一体化可观测平台，开箱即用但成本高。中小团队用 Prometheus + Grafana，预算充足用 Datadog，传统运维用 Zabbix。

面试话术：ELK 是最成熟的日志方案，功能最全但资源消耗大。Loki 是 Grafana 出品的轻量级日志系统，只索引标签不索引日志内容，存储成本最低，与 Grafana 指标面板统一。ClickHouse 是列式数据库做日志分析，分析查询极快，适合日志量大且需要复杂分析的场景。中小团队用 Loki，需要全文检索用 ELK，日志分析用 ClickHouse。

🎯场景选型指南

📈 选 Prometheus
• K8s / 微服务环境的指标监控
• 需要强大的 PromQL 查询
• 预算有限，开源免费
• 搭配 Grafana 做可视化
📊 选 Zabbix
• 传统运维（服务器、网络设备、数据库）
• 需要自动发现和 Agent 管理
• 需要完善的告警和升级机制
• 团队有 Zabbix 运维经验
🔭 选 SkyWalking
• Java 为主的微服务架构
• 需要零侵入接入（字节码增强）
• 需要全功能 APM（拓扑+指标+告警）
• 不想修改业务代码
🟡 选 Jaeger
• K8s 原生环境
• 多语言微服务（Go / Java / Python）
• 需要 CNCF 生态集成
• 搭配 OpenTelemetry 采集
📝 选 ELK
• 需要全文检索和复杂日志分析
• 日志量大，需要强大的索引能力
• 需要 Kibana 的丰富可视化
• 团队有 ELK 运维经验
🟢 选 Loki
• 已使用 Grafana 做指标监控
• 需要轻量级日志聚合
• 预算有限，存储成本敏感
• 日志查询以标签过滤为主
🔭 选 OpenTelemetry
• 需要统一的可观测性采集标准
• 多语言、多后端场景
• 避免厂商锁定
• 未来趋势，推荐提前布局

🎤面试高频对比题

可观测性的三大支柱是什么？它们之间有什么关系？
参考答案：三大支柱是 Metrics（指标）、Tracing（链路追踪）、Logging（日志）。Metrics 回答"什么出了问题"（CPU 高、延迟大），Tracing 回答"问题在哪里"（哪个服务、哪个方法慢），Logging 回答"为什么出问题"（具体异常信息）。三者通过 TraceId 关联：Metrics 告警触发 → 查看相关 Trace → 通过 TraceId 关联日志。完整的可观测性需要三者配合。
Prometheus 和 Zabbix 有什么区别？什么时候用哪个？
参考答案：Prometheus 是云原生监控标准，Pull 模型采集 /metrics，PromQL 查询强大，适合 K8s 和微服务。Zabbix 是传统运维监控，支持 Agent 上报和主动探测，内置告警和自动发现，适合服务器、网络设备、数据库。选择：容器和微服务用 Prometheus，传统基础设施用 Zabbix，两者可以共存。
SkyWalking 和 Jaeger 有什么区别？Java 项目该选哪个？
参考答案：SkyWalking 是全功能 APM 平台，Java Agent 字节码增强零侵入，内置拓扑图、指标、告警。Jaeger 是纯链路追踪系统，需要 SDK 埋点，CNCF 毕业项目。Java 项目推荐 SkyWalking：零侵入（不改代码）、70+ 内置插件（Spring/Dubbo/MySQL/Redis）、APM 能力强。如果团队已有 OpenTelemetry 基础，Jaeger + OTel 也是好选择。
ELK 和 Loki 有什么区别？什么时候用 Loki？
参考答案：ELK 基于 Elasticsearch 的倒排索引，对日志内容全文索引，查询强大但资源消耗大。Loki 只索引标签（不索引日志内容），存储成本低，与 Grafana 集成好。选择：需要全文检索和复杂分析用 ELK，日志量不大且已用 Grafana 用 Loki。Loki 的 LogQL 类似 PromQL，学习成本低。Loki 适合中小团队，ELK 适合大厂。
参考答案：OpenTelemetry（OTel）是 CNCF 孵化的可观测性标准项目，统一了 Metrics、Tracing、Logging 的采集协议和 SDK。它不是后端存储工具，而是采集标准。重要性：1）统一标准：避免每种工具各自埋点；2）厂商无关：采集一次，可发送到多个后端（Jaeger、SkyWalking、Datadog）；3）多语言支持：11 种语言 SDK；4）未来趋势：所有可观测工具都在适配 OTel。推荐：用 OTel SDK 采集数据，后端自由选择。
参考答案：分层设计——指标层：Prometheus + Grafana，监控系统指标（CPU/内存/QPS/延迟），配置告警规则。链路层：SkyWalking 或 Jaeger + OpenTelemetry，自动追踪跨服务调用链。日志层：Loki 或 ELK，收集应用日志和访问日志。关联：通过 TraceId 将三者关联。告警触发 → 查看指标趋势 → 定位 Trace → 查看日志详情。所有工具通过 Grafana 统一展示。
