⚙️存储引擎横向对比：B+Tree vs LSM-Tree vs 倒排索引

设计起点：读写 workload 决定数据结构

不同数据库的根本差异在底层存储结构。数据结构的选择本质是对"读快还是写快"的取舍——没有任何结构能同时做到随机读 O(1) 和随机写 O(1)。面试时理解这条主线，就能解释为什么 ES 写慢读快、HBase 写快读慢、MySQL 读写均衡。

三种主流存储结构对比
维度 B+Tree (MySQL/PG/Mongo) LSM-Tree (HBase/TiKV/Cassandra) 倒排索引 (ES)
数据位置 原地更新（in-place update） 追加写 + 后台合并 不可变 Segment（追加 + 合并）
写入 随机写（需找页+改页） 顺序写内存（MemStore）极快 写 Buffer + 异步 Refresh
读取 B+Tree 定位快，3-4 次 IO 需合并多层 HFile，读放大 倒排表直接定位，O(1)~O(logN)
写放大 1 次（改页即落盘） 高（Compaction 反复重写） 中（Segment 合并）
读放大 1 次（树高次 IO） 高（查 MemStore + 多层 HFile） 低（FST + Posting List）
空间放大 低（页填充） 中（过期版本待 Compaction） 高（倒排表 + FST 占内存）
范围查询 叶子链表，极快 中（需归并多 HFile） 差（倒排不擅长范围）
全文检索 差（LIKE 全表扫） 不支持 原生支持
适合场景 OLTP 读写均衡 写多读少 + 海量数据 搜索 + 聚合分析

核心权衡：为什么 ES 写慢、HBase 读慢？

ES 写慢的根因

  • 每条文档要分词 + 建倒排表，CPU 开销大
  • 更新 = 标记删除 + 重新索引，写放大严重
  • Refresh 生成新 Segment，过多需 Compaction 合并（IO 密集）
  • 不擅长频繁更新（适合 append-only 日志/搜索）

HBase 读慢的根因

  • 读需合并 BlockCache + MemStore + 多个 HFile
  • 多层 HFile → 读放大，Compaction 才能改善
  • 只能按 RowKey 查，二级索引需协处理器或 Phoenix
  • 不擅长复杂查询（适合 KV 读写 + 范围扫）
面试金句：存储引擎选型 = workload 匹配。OLTP 读写均衡选 B+Tree（MySQL），写多读少海量数据选 LSM（HBase），全文检索读多写少选倒排（ES）。没有银弹，每个结构都在读放大 / 写放大 / 空间放大三者间取舍。

LSM-Tree 的 Compaction 策略对比

策略原理代表特点
LeveledL0→L1→L2...，每层有界，层层合并RocksDB / LevelDB读放大小，写放大大
Tiered每层多个文件，size 攒够再合并到下层Cassandra STCS写放大小，读放大大（空间放大也大）
Time-Window按时间窗口分文件，过期整窗丢弃时序数据库 InfluxDB时序场景空间回收快
Hybrid (Leveled+Tiered)L0 Tiered，L1+ LeveledRocksDB / HBase 新版兼顾读写，工程实践主流
易错点：LSM 不等于"HBase 专用"——RocksDB（TiKV/Redis on Flash）、Cassandra、InfluxDB 都用 LSM。理解 Compaction 策略对调优 LSM 系统至关重要：写密集选 Tiered，读密集选 Leveled。

🎯场景选型指南

🐬 选 MySQL
• 业务 OLTP 主库，数据量 < 1TB
• 需要成熟稳定的事务支持
• 团队有 MySQL DBA
• 典型：电商订单、用户系统、CMS
🐘 选 PostgreSQL
• 需要 GIS 地理查询
• 复杂 SQL + JSONB 混合查询
• 需要丰富的扩展（全文检索、向量）
• 典型：地图服务、数据仓库、科学计算
🔗 选 TiDB
• MySQL 数据量 > 1TB，分库分表太痛
• 需要 HTAP 混合负载
• 不想改 SQL 代码，平滑迁移
• 典型：大规模电商、金融核心、实时分析
🔴 选 Redis
• 需要极致读写性能（10万+ QPS）
• 缓存、会话、排行榜、分布式锁
• 数据可丢失或可从 DB 恢复
• 典型：几乎所有后端项目的标配
🍃 选 MongoDB
• Schema 不固定，字段经常变化
• 文档嵌套复杂，关系型建模痛苦
• 需要水平扩展但不想分库分表
• 典型：内容管理、用户画像、日志存储
🔍 选 Elasticsearch
• 需要全文检索、模糊搜索
• 日志收集 + 实时分析（ELK）
• 需要复杂的聚合统计
• 典型：电商搜索、日志平台、APM
📊 选 HBase
• 数据量 PB 级，需要海量存储
• 写多读少，按 RowKey 范围查询
• 已有 Hadoop 生态（HDFS/Hive/Spark）
• 典型：用户行为日志、时序数据、画像

🎤面试高频对比题

MySQL 和 MongoDB 该选哪个？
参考答案：看数据模型。如果数据是结构化的、关系明确的（订单、用户、商品），用 MySQL，事务和 JOIN 支持好。如果数据是半结构化的、Schema 经常变（用户画像、内容、日志），用 MongoDB，文档模型灵活，不用每次改表结构。两者可以混用：MySQL 做主业务库，MongoDB 做日志/内容存储。
Elasticsearch 能替代 MySQL 吗？
参考答案：不能。ES 是搜索引擎，擅长检索和分析，但：① 不支持事务，写入不是实时可搜索（refresh 间隔 1 秒）；② 不适合频繁更新（每次更新本质是标记删除+重新索引）；③ 没有 JOIN 能力。正确用法是 ES 做二级存储，数据从 MySQL/业务库同步过来做检索。
什么时候该从 MySQL 迁移到 TiDB？
参考答案：三个信号：① 单实例数据量 > 1TB，分库分表维护成本太高；② 写入 TPS 持续增长，单机瓶颈明显；③ 需要实时分析（HTAP），不想维护单独的数据仓库。TiDB 兼容 MySQL 协议，迁移成本低，但要注意：跨 Region 事务有延迟，小数据量反而不如 MySQL 快。
Redis 和 MySQL 缓存方案怎么配合？
参考答案：经典 Cache Aside Pattern——读请求先查 Redis，命中返回，未命中查 MySQL 并回写 Redis（设 TTL）；写请求先更新 MySQL，再删除 Redis 缓存（而非更新，避免并发不一致）。进阶方案：Read/Write Through（缓存层代理 DB）、Write Behind（异步写回 DB，适合写密集）。
MongoDB 和 HBase 都能存海量数据，怎么选？
参考答案：MongoDB 是通用文档数据库，CRUD 均衡，查询灵活，适合 TB 级以内的通用场景。HBase 是列式存储，写入极快、按 RowKey 范围扫描高效，适合 PB 级时序数据和行为日志，但查询不够灵活（只能按 RowKey 查）、运维依赖 Hadoop 生态。简单说：数据量 < 1TB 选 MongoDB，> 1PB 且有 Hadoop 生态选 HBase。
如何设计一个多数据源的存储架构？
参考答案：典型的分层存储——MySQL 做业务主库（订单、用户、商品），Redis 做缓存和会话层，Elasticsearch 做搜索和日志分析，MongoDB 做非结构化内容存储（用户画像、评论、日志）。数据同步：MySQL → Binlog → Canal → ES/MongoDB。各司其职，不要用一个数据库解决所有问题。
