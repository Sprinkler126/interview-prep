Region 机制

  • Region：TiKV 数据分片的最小单位，每个 Region 是一个 Raft Group
  • 分裂：Region 大小超过阈值（默认 256MB）时自动分裂为两个 Region
  • 合并：相邻小 Region 可合并，减少 Raft Group 开销
  • Leader 调度：PD 根据负载情况调度 Region Leader 到不同节点，均衡读写
  • 3 副本：每个 Region 默认 3 副本，分布在不同的 TiKV 节点上

两阶段提交详细流程

Prewrite（第一阶段）
TiDB 选取一个 Key 作为 Primary Key，其余为 Secondary Key
并行写入所有 Key
写入 Lock
在 Key 上写入锁标记
含 Primary Key 信息
写入 Data
写入 value 到 write 列
使用 start_ts 版本
所有 Key Prewrite 成功
Commit（第二阶段）
只需提交 Primary Key（写入 commit_ts），Secondary Key 异步清理锁

MVCC 实现

  • TiKV 使用 start_ts 和 commit_ts 实现 MVCC
  • 每个 Key 存储多版本数据，按时间戳排列
  • start_ts：事务开始时从 PD 获取的全局时间戳
  • commit_ts：事务提交时从 PD 获取的全局时间戳
  • 读取时根据快照时间戳确定可见版本
PD 的 TSO (Timestamp Oracle) 通过中心化分配保证全局唯一且递增的时间戳，是分布式事务的基础。

1.4 Raft 协议在 TiDB 中的应用

Raft 在 TiDB 中的特殊优化

  • Multi-Raft：每个 Region 是独立的 Raft Group，整个集群数万个 Raft Group 并行运行
  • Raft Learner：新增副本先作为 Learner 同步数据，追上后再转为 Voter，避免影响可用性
  • Region 迁移：通过 Raft 成员变更将 Region 副本从一个节点迁移到另一个节点
  • Leader Transfer：主动将 Region Leader 转移到 Follower，用于负载均衡
  • 并行 Raft Propose：不同 Region 的 Raft 互不干扰，高并发写入

1.5 HTAP 架构

TiKV 行存 + TiFlash 列存 = HTAP
TiKV（行存）
OLTP 优化
点查/事务
RocksDB LSM Tree
异步复制
TiFlash（列存）
OLAP 优化
列式压缩
向量化执行

TiFlash 特性

  • 列式存储：同列数据连续存储，压缩率高，扫描性能好
  • 异步复制：通过 Raft Learner 从 TiKV 异步复制数据，毫秒级延迟
  • 一致性保证：读取时通过 Raft 确认数据一致性（ReadIndex），保证强一致读
  • 智能路由：TiDB 优化器自动判断将 OLAP 查询发送到 TiFlash，OLTP 查询发送到 TiKV
  • Stale Read：允许读取历史数据（指定时间戳），不阻塞实时写入
  • 向量化执行引擎：按列批处理，充分利用 CPU SIMD 指令

智能查询路由示例

-- TiDB 优化器自动选择执行引擎
-- OLTP 点查 -> TiKV
SELECT * FROM orders WHERE order_id = 1001;

-- OLAP 全表扫描 -> TiFlash
SELECT region, SUM(amount) FROM orders GROUP BY region;

-- 强制指定引擎
SELECT /*+ READ_FROM_STORAGE(TIFLASH[orders]) */ ...

2.1 PD 调度器

PD 核心职责

职责说明
TSO 分配全局唯一递增时间戳，分布式事务和 MVCC 的基础
元数据管理记录每个 Region 的位置信息
调度决策根据集群状态生成调度 Operator
热点调度检测读写热点，自动调度 Leader 或 Region
Region 分裂/合并Region 过大分裂，相邻小 Region 合并
Region 迁移扩缩容时副本迁入迁出

热点调度策略

  • 写热点：某个 TiKV 节点写入 QPS 过高，将 Leader 迁移到其他节点
  • 读热点：某个 Region Leader 读 QPS 过高，将 Leader 转移到负载低的 Follower
  • 热点打散：连续 key 范围的写热点，通过 Region 分裂 + Leader 分散
PD 每 10 秒收集一次 TiKV 心跳信息（Region 统计、磁盘使用、读写 QPS），据此做出调度决策。

基于代价的优化器 (CBO)

2.3 与 MySQL 兼容性

TiDB MySQL 兼容性
兼容点说明
协议兼容MySQL 协议，JDBC/mysql-connector 直接连接
SQL 语法大部分 MySQL 语法兼容（DML/DDL/DQL）
数据类型支持 MySQL 常用类型（INT/VARCHAR/TEXT/JSON/ENUM）
索引支持 B-tree、Hash、全文索引
存储过程逐步支持（持续完善中）
外键7.6+ 支持外键约束
AUTO_INCREMENT支持但行为有差异：分布式下非连续递增，建议使用 AUTO_RANDOM
触发器不支持
全文索引支持有限

迁移注意事项

  • AUTO_INCREMENT：TiDB 分布式环境下自增 ID 不连续，高并发写入可能导致热点，建议使用 AUTO_RANDOM
  • 自增 ID 分配：每个 TiDB Server 缓存一段 ID（默认 30000），批量分配提高性能
  • 外键：早期版本不支持外键，7.6+ 支持但建议应用层保证
  • 锁机制：TiDB 使用乐观锁 + 悲观锁（5.0+），与 MySQL 的行锁行为不完全相同
  • 事务大小限制：单事务默认限制 10MB，可通过配置调整

2.4 适用场景

适用场景

场景说明
HTAP 混合负载OLTP + OLAP 在同一平台，无需 ETL
MySQL 替代数据量增长超出 MySQL 单机能力，需要水平扩展
数据中台统一存储层，减少数据同步链路
实时分析TiFlash 列存引擎支持实时 OLAP 分析
高可用Raft 自动故障转移，RPO=0

不适合的场景

  • 小规模单机应用：分布式系统有额外开销，单机 MySQL 更简单
  • 大量存储过程/触发器：TiDB 对这些支持有限
  • 强依赖外键：虽然 7.6+ 支持，但分布式外键有性能开销
  • 纯 OLAP：如果只有分析场景，专用 OLAP 引擎（ClickHouse）更合适

🎤第三部分：模拟面试

TiDB 的整体架构是怎样的？各组件的职责是什么？
参考：TiDB 采用分层架构——TiDB Server（无状态 SQL 层，兼容 MySQL 协议）、TiKV（分布式 KV 存储，Raft 一致性）、TiFlash（列存引擎，OLAP 分析）、PD（集群大脑，元数据管理 + TSO 分配 + 调度）。各组件独立扩展，TiDB Server 和 TiKV/TiFlash 可独立水平扩展。
TiDB 的分布式事务是怎么实现的？
参考：基于 Percolator 模型的两阶段提交。Prewrite 阶段并行写入所有 Key 的锁和数据（选一个 Key 作为 Primary），Commit 阶段只需提交 Primary Key，Secondary Key 异步清理。使用 PD 分配的全局时间戳实现 MVCC。
追问：Primary Key 提交成功即事务成功，Secondary Key 通过异步清理或读取时惰性修复。
TiDB 的 HTAP 架构是怎么实现的？
参考：TiKV 行存（RocksDB LSM Tree）处理 OLTP，TiFlash 列存处理 OLAP。TiFlash 通过 Raft Learner 从 TiKV 异步复制数据（毫秒级延迟）。TiDB 优化器自动将 OLAP 查询路由到 TiFlash，OLTP 查询路由到 TiKV。TiFlash 支持向量化执行引擎，列式压缩和 SIMD 加速。
TiDB 中的 Region 是什么？为什么要分裂和合并？
参考：Region 是 TiKV 数据分片的最小单位（默认 96~256MB），每个 Region 是一个 Raft Group。Region 过大（256MB）时分裂为两个 Region，分散到不同节点。相邻小 Region 合并减少 Raft Group 开销。Region 是 PD 调度的基本单位。
Raft 协议在 TiDB 中是怎么应用的？有什么特殊优化？
参考：每个 Region 是一个 Raft Group，采用 Multi-Raft 架构（数万个 Raft Group 并行）。特殊优化：Raft Learner（新副本先同步再转 Voter）、Leader Transfer（主动转移 Leader 做负载均衡）、并行 Propose（不同 Region 互不干扰）。
PD 调度器有哪些核心功能？
参考：① TSO 分配（全局时间戳）；② 元数据管理（Region 位置映射）；③ Region 分裂/合并/迁移调度；④ 热点调度（读写热点自动打散 Leader）；⑤ 扩缩容调度（节点上线/下线时迁移 Region）。PD 3 节点 Raft 部署，高可用。
TiDB 和 MySQL 有什么区别？什么时候用 TiDB？
参考：TiDB 兼容 MySQL 协议和语法，但底层是分布式存储。区别：① TiDB 水平扩展（MySQL 单机有限）；② TiDB 内置 HTAP（MySQL 仅 OLTP）；③ TiDB 自增 ID 非连续；④ TiDB 不支持触发器。用 TiDB 的场景：数据量大需水平扩展、需要 HTAP 混合负载、需要高可用（RPO=0）。
TiDB 的自增 ID 有什么特点？为什么建议用 AUTO_RANDOM？
参考：TiDB 的 AUTO_INCREMENT 是分布式分配，每个 TiDB Server 缓存一段 ID（默认 30000），所以 ID 不连续。大量并发写入时，递增 ID 会导致写热点集中到一个 Region。AUTO_RANDOM 将 ID 高位随机化，打散到多个 Region，消除写热点。
