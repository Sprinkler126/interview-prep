第一部分：技术原理

Jenkins Pipeline

声明式 vs 脚本式 Pipeline

声明式（Declarative）

  • 结构化语法，易读易维护
  • 必须在 pipeline {} 块内
  • 提供更好的语法校验
  • 支持 Blue Ocean 可视化
  • 推荐使用

脚本式（Scripted）

  • Groovy 脚本，灵活性高
  • 在 node {} 块内编写
  • 语法校验较弱
  • 可以使用所有 Groovy 特性
  • 适合复杂逻辑

Jenkinsfile 语法

声明式 Pipeline 完整示例

pipeline {
    agent any  // 或 agent { docker { image 'maven:3.9-eclipse-temurin-17' } }

    environment {
        DOCKER_REGISTRY = 'registry.example.com'
        APP_NAME = 'my-app'
        VERSION = "${env.BUILD_NUMBER}"
    }

    options {
        timeout(time: 30, unit: 'MINUTES')
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '10'))
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean package -DskipTests'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
            post {
                always {
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }

        stage('Docker Build & Push') {
            steps {
                script {
                    docker.withRegistry("https://${DOCKER_REGISTRY}", 'registry-creds') {
                        def image = docker.build("${DOCKER_REGISTRY}/${APP_NAME}:${VERSION}")
                        image.push()
                        image.push('latest')
                    }
                }
            }
        }

        stage('Deploy') {
            when {
                branch 'main'
            }
            steps {
                sh "kubectl set image deployment/${APP_NAME} ${APP_NAME}=${DOCKER_REGISTRY}/${APP_NAME}:${VERSION}"
            }
        }
    }

    post {
        success {
            echo 'Pipeline succeeded!'
            // 通知：钉钉、邮件等
        }
        failure {
            echo 'Pipeline failed!'
        }
        always {
            cleanWs()  // 清理工作空间
        }
    }
}

核心指令说明

指令作用说明
agent指定执行节点any（任意节点）、docker（Docker 容器）、label（指定节点标签）
stages定义阶段集合包含多个 stage，按顺序执行
stage定义单个阶段包含 steps，是 Pipeline 的基本单元
steps定义具体步骤sh、bat、checkout 等操作
environment定义环境变量全局或 stage 级别
when条件执行branch、expression、not 等
post后置操作success、failure、always
parallel并行执行多个 stage 同时执行

GitLab CI

.gitlab-ci.yml 语法

# 全局配置
image: maven:3.9-eclipse-temurin-17

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"
  DOCKER_REGISTRY: "registry.example.com"

# 缓存配置
cache:
  paths:
    - .m2/repository/

# 定义阶段（按顺序执行）
stages:
  - build
  - test
  - quality
  - deploy

# 构建任务
build:
  stage: build
  script:
    - mvn clean package -DskipTests
  artifacts:
    paths:
      - target/*.jar
    expire_in: 1 hour

# 测试任务
test:
  stage: test
  script:
    - mvn test
  artifacts:
    reports:
      junit: target/surefire-reports/TEST-*.xml
  coverage: '/Code coverage: (\d+\.?\d*)%/'

# 代码质量检查
sonarqube:
  stage: quality
  script:
    - mvn sonar:sonar
  only:
    - merge_requests
    - main

# 部署到生产（仅 main 分支）
deploy-prod:
  stage: deploy
  script:
    - docker build -t $DOCKER_REGISTRY/my-app:$CI_COMMIT_SHA .
    - docker push $DOCKER_REGISTRY/my-app:$CI_COMMIT_SHA
    - kubectl set image deployment/my-app my-app=$DOCKER_REGISTRY/my-app:$CI_COMMIT_SHA
  only:
    - main
  when: manual          # 手动触发
  environment:
    name: production
    url: https://my-app.example.com

部署策略

三种部署策略对比

策略原理回滚速度资源消耗风险
蓝绿部署 准备一套新环境（绿），验证通过后切换流量到绿环境，蓝环境保留作为回滚 秒级（切换负载均衡） 2 倍资源 低
金丝雀部署 新版本先部署少量实例，逐步扩大流量比例（5%→20%→50%→100%） 快（缩容金丝雀） 少量额外 低
滚动更新 逐步用新版本替换旧版本 Pod（K8s 默认策略） 较慢（逐个回滚） 少量额外 中

第三部分：模拟面试

什么是 CI/CD？它们有什么区别？
参考：CI（持续集成）是开发人员频繁将代码合并到主干，每次合并都自动触发构建和测试，尽早发现问题。CD 有两层含义：持续交付（Continuous Delivery）是代码随时可以部署到生产，但需要手动审批；持续部署（Continuous Deployment）是代码通过所有测试后自动部署到生产。典型流程：代码提交 → 自动构建 → 自动测试 → 自动部署到 staging → 手动审批 → 部署到 production。
Jenkins Pipeline 的声明式和脚本式有什么区别？
参考：声明式 Pipeline 使用结构化语法（pipeline/stages/stage/steps），易读易维护，有语法校验，支持 Blue Ocean 可视化，推荐使用。脚本式 Pipeline 使用 Groovy 脚本，灵活性高，可以使用所有 Groovy 特性，但语法校验弱。声明式底层也是转为脚本式执行。简单场景用声明式，复杂逻辑（如条件分支、循环）用脚本式包装在声明式的 script {} 块中。
什么是 GitOps？和传统 CI/CD 有什么区别？
参考：GitOps 是一种以 Git 仓库为唯一真理来源的运维模式。传统 CI/CD 是 Pipeline 主动推送（Push）变更到集群；GitOps 是 GitOps 工具（ArgoCD/FluxCD）持续拉取（Pull）Git 仓库中的声明式配置并同步到集群。优势：所有变更都有 Git 记录（审计追溯）、Git 回滚即集群回滚、声明式管理更安全。核心工具是 ArgoCD 和 FluxCD。
蓝绿部署、金丝雀部署、滚动更新有什么区别？
参考：蓝绿部署准备完整的新环境，验证通过后一次性切换流量，回滚秒级但需要 2 倍资源。金丝雀部署先将少量流量导向新版本，逐步扩大比例，风险低但配置复杂。滚动更新逐步替换旧 Pod（K8s 默认），资源消耗少但回滚较慢。生产推荐金丝雀部署（配合 Ingress 权重或 Istio），大版本变更用蓝绿部署。
GitLab CI 的 Runner 是什么？有哪几种类型？
参考：Runner 是执行 GitLab CI Job 的代理。分为三种：1）Shared Runner：GitLab 实例共享，所有项目可用，适合通用构建；2）Group Runner：组内共享，只有该组的项目可用；3）Specific Runner：专属于某个项目。Runner 可以运行在物理机、虚拟机、Docker 容器或 K8s Pod 中。推荐使用 Docker Executor（每个 Job 在独立容器中运行，环境隔离、清理方便）。
如何保证 CI/CD Pipeline 的安全性？
参考：1）凭证管理：使用 Secret 管理工具（Vault、K8s Secrets），不在代码中硬编码密码；2）镜像安全：使用 Trivy/Snyk 扫描镜像漏洞；3）代码质量：SonarQube 代码扫描，不通过阻断 Pipeline；4）最小权限：CI/CD 的 ServiceAccount 只给必要权限；5）制品签名：对 Docker 镜像签名（cosign），防止篡改；6）审计日志：所有部署操作可追溯。
Jenkins 如何实现动态 Agent？
参考：Jenkins 支持通过 Kubernetes 插件动态创建 Agent。配置方式：在 Jenkins 中配置 K8s Cloud，定义 Pod Template（包含容器镜像、资源限制等）。Pipeline 运行时，Jenkins 自动在 K8s 中创建 Pod 作为 Agent，任务完成后自动销毁。优势：资源按需分配、环境隔离、无需维护固定 Agent 节点。配置示例：agent { kubernetes { yaml '''...''' } }。
什么是制品管理？为什么需要制品仓库？
参考：制品（Artifact）是 CI 构建的产出物（JAR、Docker 镜像、npm 包等）。制品仓库（Nexus/Artifactory/Harbor）用于统一存储和管理这些产物。必要性：1）不可变性：制品一旦构建不应修改，确保各环境部署一致；2）版本管理：支持回滚到任意历史版本；3）依赖缓存：避免每次从公网下载依赖；4）安全扫描：集成漏洞扫描；5）权限控制：不同环境访问不同制品。
