第一部分：技术原理

四种调用模式

gRPC 四种调用模式

模式请求响应典型场景
Unary单个请求单个响应普通 RPC 调用，类似 REST
Server Streaming单个请求流式响应服务端推送，如实时数据订阅
Client Streaming流式请求单个响应客户端批量上传，如文件上传
Bidirectional流式请求流式响应双向通信，如聊天、实时游戏
 
// Protobuf 定义四种模式
service Greeter {
  // Unary：一问一答
  rpc SayHello (HelloRequest) returns (HelloReply);

  // Server Streaming：服务端流式返回
  rpc ListFeatures (Rectangle) returns (stream Feature);

  // Client Streaming：客户端流式发送
  rpc RecordRoute (stream Point) returns (RouteSummary);

  // Bidirectional Streaming：双向流式
  rpc RouteChat (stream RouteNote) returns (stream RouteNote);
}

流式调用原理

Server Streaming 流程
Client 发送请求
→
Server 处理
→
Stream Response 1
→
Stream Response 2
→
Stream Response N + EOF
  • 基于 HTTP/2 的 DATA 帧传输，多个响应通过不同的 Stream ID 复用同一 TCP 连接
  • Server Streaming：Client 发送一个请求，Server 通过 stream 返回多个响应，以 trailers 标记结束
  • Client Streaming：Client 通过 stream 发送多个请求，Server 在收到全部请求后返回一个响应
  • Bidirectional：双方独立发送流，两个方向的流互不影响，可以任意顺序发送

Protobuf 原理

Protobuf 编码原理

Protobuf 采用 Tag-Length-Value (TLV) 编码格式：

// Protobuf 消息定义
message Person {
    string name = 1;      // field_number = 1
    int32 age = 2;        // field_number = 2
    string email = 3;     // field_number = 3
}

// 编码格式：每个字段 = Tag + Value
// Tag = (field_number << 3) | wire_type
// wire_type: 0=Varint, 1=64bit, 2=Length-delimited, 5=32bit

// Varint 编码（用于 int32/int64/bool 等）：
// 每字节的最高位为标志位，1 表示后续还有字节，0 表示结束
// 例如 300 = 0b100101100
//   编码为：10101100 00000010
//   第一字节: MSB=1(后续还有), 低7位=0101100
//   第二字节: MSB=0(结束), 低7位=0000010
//   解码: 0000010 << 7 | 0101100 = 300

proto3 语法要点

syntax = "proto3";

package example;

// 导入
import "google/protobuf/timestamp.proto";

// 枚举
enum Status {
    UNKNOWN = 0;    // proto3 第一个值必须为 0
    ACTIVE = 1;
    INACTIVE = 2;
}

// 消息
message User {
    int64 id = 1;
    string name = 2;
    Status status = 3;
    repeated string tags = 4;            // 列表
    map<string, string> metadata = 5;   // Map
    google.protobuf.Timestamp created = 6;
    oneof contact {                      // 联合类型（最多一个字段有值）
        string email = 7;
        string phone = 8;
    }
}

// 服务定义
service UserService {
    rpc GetUser (GetUserRequest) returns (User);
    rpc ListUsers (ListUsersRequest) returns (stream User);
}
proto3 的关键变化：移除了 required/optional 关键字（所有字段都是 optional），字段默认值不序列化，大幅减少编码体积。

HTTP/2 特性

HTTP/2 核心特性

特性说明对 gRPC 的意义
多路复用一个 TCP 连接上并发多个 Stream高并发调用无需多连接
头部压缩 (HPACK)用索引表压缩 HTTP 头减少元数据传输开销
二进制帧数据以二进制帧传输解析效率高，适合 Protobuf
服务器推送Server 主动推送资源支持 Server Streaming
流控机制基于 Stream 级别的流控防止慢消费者拖垮服务端

HTTP/2 帧与 Stream

// HTTP/2 帧结构
+-----------------------------------------------+
|                 Length (24)                    |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+-------------------------------+
|R|                 Stream Identifier (31)                      |
+-+-------------------------------------------------------------+
|                   Frame Payload (变长)                         |
+---------------------------------------------------------------+

// 帧类型：
// HEADERS  - 传输 HTTP 头部
// DATA     - 传输数据体（Protobuf 编码后的消息）
// SETTINGS - 连接配置
// WINDOW_UPDATE - 流控窗口更新
// RST_STREAM - 终止流
// PING     - 心跳检测

// gRPC 消息在 HTTP/2 中的封装：
// 1. Protobuf 序列化为 binary
// 2. 加上 5 字节 gRPC 帧头（1字节压缩标志 + 4字节长度）
// 3. 放入 HTTP/2 DATA 帧
// 4. 通过 HEADERS 帧传输 gRPC 元数据（:path, content-type 等）

拦截器

gRPC 拦截器机制

// Unary 拦截器（Client 端）
public class LoggingInterceptor implements ClientInterceptor {
    @Override
    public <ReqT, RespT> ClientCall<ReqT, RespT> interceptCall(
            MethodDescriptor<ReqT, RespT> method,
            CallOptions callOptions,
            Channel next) {
        return new ForwardingClientCall.SimpleForwardingClientCall<>(
            next.newCall(method, callOptions)) {
            @Override
            public void sendMessage(ReqT message) {
                log.info("Sending request: {}", message);
                super.sendMessage(message);
            }
            @Override
            public void onMessage(RespT response) {
                log.info("Received response: {}", response);
                super.onMessage(response);
            }
        };
    }
}

// 注册拦截器
ManagedChannel channel = ManagedChannelBuilder
    .forAddress("localhost", 50051)
    .intercept(new LoggingInterceptor())
    .usePlaintext()
    .build();

Server 端拦截器

// Server 端 Unary 拦截器
public class AuthInterceptor implements ServerInterceptor {
    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call,
            Metadata headers,
            ServerCallHandler<ReqT, RespT> next) {
        String token = headers.get(
            Metadata.Key.of("authorization", Metadata.ASCII_STRING_MARSHALLER));
        if (!validateToken(token)) {
            call.close(Status.UNAUTHENTICATED, new Metadata());
            return new ServerCall.Listener<>() {};
        }
        return next.startCall(call, headers);
    }
}

// 注册 Server 拦截器
Server server = ServerBuilder
    .forPort(50051)
    .addService(new GreeterServiceImpl())
    .intercept(new AuthInterceptor())
    .build();
拦截器链的执行顺序：Client 端按注册顺序从外到内执行，Server 端也是按注册顺序。注意拦截器的顺序对认证、日志等场景很重要。

第二部分：场景化讲解

负载均衡

客户端 vs 代理端负载均衡

客户端负载均衡

  • Client 持有所有 Server 地址列表
  • Client 内置负载均衡策略选择目标
  • gRPC 原生支持 pick_first / round_robin
  • 无额外网络跳转，性能好
  • 地址列表通过 NameResolver 获取

代理端负载均衡

  • Client 只知道代理地址
  • 代理（如 Envoy/Nginx）负责分发
  • 适合跨语言、异构系统
  • L7 代理可感知 gRPC 协议
  • 增加一跳网络延迟
// gRPC 客户端负载均衡配置
ManagedChannel channel = ManagedChannelBuilder
    .forTarget("dns:///my-service:50051")
    .defaultLoadBalancingPolicy("round_robin")
    .usePlaintext()
    .build();

// 自定义 NameResolver（对接注册中心）
ManagedChannel channel = ManagedChannelBuilder
    .forTarget("consul:///my-service")
    .nameResolverFactory(new ConsulNameResolverProvider())
    .defaultLoadBalancingPolicy("round_robin")
    .build();

超时与取消

Deadline 传播

// 设置 Deadline（从调用发起时开始计时）
stub = stub.withDeadlineAfter(5, TimeUnit.SECONDS);
try {
    response = stub.sayHello(request);
} catch (DeadlineExceededException e) {
    // 超时处理
}

// Deadline 传播机制：
// 1. Client 设置 Deadline = now + timeout
// 2. Deadline 通过 HTTP/2 头部 grpc-timeout 传递给 Server
// 3. Server 收到后计算剩余时间 = Deadline - now
// 4. Server 再调用下游时，传递剩余时间作为新的 Deadline
// 整条调用链共享同一个 Deadline，不会因为跳数增加而延长超时

// 取消调用
Context.CancellableContext cancellable = Context.current().withCancellation();
cancellable.run(() -> {
    stub.sayHello(request);
});
// 取消操作
cancellable.cancel(new CancellationException("用户取消"));
Deadline 传播是 gRPC 的重要特性：在微服务调用链中，超时时间从入口统一设置并逐级递减传递，避免因中间服务耗时导致整体超时。

与 REST 对比

gRPC vs REST

特性gRPCREST
协议HTTP/2通常 HTTP/1.1
序列化Protobuf（二进制，高效）JSON（文本，可读）
类型安全强类型（IDL 定义）弱类型（需文档约束）

第三部分：模拟面试

请介绍 gRPC 的四种调用模式，各自适用什么场景？
参考：gRPC 提供四种调用模式：1）Unary（一元调用）：一个请求一个响应，类似 REST，最常用；2）Server Streaming（服务端流）：客户端发一个请求，服务端返回一个流，适用于服务端推送场景如实时数据订阅、日志流；3）Client Streaming（客户端流）：客户端发送一个流，服务端返回一个响应，适用于客户端批量上传如文件上传、批量导入；4）Bidirectional Streaming（双向流）：双方都可以发送流，适用于聊天、实时游戏、协同编辑等场景。四种模式都基于 HTTP/2 的 Stream 机制实现。
Protobuf 的编码原理是什么？为什么比 JSON 快？
参考：Protobuf 采用 Tag-Length-Value (TLV) 编码，整数使用 Varint 变长编码（每字节最高位为标志位），字符串使用长度前缀编码。比 JSON 快的原因：1）二进制编码，无需文本解析，编解码速度快；2）Varint 编码大幅压缩整数体积（如 300 只需 2 字节）；3）字段用 field_number 而非字段名标识，体积小；4）默认值字段不序列化，减少数据量；5）强类型定义，无需类型推断。实测 Protobuf 序列化体积约为 JSON 的 1/3 到 1/10，速度快 5 到 100 倍。
gRPC 为什么选择 HTTP/2 而不是 HTTP/1.1？
参考：gRPC 选择 HTTP/2 的关键原因：1）多路复用：一个 TCP 连接上并发多个 Stream，解决 HTTP/1.1 的队头阻塞问题，支持高并发 RPC 调用；2）二进制帧：gRPC 消息封装在 DATA 帧中，解析效率高；3）头部压缩（HPACK）：RPC 调用频繁，压缩元数据开销至关重要；4）流式传输：HTTP/2 的 Stream 天然支持 gRPC 的四种流式模式；5）Trailer 支持：HTTP/2 的 Trailer 可用于传递 gRPC Status Code 和错误信息。
gRPC 的拦截器机制是什么？有哪些实际应用场景？
参考：gRPC 的拦截器类似 Servlet Filter 或 Spring AOP，可以在 RPC 调用前后插入横切逻辑。分为 ClientInterceptor 和 ServerInterceptor。实际应用：1）认证授权 — Server 端验证 Token；2）日志记录 — 记录请求/响应内容和耗时；3）链路追踪 — 注入 Trace ID（如 OpenTelemetry）；4）指标收集 — 统计 QPS、延迟、错误率；5）请求重试 — Client 端自动重试失败请求；6）限流 — Server 端限制并发。拦截器按注册顺序形成链，支持嵌套调用。
gRPC 的 Deadline 传播机制是什么？为什么很重要？
参考：Deadline 是 gRPC 的超时机制，关键特点是"传播"：Client 设置 Deadline（绝对时间），通过 HTTP/2 头部 grpc-timeout 传递给 Server。Server 收到后计算剩余时间，再调用下游时传递剩余时间作为新的 Deadline。整条调用链共享同一个 Deadline。重要性：在微服务链式调用中，如果每层都独立设置超时，总超时会随层数指数增长。Deadline 传播确保整条链的超时可控。例如入口设置 5 秒，A 服务耗时 2 秒后调用 B，B 的 Deadline 自动变为 3 秒，B 调用 C 时 Deadline 继续递减。
gRPC 的客户端负载均衡和代理端负载均衡有什么区别？
参考：客户端负载均衡：Client 内置负载均衡策略（pick_first/round_robin），通过 NameResolver 获取 Server 地址列表，直接选择目标 Server 发起调用，无额外网络跳转，性能最优。代理端负载均衡：Client 只知道代理地址（如 Envoy），代理感知 gRPC 协议（L7），将请求分发到后端 Server。优点是对 Client 透明，适合跨语言异构系统；缺点是增加一跳延迟。生产中常结合使用：客户端做基础 LB，代理做高级路由（金丝雀、A/B 测试）。
gRPC-Web 是什么？为什么需要它？
参考：gRPC-Web 是 gRPC 协议的浏览器兼容版本。浏览器不支持 HTTP/2 trailers 和完整的二进制帧控制，因此无法直接调用标准 gRPC。gRPC-Web 通过一个代理层（如 Envoy）将浏览器的 gRPC-Web 请求转换为标准 gRPC 请求转发给后端。支持 Unary 和 Server Streaming 两种模式。前端通过 protoc 生成 JavaScript/TypeScript 客户端代码。在 Service Mesh 架构中，Envoy 作为 Sidecar 天然支持 gRPC-Web 代理。
在实际项目中，gRPC 和 REST 如何选型？
参考：选型考虑因素：1）内部微服务间调用 → gRPC（性能好、类型安全、流式支持）；2）对外公开 API → REST（生态好、浏览器兼容、调试方便）；3）需要流式传输 → gRPC；4）跨语言团队 → gRPC（多语言代码生成）；5）已有 REST 生态 → 可混用，核心链路用 gRPC，非核心用 REST。实际项目中常见混用：内部服务用 gRPC，BFF 层将 gRPC 转为 REST 对外暴露。gRPC 的学习成本主要是 Protobuf IDL 定义和代码生成工具链。
