🔬第一部分：技术原理

1.1 Transformer 与 LLM 基础

面试回答主线：输入如何变成下一个 Token？

文本 Tokenize
→
Embedding + 位置编码
→
多层 Transformer
→
Logits → 采样下一个 Token
  • Self-Attention：输入经过线性层得到 Q、K、V，注意力权重为 softmax(QKᵀ / √dₖ)，再对 V 加权求和。它让每个 Token 动态关注上下文，而不是只看固定窗口。
  • 多头注意力：不同 head 学习不同关系，拼接后再投影；实际推理瓶颈常在 KV Cache 和显存带宽，不只是 FLOPs。
  • Decoder-only：使用因果 Mask，只能看当前位置之前的 Token，训练目标是 next-token prediction；Encoder-only 更适合表示学习和分类。
  • Temperature / Top-p：temperature 调整 logits 分布尖锐程度，Top-p 从累计概率达到阈值的候选中采样；事实问答通常降低随机性，但不能代替检索和校验。
不要把“上下文窗口大”回答成“模型记住了知识”。窗口只是一次推理可读入的 Token 数；参数知识来自训练，最新/私有知识通常需要 RAG、微调或工具调用。

Retrieval-Augmented Generation：先找证据，再组织答案

离线建库 + 在线问答双链路

→

→
Chunk + Embedding向量化入库
→

在线 Query：改写 → 混合召回 → 重排 → 上下文组装 → LLM → 引用与校验
阶段常见做法失败表现优化方向
Query 理解改写、拆分、多查询、意图识别问法与文档表达不一致保留原问题，扩展同义词和业务实体

生成上下文拼装、提示词约束、引用幻觉、答非所问、引用错证据不足时拒答，要求逐条引用并做 groundedness 评估

1.3 Chunking 与 Embedding

切分不是越小越好：完整语义优先

固定长度切分

  • 按 Token / 字符数切分，简单稳定
  • 配合 overlap 避免边界丢语义
  • 适合格式杂乱的初始版本

结构化切分

  • 按标题、段落、表格、代码块切分
  • 保留父标题、页码、权限、时间等 metadata
  • 适合制度、API 文档、技术手册
  • Chunk 大小权衡：太小上下文不完整，太大检索相似度被噪声稀释且占满上下文；应按文档结构、问题粒度和模型上下文预算做离线实验。
  • Embedding：把文本映射为向量，使语义相近文本距离更近。余弦相似度关注方向，点积还受向量模长影响，索引距离度量必须与模型训练目标匹配。
  • 多语种与领域词：通用 embedding 对业务缩写、产品名、代码符号可能不稳定；可加关键词检索、实体 metadata，必要时做领域微调。
  • 更新策略：文档 hash 去重，按版本增量索引；删除时同步删除向量，权限变更要重新计算可见范围，不能只在 Prompt 中提醒模型。

1.4 召回、重排与上下文工程

为什么向量检索 TopK 不是最终答案？

BM25 关键词召回
Dense 向量召回
RRF / 融合去重
Reranker 精排
  • 稀疏检索擅长专有名词、编号、错误码；稠密检索擅长语义改写和自然语言表达。混合检索通常比单一召回更稳。
  • RRF 不要求不同检索器分数可比，按排名融合；重排模型再读取 query 与候选文本的交互信息，成本高于向量相似度，应放在候选集之后。
  • 上下文组装：去重、按相关性排序、保留标题和来源、控制 Token 预算；长文档可做父子 Chunk，子块召回后回填父级上下文。
  • 提示词防幻觉：明确“仅基于证据回答”“证据不足输出未知”，要求引用 chunk ID；这能降低风险，但最终仍需评估和业务兜底。

  • 权限必须在召回前过滤，至少携带 tenant、部门、角色、文档版本等 metadata；否则会出现“模型知道但用户不该看到”的越权。
  • 对表格、代码、图片和扫描 PDF 采用不同解析器；保留页码、标题层级、来源 URL，便于引用和故障定位。
  • 建立离线评测集：真实问题、标准答案、证据片段、不可回答样本，避免只看主观 Demo。

2.2 RAG 评估与可观测

指标要分层：检索对不对，生成说没说错

层次指标回答的面试重点
检索层Recall@K、Precision@K、MRR、nDCG正确证据是否进入候选集；Recall 低时调切分/召回，别只换大模型
生成层Faithfulness、Answer Relevancy、Citation Correctness答案是否被证据支持、是否回答问题、引用是否真的支持结论
系统层P50/P95 延迟、Token、命中率、失败率、成本线上要看分阶段耗时：Embedding、召回、重排、LLM、首 Token
业务层一次解决率、转人工率、用户反馈、知识覆盖率离线分数高不代表业务有效，要闭环采集 bad case
排查顺序建议：先确认知识库中是否存在答案 → 看权限过滤 → 看召回候选 → 看重排 → 看上下文截断 → 最后看 Prompt 和模型输出。

2.3 安全、成本与生产稳定性

RAG 生产落地的高频风险

安全

  • Prompt Injection：文档中的指令不能覆盖系统规则
  • 数据外泄：租户隔离、ACL 过滤、日志脱敏
  • 工具调用：白名单、参数校验、最小权限
  • 输出安全：敏感信息检测、引用审计

成本与稳定性

  • Embedding 批量化、缓存、增量索引
  • 召回先过滤，控制 rerank 候选数
  • 小模型路由、回答缓存、流式输出
  • 超时、重试、熔断、降级到搜索/人工

🎤第三部分：模拟面试

RAG 和微调有什么区别？什么时候选 RAG？
参考：RAG 通过检索把外部知识放进上下文，知识更新快、可引用、可按权限控制，但依赖召回质量并增加延迟。微调改变模型参数，更适合固定格式、风格、领域任务能力，不适合频繁变化的事实知识。企业知识库、政策、产品文档通常先 RAG，行为模式再考虑微调。
为什么 RAG 会回答错？如何系统定位？
参考：可能是知识不存在、解析丢失、Chunk 边界不完整、Embedding 不匹配、召回被权限过滤、重排错序、上下文超长截断或模型忽略证据。按“数据 → 权限 → 召回 → 重排 → 上下文 → 生成”分层打点，使用带标准证据的评测集逐层定位。
如何防止 RAG 中的 Prompt Injection？
参考：把检索内容视为不可信数据，系统指令与证据严格分隔；只允许模型基于证据回答，不允许文档改变工具权限或系统规则；工具调用做白名单和参数校验；对输入、文档、输出做安全检测，并记录审计。不能只靠一句“忽略恶意指令”解决。
大模型应用如何控制延迟和成本？
参考：离线做增量 Embedding，在线做查询缓存和结果缓存；先 metadata 过滤，再混合召回，限制 rerank TopK；按问题复杂度路由小模型/大模型，控制上下文 Token，使用流式返回；设置超时、重试、熔断和降级。指标要看 P95、首 Token、Token 用量和单次成本。
