Init Container（初始化容器）

  • 在主容器之前启动并运行到完成，用于初始化工作
  • 多个 Init Container 按顺序串行执行，每个必须成功后才启动下一个
  • 不支持 Readiness Probe，因为它们必须在主容器之前完成
  • 典型用途：等待依赖服务就绪、数据库迁移、配置初始化
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nslookup mysql-service; do echo waiting; sleep 2; done']
    - name: init-schema
      image: myapp-migrator:1.0
      command: ['migrate', '--up']
  containers:
    - name: myapp
      image: myapp:1.0

三种探针（Probe）

探针作用失败后果典型配置
Liveness Probe 检测容器是否存活 重启容器（Restart Policy） HTTP GET /healthz，每 10s
Readiness Probe 检测容器是否就绪接收流量 从 Service Endpoints 移除 HTTP GET /ready，每 5s
Startup Probe 检测容器是否启动完成 启动期间暂停 Liveness/Readiness HTTP GET /startup，每 10s，失败 30 次 
# 探针支持的检测方式
livenessProbe:
  httpGet:           # HTTP GET 请求
    path: /healthz
    port: 8080
  initialDelaySeconds: 10   # 初始延迟
  periodSeconds: 10         # 检测间隔
  failureThreshold: 3       # 连续失败次数

readinessProbe:
  tcpSocket:         # TCP 端口检测
    port: 3306

startupProbe:
  exec:              # 执行命令
    command: ["cat", "/tmp/ready"]
  failureThreshold: 30
  periodSeconds: 10
Startup Probe 用于启动慢的应用（如 Java 应用）。在 Startup Probe 成功之前，Liveness 和 Readiness Probe 不会执行，避免应用还在启动就被误杀。

1.2b 调度器原理与调度约束

设计动机：调度器怎么决定 Pod 落到哪个 Node？

设计起点：K8s 调度的本质是"把 Pod 的资源需求与 Node 的资源供给匹配"。Scheduler 监听未调度的 Pod，经过过滤 + 打分两阶段选出最优 Node。理解调度约束是面试高频点。

未调度 Pod
→
① Filter 过滤
剔除不满足硬性条件的 Node
→
② Score 打分
对剩余 Node 按策略打分
→
选最高分 Node
绑定 Pod 到 Node

调度约束全景

约束类型作用典型场景
resources.requests/limits资源声明 Pod 需要的 CPU/内存所有 Pod 都该设
nodeSelector硬约束Pod 只调度到带指定 label 的 NodeGPU 任务 → label=gpu
nodeAffinity硬/软nodeSelector 升级版，支持多种运算符preferred 时尽量满足
podAffinity亲和Pod 调度到与某 Pod 同 Node/Zone前端 + 缓存同节点降延迟
podAntiAffinity反亲和Pod 不与某 Pod 同 Node/Zone多副本分散避免单点
Taint / Toleration排斥/容忍Node 标记污点，Pod 需容忍才能调度GPU 节点专用、节点维护
PriorityClass优先级高优先级 Pod 可抢占低优先级关键业务 vs 批处理

Taint / Toleration — 节点级排斥

设计起点：某些 Node 要"专用"（如 GPU 节点只跑 GPU 任务，维护中的 Node 不接新 Pod）。Taint 给 Node 打污点排斥 Pod，Toleration 给 Pod 写容忍才能调度上去。这是 Node 视角的"反向亲和"。

# 给 GPU 节点打污点：只允许容忍的 Pod 调度
kubectl taint nodes gpu-node-1 dedicated=gpu:NoSchedule

# Pod 声明容忍才能上 GPU 节点
spec:
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"
effect含义
NoSchedule不调度新 Pod（已运行的留下）
PreferNoSchedule尽量不调度（软约束）
NoExecute不调度且驱逐已运行的不容忍 Pod
内置 Taint：node.kubernetes.io/not-ready（节点未就绪）、node.kubernetes.io/unreachable（失联）、node.kubernetes.io/disk-pressure（磁盘压力）。这些让 K8s 自动避开不健康节点。

1.2c QoS 等级与 Pod 驱逐

设计动机：节点资源不足时，驱逐谁？

设计起点：节点资源紧张时，kubelet 要驱逐 Pod 释放资源。驱逐顺序由 QoS (Quality of Service) 等级决定——这是 K8s 在资源争抢时的"优先级"机制，根据 Pod 的 requests/limits 配置自动判定。

三种 QoS 等级（驱逐优先级从高到低）
QoS判定条件驱逐优先级典型场景
BestEffort未设 requests/limits最先驱逐不重要任务、测试
Burstable设了 requests 但 < limits，或不一致其次驱逐有波动的工作负载
Guaranteedrequests == limits（CPU 和内存都设）最后驱逐关键业务

QoS 判定与最佳实践

# Guaranteed: requests == limits，CPU 和内存都设
resources:
  requests: { cpu: 1, memory: 1Gi }
  limits:   { cpu: 1, memory: 1Gi }

# Burstable: requests < limits
resources:
  requests: { cpu: 500m, memory: 512Mi }
  limits:   { cpu: 1, memory: 1Gi }

# BestEffort: 都不设
# (无 resources 字段)
易错点：CPU 是可压缩资源（超限只 throttling 不杀），内存是不可压缩（超限 OOM Kill）。所以内存压力是驱逐主因。Guaranteed Pod 内存超限也会被 OOMKilled，但不会被主动驱逐。
面试要点：生产关键业务应设成 Guaranteed（requests==limits），保证最后被驱逐且资源预留稳定。批处理任务可设 Burstable 或 BestEffort，让出资源给关键业务。

1.2d Operator 与 CRD — K8s 的扩展范式

设计动机：K8s 内置控制器不够用怎么办？

设计起点：K8s 内置 Deployment/StatefulSet 等通用控制器，但复杂应用（如 MySQL 集群、Prometheus、Kafka）有自己的运维逻辑——主从切换、备份、扩缩容都需专门知识。Operator 模式让你把领域专家的运维知识编码成一个自定义控制器，像内置资源一样管理复杂应用。

Operator 工作原理
CRD 定义自定义资源
如 MySQLCluster
→
用户创建 CR 实例
声明期望状态
→
Operator 控制循环
监听 CR 变化
→
调谐到期望状态
创建 Pod/Service/PVC

CRD + Operator 的核心概念

  • CRD (CustomResourceDefinition)：定义一种新资源类型（如 MySQLCluster），告诉 K8s API Server 如何存储/校验它
  • CR (Custom Resource)：CRD 的实例，用户创建/修改它来声明期望状态
  • Operator：一个实现了控制循环的程序，监听 CR 变化，把实际状态调谐到期望状态
  • 本质：Operator = CRD + 自定义控制器 + 领域运维知识

知名 Operator 与选型

Operator管理对象典型能力
Prometheus OperatorPrometheus 实例 + Alertmanager声明式配置告警规则、持久化
StrimziKafka 集群主从管理、Topic/User CRD
MySQL Operator (Oracle/Percona)MySQL 主从/InnoDB Cluster备份、主从切换、扩缩容
ArgoCDGitOps 应用部署Application CRD，Git → 集群同步
Cert ManagerHTTPS 证书Certificate CRD，自动签发续期
面试要点：Operator 是 K8s 生态繁荣的关键——它把"运维专家知识"变成可复用的软件。问"K8s 怎么管理有状态应用"时，答 Operator + CRD 比 StatefulSet 更深入。开发 Operator 用 Operator Framework 或 Kubebuilder。
易错点：Operator 不是 K8s 内置功能，而是一种设计模式。CRD 是内置的扩展机制，Operator 是利用 CRD + 控制器模式构建的具体实现。两者常配合出现。

控制器

控制器类型对比

控制器用途Pod 关系典型场景
Deployment 无状态应用部署 通过 ReplicaSet 管理 Pod，Pod 可互换 Web 服务、API 网关
StatefulSet 有状态应用部署 Pod 有稳定网络标识和持久存储，有序部署 MySQL、Redis、Zookeeper
DaemonSet 每个节点运行一个 Pod 自动在每个 Node 上部署一个 Pod 副本 日志采集、监控 Agent、网络插件
Job 一次性任务 Pod 运行完成后不再重启 数据迁移、批处理
CronJob 定时任务 按 Cron 表达式周期性创建 Job 定时备份、报表生成

Deployment 滚动更新

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 更新时最多多出 1 个 Pod
      maxUnavailable: 0   # 更新时不允许不可用
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
  • maxSurge：更新过程中可以超出期望副本数的最大值（绝对数或百分比）
  • maxUnavailable：更新过程中允许不可用的最大 Pod 数
  • 滚动更新通过 ReplicaSet 实现：创建新 RS → 逐步扩容新 RS → 逐步缩容旧 RS
  • 支持回滚：kubectl rollout undo deployment/nginx-deployment

StatefulSet 特点

  • 稳定网络标识：Pod 名称格式为 {StatefulSet名称}-{序号}（如 mysql-0, mysql-1, mysql-2）
  • 稳定存储：每个 Pod 绑定固定的 PVC，Pod 重建后仍使用同一存储
  • 有序部署：按序号顺序创建（0→1→2），逆序删除（2→1→0）
  • 有序更新：按序号逆序更新（先更新最后一个 Pod）
  • 需要配合 Headless Service（clusterIP: None）实现 DNS 解析

Service 类型

四种 Service 类型

类型说明访问方式适用场景
ClusterIP（默认） 分配集群内部虚拟 IP 仅集群内部访问 服务间内部通信
NodePort 在 ClusterIP 基础上，在每个节点开放端口（30000-32767） NodeIP:NodePort 开发测试、简单外部访问
LoadBalancer 使用云厂商负载均衡器 云 LB 的外部 IP 生产环境外部访问（云环境）
ExternalName 将 Service 映射到外部域名（CNAME） 通过 DNS 解析到外部 访问集群外部服务 
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: ClusterIP          # ClusterIP / NodePort / LoadBalancer
  selector:
    app: myapp
  ports:
    - protocol: TCP
      port: 80              # Service 端口
      targetPort: 8080      # Pod 端口

Ingress 资源定义

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - example.com
      secretName: tls-secret    # HTTPS 证书
  rules:
    - host: example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
          - path: /web
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
  • Ingress 资源：定义路由规则（域名、路径 → Service 的映射）
  • Ingress Controller：实际执行规则的组件（Nginx Ingress、Traefik、Istio Gateway）
  • Ingress 是 Service 的"前端"，提供 L7（HTTP/HTTPS）路由、TLS 终止、域名分流

HPA 自动扩缩容

HPA 工作原理

Metrics Server
采集 Pod 指标
→
HPA Controller
计算期望副本数
→
调整 ReplicaSet
扩容 / 缩容
# 期望副本数 = ceil(当前副本数 * (当前指标值 / 期望指标值))
# 例：3 * (80% / 50%) = 3 * 1.6 = 5

HPA 配置示例

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60    # CPU 使用率目标 60%
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70    # 内存使用率目标 70%
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 缩容稳定窗口 5 分钟
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60             # 每分钟最多缩容 10%
  • CPU/Memory：基于资源使用率的自动扩缩容
  • Custom Metrics：基于自定义指标（如 QPS、队列长度）
  • External Metrics：基于外部系统指标（如 Kafka 消费延迟）
  • behavior 字段控制扩缩容的速度和稳定性

PV 和 PVC

# PV - 管理员定义存储资源
apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce        # 单节点读写
  storageClassName: standard
  hostPath:
    path: /data/pv

---
# PVC - 用户申请存储
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard

StorageClass 动态供应

  • 手动创建 PV 太繁琐，StorageClass 支持动态供应
  • 用户创建 PVC 时指定 StorageClass，系统自动创建 PV
  • 不同 StorageClass 对应不同的存储后端（AWS EBS、Ceph、NFS 等）
  • 可设置 default StorageClass，未指定时自动使用
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iopsPerGB: "10"
reclaimPolicy: Retain       # Delete / Retain
volumeBindingMode: WaitForFirstConsumer

第二部分：场景化讲解

ConfigMap 和 Secret

ConfigMap

  • 存储非敏感配置数据
  • 数据以明文存储
  • 可挂载为文件或环境变量
  • 支持热更新（挂载方式）
  • 大小限制 1MB

Secret

  • 存储敏感数据（密码、Token）
  • 数据以 Base64 编码存储（非加密）
  • 可挂载为文件或环境变量
  • 支持加密存储（需配置 EncryptionConfiguration）
  • 大小限制 1MB

使用方式

# 创建 ConfigMap
kubectl create configmap my-config --from-literal=key1=value1

# 创建 Secret
kubectl create secret generic my-secret --from-literal=password=abc123

# Pod 中使用（环境变量方式）
env:
  - name: CONFIG_KEY
    valueFrom:
      configMapKeyRef:
        name: my-config
        key: key1
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: my-secret
        key: password

# Pod 中使用（挂载文件方式）
volumes:
  - name: config-vol
    configMap:
      name: my-config
volumeMounts:
  - name: config-vol
    mountPath: /etc/config
Secret 默认只做 Base64 编码，不是加密！必须配合 EncryptionConfiguration 或外部密钥管理（Vault）才能保证安全性。Base64 编码可以轻松解码。

网络模型

Kubernetes 网络三大原则

  • 每个 Pod 拥有独立 IP 地址
  • 所有 Pod 可以不经过 NAT 直接互相通信
  • 节点上的代理（如 kube-proxy）可以与该节点上所有 Pod 通信

CNI（容器网络接口）

CNI 插件特点适用场景
CalicoBGP 路由、NetworkPolicy 支持好生产首选，大规模集群
Flannel简单、Overlay 网络（VXLAN）小规模集群、快速上手
CiliumeBPF 技术、高性能、安全策略高性能需求、可观测性
Weave多播、加密简单部署、小集群

Service 实现：iptables vs IPVS

iptables 模式（默认）

  • kube-proxy 维护 iptables 规则
  • Service 数量多时规则线性增长
  • 性能一般，适合中小规模集群
  • 随机负载均衡（等概率选择后端）

IPVS 模式

  • 使用 Linux 内核 IPVS 模块
  • 哈希表查找，性能优于 iptables
  • 支持多种负载均衡算法（rr / lc / sh）
  • 适合大规模集群（数千 Service）

第三部分：模拟面试

Kubernetes 的架构是怎样的？Master 和 Node 各有哪些组件？
参考：Master 节点包含：API Server（集群入口，提供 RESTful API）、etcd（分布式 KV 存储，保存集群状态）、Scheduler（为 Pod 选择最优 Node）、Controller Manager（运行各种控制器确保实际状态趋向期望状态）。Node 节点包含：kubelet（节点代理，管理 Pod 生命周期）、kube-proxy（网络代理，实现 Service 负载均衡）、Container Runtime（容器运行时，如 containerd）。
Pod 的三种探针分别是什么？各有什么作用？
参考：Liveness Probe 检测容器是否存活，失败则重启容器。Readiness Probe 检测容器是否就绪接收流量，失败则从 Service Endpoints 中移除。Startup Probe 检测容器是否启动完成，用于启动慢的应用（如 Java），在它成功之前 Liveness 和 Readiness 不会生效。三种探针都支持 HTTP GET、TCP Socket、Exec 命令三种检测方式。
Deployment 和 StatefulSet 有什么区别？
参考：Deployment 用于无状态应用，Pod 无固定标识和存储，可随意替换和扩展。StatefulSet 用于有状态应用，Pod 有稳定的网络标识（mysql-0、mysql-1）和持久存储（每个 Pod 绑定固定 PVC），支持有序部署和删除。StatefulSet 需要配合 Headless Service 实现 DNS 解析。数据库、Zookeeper 等需要有状态身份的应用用 StatefulSet。
Service 的四种类型分别是什么？
参考：ClusterIP（默认）分配集群内部虚拟 IP，仅集群内可访问。NodePort 在每个节点开放 30000-32767 端口，外部可通过 NodeIP:NodePort 访问。LoadBalancer 使用云厂商负载均衡器，适合云环境生产。ExternalName 将 Service 映射到外部域名（CNAME），用于访问集群外部服务。Ingress 在 Service 之上提供 L7 路由、TLS 终止和域名分流。
什么是 HPA？它是如何工作的？
参考：HPA（Horizontal Pod Autoscaler）根据指标自动调整 Pod 副本数。工作流程：Metrics Server 采集 Pod 的资源指标，HPA Controller 定期（默认 15 秒）检查指标，计算期望副本数（当前副本数 x 当前指标/目标指标），调整 ReplicaSet 的副本数。支持 CPU、Memory 和自定义指标。通过 behavior 字段可控制扩缩容的速度和稳定性窗口。
参考：PV（PersistentVolume）是管理员定义的存储资源，描述存储的容量、访问模式、后端类型。PVC（PersistentVolumeClaim）是用户对存储的申请，声明需要多大容量和什么访问模式。Kubernetes 自动将匹配的 PV 绑定到 PVC。StorageClass 实现动态供应：定义存储的"类别"（如 SSD、HDD），用户创建 PVC 时指定 StorageClass，系统自动创建 PV，无需管理员手动干预。
参考：RBAC（基于角色的访问控制）通过 Role/ClusterRole 定义权限（对哪些资源可以执行哪些操作），通过 RoleBinding/ClusterRoleBinding 将角色绑定到用户/组/ServiceAccount。Role 和 RoleBinding 是 Namespace 级别的，只在特定命名空间内生效。ClusterRole 和 ClusterRoleBinding 是集群级别的，对整个集群生效。典型场景：为 CI/CD 的 ServiceAccount 绑定特定命名空间的部署权限。
参考：kube-proxy 监听 API Server 的 Service 和 Endpoints 变化，在节点上维护网络规则。iptables 模式：为每个 Service 创建 iptables 规则，随机选择后端 Pod，Service 多时规则线性增长影响性能。IPVS 模式：使用 Linux 内核 IPVS 模块，哈希表查找性能更好，支持多种负载均衡算法（轮询、最少连接、源地址哈希），适合大规模集群。
