ZAB 协议

ZAB 协议两大模式

崩溃恢复（选举模式）

  • 集群启动或 Leader 故障时进入
  • 所有节点进入 Looking 状态
  • 通过投票选出新 Leader
  • 过半节点同意才能当选
  • 新 Leader 等待 Follower 同步数据
  • 同步完成后进入消息广播模式

消息广播（正常模式）

  • Leader 正常工作时进入
  • 写请求统一由 Leader 处理
  • Leader 生成 Proposal 发给 Follower
  • Follower 返回 ACK 确认
  • 过半 ACK 后 Leader 发送 COMMIT
  • 类似 2PC 但无需全部节点确认

ZAB 消息广播流程

ZAB 消息广播（类 2PC）
Client 发送写请求
→
Leader 生成 Proposal
分配全局 zxid
→
广播给 Follower
→
过半 ACK
→
Leader 发送 COMMIT
  • Leader 为每个事务分配全局唯一的 zxid（64 位：高 32 位 epoch + 低 32 位计数器）
  • Proposal 包含 zxid 和数据，按 zxid 顺序发送给 Follower
  • Follower 收到 Proposal 后写入本地日志，返回 ACK
  • Leader 收到过半 ACK 后发送 COMMIT，所有节点提交事务
  • 只须过半确认而非全部，因此允许少数节点故障
ZAB 与 Paxos/Raft 的关键区别：ZAB 保证消息的因果顺序（因果一致性），zxid 全局递增保证了顺序性。

选举机制

FastLeaderElection 算法

// 选举投票格式：(voteId, voteZxid, voteEpoch)
// voteId: 候选节点的 myid
// voteZxid: 候选节点的最新事务 ID
// voteEpoch: 当前轮次

// 选举规则（优先级从高到低）：
// 1. epoch 大的胜出（新轮次优先）
// 2. zxid 大的胜出（数据最新的优先）
// 3. myid 大的胜出（ID 大的优先）

// 选举流程（3 节点集群首次启动）：
// 1. 节点 A(myid=1) 启动，投自己一票 (1,0,0)
// 2. 节点 B(myid=2) 启动，投自己一票 (2,0,0)
// 3. 节点 A 收到 B 的票，比较：B.myid(2) > A.myid(1)
//    A 改投 B，A 的票变为 (2,0,0)
// 4. B 收到 A 的票，发现自己的票已有 2 票（过半）
//    B 当选 Leader，A 变为 Follower
// 5. 节点 C(myid=3) 启动，发现已有 Leader，直接成为 Follower

节点状态

状态含义
LOOKING正在寻找 Leader，发起投票
FOLLOWING已发现 Leader，作为 Follower 跟随
LEADING已当选 Leader，负责协调
OBSERVINGObserver 节点，不参与投票
面试重点：选举需要过半节点参与才能成功。因此 2n+1 节点的集群最多容忍 n 个节点故障。推荐奇数节点（3/5/7）。

Watcher 机制

Watcher 核心特点

  • 一次性触发：Watcher 被触发后自动移除，需要重新注册
  • 有序性：客户端先收到 Watcher 通知，再读取到新数据
  • 轻量级：WatchEvent 只包含通知类型和节点路径，不包含数据
  • 异步通知：服务端通过异步线程发送 Watcher 通知
// Watcher 事件类型
enum EventType {
    NodeCreated,        // 节点创建
    NodeDeleted,        // 节点删除
    NodeDataChanged,    // 节点数据变更
    NodeChildrenChanged // 子节点变更
}

// 注册方式（三种）
// 1. getData() - 监听节点数据变更
// 2. exists() - 监听节点创建/删除/数据变更
// 3. getChildren() - 监听子节点变更

// Java API 示例
zk.exists("/config/db", new Watcher() {
    @Override
    public void process(WatchedEvent event) {
        if (event.getType() == Event.EventType.NodeDataChanged) {
            byte[] data = zk.getData("/config/db", this, null);
            // 重新注册 Watcher 并处理新数据
        }
    }
});

Curator 的 NodeCache / TreeCache

  • NodeCache：封装了 Watcher 的自动重注册，监听单个节点的变更
  • PathChildrenCache：监听子节点的变更，自动维护子节点列表
  • TreeCache：监听整棵子树的变更（NodeCache + PathChildrenCache 的结合）
// Curator NodeCache 示例（自动重注册 Watcher）
NodeCache nodeCache = new NodeCache(client, "/config/db");
nodeCache.getListenable().addListener(() -> {
    byte[] data = nodeCache.getCurrentData().getData();
    // 自动重注册，无需手动处理
});
nodeCache.start();

会话管理

Session 生命周期

Session 状态流转
CONNECTING
正在连接
→
CONNECTED
已连接
→
RECONNECTING
重连中
→
CLOSED
已关闭
  • Session 超时时间由客户端设置（默认 30 秒），不能小于 2 倍的 tickTime
  • 客户端定期向 Server 发送心跳（PING）维持 Session，默认间隔为超时时间的 1/3
  • Server 超过 Session 超时时间未收到心跳，会删除该 Session 的所有临时节点
  • 客户端断开后在 Session 超时时间内重连到其他 Server，Session 仍然有效
Session 临时窗口（Session Timeout Window）：客户端断开后，Server 不会立即删除临时节点，而是等待 Session 超时。这为重连提供了缓冲时间。

分布式锁

临时顺序节点实现公平锁

// 基于 Curator 的分布式锁实现
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order-lock");

if (lock.acquire(10, TimeUnit.SECONDS)) {
    try {
        // 执行业务逻辑
    } finally {
        lock.release();
    }
}

// 底层实现原理：
// 1. 在 /locks/order-lock 下创建临时顺序节点
//    /locks/order-lock/_c_uuid1_0000000001
//    /locks/order-lock/_c_uuid2_0000000002
//    /locks/order-lock/_c_uuid3_0000000003
// 2. 获取所有子节点，判断自己是否是最小的
// 3. 如果是最小的 → 获取锁
// 4. 如果不是 → Watch 比自己小一号的节点
// 5. 当 Watch 的节点删除时（释放锁），收到通知，再次判断
// 效果：公平有序，避免惊群效应

读写锁

// Curator 读写锁
InterProcessReadWriteLock rwLock = new InterProcessReadWriteLock(client, "/locks/rw");
// 读锁（共享）
InterProcessMutex readLock = rwLock.readLock();
// 写锁（独占）
InterProcessMutex writeLock = rwLock.writeLock();

// 读操作：多个读者可同时进行
readLock.acquire();
try { /* 读取数据 */ } finally { readLock.release(); }

// 写操作：独占
writeLock.acquire();
try { /* 修改数据 */ } finally { writeLock.release(); }

Zookeeper 集群

集群角色与过半机制

  • Leader：处理所有写请求，协调事务顺序
  • Follower：处理读请求，参与投票和事务确认
  • Observer：处理读请求，不参与投票（用于扩展读能力）
// 集群配置 zoo.cfg
tickTime=2000
initLimit=10
syncLimit=5
dataDir=/var/lib/zookeeper
server.1=zk1:2888:3888
server.2=zk2:2888:3888
server.3=zk3:2888:3888
# Observer 配置
server.4=zk4:2888:3888:observer

// 端口说明：
// 2888 - Follower 与 Leader 通信端口
// 3888 - 选举端口

// 过半机制（Quorum）：
// 3 节点集群 → 至少 2 节点存活
// 5 节点集群 → 至少 3 节点存活
// 2n+1 节点 → 最多容忍 n 节点故障
Observer 的作用：不参与写操作的投票，因此不影响写性能。增加 Observer 可以扩展读能力而不影响集群的写性能和选举速度。

第三部分：模拟面试

请介绍 Zookeeper 的数据模型，ZNode 有哪些类型？
参考：Zookeeper 使用树形数据模型，每个节点称为 ZNode。ZNode 有四种类型：1）持久节点 — 创建后一直存在，需手动删除，适合存储配置信息；2）临时节点 — 与客户端 Session 绑定，Session 断开后自动删除，适合服务注册；3）持久顺序节点 — 持久 + 自增序号，适合全局 ID 生成；4）临时顺序节点 — 临时 + 自增序号，适合分布式锁（公平锁）。每个 ZNode 可以存储数据（最大 1MB）和子节点，还有版本号用于乐观锁控制。
ZAB 协议的工作流程是什么？与 Paxos 有什么区别？
参考：ZAB（Zookeeper Atomic Broadcast）有两个模式：崩溃恢复和消息广播。消息广播类似 2PC：Leader 为写请求生成 Proposal（带全局递增 zxid），广播给 Follower，收到过半 ACK 后发送 COMMIT。崩溃恢复：Leader 故障后所有节点进入 LOOKING 状态，通过 FastLeaderElection 选出新 Leader（比较 epoch > zxid > myid），新 Leader 确保所有 Follower 数据同步后切换到消息广播模式。与 Paxos 的区别：ZAB 保证消息的因果顺序（通过 zxid），Paxos 不保证顺序；ZAB 有明确的 Leader 角色，Paxos 的 proposer 可以是任意节点。
Zookeeper 的选举机制是如何工作的？为什么推荐奇数节点？
参考：Zookeeper 使用 FastLeaderElection 算法。每个节点投票格式为 (myid, zxid, epoch)，选举规则优先级：epoch > zxid > myid。流程：节点启动进入 LOOKING 状态并投自己一票，将投票广播给其他节点；收到其他节点的投票后比较，如果对方更优则改票并广播；当一个节点获得过半投票时当选 Leader。推荐奇数节点的原因：3 节点和 4 节点的容错能力相同（都只能容忍 1 个节点故障），但 3 节点的投票确认开销更小（2 vs 2 过半，但 4 节点多一个节点的资源消耗）。
Zookeeper 的 Watcher 机制有什么特点？为什么是一次性触发？
参考：Watcher 的核心特点：1）一次性触发 — 触发后自动移除，需要重新注册；2）有序性 — 客户端先收到 Watcher 通知，再读到新数据；3）轻量级 — WatchEvent 只包含事件类型和路径，不包含数据。一次性触发的设计原因：减少服务端存储压力，避免大量 Watcher 累积；简化服务端通知逻辑，不需要维护复杂的订阅关系。实际使用中通常在 Watcher 回调中重新注册 Watcher。Curator 的 NodeCache 封装了自动重注册逻辑，简化了使用。
如何用 Zookeeper 实现分布式锁？临时顺序节点的优势是什么？
参考：基于临时顺序节点实现公平锁的流程：1）在锁节点下创建临时顺序节点；2）获取所有子节点，判断自己是否是最小的；3）是最小的则获取锁成功；4）不是最小的则 Watch 比自己小一号的节点；5）Watch 的节点删除时收到通知，重新判断。临时顺序节点的优势：临时性保证 Session 断开自动释放锁（避免死锁）；顺序性避免惊群效应（只 Watch 前一个节点而非所有节点），实现公平有序获取。Curator 的 InterProcessMutex 封装了这个逻辑。
Zookeeper 的 Session 机制是什么？断连后临时节点会怎样？
参考：Session 是客户端与 Zookeeper 服务端之间的会话。客户端连接时创建 Session，分配 SessionID。客户端定期发送心跳（PING）维持 Session，默认间隔为 Session 超时时间的 1/3。如果客户端断开连接，在 Session 超时时间内重连到其他 Server，Session 仍然有效，临时节点不会被删除。超过 Session 超时时间未重连，Server 会删除该 Session 的所有临时节点。因此 Session 超时时间的设置很关键：太短容易误删，太长故障感知慢。建议设置为 10~30 秒。
Zookeeper 集群中的 Observer 节点有什么作用？
参考：Observer 是 Zookeeper 的一种特殊角色，只处理读请求，不参与 Leader 投票和事务确认。Observer 的作用：1）扩展读能力 — 增加 Observer 不影响写性能和选举速度；2）跨机房部署 — Observer 可以部署在远程机房，读请求就近处理，不影响主机房的写性能。Observer 从 Leader 同步数据（与 Follower 相同），但不参与过半确认。典型用法：3 节点集群（1 Leader + 2 Follower）保证写可用性，再加 N 个 Observer 扩展读能力。
在实际项目中，Zookeeper 作为配置中心和注册中心各有什么优缺点？
参考：配置中心：优点是 Watcher 机制可实时感知配置变更，ZAB 协议保证强一致性。缺点是 Watcher 一次性触发需重新注册，数据量有限（1MB/节点），大量配置管理不方便。注册中心：优点是临时节点天然支持服务注册（断连自动删除），Watch 机制支持服务发现。缺点是 CP 模型在 Leader 选举期间不可用，大规模实例下性能不如 AP 系统（如 Nacos）。现在很多项目已从 Zookeeper 迁移到 Nacos/Consul 等更现代的方案。
