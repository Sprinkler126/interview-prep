核心组件

组件职责
Prometheus Server核心组件，负责指标采集、存储和查询。包含 Retrieval（拉取指标）、TSDB（时序数据库）、HTTP API
Pushgateway接收短期任务（如 CronJob）推送的指标，供 Prometheus 拉取
Alertmanager接收告警通知，支持分组、抑制、静默、路由
Exporters将第三方系统的指标转换为 Prometheus 格式（node_exporter、mysqld_exporter 等）
Service Discovery自动发现监控目标（K8s、Consul、文件等）

指标类型

四种指标类型

类型说明特点典型场景
Counter 计数器 只增不减（除非重启），单调递增 请求总数、错误数、处理字节数
Gauge 仪表盘 可增可减，反映当前值 CPU 使用率、内存使用、温度、队列长度
Histogram 直方图 对数据分桶统计，可计算分位数 请求延迟分布、响应大小分布
Summary 摘要 客户端计算分位数，不可聚合 请求延迟（客户端计算 p99）

Histogram vs Summary

Histogram

  • 服务端计算分位数（histogram_quantile）
  • 可以跨实例聚合
  • 数据量较大（多个 bucket）
  • 推荐使用

Summary

  • 客户端计算分位数
  • 不可跨实例聚合
  • 数据量较小
  • 适合单实例监控

Pull vs Push 模式

Pull 模式（默认）

  • Prometheus 主动拉取目标的 /metrics
  • 目标不需要知道 Prometheus 地址
  • 便于集中管理和监控目标健康
  • 适合长期运行的服务

Push 模式（Pushgateway）

  • 应用主动推送指标到 Pushgateway
  • Prometheus 再从 Pushgateway 拉取
  • 适合短期任务（CronJob、Batch Job）
  • 注意：可能丢失指标（Pushgateway 不持久化）
不要滥用 Pushgateway。长期运行的服务应使用 Pull 模式直接暴露 /metrics 端点。Pushgateway 适合无法长期运行的批处理任务。Pushgateway 重启后指标会丢失。

PromQL 查询

常用函数

函数用途示例
rate() 计算 Counter 在时间窗口内的每秒平均增长率 rate(http_requests_total[5m])
increase() 计算 Counter 在时间窗口内的总增量 increase(http_requests_total[1h])
irate() 基于最近两个数据点的瞬时增长率 irate(http_requests_total[5m])
histogram_quantile() 从 Histogram 计算分位数 histogram_quantile(0.99, rate(http_duration_bucket[5m]))
sum() 求和 sum(rate(http_requests_total[5m])) by (method)
avg() 平均值 avg(cpu_usage_percent) by (instance)
topk() 取 Top K topk(5, rate(http_requests_total[5m]))
label_replace() 标签替换/提取 用于标签维度转换

PromQL 实战示例

# 请求 QPS（按状态码分组）
sum(rate(http_requests_total[5m])) by (status_code)

# P99 延迟
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# CPU 使用率
100 - (avg by(instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# 内存使用率
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100

# 磁盘使用率
(1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100

# 错误率
sum(rate(http_requests_total{status_code=~"5.."}[5m])) / sum(rate(http_requests_total[5m])) * 100

告警规则与 Alertmanager

告警规则定义

# prometheus.yml 中定义告警规则
groups:
  - name: example
    rules:
      # 高错误率告警
      - alert: HighErrorRate
        expr: |
          sum(rate(http_requests_total{status_code=~"5.."}[5m]))
          / sum(rate(http_requests_total[5m])) > 0.05
        for: 5m              # 持续 5 分钟才触发
        labels:
          severity: critical
        annotations:
          summary: "高错误率告警: {{ $value | humanizePercentage }}"
          description: "服务 {{ $labels.service }} 错误率超过 5%"

      # 实例宕机告警
      - alert: InstanceDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "实例 {{ $labels.instance }} 宕机"

Alertmanager 功能

功能说明示例
分组（Grouping）将相关告警合并为一条通知同一服务的多个实例宕机合并
抑制（Inhibition）高优先级告警抑制低优先级网络故障时抑制下游服务告警
静默（Silence）临时屏蔽特定告警维护窗口期间静默告警
路由（Route）根据标签路由到不同接收者critical → 电话，warning → 钉钉

第二部分：场景化讲解

存储（TSDB / 远程存储）

本地存储（TSDB）

  • Prometheus 内置时序数据库（TSDB），基于 LSM-Tree 结构
  • 数据按 2 小时为一个 Block 存储，每个 Block 包含 chunks（数据）和 index（索引）
  • 默认保留 15 天，可通过 --storage.tsdb.retention.time 调整
  • 适合单机短期存储，不适合长期数据保留

设计动机：为什么 Prometheus 单机 TSDB 不做集群？

设计起点：Prometheus 团队坚持"single-machine, reliable"——单机简单可靠，集群引入分布式复杂度（一致性、网络分区）违背其"运维简单"哲学。长期存储和水平扩展交给 Thanos/VictoriaMetrics 等远程方案。这是典型的"做一件事并做好"的 Unix 哲学。

✅ 单机 TSDB 的收益

  • 无分布式协调，运维简单（一个二进制即可）
  • 本地磁盘查询低延迟（无网络跳数）
  • 高可用靠双实例 + 远程存储（而非集群）
  • 适合单集群/单数据中心监控

代价与解法

  • ❌ 单机存储上限 → Thanos 上传 S3 长期存储
  • ❌ 单机吞吐上限 → 分片（federation/多实例）
  • ❌ 跨集群查询 → Thanos Query / Mimir 全局视图
  • ❌ 高可用 → 部署两个 Prometheus + Alertmanager 集群
面试要点：Prometheus 的"单机论"是刻意设计，不是缺陷。理解这点能解释为什么有 Thanos/VictoriaMetrics/Mimir 这么多远程存储方案——它们都是在不破坏 Prometheus 简单性的前提下补足水平扩展。

2.1b 监控方法论 — USE / RED / 四黄金信号

设计起点：监控什么指标才有意义？

新人常犯的错是"什么指标都监控"，仪表盘堆满却抓不住重点。监控方法论告诉你该看哪些核心指标——这是 SRE 面试的高频考点。

三大监控方法论
方法论对象核心指标记忆口诀
USE 方法 (Utilization/Saturation/Errors) 资源（硬件/基础设施） 使用率 / 饱和度 / 错误 CPU 利用率、磁盘 IO 队列长度、网卡丢包数
RED 方法 (Rate/Errors/Duration) 服务（用户请求路径） 请求率 / 错误率 / 延迟 QPS、5xx 比例、P99 延迟
四黄金信号 (Google SRE) 服务（综合） 延迟 / 流量 / 错误 / 饱和度 RED + 饱和度，最全面

应用场景对照

监控对象用哪个具体指标
CPU / 内存 / 磁盘 / 网络USE使用率%、IO 队列、丢包
HTTP API 服务REDQPS、错误率、P99
数据库USE + RED连接池使用率 + 慢查询 + QPS
消息队列四黄金生产/消费速率 + 积压(饱和度) + 错误 + 延迟
易错点：延迟要分成功和失败统计。失败请求的延迟往往很高（如超时），混在一起会让"成功延迟"看起来很差。Google SRE 强调：request_duration{status="200"} 和 {status="5xx"} 分开看。
面试金句：资源用 USE，服务用 RED，综合用四黄金信号。这是 SRE 给监控做减法的标准框架，能体现你不只是"堆指标"而是"懂监控设计"。

与 Grafana 集成

集成步骤

  1. 在 Grafana 中添加 Prometheus 作为数据源（Configuration → Data Sources → Add → Prometheus）
  2. 填写 Prometheus Server 地址（如 http://prometheus:9090）
  3. 创建 Dashboard，添加 Panel
  4. 在 Panel 中使用 PromQL 查询
  5. 推荐导入社区 Dashboard（如 Node Exporter Full ID: 1860）
Grafana 官方提供大量社区 Dashboard 模板，可在 grafana.com/grafana/dashboards 搜索导入，避免从零创建。

第三部分：模拟面试

Prometheus 的架构是怎样的？各组件有什么作用？
参考：Prometheus 采用 Pull 模式采集指标。核心组件：Prometheus Server 负责指标拉取、存储（TSDB）和查询（PromQL）。Pushgateway 接收短期任务推送的指标。Alertmanager 接收告警并处理分组、抑制、静默、路由。Exporters 将第三方系统指标转换为 Prometheus 格式。Service Discovery 自动发现监控目标。Grafana 负责可视化展示。
Prometheus 的四种指标类型分别是什么？Histogram 和 Summary 有什么区别？
参考：Counter（计数器，只增不减，如请求总数）、Gauge（仪表盘，可增可减，如 CPU 使用率）、Histogram（直方图，分桶统计，可计算分位数）、Summary（摘要，客户端计算分位数）。Histogram 和 Summary 的核心区别：Histogram 在服务端计算分位数，可以跨实例聚合，推荐使用；Summary 在客户端计算，不可聚合，适合单实例。
参考：rate() 计算时间窗口内每秒平均增长率，结果平滑，适合告警规则和趋势图。irate() 基于最近两个数据点计算瞬时增长率，灵敏度高，适合观察短期波动。告警和趋势分析用 rate()，仪表盘实时展示用 irate()。一般推荐 rate()，因为 irate() 容易被毛刺干扰。
什么是 Prometheus 的 Pull 模式？和 Push 模式有什么区别？
参考：Pull 模式是 Prometheus 主动从目标的 /metrics 端点拉取指标，目标只需暴露 HTTP 端点，不需要知道 Prometheus 地址。优势：集中管理、便于监控目标健康。Push 模式是应用主动推送指标到 Pushgateway，适合短期任务（如 CronJob），因为任务结束前 Prometheus 可能来不及拉取。长期运行的服务应使用 Pull 模式。
参考：Prometheus 内置 TSDB 是单机存储，默认保留 15 天，不支持水平扩展和长期保留。解决方案：1）Thanos：提供全局查询、长期存储（对象存储如 S3）、降采样；2）VictoriaMetrics：高性能时序数据库，兼容 PromQL，资源占用更低；3）Remote Write：将数据写入远程存储，Prometheus 只负责采集。
参考：分组（Grouping）将相关告警合并为一条通知，避免告警风暴（如同一服务多个实例同时宕机只发一条）。抑制（Inhibition）当高优先级告警触发时，自动抑制相关的低优先级告警（如网络故障时抑制下游服务告警）。静默（Silence）在维护窗口等场景下临时屏蔽特定告警，到期自动恢复。
参考：Exporter 是将第三方系统指标转换为 Prometheus 格式的组件。它暴露一个 /metrics HTTP 端点，返回 Prometheus 文本格式的指标。自定义步骤：1）使用 Prometheus 客户端库（如 prometheus/client_golang）；2）实现 Collector 接口的 Collect() 方法；3）注册指标（Counter/Gauge/Histogram）；4）暴露 HTTP 端点。也可以使用 textfile Collector 从文件读取指标。
