第一部分：技术原理

共识问题定义

什么是共识问题

共识问题是指在分布式系统中，多个节点对某个值（提案）达成一致的过程。共识算法需要满足以下四个性质：

性质定义说明
一致性（Agreement）所有正确的节点决定相同的值不会出现不同节点决定不同值的情况
合法性（Validity）决定的值必须是某个节点提出的不能凭空产生值
终止性（Termination）所有正确的节点最终都能做出决定不会无限期等待（活性保证）
容错性（Fault Tolerance）系统在部分节点故障时仍能达成共识CFT: N/2+1 正常；BFT: 2N/3+1 正常
FLP 不可能定理证明：在异步系统中，只要有 1 个节点可能宕机，就不存在确定性算法能保证共识一定达成。实际共识算法通过引入随机性或超时机制绕过这个限制。

共识算法分类

崩溃容错（CFT）

  • 节点只会宕机或超时，不会发送错误消息
  • 需要 N/2+1 个正常节点
  • 代表：Paxos、Raft、ZAB
  • 适用于可信环境（企业内部）

拜占庭容错（BFT）

  • 节点可能发送任意错误消息（含恶意行为）
  • 需要 2N/3+1 个正常节点
  • 代表：PBFT、PoW、PoS
  • 适用于不可信环境（区块链）

Paxos 算法

Paxos 角色

  • Proposer（提案者）：发起提案，提出一个值
  • Acceptor（接受者）：对提案进行投票，决定是否接受
  • Learner（学习者）：学习被选定的值，不参与投票

一个节点可以同时担任多个角色。共识的达成需要多数派（Quorum）的 Acceptor 接受同一个提案。

Basic Paxos 流程

阶段1a: Prepare
Proposer 发送 Prepare(n)
n 为提案编号（全局唯一递增）
→
阶段1b: Promise
Acceptor 承诺不再接受编号 < n 的提案
返回已接受的最大编号提案
→
阶段2a: Accept
Proposer 发送 Accept(n, value)
value = 已接受提案的值 或 自己的值
→
阶段2b: Accepted
Acceptor 接受提案
多数派接受后值被选定
Basic Paxos 的问题：活锁（两个 Proposer 交替提出更高编号的提案，导致永远无法达成共识）。Multi-Paxos 通过选出 Leader 解决此问题。

Multi-Paxos 优化

  • 选出 Leader：通过一轮完整的 Paxos 选出稳定的 Leader，后续所有提案由 Leader 发起
  • 跳过 Prepare：Leader 确定后，省略 Prepare 阶段，直接进入 Accept
  • 日志复制：每个日志槽位（log slot）运行一次 Paxos，实现连续的值复制
  • 效果：从两次 RPC 减少到一次 RPC（仅 Accept），大幅提升吞吐

Paxos 设计哲学 — 为什么是这个机制

Paxos 要解决什么问题？

设计起点：在异步网络中，消息可能延迟、丢失、乱序，节点可能宕机重启。在这样的环境下，如何让一群节点对一个值达成不可反悔的一致？

异步网络
延迟/丢失/乱序
+
节点宕机重启
可能恢复也可能永久失效
+
并发提案
多个 Proposer 同时发起
→
如何达成一致且不可变的决定？

FLP 不可能定理告诉我们：异步网络中不可能同时满足安全性 + 终止性 + 容错性。Paxos 的选择是：保证安全性（绝不选错值），放松终止性（允许活锁，实践中靠 Leader 解决）。

两阶段 Prepare/Accept 背后的哲学

设计决策解决的问题哲学
提案编号 n（全局唯一递增）区分新旧提案，打破"先后"歧义用序号替代时间（逻辑时钟思想）
Prepare 阶段：问"你们见过更大的提案吗？"抢占优先权，阻止旧提案被接受先锁后写：多数派 Promise = 获得锁
Promise 返回已接受的最大提案新 Proposer 必须沿用已选定的值尊重历史：已被多数接受的值不能被覆盖
多数派 Quorum容忍少数节点故障两个多数派必相交 → 不可能两个值都通过
Accept 阶段：带 n 和 value 请求接受正式写入并确认Prepare 已铺路，Accept 只需多数同意

为什么多数派交叉保证安全性？

Quorum 交集性质 — Paxos 安全性的数学基石
   5 个 Acceptor: A1 A2 A3 A4 A5

   提案X获多数派: {A1,A2,A3}          提案Y获多数派: {A3,A4,A5}
        ┌──┬──┬──┐                            ┌──┬──┬──┐
        │A1│A2│A3│                            │A3│A4│A5│
        └──┴──┴──┘                            └──┴──┴──┘
              └──────── 交集 A3 ────────┘
              ↑ A3 一定见过 X 和 Y，只会接受编号更大的
              → 不可能 X 和 Y 都被多数派接受
核心洞察：任何两个多数派集合必有交集（N=5 时交集至少 1 个）。交集节点遵守"只接受编号更大的提案"承诺，因此一旦某值被多数派选定，后续任何被选定的值必然与之相同——这就是安全性的保证。

Paxos 的"难"与 Raft 的"易" — 为什么要有 Raft？

Paxos 的困境

  • 只对单个值达成共识，工程上需要 Multi-Paxos 扩展
  • Multi-Paxos 没有标准实现，细节留给工程补全
  • 角色/流程抽象，难以理解和实现
  • 缺乏明确的 Leader 选举和日志模型
  • "正确但难懂"——Google Chubby 作者都说难

Raft 的设计目标

  • 可理解性优先：为教学和工程而设计
  • 把共识拆成三个清晰子问题：Leader 选举、日志复制、安全性
  • 强 Leader 模型：所有请求经 Leader，简化心智模型
  • 明确的日志模型和状态转换
  • "同样正确但易懂易实现"
面试金句：Raft 不是"更好的 Paxos"，而是"为可理解性重新设计的 Paxos"——安全性等价，但通过强 Leader 和问题分解大幅降低了实现和理解门槛。这是工程哲学的差异，而非算法能力的差异。

Raft 协议

Raft 三种角色

角色职责数量
Leader处理所有客户端请求，管理日志复制同一时刻只有一个
Follower被动接收 Leader 的日志和心跳多数节点
Candidate竞选 Leader 的中间状态选举期间临时角色

Leader 选举详解

  1. Follower 在选举超时（150~300ms 随机）内未收到心跳，转变为 Candidate
  2. Candidate 自增 Term（任期号），先给自己投票，再向所有节点发 RequestVote(term, lastLogIndex, lastLogTerm)
  3. 节点投票规则：每个 Term 只投一票（先到先得），且 Candidate 的日志不能比自己旧
  4. 获得多数派投票 → 成为 Leader；发现更高 Term → 退回 Follower
  5. 票数分裂（无多数派）→ 等待随机超时后重新选举
// 投票决策伪代码
function handleRequestVote(candidateTerm, candidateLastLogIdx, candidateLastLogTerm):
    if candidateTerm < currentTerm: return false
    if candidateTerm > currentTerm: stepDown(candidateTerm)
    if votedFor == null OR votedFor == candidateId:
        // 选举限制：候选人的日志至少和自己一样新
        if candidateLastLogTerm > lastLogTerm:
            return true
        if candidateLastLogTerm == lastLogTerm AND candidateLastLogIdx >= lastLogIndex:
            return true
    return false

应用到状态机
  • 日志条目：(term, index, command) 三元组，term 是 Leader 任期号
  • 提交条件：该条目被复制到多数节点，且当前 Leader 的最新条目已提交（Raft 安全性保证）
  • 日志匹配：AppendEntries 携带 prevLogIndex 和 prevLogTerm，Follower 校验一致性
  • 日志修复：Follower 日志不一致时，Leader 递减 nextIndex 重试直到匹配

Raft 安全性保证

  • 选举安全：每个 Term 最多一个 Leader（一 Term 一票制）
  • 日志匹配：如果两个日志在某个 index 的 term 相同，则该 index 之前所有条目都相同
  • Leader 完整性：已提交的日志条目一定出现在所有后续 Leader 的日志中（选举限制保证）
  • 状态机安全：如果一个节点在某个 index 已提交，其他节点在同一 index 不会提交不同的值

成员变更与日志压缩

成员变更

  • 单步变更：每次只增减一个节点，新旧配置的 Quorum 一定有交集
  • 联合共识：先切换到中间配置（C_old + C_new），再切换到新配置
  • 成员变更也通过日志复制实现

日志压缩（Snapshot）

  • 定期将已提交的日志压缩为快照
  • 快照包含状态机的完整状态 + 最后一个日志的 index 和 term
  • 可以丢弃快照之前的所有日志
  • Follower 落后太多时，Leader 发送 InstallSnapshot

Raft 安全性深度可视化

四大安全性保证 — 一图总览

① 选举安全 Election Safety
每个 Term 最多一个 Leader（一 Term 一票制）→ 不可能出现两个同 Term 的 Leader
② Leader 完整性 Leader Completeness
已提交的日志一定出现在所有后续 Leader 的日志中 → 新 Leader 不会丢已提交数据
③ 日志匹配 Log Matching
同一 index + 同一 term → 该 index 之前的所有日志完全一致 → 日志一致性归纳证明

依赖链：①选举安全 → ②Leader完整性 → ③日志匹配 → ④状态机安全。上层保证是下层保证的前提，环环相扣。

Leader 完整性 — 为什么选举限制如此关键？

核心问题：新选出的 Leader 如果日志比某些节点旧，可能丢掉已提交的日志。Raft 用选举限制保证：只有日志最新的节点才能当选。

✅ 选举限制规则

投票时比较 (lastLogTerm, lastLogIndex)：

  • 候选人 lastLogTerm > 我的 → 投票
  • term 相同，候选人 lastLogIndex ≥ 我的 → 投票
  • 否则拒绝（候选人日志比我旧）

效果 已提交日志的持有者一定能当选

❌ 如果没有选举限制

节点A: [t1,t2,____]  (有 t1,t2)
节点B: [t1,t2,t3,t4] (有已提交的 t3,t4)
节点C: [t1,t2,____]  (落后)

若无限制，C 可能靠多数票(A+C)当选
→ C 的日志缺少 t3,t4
→ 后续覆盖 B 的已提交数据 ❌

后果 已提交日志被覆盖，违反线性一致性

日志匹配 — 归纳法证明一致性

AppendEntries 的 prevLog 校验机制
Leader 日志:  [t1|cmd1] [t2|cmd2] [t3|cmd3] [t4|cmd4]
                                       ↑
                              要复制这条(index=4, term=4)
                              prevLogIndex=3, prevLogTerm=3

Follower 校验:
  ① 自己 index=3 的 term 是否 == 3?
     ├─ 是 → 日志在 index=3 处匹配 → 之后追加 index=4
     └─ 否 → 日志不一致 → Leader 递减 nextIndex 重试

归纳基础: prevLog 匹配 → 该 index 及之前全部相同
归纳步骤: 每次追加都校验 prev → 链式保证全段一致
  • 归纳基础：空日志（index=0）天然匹配
  • 归纳步骤：若 prevLogIndex/prevLogTerm 匹配，则追加后该 index 也匹配
  • 结论：若两个日志在某个 index 的 term 相同，则该 index 之前所有条目都相同
  • 冲突修复：Leader 维护每个 Follower 的 nextIndex，不一致时递减重试，直到找到匹配点后覆盖冲突日志

提交规则 — 为什么不能提交旧 Term 的日志？

Raft 的关键安全规则：Leader 只能提交当前 Term的日志条目。旧 Term 的日志只能随着当前 Term 日志的提交而"被间接提交"。

✅ 正确：只提交当前 Term

Leader(term=4) 要提交 index=3(term=2)
→ 不能直接提交 term=2 的条目
→ 先把当前 term=4 的条目复制到多数
→ 提交 term=4 的条目
→ term=2 的条目随之被提交 ✅

避免"幽灵提交"：旧 Term 日志可能被新 Leader 覆盖

❌ 错误：直接提交旧 Term

Leader(term=4) 直接提交 index=3(term=2)
→ 多数派已复制
→ 但新 Leader(term=5) 可能没有该条目
→ 新 Leader 覆盖 index=3
→ 已"提交"的条目消失 ❌

面试高频：Raft 论文 Figure 8 问题——旧版本 Raft 存在用旧 Term 日志计数来判断提交的 bug，会导致已提交日志被覆盖。修复方案：Leader 上任后立即提交一条当前 Term 的空操作（no-op），确保之前所有日志被间接提交。

ZAB 协议

ZAB 两种模式

消息广播模式（正常工作）

  • Leader 接收写请求，为每个事务分配全局递增的 ZXID
  • Leader 将事务以 Proposal 发送给所有 Follower
  • Follower 收到后写入日志，返回 ACK
  • Leader 收到多数派 ACK 后发送 COMMIT
  • Follower 收到 COMMIT 后将事务应用到状态机

崩溃恢复模式（Leader 故障）

  • Follower 检测到 Leader 心跳超时，进入选举
  • 选举 ZXID 最大的节点为新 Leader（数据最新）
  • 新 Leader 与 Follower 同步数据
  • 同步完成后切换到消息广播模式

ZXID 结构

// ZXID 是 64 位整数
// ┌──────────────┬──────────────┐
// │  Epoch (32位) │ Counter (32位)│
// └──────────────┴──────────────┘
//
// Epoch：Leader 编号，每次选举新 Leader 递增
// Counter：事务计数器，每个事务递增
//
// 比较规则：先比较 Epoch，再比较 Counter
// ZXID 越大 → 数据越新 → 优先成为 Leader
ZAB 与 Raft 的核心区别：ZAB 用 ZXID（Epoch+Counter）保证日志顺序，Raft 用 Term+Index。ZAB 的选举优先选数据最新的节点，Raft 通过选举限制保证安全性。

第二部分：场景化讲解

Gossip 协议

Gossip 协议概述

Gossip（流言传播）协议是一种去中心化的最终一致性协议，节点之间通过随机交换信息来传播状态。

三种通信方式

  • Push：节点主动将自己的数据推给随机选中的节点
  • Pull：节点主动从随机节点拉取数据
  • Push-Pull：双向交换数据（最高效）

两种传播模式

  • 反熵（Anti-Entropy）：每次全量同步所有数据，保证最终一致
  • 谣言传播（Rumor-Mongering）：只传播新变更的数据，收敛后停止

Gossip 特性

特性说明
去中心化无中心节点，每个节点地位平等
最终一致性不保证强一致，但保证最终所有节点收敛到相同状态
可扩展性新增节点无需特殊处理，自动融入协议
容错性部分节点故障不影响整体传播
收敛时间O(logN) 轮后所有节点收敛

PBFT 拜占庭容错

PBFT 三阶段流程

PBFT（Practical Byzantine Fault Tolerance）能在 N ≥ 3f+1 个节点中容忍 f 个拜占庭节点。

Pre-Prepare
Leader 分配序号 n
广播 PRE-PREPARE(v,n,m)
→
Prepare
节点广播 PREPARE(v,n,m,d)
收到 2f 个 PREPARE 进入 Prepared 状态
→
Commit

收到 2f+1 个 COMMIT 执行请求
  • v：视图编号（类似 Raft 的 Term）
  • n：请求序号
  • f：拜占庭节点数上限，系统总节点数 N ≥ 3f+1
  • 视图切换：Leader 故障时，通过 ViewChange 协议选举新 Leader

第三部分：模拟面试

什么是共识算法？为什么分布式系统需要共识？
参考：共识算法是让分布式系统中多个节点对某个值达成一致的算法。需要共识的原因：1）分布式系统中节点独立运行，需要协调各自的状态；2）网络不可靠，消息可能丢失、延迟、乱序；3）节点可能宕机，系统需要在部分节点故障时仍能正常工作。共识算法的四个性质：一致性（所有正确节点决定相同值）、合法性（决定的值必须是提出的值）、终止性（最终能做出决定）、容错性（部分节点故障时仍可工作）。
Raft 协议是如何保证日志一致性的？
参考：Raft 通过三个机制保证日志一致性：1）Leader 完整性——选举限制保证已提交的日志一定出现在新 Leader 中（候选人的日志必须至少和多数节点一样新）；2）日志匹配——AppendEntries 携带 prevLogIndex 和 prevLogTerm，Follower 校验前一条日志是否匹配，不匹配则拒绝；3）日志修复——Leader 递减 nextIndex 重试直到找到匹配点，然后覆盖 Follower 的冲突日志。此外，只有当前 Term 的日志被多数派复制后，之前 Term 的日志才能被间接提交，避免了已提交日志被覆盖的问题。
ZAB 协议和 Raft 协议有什么区别？
参考：主要区别：1）日志编号：Raft 用 Term+Index，ZAB 用 ZXID（Epoch+Counter）；2）选举策略：Raft 随机超时+日志限制，ZAB 优先选 ZXID 最大的节点；3）日志提交：Raft 当前 Term 的日志才能间接提交之前 Term 的日志，ZAB Leader 发 COMMIT 即可提交；4）日志连续性：Raft 允许空洞，ZAB 严格连续。两者都是 CFT 共识，需要 N/2+1 正常节点，都能保证强一致性。ZAB 专为 ZooKeeper 设计，Raft 更通用（etcd、Consul、TiKV 都使用）。
Gossip 协议的原理是什么？为什么 Redis Cluster 用 Gossip 而不用 Raft？
参考：Gossip 是去中心化的最终一致性协议，节点随机选择其他节点交换信息，像流言传播一样。Push-Pull 模式下，O(logN) 轮后所有节点收敛到相同状态。Redis Cluster 用 Gossip 而非 Raft 的原因：1）Redis Cluster 是 AP 系统，不需要强一致性，最终一致即可；2）Gossip 去中心化，无 Leader 选举，性能更高；3）Redis Cluster 只用 Gossip 传播节点状态和槽位信息（元数据），实际数据由各 Master 节点独立负责，不需要共识。如果用 Raft，每个写操作都需要多数派确认，会严重影响 Redis 的性能。
Paxos 算法和 Raft 算法有什么关系？为什么有了 Paxos 还需要 Raft？
参考：Raft 是 Paxos 的等价算法，两者在理论上能解决相同的共识问题。Paxos 的问题：1）难以理解——Lamport 的论文晦涩难懂；2）难以实现——论文只描述了单个值的共识，Multi-Paxos 的实现细节未明确说明；3）工程挑战——成员变更、日志压缩等问题需要自行解决。Raft 的改进：1）强 Leader 模型——所有日志只能从 Leader 流向 Follower，简化了推理；2）分解问题——将共识拆分为选举、日志复制、安全性三个子问题；3）工程友好——论文给出了完整的实现细节。
PBFT 是如何实现拜占庭容错的？与 Raft 有什么本质区别？
参考：PBFT 通过三阶段协议（Pre-Prepare、Prepare、Commit）实现拜占庭容错。在 Prepare 阶段收集 2f 个确认，在 Commit 阶段收集 2f+1 个确认，确保即使 f 个节点是恶意的，诚实节点也能达成一致。与 Raft 的本质区别：1）容错模型不同——Raft 容忍崩溃故障（CFT），PBFT 容忍拜占庭故障（BFT）；2）节点数量要求——Raft 需要 N/2+1，PBFT 需要 2N/3+1；3）性能差异——PBFT 需要 O(N²) 消息交换，Raft 只需 O(N)，因此 PBFT 性能较差，不适合大规模集群。
在实际系统中如何选择共识算法？
参考：选择依据：1）一致性需求——强一致选 Raft/Paxos/ZAB，最终一致选 Gossip；2）容错模型——可信环境用 CFT（Raft），不可信环境用 BFT（PBFT）；3）性能需求——高性能选 Gossip（无共识开销）或 Raft（强 Leader 模型），PBFT 性能最低；4）集群规模——Raft/Paxos 适合 3-7 节点小集群，Gossip 可扩展到数百节点。常见选型：配置中心/分布式锁用 Raft（etcd）或 ZAB（ZooKeeper），服务发现用 Gossip（Consul/Redis Cluster），区块链用 PBFT 或 PoW/PoS。
