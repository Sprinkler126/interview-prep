三大核心角色

角色职责所在位置
TM（Transaction Manager）开启/提交/回滚全局事务发起全局事务的服务
RM（Resource Manager）管理分支事务资源，向 TC 注册/报告每个参与事务的服务

TC 是独立的 Server 进程，TM 和 RM 是嵌入业务应用的 SDK。TM 和 RM 通过 Netty 与 TC 通信。

AT 模式

AT 模式原理（自动补偿）

AT（Automatic Transaction）模式是 Seata 的默认模式，通过全局锁 + undo_log + 两阶段提交自动实现分布式事务：

AT 模式两阶段提交
Phase 1：执行阶段
1. 解析 SQL，获取操作前数据快照（before image）
2. 执行业务 SQL
3. 获取操作后数据快照（after image）
4. 生成 undo_log 写入数据库（与业务 SQL 同一本地事务）
5. 向 TC 注册分支事务，申请全局锁
Phase 2 - 提交：异步删除 undo_log，释放全局锁
Phase 2 - 回滚：用 undo_log 中的 before image 反向补偿，释放全局锁

undo_log 表结构

-- undo_log 表（每个参与事务的数据库都需要）
CREATE TABLE undo_log (
    id            BIGINT(20)   NOT NULL AUTO_INCREMENT,
    branch_id     BIGINT(20)   NOT NULL,  -- 分支事务 ID
    xid           VARCHAR(100) NOT NULL,   -- 全局事务 ID
    context       VARCHAR(128) NOT NULL,   -- 上文（序列化信息）
    rollback_info LONGBLOB     NOT NULL,   -- 回滚信息（before/after image）
    log_status    INT(11)      NOT NULL,   -- 0=正常, 1=已完成, 2=已删除
    log_created   DATETIME     NOT NULL,
    log_modified  DATETIME     NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY ux_undo_log (branch_id, xid)
);

-- rollback_info 结构：
{
    "beforeImage": {     // 操作前快照
        "rows": [{"id":1, "balance":1000}]
    },
    "afterImage": {      // 操作后快照
        "rows": [{"id":1, "balance":900}]
    },
    "sqlType": "UPDATE", // SQL 类型
    "tableName": "account"
}

全局锁机制

  • AT 模式使用全局行锁保证分布式事务的隔离性
  • 分支事务在 Phase 1 执行后申请全局锁，TC 记录锁信息
  • 其他事务（包括非 Seata 管理的本地事务）修改同一行时，需要先获取全局锁
  • 获取全局锁失败会重试（默认重试 30 次，间隔 10ms）
  • 全局锁在 Phase 2 提交后释放
全局锁是 AT 模式保证隔离性的关键，但也带来了性能开销。高并发写同一行的场景下，全局锁竞争会严重影响性能。

TCC 模式

TCC 三阶段

TCC 模式流程
Try
资源预留/检查
→
Confirm
确认提交（全部成功）
或
Cancel
回滚释放（部分失败）
阶段职责示例（扣款）
Try资源检查和预留检查余额 >= 扣款金额，冻结金额
Confirm确认提交扣减冻结金额，更新余额
Cancel取消回滚释放冻结金额
 
// TCC 接口定义
@LocalTCC
public interface AccountTCC {
    @TwoPhaseBusinessAction(
        name = "deduct",
        commitMethod = "confirm",
        rollbackMethod = "cancel"
    )
    boolean tryDeduct(
        @BusinessActionContextParameter(paramName = "userId") String userId,
        @BusinessActionContextParameter(paramName = "amount") BigDecimal amount
    );

    boolean confirm(BusinessActionContext context);
    boolean cancel(BusinessActionContext context);
}

TCC 三大问题

问题描述解决方案
空回滚Try 未执行就收到 Cancel记录事务状态，Cancel 时检查 Try 是否执行过
幂等Confirm/Cancel 重复执行使用全局事务 ID 做幂等键，记录执行状态
悬挂Cancel 先于 Try 到达Try 执行前检查是否已 Cancel，已 Cancel 则拒绝执行
TCC 的三大问题是面试高频考点。核心解决思路：引入一张事务状态控制表，记录每个分支事务的状态（Try/Confirm/Cancel 的执行情况），基于状态判断是否需要执行。

Saga 模式

Saga 模式原理

  • Saga 将长事务拆分为多个本地事务，每个本地事务有对应的补偿事务
  • 正向顺序执行本地事务 T1 → T2 → T3
  • 如果某个事务失败，反向执行补偿事务 C2 → C1
  • Seata 的 Saga 通过状态机驱动（JSON DSL 定义流程）
  • Saga 不保证隔离性，适合长事务和遗留系统
// Saga 状态机定义（JSON DSL）
{

特性ATTCCSagaXA

全局事务流程

全局事务完整流程

Seata 全局事务流程（AT 模式）
TM: @GlobalTransactional
开启全局事务
→
RM 1: 执行 SQL
写 undo_log + 注册分支
→
RM 2: 执行 SQL
写 undo_log + 注册分支
→
TM: 全局提交/回滚
→
TC: 通知所有 RM
// 完整流程（AT 模式）：
// 1. TM 调用 @GlobalTransactional 标记的方法
//    → 向 TC 发起 BeginGlobalTransaction，获取 XID

// 2. 业务代码调用服务 A（RM 1）
//    → RM 1 的 DataSourceProxy 拦截 SQL
//    → 解析 SQL，获取 before image
//    → 执行业务 SQL
//    → 获取 after image
//    → 生成 undo_log，与业务 SQL 同一个本地事务提交
//    → 向 TC 注册分支事务，申请全局锁

// 3. 业务代码调用服务 B（RM 2）
//    → 流程同上，XID 通过 RPC 上下文传播

// 4a. 如果全部成功：
//    → TM 向 TC 发起 GlobalCommit
//    → TC 异步通知所有 RM 提交
//    → RM 删除 undo_log，释放全局锁

// 4b. 如果有失败：
//    → TM 向 TC 发起 GlobalRollback
//    → TC 通知所有 RM 回滚
//    → RM 读取 undo_log 中的 before image
//    → 执行反向 SQL 恢复数据
//    → 删除 undo_log，释放全局锁

AT 脏读问题

AT 模式的脏读问题

AT 模式 Phase 1 提交本地事务（包括业务 SQL + undo_log），但全局事务尚未提交。此时其他事务（非 Seata 管理的本地事务）可以读到"中间状态"数据：

// 脏读场景：
// 1. 全局事务 G1：扣减 A 账户余额 100（Phase 1 提交）
//    A.balance = 1000 → 900（本地已提交）
// 2. 此时 G1 还未全局提交/回滚
// 3. 普通事务 T：读取 A.balance = 900（读到中间状态）
// 4. G1 最终回滚，A.balance 恢复为 1000
// → T 基于错误数据做了业务决策（脏读）

// 解决方案：
// 方案一：SELECT FOR UPDATE（加全局锁）
//   → 读操作也会尝试获取全局锁，阻塞直到 G1 完成
// 方案二：使用 @GlobalLock + SELECT FOR UPDATE
//   → 不开启全局事务，但会检查全局锁是否存在
@GlobalLock
@Transactional
public BigDecimal getBalance(String userId) {
    // 会检查全局锁，如果存在则等待
    return accountMapper.selectBalanceForUpdate(userId);
}
// 方案三：使用 AT 的读隔离（Seata 1.2+）
//   → SELECT 语句自动加入全局锁检查
脏读是 AT 模式面试必问问题。核心是理解 AT 模式 Phase 1 已提交本地事务但全局事务未完成这个时间窗口。

高可用

TC 高可用方案

  • 集群部署：多个 TC 实例组成集群，通过注册中心（Nacos）注册

第三部分：模拟面试

请介绍 Seata 的三大角色（TM、RM、TC）以及它们之间的交互流程。
参考：TM（事务管理器）是全局事务的发起者，负责开启、提交和回滚全局事务；RM（资源管理器）管理分支事务资源，每个参与分布式事务的服务都是一个 RM，负责向 TC 注册分支事务和报告执行状态；TC（事务协调者）是独立部署的 Server，维护全局事务和分支事务的状态，协调各 RM 的提交或回滚。交互流程：TM 向 TC 发起全局事务开启请求获取 XID；业务调用链中 XID 通过 RPC 上下文传播；每个 RM 执行本地事务后向 TC 注册分支事务；全部成功后 TM 通知 TC 全局提交，TC 异步通知所有 RM 提交；有失败则全局回滚，TC 通知所有 RM 回滚。
AT 模式的原理是什么？undo_log 是如何工作的？
参考：AT 模式通过全局锁 + undo_log + 两阶段提交自动实现分布式事务。Phase 1：Seata 的 DataSourceProxy 拦截 SQL，解析得到 before image（操作前数据快照），执行业务 SQL，获取 after image（操作后快照），将两者序列化为 rollback_info 写入 undo_log 表，与业务 SQL 在同一个本地事务中提交，同时向 TC 注册分支事务申请全局锁。Phase 2 提交：异步删除 undo_log，释放全局锁。Phase 2 回滚：读取 undo_log 中的 before image，生成反向 SQL（如 UPDATE 的反向是用 before image 的值覆盖当前值）执行回滚，然后删除 undo_log 释放全局锁。
TCC 模式的空回滚、幂等和悬挂问题是什么？如何解决？
参考：空回滚：Try 未执行（如超时）就收到了 Cancel，Cancel 需要正确处理这种情况。解决：引入事务状态控制表，Cancel 执行前检查 Try 是否执行过，未执行则标记已 Cancel 直接返回成功。幂等：Confirm/Cancel 可能因为 TC 重试而重复执行。解决：用全局事务 ID + 分支事务 ID 作为幂等键，记录执行状态，重复执行直接返回成功。悬挂：Cancel 先于 Try 到达并执行后，Try 才到达执行。解决：Try 执行前检查事务状态表，如果已 Cancel 则拒绝执行。核心思路：都需要一张事务状态控制表来记录和判断事务执行状态。
AT 模式的脏读问题是什么？如何解决？
参考：AT 模式 Phase 1 已提交本地事务（业务 SQL + undo_log），但全局事务尚未完成。此时非 Seata 管理的本地事务可以读到"中间状态"数据，如果全局事务最终回滚，则读到的数据是错误的。解决方案：1）使用 @GlobalLock + SELECT FOR UPDATE — @GlobalLock 不开启全局事务但会检查全局锁，如果有其他全局事务持有该行的锁则阻塞等待；2）SELECT FOR UPDATE — AT 模式下 SELECT FOR UPDATE 会自动申请全局锁；3）使用 AT 模式的读隔离特性（Seata 1.2+），SELECT 语句自动加入全局锁检查。
Seata 的四种事务模式如何选型？
参考：选型考虑因素：1）AT 模式 — 无侵入、自动补偿，适合大多数微服务场景，但有全局锁性能开销和脏读问题；2）TCC 模式 — 需要手动实现 Try/Confirm/Cancel，侵入性高但性能好，适合高并发、资金类场景（如支付、转账）；3）Saga 模式 — 长事务、无隔离性保证，适合跨多系统的长流程和遗留系统改造；4）XA 模式 — 数据库原生支持，强一致性但性能最差，适合对一致性要求极高的场景。一般建议：先用 AT 快速实现，遇到性能瓶颈再优化为 TCC。
Seata 的全局锁是什么？它解决了什么问题？
参考：全局锁是 AT 模式保证分布式事务隔离性的机制。Phase 1 提交后，分支事务向 TC 申请全局锁，TC 在内存中记录行锁信息（XID + branchId + resourceId + 行键）。当其他事务（包括非 Seata 管理的本地事务）要修改同一行时，需要先向 TC 检查是否存在全局锁，如果存在则阻塞等待（默认重试 30 次，间隔 10ms）。全局锁解决的问题是防止其他事务在全局事务未完成时修改同一行数据，避免回滚时数据冲突。全局锁在 Phase 2 提交或回滚后释放。
Seata TC 如何实现高可用？
参考：TC 高可用方案：1）集群部署 — 多个 TC 实例注册到 Nacos，TM/RM 通过注册中心发现 TC 集群；2）DB 存储模式 — 全局事务信息和全局锁信息存储在共享数据库（MySQL），所有 TC 实例共享同一数据库，任何一个 TC 故障不影响整体可用性；3）Session 存储 — 支持 file（单机）/ db（集群）/ redis（高性能）三种模式；4）负载均衡 — TM/RM 通过注册中心的负载均衡机制连接 TC 集群中的某个实例。生产环境建议至少 2 个 TC 实例 + DB 存储模式。
