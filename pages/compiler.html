1.2 词法分析

Token 与词法规则

  • Token：词法单元，由 类型 + 值 组成（如 <KEYWORD, "if">、<ID, "count">、<NUM, 42>）
  • 正则表达式：描述词法规则（如标识符：[a-zA-Z_][a-zA-Z0-9_]*）
  • NFA（非确定有限自动机）：正则表达式 → NFA（Thompson 构造法）
  • DFA（确定有限自动机）：NFA → DFA（子集构造法）→ 最小化 DFA
  • 词法分析器：基于 DFA 逐字符扫描，识别 Token

1.3 语法分析与 AST

语法分析方法

方法类型特点示例
递归下降自顶向下每个非终结符对应一个函数，直观易写手写编译器常用
LL(k)自顶向下向前看 k 个 Token，左递归需消除ANTLR
LR(k)自底向上更强大，能处理左递归Yacc/Bison
SLR/LALR自底向上LR 的简化版本，状态数更少大多数编程语言
AST（抽象语法树）：语法分析的输出，树形结构表示程序的语法结构。每个节点表示一个语法结构（如 IfStatement、BinaryExpression、MethodCall）。AST 是后续语义分析、代码生成的基础。

1.6 JIT 编译

C1 / C2 编译器

C1（Client Compiler）

  • 快速编译，较少优化
  • 适合客户端应用（启动快）
  • 简单的方法内联、空值检查消除
  • 编译阈值较低（1500 次调用）

C2（Server Compiler）

  • 深度优化，编译较慢
  • 适合服务端应用（运行性能高）
  • 逃逸分析、标量替换、循环展开
  • 编译阈值较高（10000 次调用）
JDK 8 的分层编译（Tiered Compilation）：Level 0 解释执行 → Level 1 C1 编译（无 profiling）→ Level 2 C1 编译（有限 profiling）→ Level 3 C1 编译（完整 profiling）→ Level 4 C2 编译。先用 C1 快速编译收集性能数据，再用 C2 深度优化。

JIT 优化技术

优化原理效果
方法内联将被调用方法的代码直接嵌入调用处消除方法调用开销，为其他优化创造条件
逃逸分析分析对象是否逃出方法/线程不逃逸的对象可以栈上分配或标量替换
标量替换将对象拆分为基本类型变量避免对象创建，减少 GC 压力
栈上分配不逃逸的对象在栈上分配方法结束自动释放，无需 GC
循环展开减少循环次数，增加每次迭代的工作量减少循环控制开销
死代码消除删除永远不会执行的代码减少代码体积
常量折叠编译期计算常量表达式减少运行时计算

🎯第二部分：场景化讲解

2.1 AOT vs JIT

AOT 与 JIT 对比

AOT（Ahead-of-Time）

  • 编译发生在运行前
  • 直接生成本地机器码
  • 启动快（无需预热）
  • 无运行时优化
  • 代表：GraalVM Native Image、Go 编译器

JIT（Just-in-Time）

  • 编译发生在运行时
  • 根据运行时信息优化
  • 需要预热（热点代码才编译）
  • 可做深度优化（逃逸分析等）
  • 代表：HotSpot JVM、V8
GraalVM 的 SubstrateVM 实现了 AOT 编译 Java 为本地可执行文件，启动时间从秒级降到毫秒级，但峰值性能可能不如 JIT（缺乏运行时 profiling 数据）。

2.2 类加载机制

类加载过程

加载（Loading）
→
验证（Verification）
→
准备（Preparation）
→
解析（Resolution）
→
初始化（Initialization）
阶段核心任务
加载通过全限定名获取字节流 → 转为方法区的运行时数据结构 → 生成 Class 对象
验证文件格式验证（魔数、版本）→ 元数据验证 → 字节码验证 → 符号引用验证
准备为类变量（static）分配内存并设置零值（不是初始值，final 除外）
解析将常量池中的符号引用替换为直接引用（内存地址）
初始化执行类构造器 <clinit>（static 变量赋值 + static 代码块）

触发初始化的时机

  • new 实例：new 对象时
  • 读写 static 字段（final 常量除外）
  • 调用静态方法
  • 反射调用：Class.forName()
  • 子类初始化：会先触发父类初始化
  • 主类：包含 main() 的类
不会触发初始化的情况：① 子类引用父类的静态字段（只初始化父类）；② 数组定义 new MyClass[10]；③ 引用 final 常量（编译期已放入常量池）。

2.3 双亲委派模型

类加载器层次

双亲委派模型
Bootstrap ClassLoader（启动类加载器）
C++ 实现，加载 JAVA_HOME/lib（rt.jar 等核心类库）
⬆️ 委派
Extension ClassLoader（扩展类加载器）
Java 实现，加载 JAVA_HOME/lib/ext（扩展类库）
⬆️ 委派
Application ClassLoader（应用类加载器）
Java 实现，加载 classpath（应用代码和第三方 jar）
⬆️ 委派
Custom ClassLoader（自定义类加载器）
用户自定义，继承 ClassLoader，重写 findClass()
  • 双亲委派：收到加载请求时，先委派给父加载器，父加载器无法完成时才自己加载
  • 优点：① 避免类的重复加载；② 保护核心类库不被篡改（如自定义 java.lang.String 不会被加载）
  • 核心方法：loadClass()（委派逻辑）、findClass()（子类重写，实现加载逻辑）、defineClass()（字节转 Class 对象）

打破双亲委派

场景方式原因
SPI（Service Provider Interface）线程上下文类加载器（Thread Context ClassLoader）JDBC Driver 由 Bootstrap 加载的 DriverManager 需要加载 classpath 上的实现类
Tomcat每个 Web 应用有独立的 WebAppClassLoader不同应用可以使用不同版本的同名类
OSGi网状类加载器结构模块化热部署，模块间依赖管理
热部署每次创建新的类加载器加载修改后的类不重启 JVM 更新代码

2.4 字节码增强

字节码操作框架

框架层次特点典型应用
ASM底层（字节码指令级）性能最好，API 复杂CGLIB、Spring、Gradle
Javassist中层（源码字符串）使用简单，可写 Java 代码片段Hibernate、Dubbo
Byte Buddy中层（流式 API）API 友好，功能强大Mockito、SkyWalking、Spring
CGLIB中层（基于 ASM）专注于生成子类（代理）Spring AOP、Hibernate
应用场景：AOP 代理、ORM 字段映射、Mock 框架、APM 链路追踪（字节码注入）、热部署。

🎤第三部分：模拟面试

Java 从源码到执行经历了哪些过程？
参考：① 编译期：javac 编译器将 .java 文件编译为 .class 字节码文件（词法分析→语法分析→语义分析→字节码生成）；② 类加载：JVM 通过类加载器将 .class 文件加载到方法区（加载→验证→准备→解析→初始化）；③ 执行：解释器逐条解释执行字节码，热点代码由 JIT 编译器编译为本地机器码。
什么是双亲委派模型？为什么要使用它？如何打破？
参考：双亲委派是类加载器的工作模式：收到加载请求先委派给父加载器，父加载器无法完成才自己加载。目的：① 避免重复加载；② 保护核心类安全。
打破方式：① SPI 用线程上下文类加载器（Bootstrap 加载的类要反向委托给应用类加载器）；② Tomcat 每个 Web 应用用独立的 WebAppClassLoader；③ 热部署场景每次新建类加载器。
追问：重写 loadClass() 可以打破双亲委派（改变委派逻辑），重写 findClass() 则不会打破（只是自定义加载逻辑）。
JIT 编译器有哪些优化？方法内联的条件是什么？
参考：JIT 优化包括方法内联、逃逸分析、标量替换、栈上分配、循环展开、死代码消除、常量折叠等。
方法内联条件：① 方法体足够小（< 35 字节码，可通过 -XX:MaxInlineSize 调整）；② 被调用次数足够多（热点方法，阈值通过 -XX:FreqInlineSize 调整）；③ 非虚方法（invokestatic/invokespecial 直接内联，虚方法需要类型分析或通过 Inline Cache 内联）。
类的初始化时机是什么？哪些情况不会触发初始化？
参考：触发初始化：new 实例、读写非 final 的 static 字段、调用静态方法、反射（Class.forName）、子类初始化时先触发父类。
不触发：① 子类引用父类的 static 字段（只触发父类）；② 数组定义 new MyClass[10]（不会初始化 MyClass）；③ 引用编译期常量（final static，已内联到常量池）。
invokevirtual、invokeinterface、invokespecial、invokestatic 有什么区别？
参考：invokevirtual 调用实例方法（虚方法表分派，支持多态）；invokeinterface 调用接口方法（接口方法表分派）；invokespecial 调用构造方法、private 方法、super 方法（编译期确定，静态绑定）；invokestatic 调用静态方法（编译期确定）；invokedynamic 动态绑定（Lambda 和方法引用的基础，运行时由引导方法决定目标方法）。
什么是逃逸分析？它能带来哪些优化？
参考：逃逸分析是 JIT 编译器分析对象是否逃出方法或线程的作用域。三种逃逸状态：① 不逃逸（方法内使用）；② 方法逃逸（作为参数或返回值传出）；③ 线程逃逸（被其他线程访问）。
优化：① 栈上分配：不逃逸的对象在栈上分配，方法结束自动释放，减少 GC；② 标量替换：将对象拆分为基本类型变量；③ 锁消除：线程不逃逸的同步锁可以消除。
ASM 和 Javassist 有什么区别？什么时候用哪个？
参考：ASM 是底层字节码操作框架，直接操作字节码指令，性能最好但 API 复杂，适合需要精细控制字节码的场景（如 Spring、CGLIB 底层）。Javassist 允许用 Java 源码字符串修改类，使用简单但性能稍差，适合快速开发（如 Hibernate、Dubbo）。
选择：追求性能和精细控制用 ASM；追求开发效率用 Javassist 或 Byte Buddy。
AOT 和 JIT 各自的优缺点？GraalVM 解决了什么问题？
参考：AOT：启动快、内存占用小，但无法做运行时优化（缺少 profiling 数据），峰值性能可能不如 JIT。JIT：需要预热，但可以根据运行时信息做深度优化（逃逸分析、内联等），长期运行性能更好。
GraalVM：通过 Native Image 实现 AOT 编译 Java 为本地可执行文件，将启动时间从秒级降到毫秒级，非常适合 Serverless 和容器化场景。但它限制了反射、动态代理等功能的使用，需要额外配置。
