跳表 (Skip List) — ZSet 核心

跳表结构示意
Level 3: HEAD ──────────────────────────→ 30 ──→ NULL
Level 2: HEAD ──────────→ 15 ──────────→ 30 ──→ NULL
Level 1: HEAD ──→ 7 ──→ 15 ──→ 22 ──→ 30 ──→ NULL

  • 查找 O(logN)，与平衡树相当；实现简单，范围查询天然支持

面试追问：跳表层高概率 P=0.25 为什么不是 1/2？P 越小高层节点越稀疏，内存开销更低（Redis 节点多，省内存重要），但查找路径略长。P=0.25 是内存 vs 查找效率的折中：平均每节点约 1.33 个指针，比 P=0.5 的 2 个省 1/3 内存。

listpack — 取代 ziplist 的新一代紧凑编码（Redis 7.0）

设计起点：Redis 7.0 用 listpack 全面替代 ziplist，根本原因是 ziplist 的连锁更新（cascade update）缺陷。

ziplist 的连锁更新隐患

ziplist 每个 entry 存 prev_entry_length 记录前一节点长度：

  • 前一节点 <254B → 占 1 字节；≥254B → 占 5 字节
  • 若某节点从 253→254B，其后所有节点 prevlen 都需 1B→5B 扩展
  • 连锁反应：后续每个节点变大 → 再触发后续 prevlen 扩展 → 最坏 O(N²)

概率极低（需连续多个 ~252B 节点），但一旦触发阻塞主线程

✅ listpack 的解法

  • 每个 entry 只存自身长度和编码，不记录前一节点长度
  • 反向遍历：从末尾 total bytes 逐个倒退，靠当前 entry 的 encoding 长度定位
  • 彻底消除连锁更新：修改任意 entry 不影响其他 entry
  • 同样紧凑：变长编码，小数据极致省内存
面试要点：连锁更新是 ziplist 的经典缺陷。Redis 7.0 用 listpack 替代后，Hash/Set/ZSet 的小数据编码全部换成 listpack。问「ziplist 有什么问题」→ 核心答案就是连锁更新。

quicklist — List 的终极编码（listpack + 双向链表）

设计起点：纯链表每个节点一个 element，指针开销大且内存不连续；纯 ziplist/listpack 元素多了又有连锁/压缩开销。quicklist = 双向链表的节点每个是一个 listpack，兼顾两者。

深入：RDB 的 fork + Copy-on-Write 内存陷阱

设计起点：RDB 要对某一时刻的内存做完整快照，但 Redis 不能停下来等快照写完。解法：fork() 子进程 + 操作系统 COW（Copy-on-Write）。

fork + COW 工作原理
主进程 fork()
子进程获页表副本
父子共享物理内存(只读)
→
子进程遍历内存
写 .rdb 文件
不阻塞主进程
→
主进程收到写请求
修改某内存页
→
OS 触发 COW
复制该页给主进程

风险一 — 内存翻倍：COW 按页复制（4KB/页）。BGSAVE 期间写入量大，大量页被复制，最坏物理内存接近2 倍。16GB+ 实例做 BGSAVE 需预留 50% 以上内存，否则 OOM 被 kill。
风险二 — fork 本身阻塞：fork 需复制页表（不是数据，是页表元数据）。实例越大页表越大，fork 越慢。16GB fork 可能阻塞 几十~几百 ms，32GB 可能秒级——这是大实例用 RDB 的痛点。
优化：① 关闭 THP（Transparent Huge Pages），否则 COW 以 2MB 大页复制，放大内存开销；② info memory | grep mem_fork_time 监控 fork 耗时；③ 超大实例分片降低单实例内存。

深入：AOF Rewrite 全过程与双缓冲

AOF 不断追加写命令，文件越来越大。Rewrite 是对当前内存做一次「命令压缩」：用最少的命令表示当前数据，丢弃已过期/已删除/被覆盖的冗余命令。

AOF Rewrite 流程
① fork 子进程，遍历内存生成新 AOF（内存状态 → 最简命令）
⬇️
② 主进程继续处理请求，新写命令同时写入 AOF 缓冲区 + AOF 重写缓冲区
⬇️
③ 子进程写完新 AOF，发信号给主进程
⬇️
④ 主进程将 AOF 重写缓冲区的增量命令追加到新 AOF 末尾
⬇️
⑤ 原子替换旧 AOF 文件（rename 保证原子性）
易错点（面试高频）：Rewrite 期间有两个缓冲区——AOF 缓冲区（正常追加用）和 AOF 重写缓冲区（暂存 Rewrite 期间的增量）。后者确保新 AOF 不丢失 Rewrite 期间的新写入。双缓冲设计是常考点。

Redis 7.0 multi-part AOF — 格式演进

7.0 之前：单文件 AOF

  • 一个 appendonly.aof 文件
  • Rewrite 时临时文件 + rename 原子替换
  • 大文件 rename 期间崩溃可能损坏

✅ 7.0+：multi-part AOF

  • AOF 拆为目录：appendonlydir/
  • base 文件（RDB 或 AOF 格式的全量快照）
  • incr 文件（增量 AOF 命令）
  • manifest 文件（清单，记录 base+incr 列表）
  • Rewrite 只新增 base+清空 incr，旧文件延迟删除保安全
设计动机：multi-part 把「全量快照」和「增量日志」物理分离，Rewrite 不再需要大文件 rename，降低崩溃损坏风险，支持更灵活的增量保留策略。

设计动机：为什么 Redis 的 LRU/LFU 是"近似"而非精确？

设计起点：精确 LRU 需要维护全局双向链表，每次访问都要移动节点到头部——这是 O(1) 但每次操作都有额外开销，且链表节点本身占内存。Redis 的核心卖点是"单线程极致性能"，不能为淘汰策略拖慢每条命令。Redis 的解法：随机采样——淘汰时随机抽 N 个 key（maxmemory-samples，默认 5），从中选最该淘汰的，近似 LRU/LFU。

精确 LRU 的代价

  • 每次 GET/SET 都要移动链表节点 → 全局锁/指针操作
  • 链表节点元数据占额外内存（每个 key +16~24 字节）
  • 与 Redis 单线程模型冲突：增加每命令延迟

✅ 采样近似 LRU 的收益

  • 访问时只更新 lru 字段（每个 key 已有 24bit 时间戳字段）
  • 淘汰时随机采样 5 个选最旧的，开销恒定且小
  • 采样数调大（如 10）更接近精确 LRU，但淘汰更慢
  • 实测 5 个采样已接近精确 LRU 效果（Redis 官方基准）
面试要点：Redis 的淘汰策略本质是"用精度换性能"——单线程不能为淘汰拖慢命令。这也是为什么 Redis 没有"真正"的 LRU，而是 approximate LRU。LFU 用 Morris 计数器（概率计数）也是同样思路。

深入：LRU 与 LFU 在 RedisObject 中的位级实现

每个 RedisObject 有一个 24bit 的 lru 字段，LRU 和 LFU 复用这同一字段，只是解释不同：

LRU 模式：24bit 全存时间戳

  • 24bit 存「秒级时间戳」低 24 位，约 194 天循环一次
  • 访问时更新该字段，淘汰时比较谁最旧
  • 精度：秒级，足够区分访问新旧

LFU 模式：8bit 衰减 + 16bit 计数

  • 高 8bit：最后访问时间衰减因子（分钟级）
  • 低 16bit：Morris 近似计数器，记录访问频率
  • 16bit 范围 0~65535，但 Morris 算法使其可达数百万次

Morris 计数器：第 N 次访问时，以 1/(counter+1) 的概率才 +1。这样 counter 增长越来越慢，小空间表示大数值。衰减机制：超过 lfu-decay-time（默认 1 分钟）没访问，counter 衰减 1，防止老热点永久占位。

LRU vs LFU 选择：有批量扫描场景（如定时全表扫缓存）用 LFU——LRU 会让扫描到的冷数据成为"最近访问"挤掉热点；LFU 看频次不受单次扫描影响。无扫描场景 LRU 够用且更简单。

1.4b 过期 Key 删除策略 — 惰性 + 定期 的组合

设计起点：过期 key 怎么清理才不阻塞主线程？

Redis 给 key 设 TTL 后，到期要清理。两种朴素方案都有硬伤：① 定时删除（每个 key 一个定时器）→ 大量 key 同时过期时定时器风暴，阻塞主线程；② 惰性删除（访问时才查是否过期）→ 不访问的 key 永不清理，内存泄漏。Redis 的解法：惰性 + 定期 组合。

① 惰性删除（主防线）

  • 每次 GET/SET 等访问时检查 TTL，过期则删除返回 nil
  • 优势：不额外占用 CPU
  • 劣势：永不被访问的 key 持续占内存

② 定期删除（兜底）

  • 后台定时随机采样 active_expire_cycle，每次抽 20 个 key，删除过期的
  • 若过期比例 >25%，继续抽，直到时间片用完（25ms）
  • 自适应：过期 key 多时多清理，少时快速结束
内存兜底：如果惰性+定期都没清理干净，内存涨到 maxmemory 触发内存淘汰策略（noeviction/allkeys-lru 等）。三道防线层层兜底，保证内存不爆。
面试要点：Redis 的清理哲学是"绝不主动做大量工作阻塞主线程"——过期删除摊平到每次访问 + 短时间片的定期任务。理解这点就能理解 Redis 所有"近似/惰性"设计的统一思想。

为什么单线程还能这么快？

  • 纯内存操作：瓶颈在网络 IO 而非 CPU
  • IO 多路复用：单线程同时监听多个 socket
  • 无锁设计：避免线程切换和锁竞争
  • 高效数据结构：SDS、跳表、压缩列表等优化
Redis 6.0+ 引入多线程 IO（io-threads）：网络读写多线程，命令执行仍是单线程。不是多线程执行命令！

设计动机：为什么 6.0 才引入多线程 IO？为什么命令执行仍单线程？

设计起点：Redis 早年单线程够用，因为瓶颈在内存操作（纳秒级），单核能扛 10 万 QPS。但随着网络从 1G → 10G → 25G，网络 IO（read/write socket + 协议解析）成了新瓶颈——单线程处理网络包来不及。6.0 的多线程 IO 就是针对这个瓶颈。

✅ 为什么只多线程化 IO？

  • 网络 IO 是纯等待，多线程能并行处理多个连接的读写
  • 协议解析（RESP 协议）也是 CPU 密集，可并行
  • 这两步不涉及共享数据结构，无锁竞争
  • 实测 10G 网络下，多线程 IO 提升 ~1 倍吞吐

为什么命令执行仍单线程？

  • 命令操作共享数据结构（dict/skiplist），多线程需加锁
  • 加锁引入竞争和上下文切换，反而拖慢简单命令
  • 保持单线程 = 无需锁，命令原子性天然保证
  • 多线程命令的收益（CPU 利用）在内存操作场景不显著
易错点：6.0 多线程默认关闭，需 io-threads 4（建议 CPU 核数的一半）+ io-threads-do-reads yes 开启。且对小数据包收益不明显，适合大 value（如大 Hash/List）场景。
面试金句：Redis 的线程模型演进体现"精准优化瓶颈"——单线程够用时不动，网络成瓶颈就只多线程化网络，命令执行仍单线程保持无锁优势。这是工程优化的范本：哪里慢优化哪里，不盲目全多线程。

1.6 渐进式 rehash 与对象编码转换

设计起点：为什么 Redis 要「渐进式」rehash？

Redis 的 dict（hashtable）会随数据增长触发 rehash 扩容（负载因子过高）。传统一次性 rehash 要把全部键值对从旧表 ht[0] 迁到新表 ht[1]，如果字典有上百万个 key，这一次集中迁移会阻塞主线程数秒——对 Redis 这种内存数据库是灾难性的。Redis 的解决方案：把 rehash 摊平到每次字典操作上，每次只迁移一小部分，让长任务变成"看不见"的背景工作。

渐进式 rehash 的哲学：将一个长阻塞操作拆成无数个 O(1) 微操作，附着在正常读写上顺带完成。这是 Redis 「绝不阻塞主线程」设计理念的一个缩影。

渐进式 rehash 实现机制

dict 双 hashtable 结构
ht[0]
旧表，正在搬出
+
ht[1]
新表，正在搬入
+
rehashidx
迁移进度指针
  1. 触发扩容：负载因子 = used/size 超过阈值（如 1，有 BGSAVE 时为 5）时，分配 ht[1]，rehashidx = 0
  2. 每次操作顺带迁移：增删改查时，执行 rehashidx 所指桶的全部 key 搬到 ht[1]，rehashidx++（每次最多搬 1 个桶，或空桶最多访问 10*N 个空桶）
  3. 期间读写规则：读在 ht[0]、ht[1] 都查；写在 ht[1]（保证新数据在新表）；删除两者都查
  4. 定时辅助：另有定时任务每次 1ms 帮忙迁多几桶，防止长期空闲的字典一直占着两个表
  5. 完成：ht[0] 全部迁完，释放 ht[0]，令 ht[0]=ht[1]，ht[1]=null，rehashidx=-1
渐进式 rehash 期间字典同时占用两份哈希表内存，内存使用会短暂翻倍。大字典扩容时要预留内存，否则可能 OOM。

对象编码转换：为什么 Redis 同一类型有多种底层编码？

设计起点：时间换空间，空间换时间。数据量小时，紧凑编码（listpack/intset）省内存、缓存友好；数据量大或需要复杂操作时，转为高性能结构（hashtable/skiplist）保证性能。Redis 在每次操作后自动检测阈值，按需「升级」编码，对用户透明。

深入：Cache Aside 的并发一致性问题

设计起点：Cache Aside（旁路缓存）是业界最常用的缓存模式——读先查缓存，写时先更新 DB 再删缓存。但看似简单，并发下仍有经典的一致性漏洞。

漏洞一：先删缓存再更 DB

线程A 删缓存
线程B 读缓存(未命中) → 读旧DB
线程B 写旧值到缓存
线程A 更新DB → 缓存仍是旧值！脏数据

所以 Cache Aside 必须先更 DB 再删缓存

漏洞二：先更 DB 再删缓存（仍有小概率）

缓存刚好失效
线程A 读旧DB（拿到旧值）
线程B 更新DB + 删缓存
线程A 写旧值到缓存 → 脏数据

概率极低（需读旧值比写慢），但理论存在

解法：延迟双删（Sleep + Delete）

① 删缓存
→
② 更新DB
→
③ sleep N ms
等读线程读完旧值
→
④ 再删一次缓存
清理可能写入的脏值

N 取「一次读请求耗时 + 几百 ms 缓冲」。代价是更新流程变长，且第二次删可能失败（需重试队列兜底）。

面试要点：Cache Aside 的最佳实践是先更 DB 再删缓存（不是更新缓存——并发写会互相覆盖）。极端一致性要求用延迟双删 + 删除重试（MQ/订阅 binlog 异步删）。彻底一致可用「通过 DB binlog 订阅（Canal）异步刷缓存」。

四种缓存读写模式横向对比

Cache Aside / Read-Through / Write-Through / Write-Behind
模式读流程写流程一致性适用场景
Cache Aside ⭐查缓存→未命中查DB→回填更DB→删缓存最终一致最常用，应用层控制
Read-Through查缓存→未命中由缓存服务查DB并回填同上最终一致应用不关心DB，缓存封装
Write-Through同上写缓存→缓存同步写DB强一致写性能要求不高
Write-Behind同上写缓存→缓存异步批量刷DB弱一致写极多，可容忍丢数据
关键区别：Cache Aside 是应用层管缓存读写；Read/Write-Through 是缓存层代理 DB 访问（应用只认缓存）。Write-Behind（回写）写速度最快但有数据丢失风险（缓存宕机未刷盘的写会丢）。

深入：RedLock 算法与 Martin Kleppmann 争议

设计起点：单主 Redis 锁有主从切换丢锁风险——加锁成功后 Master 还没同步给 Slave 就宕机，Slave 升主后锁丢失，另一个线程也能加锁成功。RedLock 是 Antirez 提出的多节点多数派方案。

RedLock 算法流程（5 个独立 Master 实例）
① 客户端记录当前时间 T1，对 5 个独立 Redis 实例依次 SET NX EX
⬇️
② 统计成功数，记录耗时 T2-T1
⬇️
③ 成功数 ≥3（多数派）且 T2-T1 < 锁有效期 → 加锁成功
⬇️
④ 锁实际有效时间 = 有效期 - (T2-T1)，扣掉网络耗时
⬇️
⑤ 失败（未达多数）→ 向所有实例发 DEL 释放

Martin Kleppmann 的反驳

  • GC 停顿破坏假设：客户端加锁后 STW（GC 暂停几秒），锁过期自动释放，恢复后仍以为持有锁 → 两个客户端同时操作
  • 时钟依赖：RedLock 强依赖各节点时钟准确，若某节点时钟跳变（NTP 校正、VM 迁移），锁有效期计算出错
  • 结论：需要正确性的分布式锁应用 fencing token 方案（每次加锁递增序号，DB 层拒绝旧 token 的写）

Antirez 的回应

  • GC 问题对所有锁都存在，非 RedLock 独有
  • 时钟跳变可通过运维避免（禁止 VM 迁移、合理 NTP）
  • RedLock 定位是效率优先（避免重复计算），非绝对正确性
  • fencing token 需 DB 支持，很多场景做不到
面试要点：这个争议是分布式系统的经典案例。结论：对效率型锁（防重复执行）RedLock 够用；对正确性型锁（如金融扣款）用 ZooKeeper/etcd（基于 Raft 共识）+ fencing token。能讲清争议双方观点是大加分项。

🏠 主从复制 (Master-Slave)

原理：Slave 连接 Master 后发送 PSYNC runid offset，Master 回复数据

  • 全量同步：首次连接或 offset 失效 → Master 执行 BGSAVE 生成 RDB → 发送给 Slave → 后续命令通过 repl buffer 增量同步
  • 增量同步：网络断开重连 → Master 检查 repl_backlog 中是否还有 offset 对应的数据 → 有则只发断线期间的增量
  • repl_backlog：环形缓冲区（默认 1MB），断线时间过长或写入量太大导致 offset 被覆盖 → 退化为全量同步

❌ Master 宕机后需手动将某个 Slave 提升为 Master，服务中断时间长

🛡️ 哨兵 (Sentinel)

原理：Sentinel 进程监控 Redis 节点，自动故障转移

  • 监控：每秒 PING 所有 Master/Slave，超过 down-after-milliseconds（默认 30s）未响应标记为主观下线（SDOWN）
  • 客观下线：Sentinel 之间互相询问，quorum（多数派）都认为 Master 下线 → ODOWN
  • Leader 选举：Raft 协议选举 Sentinel Leader，由 Leader 执行故障转移
  • 故障转移：选 Slave（优先级 → offset → runid）→ SLAVEOF NO ONE 提升为新 Master → 其余 Slave 指向新 Master
至少 3 个 Sentinel（奇数），部署在不同机器/可用区，避免脑裂

repl_backlog 环形缓冲区

  • Master 维护一个环形数组（默认 1MB），存最近的写命令
  • 每个命令有 offset，Slave 断线重连时报告自己的 offset
  • offset 还在 backlog 内 → 增量同步，否则退化全量
  • 调优：写入量大或网络不稳时调大 repl-backlog-size（如 64MB），减少全量同步概率

异步复制的数据丢失

  • Redis 复制是异步：Master 写入后立即返回客户端，不等 Slave ACK
  • 若 Master 返回成功后立即宕机，未同步的写入丢失
  • min-slaves-to-write N：至少 N 个 Slave 确认才允许写（半同步），但会牺牲可用性
  • 权衡：一致性 vs 可用性，CP 还是 AP——Redis 默认选 AP
面试高频：Redis 主从复制是异步的，这是它「快」的原因，也是「可能丢数据」的根源。问「主从切换会丢数据吗」→ 会，Master 宕机时未同步到 Slave 的写入会丢。要强一致需 WAIT numreplicas timeout 命令（同步等待）或用 min-slaves-to-write。

深入：Cluster 为什么是 16384 个 slot？slot 迁移怎么做？

为什么是 16384 而不是 65536？

  • 节点间 Gossip 心跳要交换slot 位图（每个 slot 1 bit）
  • 16384 slot → 位图 2KB；65536 slot → 8KB
  • Redis Cluster 官方建议节点数 <1000，16384 足够分，且心跳包小
  • Antirez 原话：8KB 心跳包在 1000 节点时带宽浪费明显，2KB 刚好

② 目标节点标记 slot 为 IMPORTING

脑裂风险：网络分区时，原 Master 与多数派隔离，少数派侧的 Slave 被提升为新 Master，分区恢复后旧 Master 降为 Slave。分区期间旧 Master 的写入会丢失。Cluster 用 cluster-node-timeout（默认 15s）判定节点下线，超时才触发故障转移，一定程度上减少脑裂窗口。

2.5b 限流算法横向对比

设计起点：解决什么问题——"单位时间内只允许 N 次请求"看似简单，难点在于窗口边界突变（临界突刺）、平滑性（是否允许突发）、分布式一致性三个维度。四种经典算法各自在这三个维度上做取舍。

算法核心思想突发流量临界突刺实现复杂度
固定窗口每个时间窗口内计数，超限拒绝，窗口结束清零允许❌ 有（窗口边界 2 倍流量）低（INCR + EXPIRE）
滑动窗口用 ZSET 记录每次请求时间戳，统计窗口内元素数允许✅ 无中（ZADD/ZREMRANGEBYSCORE/ZCARD）
漏桶请求入桶，以固定速率漏出；桶满则拒绝❌ 不允许（强制平滑）✅ 无中（需定时漏出线程）
令牌桶以固定速率向桶中放令牌，请求消耗令牌；桶空则拒绝✅ 允许（桶中令牌可累积）✅ 无中（Lua 脚本原子取令牌）

⚡ 临界突刺问题（固定窗口的致命伤）

限流 100/s。0.9s 时来了 100 个请求（放行），1.1s 时又来 100 个（新窗口放行）——0.2s 内放过 200 请求，后端可能被打垮。

滑动窗口解法：窗口不是固定的时间格，而是"当前时刻往前推 1s"，任何时刻窗口内都不会超过阈值。

🪣 漏桶 vs 令牌桶

漏桶：无论来多少请求，输出速率恒定。适合保护下游（如对接第三方 API，对方限速严格）。

令牌桶：空闲时攒令牌，突发时可瞬间消费攒下的令牌。适合允许合理突发的业务（如用户登录峰值）。

Guava RateLimiter、Sentinel 默认都是令牌桶变体。

面试要点：分布式限流必须用 Lua 脚本保证"取令牌/计数"原子性，否则多节点各自计数会突破总阈值。Redisson RRateLimiter 已封装好分布式令牌桶。

2.6 大 Key 与 热 Key 专题

设计起点：解决什么问题——Redis 单线程执行命令，一条命令的耗时取决于它操作的数据量和访问频率。数据量过大（大 Key）会阻塞主线程；访问过于集中（热 Key）会造成单分片瓶颈和热备不一致。两者是 Redis 规模化后最常见的事故源。

📦 大 Key 的危害

  • 阻塞主线程：DEL 一个 10MB 的 list/hash 耗时可达数十毫秒，期间所有其他请求排队
  • 网络阻塞：单次响应过大占满网卡缓冲区，影响其他客户端
  • 集群迁移卡死：slot 迁移时大 Key 要整体 MIGRATE，可能触发 cluster-replica-no-failover 超时
  • 阻塞式淘汰：内存淘汰时大 Key 回收慢，放大 jitter

📏 大 Key 判定标准

  • string：value > 10KB
  • list/set/zset/hash：元素数 > 5000，或总大小 > 10MB
  • 业务上：一个 Key 承载了本该分散到多 Key 的数据（如全站用户会话塞进一个 hash）

排查工具：redis-cli --bigkeys（采样）、MEMORY USAGE key（精确）、RDB 离线分析工具 rdb-tools

大 Key 的发现与处理

阶段手段说明
发现--bigkeys / scan + MEMORY USAGE线上禁用 KEYS，用 SCAN 遍历避免阻塞
拆分按业务维度拆分如 user:1000:cart 拆成 user:1000:cart:202406 这种按时间/分片
删除UNLINK（4.0+）异步删除DEL 是同步阻塞，UNLINK 丢给 bio 线程回收，不卡主线程
过期分批惰性删除大 hash 用 hscan+hdel 分批清，避免同时过期引发抖动

🔥 热 Key 的危害

  • 单分片 CPU 打满：Cluster 模式下热 Key 只落在一个分片，无法横向分摊
  • 热备不一致：从节点异步复制跟不上，读从库会读到旧数据
  • 缓存击穿放大：热 Key 过期瞬间，所有请求穿透到 DB

🛡️ 热 Key 的应对

  • 本地缓存：在应用层用 Caffeine 缓存热 Key，减少对 Redis 的直接访问（多级缓存）
  • 副本打散：把 hot_key 复制成 hot_key:1 / hot_key:2 ...，读取时随机选一个副本
  • 读写分离：热 Key 读走从库，减轻主库压力
  • 发现工具：redis-cli --hotkeys（需开启 LFU）、代理层统计、客户端采样
面试易混点：大 Key ≠ 热 Key。大 Key 看的是单 Key 数据量（影响单命令耗时）；热 Key 看的是访问 QPS（影响单分片负载）。一个 1KB 的 Key 被 10w QPS 访问是热 Key 不是大 Key；一个 50MB 的 list 每天只读一次是大 Key 不是热 Key。两者处理手段完全不同。

🎤第三部分：模拟面试

Redis 为什么这么快？
参考：① 纯内存操作；② 单线程避免上下文切换和锁；③ IO 多路复用（epoll）；④ 高效数据结构（SDS、跳表、压缩列表）。
追问：6.0 多线程矛盾吗？不矛盾。6.0 多线程仅用于网络 IO 读写，命令执行仍是单线程。
缓存穿透、击穿、雪崩是什么？怎么解决？
穿透：查不存在的数据 → 缓存空值 + 布隆过滤器。
击穿：热点 key 过期 → 互斥锁 / 逻辑过期。
雪崩：大量 key 同时过期 → TTL 加随机 / 集群 / 多级缓存。
追问：布隆过滤器缺点？有误判率，不支持删除。
Redis 持久化怎么选？
RDB 快照（文件小恢复快，可能丢数据）+ AOF 日志（最多丢 1 秒，文件大恢复慢）。生产推荐同时开启，4.0+ 混合持久化兼顾两者。
追问：fork 会阻塞吗？大内存实例（16GB+）fork 时复制页表可能阻塞几十到几百 ms。
如何用 Redis 实现分布式锁？
SET key uuid NX EX 30 加锁，Lua 脚本原子判断+删除释放锁。UUID 防误删，EX 防死锁。Redisson Watch Dog 自动续期。
追问：为什么不用 DEL？先 GET 再 DEL 不原子，可能误删别人的锁。
Redis 数据类型底层结构？
String→SDS，List→quicklist，Hash→listpack/hashtable，Set→intset/hashtable，ZSet→skiplist+hashtable。小数据用压缩存储，超过阈值自动转换。
追问：为什么 ZSet 用跳表不用红黑树？① 实现简单；② 范围查询高效；③ 并发友好。
Redis 集群怎么分片？
16384 个 slot，CRC16(key) % 16384 计算归属。不在此节点则 MOVED 重定向。{hash_tag} 让多个 key 同 slot。
追问：为什么 16384？节点数通常 <1000，16384 的 bitmap（2KB）心跳包传输开销合理。
Redis vs Memcached？
Redis：丰富数据结构、持久化、原生集群、发布订阅。Memcached：仅 KV、无持久化、多线程、内存效率更高（slab）。99% 场景选 Redis。
大 Key 怎么发现和处理？
发现：--bigkeys 扫描、MEMORY USAGE、DEBUG OBJECT。
危害：阻塞请求、网络慢、内存不均。
处理：拆分、UNLINK 异步删除、HSCAN+HDEL 渐进删除。
RDB 的 fork + COW 机制？大内存实例为什么要小心？
机制：BGSAVE 调用 fork()，子进程共享父进程内存页；任意一方写某页时，内核才触发 COW（写时复制）复制该页，子进程据此得到一份"快照时刻"的内存副本。
大内存风险：① fork 本身阻塞——需复制页表，16GB 实例复制页表可能耗时几十到几百 ms，期间主线程停顿；② 内存倍增——若写操作密集，大量页被 COW，父子两份内存可能瞬时接近 2 倍。
追问：为什么不用线程做快照？快照要求"某一时刻一致性视图"，多线程难保证；fork+COW 借助 OS 的页表机制天然拿到一致性视图，子进程无需加锁即可遍历。
AOF Rewrite 的双缓冲机制？为什么 Rewrite 期间还能正常服务？
Rewrite 时 fork 子进程遍历内存，把当前数据状态转成写入命令写到新 AOF 文件；同时父进程继续处理请求，期间产生的新命令同时写入旧 AOF 缓冲和AOF Rewrite 缓冲两处。子进程写完后通知父进程，父进程把 Rewrite 缓冲里的增量追加到新文件，最后 rename 替换旧文件。
双缓冲意义：旧缓冲保证 Rewrite 期间崩溃不丢数据；Rewrite 缓冲保证新文件包含 Rewrite 期间的所有变更。
追问：7.0 多部件 AOF 解决了什么？旧版 Rewrite 末尾"追加增量"那一步父进程要短暂阻塞；多部件 AOF 把文件拆成 base（RDB/命令快照）+ incr（增量），Rewrite 只重写 base，incr 始终追加，省去末尾阻塞，且可独立复用 incr。
Redis 的 LRU/LFU 是如何用很少 bit 实现的？
每个对象的 redisObject 末尾留 24 bit 给 LRU 字段。LRU：24 bit 存"最近访问时间戳"（秒，约 194 天回绕），淘汰时随机采样 N 个 key 比较时间戳取最久未访问的。LFU：24 bit 拆成 16 bit 存"最后衰减时间" + 8 bit 存"访问频次"，8 bit 频次用Morris 近似计数器（不是线性计数，而是概率递增：计数越大越难再 +1，可用 0-255 表达远超 255 的频次），并按时间衰减防止老热点永驻。
追问：为什么不用真 LRU？真 LRU 要维护双向链表，每个 key 多两个指针，内存开销大；Redis 采用"随机采样近似 LRU"（默认采 5 个），以可接受的精度换显著的内存节省。
PSYNC 全量/增量如何判定？repl_backlog 丢了怎么办？
从库上报 replid + offset。主库判断：若 replid 匹配且 offset 在 repl_backlog 环形缓冲范围内 → 增量同步，从 offset 起补发缺失命令；否则 → 全量同步（BGSAVE 生成 RDB 传输 + 期间增量缓冲后续补发）。
repl_backlog 丢数据：它是固定大小的环形缓冲（默认 1MB），主从断连期间主库写入超出缓冲容量时，旧命令被覆盖，从库重连后 offset 命中不了 → 触发全量同步，断连期间的写入若已不在缓冲也只在新 RDB 里体现。异步复制本质上就是"可能丢最新写入"，主库宕机时未同步到从库的那部分命令永久丢失。
追问：怎么减少全量同步？调大 repl-backlog-size（按峰值写入速率 × 预计断连时长估算），并开启 min-slaves-to-write 防止主库"脱队"写入。
RedLock 算法的步骤？Martin Kleppmann 为什么反对？
RedLock 步骤（向 N 个独立 Master 节点加锁）：① 记录开始时间 T1；② 依次向每个节点 SET key NX EX，单节点超时很短；③ 加锁成功的节点数 ≥ ⌈N/2 + 1⌉ 且总耗时 < TTL → 加锁成功，实际有效时间 = TTL - (T2 - T1)；否则向所有节点释放锁。
Kleppmann 反对：① 依赖系统时钟，GC 暂停/时钟漂移会让持有者以为锁还没过期实际已过期，导致两个客户端同时持锁；② Redis 没有 fencing token，无法防止过期锁导致的并发写。
Antirez 回应：可加 fencing token；时钟漂移概率低；对正确性要求极高的场景本就不该用 Redis 做锁，应用 ZooKeeper/etcd（基于 Raft 共识 + 租约）。
结论：业务级互斥用 Redisson 单节点锁足够；金融级强一致用 etcd/ZooKeeper。
Cache Aside 的并发漏洞？延迟双删为什么也要加 TTL？
漏洞一（先删缓存后更 DB）：删缓存后、更新 DB 前，另一请求读 DB 旧值并回写缓存 → 缓存被旧值污染，直到下次 TTL。
漏洞二（先更 DB 后删缓存）：删缓存失败 → 缓存仍是旧值；或读请求在"删缓存之前"已读到旧缓存并发起 DB 读，写请求删完后读请求又把旧值写回。
延迟双删：更新 DB 后先删一次缓存，休眠 N 秒（约一次读耗时）再删一次，覆盖期间被并发回写的旧值。
为什么还要 TTL：延迟双删覆盖不了"延迟窗口内的所有并发回写"（N 取不准）、也覆盖不了删缓存失败的情况；TTL 是兜底，保证即使有脏数据最终也会过期自愈。结论：缓存无法做到强一致，延迟双删 + TTL + 订阅 binlog 重做缓存是工程上常用的组合拳。
