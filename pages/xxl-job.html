核心组件

组件职责部署
调度中心管理任务配置、触发调度、管理日志、任务编排独立部署（支持集群）
执行器接收调度请求、执行任务逻辑、回调结果嵌入业务应用
  • 调度中心是独立的 Web 应用（Spring Boot），自带管理界面
  • 执行器通过自动注册或手动注册到调度中心
  • 调度中心通过 HTTP 调用执行器触发任务
  • 执行器执行完成后通过 HTTP 回调结果给调度中心
  • 调度中心集群部署时，通过数据库锁保证同一任务只被一个节点调度

路由策略

路由策略详解

策略说明适用场景
FIRST固定选择第一个执行器单点执行，固定节点
LAST固定选择最后一个执行器单点执行，固定节点
ROUND轮询均匀分配负载
RANDOM随机简单随机分配
CONSISTENT_HASH一致性 Hash有状态任务
LEAST_FREQUENTLY_USED最不经常使用均衡调度频次
LEAST_RECENTLY_USED最近最久未使用均衡调度时间
FAILOVER故障转移高可用场景
BUSYOVER忙碌转移避免阻塞
 
// 路由策略配置（在调度中心管理界面配置）
// FAILOVER 故障转移流程：
// 1. 选择第一个执行器发起调用
// 2. 如果调用失败（超时/异常），自动切换到下一个
// 3. 直到找到一个可用的执行器
// 4. 所有都失败则任务失败

// BUSYOVER 忙碌转移流程：
// 1. 选择第一个执行器发起调用
// 2. 如果返回"忙碌"状态，自动切换到下一个
// 3. 避免任务阻塞在繁忙的执行器上
面试重点：FAILOVER 和 BUSYOVER 的区别。FAILOVER 在调用失败时转移，BUSYOVER 在执行器忙碌时转移。两者都提升了任务执行的可靠性。

分片广播

分片广播原理

// 分片广播任务执行流程：
// 1. 调度中心向执行器的所有实例广播触发
// 2. 每个实例收到分片参数：shardIndex（当前分片序号）、shardTotal（总分片数）
// 3. 任务代码根据分片参数处理对应的数据子集

// 示例：处理 100 万条数据
@XxlJob("shardingJobHandler")
public void execute() {
    int shardIndex = XxlJobHelper.getShardIndex();  // 当前分片（0,1,2,...）
    int shardTotal = XxlJobHelper.getShardTotal();  // 总分片数

    // 分片查询：只处理 shardIndex 对应的数据
    // SELECT * FROM orders WHERE id % shardTotal = shardIndex
    List<Order> orders = orderMapper.selectByShard(shardTotal, shardIndex);

    for (Order order : orders) {
        processOrder(order);
    }
}

// 优势：
// - 3 个实例分片并行处理，速度提升 3 倍
// - 每个实例只处理 1/3 的数据
// - 天然支持水平扩展

阻塞策略

阻塞处理策略

策略行为适用场景
SERIAL_EXECUTION串行执行，上一次完成后再执行下一次顺序敏感任务
DISCARD_LATER丢弃本次调度，等待下一次非关键周期任务
COVER_EARLY覆盖之前未完成的调度，立即执行实时性要求高
 
// 场景：任务每 10 秒触发一次，但执行需要 30 秒

// SERIAL_EXECUTION（串行）：
// 第 1 次调度 → 执行（0-30s）
// 第 2 次调度 → 等待 → 第 1 次完成后执行（30-60s）
// 第 3 次调度 → 等待 → 第 2 次完成后执行（60-90s）
// 结果：任务堆积，延迟越来越大

// DISCARD_LATER（丢弃）：
// 第 1 次调度 → 执行（0-30s）
// 第 2 次调度 → 丢弃（因为上一次还没完成）
// 第 3 次调度 → 丢弃
// 第 4 次调度 → 执行（第 1 次已完成）
// 结果：不堆积，但可能丢失执行

// COVER_EARLY（覆盖）：
// 第 1 次调度 → 执行（0-30s）
// 第 2 次调度 → 中断第 1 次，立即执行
// 结果：实时性最好，但可能中断正在执行的任务

任务日志机制

// 任务执行中写日志
@XxlJob("demoJobHandler")
public void execute() {
    XxlJobHelper.log("任务开始执行");

    // 业务逻辑
    List<Order> orders = orderMapper.selectPending();
    XxlJobHelper.log("查询到 {} 条待处理订单", orders.size());

    for (Order order : orders) {
        processOrder(order);
        XxlJobHelper.log("处理订单 {} 完成", order.getId());
    }

    XxlJobHelper.log("任务执行完成");
    // 日志会通过回调发送给调度中心
}

// 日志回调流程：
// 1. 执行器将日志写入本地文件（logpath 目录）
// 2. 任务完成后，执行器向调度中心回调结果
// 3. 调度中心记录任务执行日志（成功/失败/耗时）
// 4. 管理界面可查看实时日志（通过 HTTP 实时读取执行器日志文件）

第三部分：模拟面试

请介绍 XXL-Job 的架构，调度中心和执行器是如何交互的？
参考：XXL-Job 由调度中心和执行器两部分组成。调度中心是独立部署的 Web 应用，负责管理任务配置、触发调度、管理日志。执行器嵌入业务应用，负责执行任务逻辑。交互流程：1）执行器启动时向调度中心注册地址，每 30 秒心跳续约；2）调度中心根据 Cron 表达式到时间后，通过 HTTP 调用执行器触发任务；3）执行器收到调度请求后异步执行任务；4）执行完成后通过 HTTP 回调结果给调度中心。调度中心集群部署时，通过数据库行锁保证同一任务只被一个节点调度。
XXL-Job 的路由策略有哪些？FAILOVER 和 BUSYOVER 有什么区别？
参考：XXL-Job 提供 9 种路由策略：FIRST、LAST、ROUND（轮询）、RANDOM（随机）、CONSISTENT_HASH（一致性 Hash）、LEAST_FREQUENTLY_USED（最不经常使用）、LEAST_RECENTLY_USED（最近最久未使用）、FAILOVER（故障转移）、BUSYOVER（忙碌转移）。FAILOVER 和 BUSYOVER 的区别：FAILOVER 在调用执行器失败时（超时、网络异常等）自动切换到下一个执行器重试；BUSYOVER 在执行器返回"忙碌"状态时自动切换到下一个。两者都提升了任务执行的可靠性，但 FAILOVER 关注的是"失败"，BUSYOVER 关注的是"阻塞"。
XXL-Job 的分片广播是什么原理？适合什么场景？
参考：分片广播是 XXL-Job 的并行任务处理机制。当任务配置为分片广播模式时，调度中心会向执行器的所有实例广播触发，每个实例收到两个分片参数：shardIndex（当前分片序号，从 0 开始）和 shardTotal（总分片数）。任务代码根据分片参数处理对应的数据子集，例如 SELECT * FROM table WHERE id % shardTotal = shardIndex。适合场景：1）大批量数据处理（如百万条数据导出）；2）定时数据同步（按 ID 取模分片并行同步）；3）报表生成（按时间维度分片计算）。优势是天然支持水平扩展，增加执行器实例即可提升并行度。
XXL-Job 的阻塞策略是什么？三种策略分别适用于什么场景？
参考：当任务的上一次调度还未完成时，新的调度触发就会被"阻塞"。三种策略：1）SERIAL_EXECUTION（串行执行）——新调度等待上一次完成后才执行，适合顺序敏感的任务，但可能导致任务堆积延迟；2）DISCARD_LATER（丢弃调度）——新调度被丢弃，等待下一次正常调度，适合非关键的周期任务，不会堆积但可能丢执行；3）COVER_EARLY（覆盖之前）——中断之前未完成的调度，立即执行新调度，适合实时性要求高的任务，但可能中断正在执行的业务逻辑。
XXL-Job 和 Elastic-Job 如何选型？
参考：选型建议：1）XXL-Job 适合大多数场景 — 轻量级、开箱即用、自带管理界面、支持失败重试和告警、社区活跃；2）Elastic-Job 适合需要精细分片的场景 — 基于 Zookeeper 的去中心化架构，支持分片个性化（每个分片可以有不同逻辑）；3）Quartz 适合简单场景 — 单机或简单集群，不需要分片和复杂路由。综合来看，XXL-Job 是首选：功能最全面（分片、路由、重试、告警、日志、任务编排 DAG），接入最简单（引入 starter 即可），管理最方便（Web 界面）。
XXL-Job 的 GLUE 模式是什么？有什么优势和风险？
参考：GLUE 模式允许在调度中心 Web 界面在线编辑任务代码（Java/Shell/Python 等），系统动态编译并执行。优势：1）修改任务逻辑无需重新部署应用，实现热更新；2）支持版本管理，每次修改都有历史记录，可回滚；3）支持多种语言，灵活性高。风险：1）安全风险 — 在线执行代码需要严格的权限控制，防止恶意代码注入；2）调试困难 — GLUE 代码在远程执行器上运行，本地无法调试；3）依赖限制 — GLUE(Java) 只能使用执行器已有的依赖。建议：简单任务用 GLUE 模式，复杂任务用 BEAN 模式在代码中实现。
XXL-Job 调度中心集群部署时，如何保证同一任务不被重复调度？
参考：XXL-Job 调度中心集群通过数据库行锁保证不重复调度。流程：1）所有调度中心节点共享同一个 MySQL 数据库；2）调度中心使用 xxl_job_lock 表的 FOR UPDATE 行锁进行调度竞争；3）一个调度周期开始时，所有节点竞争获取锁；4）获取锁成功的节点执行本次调度，其他节点跳过；5）调度完成后释放锁。这是典型的分布式锁方案，基于数据库的悲观锁实现。锁粒度是 schedule_type 级别（秒/分/时），不会出现同一任务被多个节点同时触发的情况。
