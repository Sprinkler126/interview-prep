1. 整体架构

Pulsar 三层架构
Broker（无状态）
消息路由与服务
无本地存储
可快速扩缩容
⬇️ 消息写入 / 读取
BookKeeper（持久化层）
分布式日志存储
Bookie 节点集群
Ledger + Entry 存储
⬇️ 元数据管理
ZooKeeper（元数据）
集群元数据
Broker 注册与发现
Topic ownership 管理

组件职责详解

  • Broker：无状态的消息服务层。接收 Producer 的消息写入请求，将消息持久化到 BookKeeper；接收 Consumer 的读取请求，从 BookKeeper 读取消息返回。Broker 不存储任何消息数据，可随时扩缩容。每个 Topic 由一个 Broker 负责（Owner），通过 ZooKeeper 选举。
  • BookKeeper (Bookie)：分布式日志存储系统，负责消息的持久化。数据以 Ledger 为单位管理，每个 Ledger 由多个 Entry（消息条目）组成。Bookie 节点将数据写入 Journal（预写日志）和 EntryLog（实际数据文件），并维护 LedgerIndex 用于快速查找。
  • ZooKeeper：管理集群元数据，包括 Broker 注册、Topic ownership、Namespace 配置、BookKeeper 集群信息等。Pulsar 正在逐步引入 etcd 作为替代方案。

2. 存算分离

存算分离 vs 存算一体

Pulsar 存算分离

  • Broker 无状态，不存储数据
  • 数据持久化在 BookKeeper
  • Broker 扩缩容不影响数据
  • Topic 迁移只需切换 Owner
  • 存储和计算独立扩展

Kafka 存算一体

  • Broker 既做路由又存数据
  • Partition 与 Broker 绑定
  • 扩缩容需要数据迁移（Rebalance）
  • Partition 越多，迁移越慢
  • 存储和计算耦合，扩展不灵活

存算分离的优势

  • 弹性伸缩：Broker 无状态，秒级扩缩容，无需数据迁移
  • 故障恢复快：Broker 宕机后，其他 Broker 可以立即接管 Topic（数据在 BookKeeper，无本地状态）
  • 独立扩展：计算瓶颈加 Broker，存储瓶颈加 Bookie，互不影响
  • 冷热数据分离：热数据在 BookKeeper，冷数据可自动卸载到 S3/HDFS（Tiered Storage）

3. 多租户

Pulsar 多租户层次结构
Tenant（租户） — 顶层隔离单元，如不同业务线、不同客户。独立的权限管理和配额
Namespace（命名空间） — 租户下的逻辑分组，如 dev/staging/prod。配置策略（TTL、保留策略、去重等）
Topic（主题） — 实际的消息通道，如 persistent://tenant/namespace/topic-name

多租户特性

  • 隔离性：不同租户的 Topic 互相隔离，权限独立管理
  • 配额管理：可按租户/命名空间设置存储容量、带宽、消息速率等配额
  • 策略继承：Namespace 级别的配置（TTL、保留策略、去重等）自动应用于其下所有 Topic
  • 命名规范：persistent://tenant/namespace/topic 或 non-persistent://tenant/namespace/topic

多租户是 Pulsar 区别于 Kafka 的核心特性之一。Kafka 的隔离需要通过多个集群实现，而 Pulsar 原生支持在同一集群内隔离多个租户。

Segment 存储的核心优势：Topic 的数据被自动分散到整个 BookKeeper 集群，不存在"热点 Broker"问题，天然实现了负载均衡。

5. 消息模型与 Subscription

四种 Subscription 模式
Exclusive
独占模式
一个 Subscription 只允许一个 Consumer
类似 Kafka 的独占消费
Shared
共享模式
多个 Consumer 轮询消费
不保证顺序，不能 ACK 单条
Failover
故障转移模式
一个 Active + 多个 Standby
Active 挂了 Standby 接管
Key_Shared
键共享模式
相同 Key 的消息发给同一 Consumer
保证 Key 级别顺序

Subscription 详解

模式并发顺序适用场景
Exclusive1 个 Consumer全局有序严格顺序场景
Shared多个 Consumer不保证高吞吐、允许乱序
Failover1 Active + N Standby全局有序高可用 + 顺序保证
Key_Shared多个 ConsumerKey 级有序按 Key 分区消费

队列模型 vs 流模型

Pulsar 统一了队列模型（RabbitMQ 风格）和流模型（Kafka 风格）：

  • 队列模型：Shared / Key_Shared 模式，消息被消费后 ACK，多消费者竞争消费
  • 流模型：Exclusive / Failover 模式，消息被持久化保留，按 offset 回溯消费
  • Cursor：每个 Subscription 维护一个 Cursor（消费位移），支持独立的消费进度管理

6. Pulsar Functions

轻量级流处理

Pulsar Functions 是内建的轻量级计算框架，无需部署 Flink/Spark 即可实现简单的消息转换和处理。

Input Topic
→
Function（用户代码）
→
Output Topic
  • 编程模型：只需实现一个简单的函数（Java/Python/Go），接收消息、处理、返回结果
  • 部署方式：pulsar-admin functions create 一键部署，无需管理集群
  • 语义保证：支持 At-Least-Once 和 Effectively-Once（通过去重）
  • 适用场景：数据过滤、格式转换、简单聚合、事件路由

7. Pulsar IO (Connector)

Source 和 Sink Connector

Pulsar IO 是连接器框架，类似于 Kafka Connect，支持将外部数据源/目标与 Pulsar 打通。

Source Connector

  • 数据源 → Pulsar Topic
  • 内置：Kafka、RabbitMQ、文件、JDBC、CDC
  • 自定义：实现 Source 接口

Sink Connector

  • Pulsar Topic → 数据目标
  • 内置：ES、HDFS、S3、JDBC、Redis
  • 自定义：实现 Sink 接口

8. 跨地域复制（Geo-Replication）

Pulsar 跨地域复制架构
集群 A（北京）
Producer A → Topic
自动复制到集群 B/C
集群 B（上海）
Producer B → Topic
自动复制到集群 A/C
集群 C（广州）
Producer C → Topic
自动复制到集群 A/B

Geo-Replication 特性

  • 双向同步：支持 Active-Active 多活，各集群都可以读写
  • 异步复制：消息异步复制到其他集群，低延迟
  • 全局有序：通过 MessageId（时间戳 + 所在集群）保证全局顺序
  • 命名空间级别：可配置哪些 Namespace 需要跨地域复制
  • 自动故障切换：某集群宕机，Producer 自动切换到其他集群

9. 延迟消息

原生支持任意延迟

Pulsar 原生支持任意时间的延迟消息，无需像 Kafka 那样自行实现，也无需像 RocketMQ 4.x 那样受 18 个固定级别限制。

  • 发送端：producer.newMessage().deliverAfter(delay, unit).value(msg).send()
  • 原理：延迟消息存入 __change_events Topic 的延迟跟踪 Ledger，到期后投递到目标 Topic
  • 精度：毫秒级精度，支持任意延迟时间
  • 共享模式支持：延迟消息在 Shared 模式下也能正常工作

延迟消息是 Pulsar 的一大卖点。Kafka 不原生支持延迟消息，RocketMQ 4.x 只有 18 个级别，Pulsar 原生支持任意延迟且精度高。

🎯第二部分：场景化讲解

2.1 多租户 SaaS 平台

场景描述

SaaS 平台为每个客户提供独立的消息通道，要求租户间隔离、独立配额、独立权限。

Tenant: ClientA
Tenant: ClientB
Tenant: ClientC
  • 每个租户有独立的 Namespace，配置独立的 TTL、保留策略
  • 通过 Pulsar 的 ACL 控制租户间的消息访问权限
  • 配额管理：限制每个租户的消息速率和存储容量
  • 一套集群服务多个租户，运维成本低

2.2 跨机房数据同步

Geo-Replication 应用

金融、电商等场景需要跨地域部署，Pulsar 的 Geo-Replication 可以实现：

  • 就近接入：用户消息发送到最近的集群，延迟最低
  • 双向同步：消息自动复制到其他集群，保证数据一致性
  • 灾备切换：某集群故障，用户自动切换到其他集群继续服务
  • 合规要求：数据跨地域备份满足监管合规

2.3 统一消息平台

一套 Pulsar 替代 Kafka + RabbitMQ + 延迟队列

Pulsar 统一了队列模型和流模型，可以在一套系统中替代多个消息中间件：

场景Pulsar 方案传统方案
日志/流处理Exclusive/Failover 订阅Kafka
任务队列Shared/Key_Shared 订阅RabbitMQ
延迟任务原生延迟消息Redis ZSet / RocketMQ

2.7 运维与部署

部署组件

  • ZooKeeper 集群：至少 3 节点，管理元数据
  • BookKeeper 集群：至少 3 个 Bookie 节点，消息持久化
  • Broker 集群：至少 2 个 Broker 节点，消息路由
  • Pulsar Manager / Dashboard：管理控制台

运维注意事项

  • BookKeeper 的 Journal 和 Ledger 存储建议使用 SSD
  • ZooKeeper 是单点依赖，需保证其高可用
  • Pulsar 正在引入 Oxia（基于 etcd）替代 ZooKeeper，降低运维复杂度
  • 监控指标：Broker 堆积、Bookie 磁盘使用率、消费延迟

🎤第三部分：模拟面试

Pulsar 的核心架构是什么？
三层架构——Broker（无状态消息路由层，不存储数据，可快速扩缩容）；BookKeeper（分布式日志存储层，消息持久化在 Bookie 节点）；ZooKeeper（元数据管理层，Topic ownership、集群配置）。核心特点是存算分离：Broker 无状态，数据在 BookKeeper，两者独立扩展。
Pulsar 的存算分离有什么优势？
四大优势——① 弹性伸缩：Broker 秒级扩缩容，无需数据迁移；② 故障恢复快：Broker 宕机，其他 Broker 立即接管（无本地状态）；③ 独立扩展：计算瓶颈加 Broker，存储瓶颈加 Bookie；④ 冷热分离：热数据在 BookKeeper，冷数据可卸载到 S3/HDFS（Tiered Storage）。相比 Kafka 的存算一体（Partition 与 Broker 绑定），Pulsar 的扩缩容不需要 Rebalance 数据迁移。
Pulsar 的多租户是怎么实现的？
三层层次结构——Tenant（租户，顶层隔离单元，独立权限管理）→ Namespace（命名空间，配置策略如 TTL、保留策略）→ Topic（实际消息通道）。命名规范：persistent://tenant/namespace/topic。支持按租户/命名空间设置配额（存储容量、带宽、速率）。这是 Pulsar 区别于 Kafka 的核心特性，Kafka 的隔离需要多集群实现。
Pulsar 的四种 Subscription 模式？
① Exclusive：独占，只允许一个 Consumer，全局有序；② Shared：共享，多个 Consumer 轮询消费，不保证顺序，适合高吞吐；③ Failover：故障转移，一个 Active + 多个 Standby，Active 挂了 Standby 接管，保证有序；④ Key_Shared：键共享，相同 Key 的消息发给同一 Consumer，Key 级有序。Pulsar 统一了队列模型（Shared/Key_Shared）和流模型（Exclusive/Failover）。
Pulsar 的 Segment 存储和 Kafka 的 Partition 有什么区别？
Pulsar：Topic 自动分割为多个 Segment（Ledger），每个 Ledger 分布在多个 Bookie 上，新 Segment 自动分配到新节点，天然负载均衡。Kafka：Partition 是固定分区，整个 Partition 的数据在一个 Broker 磁盘上，扩缩容需要 Rebalance 迁移数据。Segment 存储的核心优势是数据自动分散到整个集群，不存在热点 Broker。
Pulsar 和 Kafka 怎么选？
选 Pulsar：需要多租户隔离、频繁扩缩容、原生延迟消息、跨地域复制、统一消息平台（替代 Kafka + RabbitMQ）。选 Kafka：大数据生态集成（Flink/Spark/Hadoop）、成熟稳定的场景、已有 Kafka 运维经验。Pulsar 的劣势是运维复杂度高（Broker + BookKeeper + ZooKeeper），社区生态不如 Kafka 成熟。
Pulsar Functions 和 Flink 怎么选？
Pulsar Functions：轻量级，无需部署集群，适合简单的消息过滤、格式转换、事件路由。部署简单，一条命令即可。Flink：重量级，适合复杂流处理（CEP、窗口聚合、多流 Join、状态管理）。简单场景用 Functions，复杂场景用 Flink。两者也可以结合使用。
Pulsar 的 Geo-Replication 怎么实现？
在 Namespace 级别配置，支持 Active-Active 双向复制。消息写入本地集群后异步复制到其他集群，通过 MessageId（时间戳 + 集群标识）保证全局顺序。支持自动故障切换：某集群宕机，Producer 自动连接其他集群。适合跨地域部署、就近接入、灾备等场景。
Pulsar 的延迟消息怎么实现？
原生支持任意时间延迟，毫秒级精度。发送时 deliverAfter(delay, unit) 或 deliverAt(timestamp)。延迟消息存入内部 Topic __change_events 的延迟跟踪 Ledger，到期后自动投递到目标 Topic。无需像 Kafka 那样自行实现，也无需像 RocketMQ 4.x 受 18 个级别限制。
