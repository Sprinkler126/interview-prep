负载均衡

Ribbon vs Spring Cloud LoadBalancer

Ribbon（维护模式）

  • Netflix 开源，已停止维护
  • 客户端负载均衡
  • 丰富的负载策略（轮询/随机/权重/最少连接）
  • 与 Eureka 深度集成
  • 基于 ServerList + IRule
  • 支持区域感知

Spring Cloud LoadBalancer

  • Spring Cloud 官方实现
  • 客户端负载均衡
  • 默认轮询策略
  • 与 Nacos/Consul 集成
  • 基于 Reactor 的响应式
  • 可自定义 LoadBalancerClient
// 自定义负载均衡策略
@Configuration
public class LoadBalancerConfig {
    @Bean
    public ReactorLoadBalancer randomLoadBalancer(
            Environment environment,
            LoadBalancerClientFactory factory) {
        String name = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(
            factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
    }
}

// 指定服务使用自定义策略
@LoadBalancerClient(name = "user-service", configuration = LoadBalancerConfig.class)

@SentinelResource(
    value = "getOrder",
    blockHandler = "getOrderBlockHandler",    // 限流降级处理
    fallback = "getOrderFallback",            // 业务异常降级
    exceptionsToIgnore = {IllegalArgumentException.class}
)
public Order getOrder(Long id) {
    return orderService.getById(id);
}

// 限流降级方法（参数和返回值需一致，加 BlockException）
public Order getOrderBlockHandler(Long id, BlockException ex) {
    return new Order(id, "限流降级返回");
}

// 业务异常降级方法
public Order getOrderFallback(Long id, Throwable t) {
    return new Order(id, "服务降级返回");
}

// Feign 接口定义
@FeignClient(
    name = "user-service",          // 服务名
    path = "/api/users",            // 基础路径
    fallbackFactory = UserClientFallbackFactory.class,  // 降级工厂
    configuration = FeignConfig.class                    // 自定义配置
)
public interface UserClient {

    @GetMapping("/{id}")
    User getUser(@PathVariable("id") Long id);

    @PostMapping
    User createUser(@RequestBody User user);
}

// 降级工厂
@Component
public class UserClientFallbackFactory implements FallbackFactory {
    @Override
    public UserClient create(Throwable cause) {
        return new UserClient() {
            @Override
            public User getUser(Long id) {
                return new User(id, "降级用户", cause.getMessage());
            }
            @Override
            public User createUser(User user) {
                throw new RuntimeException("用户服务不可用", cause);
            }
        };
    }
}

第二部分：场景化讲解

API 网关

Gateway vs Zuul

Zuul 1.x

  • Netflix 开源，已停止维护
  • 基于 Servlet 的阻塞 IO
  • 一个请求一个线程
  • 不适合高并发场景
  • Filter 类型：pre/route/post/error

Spring Cloud Gateway

  • Spring Cloud 官方
  • 基于 WebFlux 的非阻塞 IO
  • Reactor 响应式编程
  • 高并发性能好
  • Route + Predicate + Filter

Gateway 核心概念

Route（路由）
ID + URI + Predicate + Filter
→
Predicate（断言）
匹配条件（Path/Header/Method 等）
→
Filter（过滤器）
请求/响应修改
# Gateway 路由配置
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service           # lb:// 表示负载均衡
          predicates:
            - Path=/api/users/**           # 路径匹配
            - Method=GET,POST              # 方法匹配
            - Header=X-Token, \d+          # 请求头匹配
          filters:
            - StripPrefix=1                # 去掉前缀 /api
            - AddResponseHeader=X-Response-Time, {elapsed}
            - name: RequestRateLimiter     # 限流过滤器
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - CircuitBreaker=name=myCircuitBreaker,fallbackUri=forward:/fallback

// 自定义全局过滤器（鉴权）
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {
    @Override
    public Mono filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (!StringUtils.hasText(token) || !validateToken(token)) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        return chain.filter(exchange);
    }

    @Override
    public int getOrder() {
        return -1; // 优先级，越小越先执行
    }
}

分布式事务 Seata

Seata 四种事务模式

模式原理优点缺点适用场景
AT自动补偿（拦截 SQL 生成 undo_log）无侵入、使用简单有全局锁、性能损耗大多数业务场景
TCCTry-Confirm-Cancel 手动补偿性能好、无全局锁侵入性强、需实现三个方法高性能要求
Saga长事务正向操作 + 补偿操作无锁、适合长流程补偿逻辑复杂长事务、跨系统
XA两阶段提交（2PC）强一致性性能差、锁粒度大强一致性要求

Seata AT 模式原理

TM 开启全局事务
@GlobalTransactional
→
RM 执行业务 SQL
拦截 SQL，记录 before/after image
→
RM 注册分支事务
写入 undo_log
→
TM 提交/回滚
TC 通知所有 RM
  • 一阶段：拦截业务 SQL，解析 SQL 语义，保存 before image 和 after image 到 undo_log 表，提交本地事务
  • 二阶段提交：异步清理 undo_log，释放全局锁
  • 二阶段回滚：根据 undo_log 中的 before image 生成反向补偿 SQL，执行回滚
// 使用 AT 模式
@Service
public class OrderService {

    @GlobalTransactional(timeoutMills = 60000, name = "create-order")
    public void createOrder(OrderDTO orderDTO) {
        // 1. 扣减库存（远程调用，自动加入分支事务）
        storageService.deduct(orderDTO.getProductId(), orderDTO.getCount());
        // 2. 扣减余额（远程调用）
        accountService.debit(orderDTO.getUserId(), orderDTO.getTotalAmount());
        // 3. 创建订单（本地事务）
        orderMapper.insert(orderDTO);
    }
}

第三部分：模拟面试

Spring Cloud 中服务注册与发现的原理是什么？为什么选择 Nacos？
参考：服务注册与发现原理：服务启动时向注册中心注册自己的地址信息（IP/端口/服务名/元数据），注册中心维护服务实例列表。消费者从注册中心获取服务列表，通过负载均衡选择实例发起调用。注册中心通过心跳检测实例健康状态，不健康的实例会被剔除。选择 Nacos 的原因：1）同时支持 AP 和 CP 模式，临时实例用 Distro 协议保证可用性，持久化实例用 Raft 保证一致性；2）内置配置管理功能，一个组件解决服务发现和配置两个问题；3）自带控制台，管理方便；4）Spring Cloud Alibaba 原生支持，社区活跃。
参考：Sentinel 熔断原理：通过滑动窗口统计资源的调用信息（成功数/异常数/响应时间），当统计指标达到阈值时触发熔断。熔断器有三个状态：Closed（正常放行）→ Open（直接拒绝，走降级逻辑）→ Half-Open（放行部分请求探测）。与 Hystrix 的区别：1）Sentinel 支持更丰富的流控（QPS/线程数/关联/链路/热点参数），Hystrix 只有线程池和信号量隔离；2）Sentinel 支持实时监控 Dashboard，Hystrix Dashboard 功能简单；3）Sentinel 规则可持久化到 Nacos/DataSource，Hystrix 只在内存中；4）Sentinel 支持系统保护（CPU/负载），Hystrix 不支持；5）Sentinel 使用滑动窗口统计，Hystrix 使用 RxJava。
参考：Gateway 基于 WebFlux + Reactor 实现非阻塞 IO。核心概念：Route（路由）= URI + Predicate + Filter。请求到达时，Gateway Handler Mapping 根据 Predicate 匹配路由，然后通过 Filter 链处理请求。Filter 分为 GatewayFilter（针对单个路由）和 GlobalFilter（全局生效）。自定义过滤器方式：1）实现 GatewayFilterFactory 创建局部过滤器；2）实现 GlobalFilter + Ordered 创建全局过滤器（如鉴权、日志）。Gateway 内置了 AddRequestHeader、StripPrefix、RequestRateLimiter、CircuitBreaker 等过滤器。执行顺序：pre filter → 转发请求 → post filter。
参考：Feign 原理：1）通过 @FeignClient 定义接口，Spring 启动时扫描并为接口创建 JDK 动态代理；2）调用接口方法时，代理对象解析注解信息（@GetMapping、@PathVariable 等），构建 HTTP 请求；3）通过 LoadBalancer 选择目标实例；4）通过 HTTP Client（默认 HttpURLConnection）发送请求。性能优化：1）替换 HTTP Client：使用 OkHttp 或 Apache HttpClient 开启连接池（feign.okhttp.enabled=true）；2）开启请求/响应压缩（gzip）；3）合理设置超时时间（connect-timeout、read-timeout）；4）减少日志输出（生产用 BASIC 或 NONE）；5）使用 @Cacheable 缓存不常变化的调用结果。
参考：Seata AT 模式是一种无侵入的分布式事务方案。原理：一阶段——拦截业务 SQL，解析 SQL 语义获取表名、WHERE 条件等，查询数据前镜像（before image），执行业务 SQL 后查询数据后镜像（after image），将前后镜像和 SQL 信息写入 undo_log 表，提交本地事务并注册分支事务到 TC。二阶段提交——异步清理 undo_log 和全局锁。二阶段回滚——根据 undo_log 的 before image 生成反向 SQL 执行回滚，回滚前校验数据是否被修改（对比 after image）。优点：对业务无侵入，使用简单（只需 @GlobalTransactional）。缺点：1）有全局锁竞争，高并发下性能受限；2）依赖 undo_log 表，增加数据库负担；3）不支持含有外键的表；4）SELECT FOR UPDATE 等特殊 SQL 需手动处理。
参考：分布式事务方案选择：1）强一致性方案：XA 两阶段提交（Seata XA 模式），性能差但保证强一致；TCC（Try-Confirm-Cancel），性能好但侵入性强。2）最终一致性方案：本地消息表 + MQ，可靠消息最终一致性；Seata Saga，适合长事务流程补偿；Seata AT 模式，无侵入但有全局锁。3）业务层面：尽量通过服务拆分避免分布式事务；使用补偿机制替代事务（如订单创建失败 → 发起退款）；幂等设计保证重试安全。推荐：大多数场景使用 Seata AT 模式；高性能场景使用 TCC；长事务使用 Saga；通过消息队列实现最终一致性。
参考：Nacos Config 动态刷新：1）客户端通过长轮询监听配置变更，配置变更时 Nacos Server 立即返回新配置；2）客户端收到新配置后触发 RefreshEvent；3）@RefreshScope 标注的 Bean 会被销毁重建，注入新的配置值；4）@Value 标注的属性通过 EnvironmentChangeEvent 更新。自定义监听：可以使用 @NacosConfigListener 监听特定配置变更。Spring Cloud Config 动态刷新：需要配合 Spring Cloud Bus（消息总线），配置变更后通过 Webhook 发送 BusRefreshEvent，所有客户端订阅消息后重新拉取配置。Nacos 方案更简单，不需要额外的 Bus 组件。
