JDK 动态代理 vs CGLIB

JDK 动态代理

  • 基于接口的代理
  • 使用 java.lang.reflect.Proxy
  • 目标类必须实现接口
  • 通过 InvocationHandler 拦截方法
  • 性能较好（JDK 8+ 优化）
  • Spring 默认方式（有接口时）
// JDK 动态代理核心
Object proxy = Proxy.newProxyInstance(
    classLoader,
    interfaces,
    (proxy, method, args) -> {
        // 前置增强
        Object result = method.invoke(target, args);
        // 后置增强
        return result;
    }
);

CGLIB 代理

  • 基于继承的代理
  • 使用字节码生成技术（ASM）
  • 目标类不能是 final 的
  • 生成目标类的子类作为代理
  • 创建代理较慢，调用较快
  • 无接口时使用
// CGLIB 代理核心
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(targetClass);
enhancer.setCallback(
    (MethodInterceptor) (obj, method, args, proxy) -> {
        // 前置增强
        Object result = proxy.invokeSuper(obj, args);
        // 后置增强
        return result;
    }
);
Object proxy = enhancer.create();
Spring Boot 2.x 默认使用 CGLIB 代理（spring.aop.proxy-target-class=true），即使目标类实现了接口也会使用 CGLIB，避免类型转换问题。

五种通知类型

通知注解执行时机参数
前置通知@Before方法执行前JoinPoint
后置通知@After方法执行后（无论是否异常）JoinPoint
返回通知@AfterReturning方法正常返回后JoinPoint, returning
异常通知@AfterThrowing方法抛出异常后JoinPoint, throwing
环绕通知@Around方法执行前后ProceedingJoinPoint
 
@Aspect
@Component
public class LogAspect {
    @Around("execution(* com.example.service.*.*(..))")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            return result;
        } finally {
            long cost = System.currentTimeMillis() - start;
            log.info("{}.{} cost {}ms",
                pjp.getTarget().getClass().getSimpleName(),
                pjp.getSignature().getName(), cost);
        }
    }
}

Spring 事务

七种事务传播行为

传播行为说明
REQUIRED（默认）当前有事务就加入，没有就新建事务
SUPPORTS当前有事务就加入，没有就以非事务方式执行
MANDATORY当前必须有事务，否则抛出异常
REQUIRES_NEW总是新建事务，挂起当前事务
NOT_SUPPORTED以非事务方式执行，挂起当前事务
NEVER以非事务方式执行，当前有事务则抛出异常
NESTED当前有事务则创建嵌套事务（保存点），没有则新建
面试高频：REQUIRED vs REQUIRES_NEW vs NESTED。REQUIRED 加入当前事务，内外一起回滚；REQUIRES_NEW 独立事务，内层回滚不影响外层；NESTED 嵌套事务，内层回滚不影响外层（通过 SavePoint 实现）。

// 自调用问题示例
@Service
public class OrderService {
    public void createOrder() {
        // this 调用，不走代理，事务不生效！
        this.updateStock();
    }

    @Transactional
    public void updateStock() {
        // 事务不生效
    }
}

// 解决方案 1：注入自身
@Autowired
private OrderService self;

public void createOrder() {
    self.updateStock(); // 通过代理对象调用
}

// 解决方案 2：AopContext
public void createOrder() {
    ((OrderService) AopContext.currentProxy()).updateStock();
}

为什么需要三级缓存？

  • 一级缓存：存储完全初始化好的 Bean，避免重复创建
  • 二级缓存：存储提前暴露的半成品 Bean，解决循环依赖
  • 三级缓存：存储 Bean 工厂，延迟生成代理对象。如果 A 被 AOP 代理，需要在属性注入前就暴露代理对象，三级缓存的 ObjectFactory 可以在需要时调用 getEarlyBeanReference() 生成代理
不能解决的循环依赖：1）构造器注入的循环依赖（实例化阶段就需要对方，无法提前暴露）；2）prototype 作用域的循环依赖（不放入缓存）。@Async 的循环依赖也需要特殊处理。

常见面试陷阱题

@Transactional 加在 private 方法上会怎样？

答：事务不会生效。Spring AOP 默认使用 JDK 动态代理或 CGLIB，只能代理 public 方法。private 方法无法被代理，@Transactional 注解会被忽略，不会抛异常也不会报错。

Spring Bean 的初始化是线程安全的吗？

答：Bean 的创建过程（实例化、属性注入、初始化）是线程安全的，由 Spring 容器在单线程中完成。但 Bean 实例本身不一定线程安全——如果 Bean 有可变的成员变量，多线程并发访问时可能出现线程安全问题。Spring 推荐 Bean 设计为无状态的。

ApplicationContext 和 BeanFactory 的区别？为什么不直接用 BeanFactory？

答：ApplicationContext 继承了 BeanFactory，功能更丰富：支持国际化（MessageSource）、事件发布（ApplicationEvent）、AOP 自动集成、Environment 抽象、资源加载等。BeanFactory 是延迟加载，ApplicationContext 是预加载（容器启动时创建所有单例 Bean），能更快发现配置错误。实际开发中几乎都使用 ApplicationContext。

第三部分：模拟面试

请详细介绍一下 Spring Bean 的完整生命周期。
参考：Bean 生命周期包括：1）实例化：通过构造方法或工厂方法创建 Bean 实例；2）属性填充：注入 @Autowired 依赖和 @Value 值；3）Aware 回调：依次调用 BeanNameAware、BeanFactoryAware、ApplicationContextAware；4）BeanPostProcessor 前置处理；5）@PostConstruct 标注的方法；6）InitializingBean#afterPropertiesSet；7）自定义 init-method；8）BeanPostProcessor 后置处理（AOP 代理在此创建）；9）Bean 就绪，放入容器；10）使用；11）销毁：@PreDestroy → DisposableBean#destroy → 自定义 destroy-method。关键点：AOP 代理在第 8 步创建，所以 @PostConstruct 中获取的是原生对象。
Spring 是如何解决循环依赖的？为什么需要三级缓存而不是两级？
参考：Spring 通过三级缓存解决 singleton 的属性注入循环依赖。一级缓存存完整 Bean，二级缓存存提前暴露的半成品 Bean，三级缓存存 ObjectFactory。当创建 A 时发现依赖 B，将 A 的 ObjectFactory 放入三级缓存后去创建 B，B 创建时从三级缓存获取 A 的早期引用。为什么不能用两级缓存？因为如果 A 需要 AOP 代理，代理对象应该在初始化后创建（postProcessAfterInitialization），但循环依赖需要在属性注入阶段就暴露对象。三级缓存的 ObjectFactory 的 getEarlyBeanReference() 方法可以在需要时提前创建代理，如果不需要代理则返回原对象，既保证了正确性又避免了过早创建代理。注意：构造器注入和 prototype 作用域的循环依赖无法解决。
@Transactional 的传播行为 REQUIRED、REQUIRES_NEW、NESTED 有什么区别？
参考：REQUIRED（默认）：当前有事务就加入，没有就新建。内外方法在同一事务中，任一异常都会整体回滚。REQUIRES_NEW：总是新建事务，挂起当前事务。内层事务独立提交或回滚，不影响外层事务。NESTED：如果当前有事务，创建嵌套事务（通过 SavePoint 实现），内层回滚只回滚到保存点，不影响外层。如果没有事务则新建。实际场景：REQUIRED 用于大多数业务方法；REQUIRES_NEW 用于日志记录等需要独立提交的场景；NESTED 用于部分失败不影响整体的场景。
Spring AOP 的实现原理是什么？JDK 动态代理和 CGLIB 有什么区别？
参考：Spring AOP 在运行期通过代理模式实现。JDK 动态代理基于 java.lang.reflect.Proxy，通过 InvocationHandler 拦截方法调用，要求目标类实现接口。CGLIB 基于 ASM 字节码生成库，生成目标类的子类作为代理，不要求实现接口但目标类不能是 final 的。区别：JDK 代理创建快，调用稍慢（反射）；CGLIB 创建慢（生成字节码），调用快（直接调用）。Spring Boot 2.x 默认使用 CGLIB 代理。Spring 5 引入了基于 AspectJ 的编译期织入作为补充。
Spring 事务失效有哪些常见场景？如何避免？
参考：事务失效场景：1）方法非 public：AOP 只能代理 public 方法；2）自调用：通过 this.method() 调用绕过了代理，解决：注入自身或使用 AopContext；3）异常被 catch：Spring 默认只回滚 RuntimeException，解决：加 rollbackFor=Exception.class；4）异常类型不匹配：抛出 checked 异常不回滚；5）传播行为配置错误：如 NOT_SUPPORTED；6）数据库不支持事务：MySQL MyISAM；7）Bean 未被 Spring 管理。最佳实践：始终加 rollbackFor=Exception.class，避免自调用，使用构造器注入。
参考：1）工厂模式：BeanFactory 创建和管理 Bean；2）单例模式：Bean 默认 singleton，通过三级缓存管理；3）代理模式：AOP 通过 JDK 动态代理或 CGLIB 实现方法增强；4）模板方法：JdbcTemplate 封装了获取连接、执行 SQL、关闭连接的固定流程，子类只需实现 SQL 逻辑；5）观察者模式：ApplicationEvent + ApplicationListener 实现事件驱动；6）适配器模式：Spring MVC 的 HandlerAdapter 适配不同类型的 Handler（Controller 方法、HttpRequestHandler 等）；7）策略模式：Resource 接口有 ClassPathResource、FileSystemResource 等多种实现。
参考：@Autowired 是 Spring 注解，按类型注入（byType），找到多个候选时按字段名匹配，可配合 @Qualifier 指定名称。@Resource 是 JSR-250 标准注解，先按名称（byName）再按类型（byType）注入。区别：1）来源不同：@Autowired 是 Spring 特有，@Resource 是 Java 标准；2）注入策略不同：@Autowired 先类型后名称，@Resource 先名称后类型；3）@Autowired 支持 required=false 允许 null，@Resource 不支持。推荐使用构造器注入（Spring 官方推荐），可以保证依赖不为空且便于单元测试。
参考：BeanPostProcessor 是 Spring 的扩展点，在 Bean 初始化前后进行处理。postProcessBeforeInitialization 在 @PostConstruct 之前执行，postProcessAfterInitialization 在初始化之后执行（AOP 代理在此创建）。常见实现：1）AutowiredAnnotationBeanPostProcessor：处理 @Autowired 注入；2）CommonAnnotationBeanPostProcessor：处理 @Resource、@PostConstruct、@PreDestroy；3）AbstractAutoProxyCreator：创建 AOP 代理；4）ApplicationContextAwareProcessor：注入 ApplicationContext；5）ScheduledAnnotationBeanPostProcessor：处理 @Scheduled 定时任务。通过实现 BeanPostProcessor 可以在不修改业务代码的情况下增强 Bean 功能。
参考：问题：singleton Bean 在容器启动时创建并注入 prototype Bean 的实例，之后每次调用 singleton Bean 的方法时，使用的都是同一个 prototype 实例，prototype 的"每次创建新实例"特性失效。解决方案：1）@Lookup 注解：在 singleton Bean 中添加 @Lookup 方法，Spring 会通过 CGLIB 重写该方法，每次调用时从容器获取新的 prototype 实例；2）注入 ObjectFactory<PrototypeBean>，每次调用 getObject() 获取新实例；3）注入 ApplicationContext，每次调用 getBean() 获取新实例。推荐使用 @Lookup 方式，代码最简洁。
