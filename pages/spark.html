核心组件

  • Driver：运行用户 main() 函数，创建 SparkContext，将用户程序转化为 Job，划分 Stage，调度 Task 到 Executor 执行。Driver 还负责维护 DAG、Stage 划分、Task 分发和结果收集。
  • Executor：Worker 节点上的 JVM 进程，负责执行 Task。每个 Executor 有多个线程槽（cores），可并行执行多个 Task。Executor 还负责将数据缓存在内存/磁盘中。
  • Cluster Manager：集群资源管理器，负责资源分配和调度。支持 Standalone（Spark 自带）、YARN（Hadoop）、Kubernetes、Mesos 等。
  • DAGScheduler：将 RDD 的依赖关系转化为 DAG，按 Shuffle 边界划分 Stage。
  • TaskScheduler：将 Stage 中的 Task 分发到 Executor 执行，处理失败重试。

Job → Stage → Task 层次

User Code

  • Job：每个 Action 操作（如 collect、save）触发一个 Job
  • Stage：按 Shuffle 依赖划分，窄依赖在一个 Stage 内，宽依赖是 Stage 边界
  • Task：Stage 内每个 Partition 对应一个 Task，Task 是最小执行单元

2. RDD 五大特性

RDD (Resilient Distributed Dataset) 核心特性
① 一组 Partition — 数据的最小分片，每个 Partition 对应一个 Task
② 一个计算函数 — 对每个 Partition 执行的 compute() 函数，惰性求值
③ RDD 间的依赖关系 — 窄依赖（OneToOneDependency）或宽依赖（ShuffleDependency）
④ 一个 Partitioner — 分区器（HashPartitioner / RangePartitioner），决定 KV 类型 RDD 的分区策略
⑤ 一组首选位置 — 数据本地性偏好（Preferred Location），调度 Task 时优先在数据所在节点执行

窄依赖 vs 宽依赖

窄依赖（NarrowDependency）

  • 父 RDD 的一个 Partition 只被子 RDD 的一个 Partition 依赖
  • 如：map、filter、union
  • 可以在同一个 Stage 内流水线执行
  • 无需 Shuffle

宽依赖（ShuffleDependency）

  • 父 RDD 的一个 Partition 被子 RDD 的多个 Partition 依赖
  • 如：groupByKey、reduceByKey、join
  • 需要 Shuffle，是 Stage 的边界
  • 涉及磁盘 IO 和网络传输

3. RDD 血统（Lineage）与容错

Lineage 机制

RDD 不存储实际数据，只记录数据的血统信息（即从数据源到当前 RDD 的一系列变换操作）。当某个 Partition 数据丢失时，Spark 根据 Lineage 信息重新计算该 Partition，而非全量重算。

HDFS 文件
→
map()
→
filter()
→
reduceByKey()

如果 reduceByKey 阶段某个 Partition 丢失，Spark 只需从 HDFS 重新读取对应的 Partition 并重算 map → filter → reduceByKey，而非重算所有 Partition。

Checkpoint 机制

Lineage 过长时（如迭代算法），容错重算代价很大。Checkpoint 将 RDD 数据持久化到 HDFS，截断 Lineage。

  • Reliable Checkpoint：数据写入 HDFS，可靠存储
  • Local Checkpoint：数据写入本地磁盘，适合迭代算法中间结果
  • 使用前需调用 sc.setCheckpointDir("hdfs://...")

Catalyst 四阶段优化

  • 1. 解析（Parse）：SQL 文本 → Unresolved Logical Plan（未绑定 Schema）
  • 2. 分析（Analyze）：绑定 Schema → Analyzed Logical Plan（解析表名、列名、函数）
  • 3. 优化（Optimize）：应用优化规则 → Optimized Logical Plan（谓词下推、列裁剪、常量折叠、Join 重排序）
  • 4. 物理计划（Physical Plan）：选择具体执行策略 → 生成 Java 字节码（Whole-Stage Code Generation）

Tungsten 执行引擎

  • 内存管理：Off-Heap 内存管理，绕过 JVM GC，使用 Sun.misc.Unsafe 直接操作内存
  • 缓存友好：数据以二进制格式存储（UnsafeRow），紧凑排列，提高 CPU Cache 命中率
  • 代码生成：Whole-Stage Code Generation，将多个操作合并为一个函数，消除虚函数调用
  • 序列化：自定义二进制序列化，比 Java 序列化快 10 倍以上

核心思想：无限表

Structured Streaming 将流数据视为一张不断追加的无限表。每个触发间隔（Trigger Interval）处理新到达的数据行，就像对一张表执行增量查询。

输出模式

模式说明适用场景
Append只输出新增行无聚合操作、有水印的窗口聚合
Complete输出完整结果表聚合查询（groupBy）
Update只输出有变化的行聚合查询（增量更新）

水印（Watermark）机制

处理乱序数据的核心机制。水印定义了"最大允许延迟"：超过水印的迟到数据会被丢弃。

事件时间 - 最大延迟 = 水印
→
水印之前的数据窗口关闭
→
超过水印的迟到数据丢弃

代码示例：df.withWatermark("eventTime", "10 minutes") 表示允许最大 10 分钟的乱序延迟。

微批处理 vs 连续处理

微批处理（默认）

  • 按 Trigger Interval 切分批次
  • 每个批次是一次完整的批处理
  • 延迟：秒级（通常 100ms~数秒）
  • Exactly-Once 语义
  • 所有操作都支持

连续处理（实验性）

  • 持续处理数据，低延迟
  • 延迟：毫秒级
  • At-Least-Once 语义
  • 只支持部分操作
  • 目前仍为实验性功能

7. Shuffle 机制

Shuffle 演进：Hash Shuffle → Sort Shuffle

Hash Shuffle（已废弃）

  • 每个 Map Task 为每个 Reduce Task 创建一个文件
  • 文件数 = Map Tasks × Reduce Tasks
  • 大量小文件，随机 IO 严重
  • 内存开销大

Sort Shuffle（默认）

  • 每个 Map Task 只输出一个文件
  • 先在内存中排序，再 spill 到磁盘
  • 最后合并为一个有序文件 + 索引
  • 大幅减少文件数和随机 IO

Shuffle Write / Read 流程

  • Shuffle Write：Map 端将结果按 Reduce 端分区排序，写入 Shuffle 文件（一个 Map Task 一个文件），同时生成索引文件记录每个分区的偏移量
  • Shuffle Read：Reduce 端从所有 Map Task 的 Shuffle 文件中拉取自己对应分区的数据，进行归并排序
  • Shuffle Manager：Spark 3.0 引入 External Shuffle Service，Shuffle 数据写入外部服务而非 Executor，Executor 可以独立扩缩容

Shuffle 优化

  • 减少 Shuffle：用 reduceByKey 替代 groupByKey（Map 端预聚合）
  • Broadcast Join：小表广播，避免 Shuffle
  • AQE（Adaptive Query Execution）：Spark 3.0+，运行时动态调整 Shuffle 分区数
  • Shuffle 数据压缩：spark.shuffle.compress=true（默认开启）

AQE 自适应查询执行 — 设计动机

设计起点：传统 Spark 的执行计划在编译期一次性确定，依赖统计信息估算。但统计信息可能过期、Join 后行数难预估，导致 Shuffle 分区数不合理——分区太多产生海量小文件（Task 调度开销大），分区太少导致单个 Task 数据倾斜（OOM 或长尾）。

编译期生成逻辑计划
→
执行到 Shuffle 边界
拿到实际数据统计
→
动态调整后续计划
合并小分区/拆分大分区
AQE 优化解决的问题原理
动态合并 Shuffle 分区小分区过多（默认 200 可能浪费）把小分区合并成大分区，减少 Task 数
动态切换 Join 策略编译期以为大表，运行时发现是 小表自动转 Broadcast Hash Join，避免 Shuffle
动态拆分倾斜分区某分区数据远超其他（数据倾斜）把大分区按 Key 拆成多个子分区并行处理
面试要点：AQE 的核心思想是"用运行时真实统计信息修正编译期估算"——把静态优化变成自适应优化。开启：spark.sql.adaptive.enabled=true（Spark 3.2+ 默认开启）。这是 Spark 3.0 最重要的特性之一。

内存管理要点

2.6b 数据湖三剑客 — Iceberg / Hudi / Delta Lake

设计起点：为什么需要数据湖格式？

传统数仓用 Hive/HDFS，痛点：① 不支持 ACID（并发写覆盖、读到半成品）；② 不支持 upsert/delete（只能整表覆盖或分区覆盖）；③ 小文件多，元数据管理难。数据湖格式在 Parquet/ORC 之上加一层元数据层 + 事务日志，把"文件集合"变成"可事务的表"。

数据湖格式对比
维度Apache IcebergApache HudiDelta Lake
主导方Netflix 开源Uber 开源Databricks (Spark 母公司)
核心特性表格式规范，引擎无关Upsert/Delete 优化，CDC 友好与 Spark 深度集成
更新能力Copy-on-Write / Merge-on-ReadCoW / MoR（MoR 写快读慢）Copy-on-Write 为主
时间旅行✅ Time Travel✅✅
Schema 演进✅ 强（增删改列、重命名）✅✅
分区演进✅ 隐藏分区需重建需重建
引擎兼容Spark/Flink/Trino/HiveSpark/Flink/HiveSpark 为主（Flink 有 connector）
适用场景多引擎、海量分析、表格式标准流批一体、频繁 upsert、CDC 入湖已用 Databricks/Spark 生态

Copy-on-Write vs Merge-on-Read — 更新策略的取舍

Copy-on-Write (CoW)

  • 更新时重写整个文件，新文件含合并后的数据
  • 读快：读时无需合并，直接读
  • 写慢：每次更新放大（改一条要重写一个文件）
  • 适合读多写少、批量更新

Merge-on-Read (MoR)

  • 更新写入增量 log 文件，读时合并 base + log
  • 写快：只追加 log，不重写
  • 读慢：读时需合并，Compaction 后才变快
  • 适合写多读少、频繁 upsert（如 CDC 入湖）
面试要点：数据湖格式本质是"给 Parquet 文件集合加 ACID 事务日志"。Iceberg 的隐藏分区（按 timestamp 自动转 day/month）解决"Hive 分区字段必须硬编码进 SQL"的痛点。三者选型：多引擎/Iceberg 标准化选 Iceberg，CDC 频繁更新选 Hudi，Databricks 生态选 Delta。

2.7 常见问题排查

数据倾斜

表现：个别 Task 执行时间远超其他 Task。

排查：Spark UI 查看各 Stage 的 Task 执行时间分布。

解决：

  • 加盐打散：给倾斜 Key 加随机前缀，分散到多个 Task
  • 两阶段聚合：先局部聚合再全局聚合
  • Broadcast Join：小表广播避免 Shuffle
  • AQE：Spark 3.0+ 自动拆分倾斜分区

OOM 问题

  • Driver OOM：collect() 收集过多数据到 Driver，增大 spark.driver.memory 或避免 collect
  • Executor OOM：增大 spark.executor.memory、减少 spark.executor.cores、增加 Shuffle 分区数
  • GC 问题：使用 Kryo 序列化、减少缓存、增大 Off-Heap 内存

🎤第三部分：模拟面试

Spark 的整体架构是什么？
三层架构——Driver（运行用户 main()，创建 SparkContext，DAGScheduler 划分 Stage，TaskScheduler 分发 Task）；Cluster Manager（资源调度器，Standalone/YARN/K8s/Mesos）；Executor（Worker 节点的 JVM 进程，执行 Task，缓存数据）。Job 由 Action 触发，按 Shuffle 边界划分 Stage，每个 Partition 一个 Task。
RDD 的五大特性是什么？
① 一组 Partition（数据分片，每个 Partition 对应一个 Task）；② 一个计算函数（对每个 Partition 的 compute()，惰性求值）；③ RDD 间的依赖关系（窄依赖不需 Shuffle，宽依赖是 Stage 边界）；④ 一个 Partitioner（Hash/Range 分区器，决定 KV RDD 的分区策略）；⑤ 一组首选位置（数据本地性，优先在数据所在节点调度 Task）。
Spark 如何实现容错？
通过 Lineage（血统）：RDD 不存储实际数据，只记录从数据源到当前 RDD 的变换操作链。Partition 丢失时，根据 Lineage 只重算该 Partition，而非全量重算。对于迭代算法（Lineage 过长），使用 Checkpoint 将 RDD 持久化到 HDFS，截断 Lineage，降低重算代价。
DataFrame、Dataset 和 RDD 的区别？
RDD：最基础，类型安全，无 Catalyst 优化，Java 序列化，适合非结构化数据。DataFrame：带 Schema 的 Dataset[Row]，有 Catalyst 优化器和 Tungsten 引擎，SQL + DSL API。Dataset：编译时类型安全 + Catalyst 优化，Scala/Java 专属。优先使用 DataFrame/Dataset（有优化），只在需要底层控制时用 RDD。
Spark SQL 的 Catalyst 优化器做了什么？
四阶段优化——① Parse：SQL → Unresolved Logical Plan；② Analyze：绑定 Schema；③ Optimize：谓词下推（filter 推到数据源）、列裁剪（只读需要的列）、常量折叠、Join 重排序；④ Physical Plan：选择执行策略 + Whole-Stage Code Generation（合并操作，生成 Java 字节码，消除虚函数调用，提升 5~10 倍）。
Structured Streaming 的水印机制？
水印（Watermark）处理乱序数据。定义"最大允许延迟"：水印 = max event time - 允许延迟。窗口只有在水印超过窗口结束时间后才会关闭并输出结果。超过水印的迟到数据被丢弃。例如 withWatermark("eventTime", "10 minutes") 表示允许 10 分钟乱序。配合输出模式：Append 模式需要水印才能输出窗口聚合结果。
Spark 的 Shuffle 机制？
Sort Shuffle（默认）：每个 Map Task 输出一个文件（先内存排序，spill 到磁盘，最后合并为有序文件 + 索引）。Reduce 端拉取所有 Map 的对应分区数据，归并排序。优化：① 减少 Shuffle（reduceByKey 替代 groupByKey，Map 端预聚合）；② Broadcast Join（小表广播）；③ AQE（运行时动态调整分区数）；④ Shuffle 数据压缩。
Spark 和 Flink 怎么选？
选 Spark：批处理为主、离线数仓、机器学习、SQL 分析、延迟要求不高（秒级可接受）的流处理。选 Flink：低延迟流处理（毫秒级）、复杂事件处理 CEP、精确状态管理、实时风控/监控。趋势：Spark 向流靠拢（连续处理），Flink 向批靠拢（流批一体），两者差距在缩小。
Spark 的内存管理模型？
统一内存管理（1.6+）：Spark 内存（60%）= Storage（50%）+ Execution（50%），两者可互相借用，Execution 优先级更高。Storage 用于缓存 RDD/DataFrame，Execution 用于 Shuffle/Join/Sort。用户内存（40%）用于用户数据结构。Spark 3.0+ 支持 Off-Heap 内存，绕过 JVM GC。
Spark on K8s 的优势？
① 资源隔离：每个 Spark 作业运行在独立 Pod 中；② 弹性伸缩：K8s 自动调度 Executor Pod；③ 统一资源管理：K8s 管理所有计算任务（Spark、Flink、TensorFlow）；④ GPU 支持：原生支持 GPU 资源调度。Cluster 模式（Driver 在 K8s 中）适合生产，Client 模式（Driver 在客户端）适合调试。
如何排查 Spark 数据倾斜？
排查：Spark UI 查看各 Stage Task 执行时间分布，个别 Task 远超其他即为倾斜。解决：① 加盐打散：给倾斜 Key 加随机前缀；② 两阶段聚合：先局部聚合再全局聚合；③ Broadcast Join：小表广播避免 Shuffle；④ AQE（Spark 3.0+）：自动拆分倾斜分区。
