核心架构要点

Nacos 是阿里巴巴开源的动态服务发现、配置管理和服务管理平台，主要提供两大功能：

Naming Service（服务注册与发现）：服务端维护内存注册表 ConcurrentHashMap<ServiceName, Map<Cluster, List<Instance>>>，客户端通过 Open API 或 gRPC 与服务端交互。

Configuration Service（配置管理）：支持配置的 CRUD、灰度发布、版本管理、监听机制，底层数据持久化到 MySQL 或内嵌 Derby 数据库。

临时实例（Ephemeral）

AP 模式 默认类型

  • 客户端主动发送心跳维持注册（默认 5 秒）
  • 超过 15 秒未心跳标记不健康，超过 30 秒摘除
  • 使用 Distro 协议（AP）同步数据
  • 不健康实例不会被持久化，服务端重启后丢失
  • 适合大规模微服务、对可用性要求高的场景

持久化实例（Persistent）

CP 模式 需手动设置

  • 服务端主动发起健康检查（TCP/HTTP 探测）
  • 数据持久化到数据库，服务端重启不丢失
  • 使用 Raft 协议（CP）保证数据一致性
  • 需要选出 Leader，写入需多数节点确认
  • 适合需要强一致性的场景（如数据库服务）

CP（Raft）与 AP（Distro）选择

特性AP 模式（Distro）CP 模式（Raft）
协议Distro（类 Gossip）Raft（强 Leader）
一致性最终一致性强一致性
可用性高（分区容忍）可能因选举短暂不可用
实例类型临时实例持久化实例
数据同步全量同步 + 校验和日志复制
适用场景微服务注册发现配置管理、持久化服务
Nacos 2.x 中 Naming 模块默认使用 Distro（AP），Config 模块使用 Raft（CP）。Distro 协议是 Nacos 自研的去中心化协议，每个节点负责一部分数据，定期与其他节点全量同步。

服务发现机制

Nacos 采用 Push + Pull 结合的方式实现服务发现：

  • Pull（客户端定时拉取）：客户端默认每 10 秒从服务端拉取一次服务列表（HTTP 长轮询）
  • Push（UDP 推送）：当服务实例发生变更时，服务端通过 UDP 主动推送变更事件给订阅了该服务的客户端
  • Nacos 2.x gRPC：客户端与服务端建立长连接，服务端可直接通过 gRPC 长连接推送变更
Nacos 2.x 用 gRPC 取代了 HTTP 长轮询，通信效率更高。默认连接超时 5 秒，客户端每 10 秒发送心跳保持连接。

持久化实例健康检查（服务端主动探测）

  • TCP 探测：服务端尝试 TCP 连接实例的 IP + Port，成功则健康
  • HTTP 探测：发送 HTTP GET 请求到指定 URL，返回 2xx 则健康
  • 探测间隔默认 5 秒，连续失败 3 次标记不健康
  • 持久化实例即使不健康也不会自动摘除（需手动删除）

长轮询机制（Long Polling）

配置变更通知流程
客户端发起请求
携带 MD5 值
→

一致则挂起 30s
→
配置变更
或超时 30s
→
立即返回
最新配置
  • 客户端向服务端发起 HTTP 请求，携带本地配置的 MD5 摘要
  • 服务端对比 MD5：若相同则 hold 住连接（最长 30 秒），期间配置变更则立即返回
  • 若 30 秒内无变更，返回 304 Not Modified，客户端重新发起请求
  • 客户端还有一层 定时拉取 作为兜底（默认每 15 秒）
长轮询不是真正的 Push，本质是客户端发起长连接请求，服务端延迟响应。相比短轮询，大幅减少了无效请求。

配置灰度发布与加密

Beta 发布：支持将配置灰度推送给部分 IP 的实例，验证无误后再全量发布。灰度期间只有指定 IP 的客户端会拉取到新配置。

配置加密：Nacos 2.1+ 支持加密插件，可对接 KMS 或自定义加密算法。配置项可标记为加密字段，存储和传输时自动加解密。

数据存储：内嵌 Derby vs 外部 MySQL

内嵌 Derby（默认）

  • 单机模式使用，零配置
  • 数据存储在本地文件
  • 不支持集群数据共享
  • 适合开发测试

外部 MySQL（生产推荐）

  • 集群模式必须使用
  • 支持主从复制高可用
  • 所有节点共享同一数据库
  • 建议 MySQL 5.7+ 或 8.0

集群节点间数据同步

AP 模式（Distro 协议）：

  • 去中心化架构，每个节点负责一部分数据（根据 hash 分片）
  • 注册请求由负责该数据的节点处理，然后异步同步给其他节点
  • 节点间定期全量数据同步（每 10 秒），通过校验和（checksum）比对差异
  • 新增节点加入时，从其他节点全量拉取数据

CP 模式（Raft 协议）：

  • 强 Leader 架构，所有写操作必须经过 Leader
  • Leader 将日志复制到多数 Follower 后才返回成功
  • Leader 故障时触发选举（选举超时 15-30 秒）
  • Nacos 2.x 使用 JRaft（百度开源的 Java Raft 实现）

多环境配置管理最佳实践

  • Group：按业务域划分（如订单组、用户组），同组配置统一管理

  • 公共配置：使用 shared-configs 或 extension-configs 共享通用配置（如数据库连接池）

服务治理实践

权重配置（流量比例分配）

权重范围 0~100，值越大分配的流量比例越高。权重为 0 时不接收流量（用于下线过渡）。

# 通过 API 设置权重
curl -X PUT "http://localhost:8848/nacos/v1/ns/instance?\
serviceName=user-service&ip=192.168.1.100&port=8080&weight=5"

# 权重分配示例
# 旧实例（权重 1）: 新实例（权重 9）= 10% : 90%

元数据管理

元数据是附加在实例上的 Key-Value 键值对，用于服务路由、灰度等高级功能：

  • version: v1 — 版本号，支持按版本路由
  • env: gray — 灰度标识
  • region: hangzhou — 区域信息
  • 自定义业务标签，配合负载均衡策略使用

服务保护阈值

保护阈值（protectThreshold）范围 0~1，默认 0。当健康实例比例低于阈值时，Nacos 会将不健康的实例也返回给消费者，防止流量全部打到少数健康实例导致雪崩。

# 设置保护阈值为 0.5（健康实例低于 50% 时触发保护）
curl -X PUT "http://localhost:8848/nacos/v1/ns/service?\
serviceName=user-service&protectThreshold=0.5"
保护阈值是 Nacos 的雪崩保护机制，类似 Eureka 的自我保护模式。生产环境建议设置为 0.5~0.8。

优雅上下线

上线流程：服务先注册到 Nacos，待健康检查通过后再接入流量。

下线流程：

  • 先将权重设为 0，停止接收新流量
  • 等待存量请求处理完成（优雅等待期）
  • 调用下线 API 注销实例：PUT /nacos/v1/ns/instance?enable=false
  • 最后停止服务进程

与 Spring Cloud 集成

@NacosValue 动态刷新

// 使用 @NacosValue 实现配置动态刷新
@NacosValue(value = "${custom.timeout:3000}", autoRefreshed = true)
private int timeout;

// 传统 @Value 不支持动态刷新，需配合 @RefreshScope
@Value("${custom.timeout}")
private int timeout;

@RefreshScope 原理

  • @RefreshScope 将 Bean 标记为 RefreshScope（一种特殊的 Scope）
  • 配置变更时，Spring Cloud 发布 EnvironmentChangeEvent
  • RefreshEventListener 监听事件，销毁旧 Bean 并创建新实例
  • 本质是 销毁 + 重建 Bean，注入新的属性值
  • 注意：正在执行中的方法仍使用旧值，新请求才会使用新值

第三部分：模拟面试

Nacos 作为注册中心，是如何保证服务实例信息的可用性和一致性的？
参考：Nacos 同时支持 AP 和 CP 两种模式。对于临时实例（默认），使用自研的 Distro 协议（AP），基于去中心化的最终一致性模型，每个节点负责部分数据并异步同步给其他节点，保证高可用。对于持久化实例，使用 Raft 协议（CP），写操作需经过 Leader 节点并复制到多数节点，保证强一致性。
追问：Distro 协议是怎么实现的？ Distro 类似 Gossip 协议的简化版，每个节点有自己负责的数据分片（通过 hash 路由），注册请求由负责节点处理后异步全量同步给其他节点。节点间每 10 秒交换一次数据校验和，发现不一致则拉取全量数据修复。
Nacos 的配置变更通知机制是怎样的？为什么不用 WebSocket？
参考：Nacos 1.x 使用 HTTP 长轮询机制：客户端发起请求，携带配置的 MD5 值，服务端对比一致则 hold 住连接最长 30 秒，期间配置有变更立即返回；超时则返回 304。客户端还有定时拉取作为兜底。Nacos 2.x 升级为 gRPC 长连接，服务端可主动推送变更。
追问：为什么不用 WebSocket？ 长轮询在 HTTP 层面即可实现，无需协议升级，对负载均衡和防火墙更友好。且配置变更是低频事件，长轮询的开销可接受。Nacos 2.x 选择 gRPC 而非 WebSocket，因为 gRPC 提供更好的类型安全、流式支持和连接管理。
Nacos 集群部署时，节点之间如何同步数据？
参考：集群中 Naming（服务注册）和 Config（配置管理）使用不同协议同步。Naming 模块默认使用 Distro 协议：每个节点按 hash 负责一部分数据，注册信息由负责节点处理后异步同步，节点间定期校验和比对。Config 模块使用 Raft 协议：所有写操作经 Leader 节点，日志复制到多数节点后才返回成功。集群配置通过 cluster.conf 文件指定所有节点 IP。
追问：集群模式下数据库如何配置？ 所有节点连接同一个 MySQL 实例（建议主从），通过数据库实现数据持久化和跨节点共享。
Nacos 的命名空间、Group、DataId 分别有什么作用？在实际项目中如何规划？
参考：Namespace 用于环境隔离（dev/test/prod），不同 Namespace 下的服务和配置完全隔离。Group 用于业务分组（如 DEFAULT_GROUP、ORDER_GROUP），可按微服务域划分。DataId 对应具体配置文件（如 user-service.yml）。三者唯一标识一份配置。实际项目中：Namespace 按环境划分，Group 按业务线划分，DataId 按服务名命名。公共配置通过 shared-configs 共享。
Nacos 如何实现雪崩保护？保护阈值的作用是什么？
参考：Nacos 通过保护阈值（protectThreshold）实现雪崩保护。当健康实例占总实例的比例低于阈值时，Nacos 会将不健康的实例也返回给消费者，避免所有流量集中到少数健康实例导致级联故障。默认值为 0（不启用），生产建议设置为 0.5~0.8。这类似于 Eureka 的自我保护模式。
追问：如果保护阈值触发了，返回不健康实例不会导致调用失败吗？ 确实可能调用到不健康实例，但总比所有流量打垮少数健康实例要好。配合客户端的重试机制和熔断降级，可以保证整体可用性。
Spring Cloud 应用启动时，Nacos 的配置是如何加载的？加载优先级是怎样的？
参考：加载顺序为：1）bootstrap.yml 最先加载，包含 Nacos Server 地址等连接配置；2）通过 NacosPropertySourceLocator 从 Nacos 拉取远程配置，注入 Environment；3）application.yml 加载，本地配置优先级低于远程配置；4）@PropertySource 等注解配置。远程配置可通过 shared-configs（共享配置）和 extension-configs（扩展配置）引入多个配置文件。
追问：如果 bootstrap.yml 中没有配置 Nacos 地址会怎样？ 将无法从 Nacos 拉取远程配置，Spring Boot 2.4+ 还需引入 spring-cloud-starter-bootstrap 依赖，否则 bootstrap.yml 不会被加载。
如何实现 Nacos 配置的灰度发布？
参考：Nacos 控制台支持 Beta 发布功能：编辑配置后选择「灰度发布」，填写灰度 IP 列表。灰度期间，只有指定 IP 的客户端会拉取到新配置，其他客户端仍使用旧配置。验证无误后可「停止 Beta」全量发布或回滚。实现原理是服务端在返回配置时，根据客户端 IP 判断是否属于灰度列表，决定返回新版还是旧版配置。
