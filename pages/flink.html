0. 版本演进 — 从流批分离到流批统一

Flink 版本演进与技术方向
1.0 (2016) — 首个正式版 · DataStream API · DataSet API（批处理）· 基础 Window/State
1.5 (2018) — Blink planner 引入（SQL 性能大幅提升）· 状态后端改进
1.9 / 1.11 (2019-2020) — Table API / SQL 统一 · PyFlink · CDC 支持 · Kubernetes 集成
1.12 / 1.13 (2020-2021) — Batch 执行模式 · DataSet API 弃用方向 · Window TVF · 动态表
1.14 / 1.15 (2021-2022) — Unaligned Checkpoint · Application Mode · Reactive Scaling
1.17+ / 2.0 (2023-2025) — 流批一体成熟 · SQL 优先 · 云原生部署 · 性能持续优化

技术演进思想

  • 流批分离 → 流批统一：早期 DataSet（批）和 DataStream（流）两套 API，1.12+ 统一为流执行，批只是有界流
  • API 优先 → SQL 优先：SQL/Table API 成为一等公民，降低使用门槛
  • Aligned → Unaligned Checkpoint：背压下也能快速完成快照（1.14+）
  • Session 集群 → Application Mode：每个 Job 独立集群，更好的资源隔离
  • 方向：云原生、SQL 优先、流批一体、易用性提升

State TTL（过期清理）

设置 State 的过期时间，自动清理不再需要的数据：

策略行为适用

设计动机：为什么用 Chandy-Lamport 而不是"暂停-快照"?

设计起点：流处理要保证故障后状态一致，必须定期做"全局快照"。最朴素的想法是"暂停所有算子 → 同步快照 → 恢复"，但这会中断整个流处理，秒级停顿在 7×24 实时风控等场景不可接受。Chandy-Lamport 算法的巧妙之处：用随数据流动的 Barrier 标记把快照"摊平"到正常数据流中，不暂停处理就能拿到一致的全局状态。

Barrier 随数据流传播
  Source ──[d1][d2]──Barrier_n──[d3][d4]──→  Operator
   ↓ 快照本地状态          ↑ 收到 Barrier_n 后：
   ↓ (Source offset)       ① 对齐所有输入的 Barrier
                          ② 快照本地 State
                          ③ 向下游广播 Barrier_n
                          ④ 继续处理 Barrier 后的数据

❌ 朴素"暂停-快照"

  • 全局停顿，业务感知明显
  • 快照期间无数据处理，延迟飙升
  • 实现简单但不可用于生产

✅ Chandy-Lamport Barrier

  • 不停顿：算子边处理数据边等 Barrier
  • 全局一致：所有算子快照同一 Barrier 之前的状态
  • 异步持久化：State 快照后异步写 State Backend，不阻塞处理
  • 代价：Barrier 对齐时需缓存其他输入的数据（背压下问题，催生 Unaligned）
面试要点：Chandy-Lamport 是 1985 年的理论算法，Flink 把它工程化落地。核心思想是"用标记而非停顿来实现一致性快照"——这是分布式快照的通用范式，Spark Structured Streaming、Flink、Kafka 事务都借鉴了类似思路。

Aligned vs Unaligned Checkpoint（1.14+）

Aligned（传统）

  • Barrier 必须等待所有输入到齐
  • 保证 Exactly-Once
  • 问题：背压时 Barrier 排在数据后面，Checkpoint 超时

Unaligned（1.14+）⭐

  • Barrier 超越缓冲区中的数据
  • 背压下也能快速完成 Checkpoint
  • 代价：Checkpoint 文件更大（含缓冲数据）
  • execution.checkpointing.unaligned.enabled=true

思想演进：旧版"精确对齐"在背压下变成瓶颈，新版"不对齐"用存储换时间。这体现了"在不同约束间做权衡"的工程思想。

Checkpoint

Flink 自动触发 · Job 取消后默认删除 · 用于故障恢复

Savepoint

用户手动触发 · 不自动删除 · 用于版本升级、A/B 测试、集群迁移

1.7 Flink SQL / Table API

  • 动态表 (Dynamic Table)：流数据映射为持续更新的表

与 DataStream 互操作

2.6 性能调优

  • 并行度：算子并行度 = min(Partition 数, Slot 数)
  • 算子链：相邻算子合并减少网络开销
  • Mini-Batch：SQL 层微批聚合，减少 State 访问
  • State Backend：大状态用 RocksDB + 增量 Checkpoint
  • 反压：增加并行度、优化算子逻辑、增加网络缓冲区

反压 (Backpressure) 机制详解

设计起点：流处理是流水线，上游产出速度 > 下游处理速度时，数据会在网络缓冲区堆积，最终反向传导阻塞上游——这就是反压。Flink 用基于 Credit 的流控解决，类似 TCP 滑动窗口。

Credit-Based 反压传导
  上游 Operator ──→ 网络缓冲 ──→ 下游 Operator (慢)
       ↑                                │
       │  下游声明 Credit=2 (只能再收2个)  │
       │←─────────────────────────────────┘
       │  上游只发 2 个，发完等新 Credit
       │←─────────────────────────────────┘
  上游也被阻塞 → 反压传导到 Source → 整条流水线降速
  • Credit 机制：下游告诉上游"我还能收几个 buffer"，上游按 Credit 发送，避免无脑堆积
  • 反压的连锁反应：一个慢算子会反压到所有上游，最终 Source 也降速
  • 排查：Flink Web UI 的 BackPressure 面板，红色算子即瓶颈
  • 解决：① 增加瓶颈算子并行度；② 优化算子逻辑（异步 IO、批量写）；③ 检查数据倾斜（某 key 数据过多）；④ 增加网络缓冲（治标不治本）
反压 vs Checkpoint 超时：反压时 Barrier 排在数据后面迟迟到不了，导致 Aligned Checkpoint 超时失败。这就是 1.14 引入 Unaligned Checkpoint 的动机——Barrier 超越缓冲数据，背压下也能快速完成快照。

🎤第三部分：模拟面试

Flink 和 Spark Streaming 最本质的区别？
计算模型：Flink 是真正流处理（逐条），延迟 ms 级。Spark Streaming 是微批处理，延迟秒级。这导致 Flink 天然支持 Event Time、Watermark、完善的 State 管理和 Exactly-Once Checkpoint。
什么是 Watermark？为什么需要它？
Watermark 是时间戳，表示"在此之前的数据基本到齐了"。网络传输导致乱序，Watermark 告诉 Flink 可以触发窗口。配合 Allowed Lateness + Side Output 处理迟到数据。BoundedOutOfOrderness 是最常用的策略。
Flink 的 Checkpoint 机制？
基于 Chandy-Lamport 分布式快照。JobManager 注入 Barrier，Barrier 随数据传播，算子收到所有 Barrier 后快照 State。1.14+ 引入 Unaligned Checkpoint：Barrier 超越数据，背压下也能快速完成。
如何保证端到端 Exactly-Once？
Source 可重放（Kafka offset）+ Checkpoint 保证 State 一致性 + Sink 两阶段提交（2PC）或幂等写入。Flink 的 TwoPhaseCommitSinkFunction：Pre-commit 写临时文件，Checkpoint 完成后 Commit。
Window 有哪些类型？
Tumbling（固定不重叠）、Sliding（有滑动步长）、Session（按活跃间隔）、Count（按数量）、Global（配合 Trigger）。Window Function：ReduceFunction、AggregateFunction、ProcessWindowFunction，可增量+全量组合。
State 有哪些类型？
Keyed State：ValueState（单值）、ListState（列表）、MapState（映射）、ReducingState（聚合同类型）、AggregatingState（聚合不同类型）。Operator State：绑定在算子实例上，如 Source 的 offset。
State Backend 怎么选？
HashMap：State 存 JVM Heap，最快但受 GC 影响，适合小 State（<100MB）。RocksDB：State 存磁盘，不受 GC，支持增量 Checkpoint，适合大 State（GB~TB）。生产推荐 RocksDB。
Aligned vs Unaligned Checkpoint？
Aligned：Barrier 对齐，保证 Exactly-Once，但背压时超时。Unaligned（1.14+）：Barrier 超越数据，背压下也能快速完成，代价是 Checkpoint 文件更大。思想：用存储换时间，在不同约束间做权衡。
Flink SQL 和 DataStream 怎么选？
SQL 适合：标准 ETL、聚合、Join、简单逻辑。DataStream 适合：复杂状态逻辑、CEP、自定义 Trigger、需要低级控制。两者可互操作：Table→DataStream（toDataStream）和 DataStream→Table（fromDataStream）。建议：能用 SQL 就用 SQL，复杂逻辑用 DataStream。
State TTL 的两种策略？
UpdateOnCreateAndWrite（默认）：创建和写入时更新 TTL，读不影响过期。OnReadAndWrite：读和写都更新 TTL。选择看业务：读取也算"活跃"就用后者，否则用默认。注意：TTL 只支持 Keyed State，RocksDB 后台 compaction 负责实际清理。
Operator Chain 和 Slot Sharing？
Operator Chain：相邻算子合并为一个 Task，减少网络开销和序列化。可通过 startNewChain/disableChain 控制。Slot Sharing：同一 Job 的不同算子共享 Slot，提高资源利用率。一个 Slot 可以运行整个 Pipeline。
Flink CDC 2.x 和 3.x 的区别？
2.x 内嵌 Debezium，单并行度全量读取，需要 FTWRL 全局锁。3.x 自研增量快照算法，表级并行读取，无锁（基于 Binlog Position），完整 DDL 同步。核心改进：无锁并行快照，对生产库影响更小。
如何处理迟到数据？
三层防线：① Watermark（允许延迟，如 3 秒）；② Allowed Lateness（窗口触发后再等 1 分钟）；③ Side Output（超过阈值输出到侧输出流）。三层配合：Watermark 触发窗口 → Allowed Lateness 处理轻微迟到 → Side Output 兜底严重迟到。
什么是背压？Flink 怎么处理？
下游处理速度跟不上上游，缓冲区满导致阻塞。Flink 基于信用-based 流控。排查：Web UI 反压面板。解决：增加并行度、优化算子逻辑、增加网络缓冲、检查数据倾斜。
