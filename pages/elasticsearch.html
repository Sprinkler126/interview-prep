🔬第一部分：技术原理

1.1 倒排索引原理

正排索引 vs 倒排索引

正排索引 (Forward Index)

文档 → 包含的词

Doc1 → ["Java", "Spring", "Redis"]
Doc2 → ["Java", "MySQL", "Redis"]
Doc3 → ["Python", "Redis"]

搜索 "Redis" 需遍历所有文档

倒排索引 (Inverted Index)

词 → 包含该词的文档列表

"Java"   → [Doc1, Doc2]
"Redis"  → [Doc1, Doc2, Doc3]
"MySQL"  → [Doc2]
"Python" → [Doc3]

搜索 "Redis" 直接定位 [Doc1, Doc2, Doc3]

倒排索引三层结构

Term Dictionary（词典）
所有去重后的词项，按字典序排列，支持二分查找
⬇️ 每个 Term 指向
Posting List（倒排列表）
DocID + Term Frequency + Position + Offset
⬇️ 加速查找
FST (Finite State Transducer)
前缀树压缩结构，Term Dictionary 的内存索引，前缀共享，极省内存

Posting List 压缩技术

  • Frame of Reference (FOR)：差值编码 + 位压缩，如 [73, 300, 302, 332] → [73, 227, 2, 30] 再位压缩
  • Roaring Bitmap：大数值范围使用分块 bitmap，小范围使用有序数组，ES 5.0+ 使用
  • 跳表加速：Posting List 之上构建跳表，加速合并（AND/OR）操作

1.2 分词器 (Analyzer)

分词器组成
Character Filter
字符过滤（去HTML、转义）
→
Tokenizer
分词器（核心）
→
Token Filter
词项过滤（小写、去停用词、同义词）
常用分词器对比
分词器特点适用场景
Standard按 Unicode 文本分割，去标点，转小写英文默认，中文逐字切分（效果差）
IK Smart粗粒度分词，"中华人民共和国" 一个词搜索时使用
IK Max Word细粒度分词，穷尽所有可能组合索引时使用（召回率高）
jiebaHMM 模型，支持新词发现中文分词
自定义基于 Standard + 自定义词典 + 同义词业务专业术语

索引时 vs 搜索时分词

  • 索引时：使用细粒度分词（IK Max Word），增加召回率
  • 搜索时：使用粗粒度分词（IK Smart），提高精确度
  • 索引和搜索分词器必须一致，否则无法匹配
// 创建索引时指定分词器
PUT /my_index
{
  "settings": {
    "analysis": {
      "analyzer": {
        "my_analyzer": {
          "type": "custom",
          "tokenizer": "ik_max_word",
          "filter": ["lowercase", "synonym"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "my_analyzer",
        "search_analyzer": "ik_smart"
      }
    }
  }
}

1.3 文档写入流程

文档写入全链路
客户端写入请求
→
协调节点路由
hash(doc_id) → shard
→
Primary Shard
写入处理

Primary Shard 写入流程

① 写入内存 Buffer
文档进入 In-Memory Buffer
② 写入 Translog
预写日志，防止宕机丢数据
每 1 秒 Refresh ⬇️
③ Refresh → 生成 Segment
Buffer → 内存中的 Segment（此时可搜索，近实时 NRT）
Translog 达到阈值（512MB / 30min）⬇️
④ Flush → Segment 持久化到磁盘
fsync Segment 到磁盘 + 清空 Translog
同步副本 ⬇️
⑤ Replica Shard 同步
并发同步到所有副本，全部成功后返回客户端确认

1.4 相关性评分 BM25

TF-IDF (旧版默认)

  • TF (词频)：词在文档中出现的次数越多，越相关
  • IDF (逆文档频率)：词在越少文档中出现，区分度越高
  • 问题：TF 无限增长，长文档天然 TF 高

BM25 (ES 5.0+ 默认)

  • TF 有饱和机制：词频增长到一定值后贡献不再增加
  • 考虑文档长度：长文档归一化，避免长文档天然高分
  • 参数 k1（词频饱和度）和 b（文档长度影响）可调

BM25 公式核心思路

Score(D, Q) = Σ IDF(qi) * ( f(qi, D) * (k1 + 1) ) / ( f(qi, D) + k1 * (1 - b + b * |D|/avgdl) )

f(qi, D) = 词 qi 在文档 D 中的词频
|D| = 文档长度
avgdl = 平均文档长度
k1 = 1.2 (默认), b = 0.75 (默认)

BM25 本质上是：IDF 加权 × TF 饱和函数 × 文档长度归一化

1.5 近实时搜索 (NRT) 原理

为什么不是实时搜索？

  • 文档写入后先进入 Buffer，此时不可搜索
  • Refresh（默认 1 秒）将 Buffer 生成新的 Segment，此后可搜索
  • 这个 1 秒延迟就是 "近实时" 的由来
  • Refresh 不会触发 fsync，数据在内存中的 Segment，进程崩溃可能丢失
  • Flush（fsync + 清空 Translog）才将数据持久化到磁盘
Segment 不可变性
  • Segment 一旦生成就不可修改（Immutable）
  • 删除操作：在 .del 文件中标记删除，查询时过滤
  • 更新操作：先标记旧文档删除，再写入新文档到新 Segment
  • 不可变的好处：天然支持并发读，无需加锁

1.6 段合并 (Merge) 策略

为什么需要段合并？

每次 Refresh 产生新 Segment，Segment 过多会导致：① 文件句柄过多；② 搜索需要遍历所有 Segment；③ 删除标记占用空间。

段合并过程
Seg1 Seg2 Seg3 Seg4 Seg5
Merge →
Seg6 (合并后)
→
删除旧 Segment

Tiered Merge Policy（默认策略）

  • 将 Segment 按大小分层，每层合并大小相近的 Segment
  • max_merged_segment：合并后的最大 Segment 大小（默认 5GB）
  • merge factor：每层最多多少个 Segment 合并
  • 合并是后台异步操作，使用独立线程池
  • 合并时会物理删除标记为 deleted 的文档，释放空间
段合并消耗大量 IO 和 CPU，可通过 index.merge.scheduler.max_thread_count 控制并发度。SSD 上可设为 1，HDD 上可设为核心数/2。

🎯第二部分：场景化讲解

2.1 查询 DSL

查询分类：Query vs Filter
类型特点缓存示例
Query Context计算相关性评分 _score不缓存match、multi_match
Filter Context只判断是否匹配，不评分可缓存（Bitset）term、range、exists

性能原则：不需要评分的条件尽量放在 filter 中（利用缓存，跳过评分计算）。

常用查询 DSL
GET /my_index/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "分布式系统" } }
      ],
      "filter": [
        { "term": { "status": "published" } },
        { "range": { "publish_date": { "gte": "2025-01-01" } } }
      ],
      "should": [
        { "match": { "content": "Redis" } }
      ],
      "must_not": [
        { "term": { "author": "admin" } }
      ]
    }
  },
  "sort": [{ "publish_date": "desc" }],
  "from": 0, "size": 10,
  "_source": ["title", "author", "publish_date"]
}

常用查询类型

查询用途特点
match全文检索先分词再匹配，计算评分
match_phrase短语匹配分词后必须相邻且有序
term精确匹配不分词，用于 keyword/数值/日期
range范围查询gt/gte/lt/lte
bool布尔组合must/filter/should/must_not
nested嵌套对象查询嵌套文档独立评分
wildcard通配符性能差，避免前缀通配
fuzzy模糊匹配容错搜索，编辑距离

2.2 聚合分析

聚合类型
类型说明示例
Metric指标聚合：计算单个值avg、sum、min、max、cardinality（去重计数）、percentiles
Bucket桶聚合：将文档分到桶中terms、date_histogram、range、histogram、filters
Pipeline管道聚合：对聚合结果再聚合avg_bucket、derivative、cumulative_sum

聚合示例：按状态分组 + 计算平均价格

GET /products/_search
{
  "size": 0,
  "aggs": {
    "by_status": {
      "terms": { "field": "status", "size": 10 },
      "aggs": {
        "avg_price": { "avg": { "field": "price" } },
        "price_ranges": {
          "range": {
            "field": "price",
            "ranges": [
              { "to": 100 },
              { "from": 100, "to": 500 },
              { "from": 500 }
            ]
          }
        }
      }
    }
  }
}

聚合性能优化

  • 精确去重：cardinality 使用 HyperLogLog++，占用内存小，0.8% 误差
  • terms 聚合：设置合理 size，避免返回过多桶
  • shard_size：增大可提高精确度，但增加开销
  • execution_hint：map（低基数）、global_ordinals（高基数）

2.3 集群架构

ES 集群节点角色
节点角色职责配置建议
Master集群元数据管理、分片分配、集群状态维护至少 3 个专用 Master 节点，CPU/内存要求不高
Data存储数据、执行 CRUD、搜索、聚合高内存 + SSD，分 Hot/Warm/Cold
Coordinating接收客户端请求，分发到数据节点，汇聚结果可配置为专用协调节点
Ingest预处理文档（Pipeline），类似 Logstash需要数据预处理时部署

分片与副本

  • Primary Shard：数据水平拆分，每个文档属于一个 Primary Shard
  • Replica Shard：Primary 的副本，提供高可用和读扩展
  • 路由算法：shard_num = hash(_routing) % num_primary_shards
  • _routing：默认为文档 _id，可自定义路由（相关文档落同一 shard）
  • 分片数不可更改（创建索引后固定，Reindex 可重新分配）

读写请求路由

客户端请求
→
Coordinating Node
计算目标 Shard
→
Data Node
Primary Shard 处理
→
Replica 同步

搜索请求：Coordinating Node 并发查询所有相关 Shard → 各自返回 Top N → 协调节点合并排序 → 返回最终结果。

🎤第三部分：模拟面试

Elasticsearch 的倒排索引是怎么工作的？
参考：倒排索引由 Term Dictionary + Posting List + FST 三层结构组成。Term Dictionary 存储所有去重词项，Posting List 记录每个词出现在哪些文档（DocID + TF + Position），FST 是内存中的前缀树结构加速词项查找。
追问：Posting List 使用 Roaring Bitmap 压缩，支持高效 AND/OR 合并。
ES 的近实时搜索是怎么实现的？Refresh 和 Flush 有什么区别？
参考：文档写入 Buffer 后默认 1 秒 Refresh 生成内存 Segment（此时可搜索），这是 NRT 的由来。Refresh 不 fsync，可能丢数据。Flush 将 Segment fsync 到磁盘并清空 Translog，保证持久化。
追问：手动 POST /_refresh 可强制刷新，但会增加 IO 负载。
ES 的分词器有哪些？中文分词怎么处理？
参考：Standard（默认，中文逐字切分）、IK Smart（粗粒度）、IK Max Word（细粒度穷尽组合）、jieba。中文场景推荐索引时用 IK Max Word（高召回），搜索时用 IK Smart（高精度）。还可自定义词典和同义词。
ES 中 Query 和 Filter 有什么区别？
参考：Query 计算相关性评分（_score），用于全文检索场景。Filter 只判断匹配与否，不评分，结果可缓存（Bitset），性能更好。原则：不需要评分的条件放 filter，需要评分的放 must/should。
ES 集群有哪些节点角色？分片怎么路由？
参考：Master（元数据管理）、Data（数据存储和搜索）、Coordinating（请求路由和汇聚）、Ingest（预处理）。分片路由：hash(_routing) % primary_shards，默认 _routing 为 _id。
追问：分片数创建后不可改，需提前规划。可自定义 _routing 让相关文档落同一分片。
ES 的段合并机制是什么？有什么影响？
参考：每次 Refresh 产生新 Segment，后台线程异步合并小 Segment 为大 Segment。合并时会物理删除标记删除的文档。Tiered Merge Policy 按大小分层合并。合并消耗 IO 和 CPU，可通过 max_thread_count 控制并发度。
ES 如何保证高可用？
参考：① Primary Shard + Replica Shard 机制，Primary 故障 Replica 自动提升；② Master 节点至少 3 个（奇数），Raft 选举；③ 跨机架/可用区部署避免单点故障；④ 分片自动再平衡。
ES 和 MySQL 的区别？什么时候用 ES？
参考：ES 擅长全文检索、日志分析、复杂聚合，倒排索引搜索性能远超 MySQL B+Tree 的 LIKE 查询。MySQL 擅长事务、关系查询、精确匹配。场景选择：全文搜索/日志系统/实时分析用 ES，OLTP/强事务用 MySQL。两者常共存，MySQL 做主存储，ES 做搜索层。
