Linux 底层技术

  • Namespace（命名空间）：隔离进程视图。包括 PID（进程号）、NET（网络）、MNT（挂载）、UTS（主机名）、IPC（进程间通信）、USER（用户）、Cgroup 等 7 种
  • Cgroups（控制组）：限制资源使用。控制 CPU、内存、磁盘 IO、网络带宽等资源上限
  • UnionFS（联合文件系统）：实现镜像分层共享，多个容器可共享相同的底层镜像层
  • Capabilities：细粒度权限控制，替代传统的 root 全权限模型

UnionFS 联合文件系统

  • Docker 镜像由多个只读层（read-only layer）叠加组成，每层对应 Dockerfile 中的一条指令
  • 使用 UnionFS（如 overlay2）将多个层合并为一个统一的文件系统视图
  • 相同的基础镜像层可以在多个镜像之间共享，节省磁盘空间
  • 容器启动时在最顶层添加一个可写层（Container Layer），所有修改都在此层

Copy-on-Write（写时复制）

  • 读取文件时，直接从只读层读取，无需复制
  • 修改文件时，先将文件从只读层复制到可写层，再在可写层修改
  • 删除文件时，在可写层创建一个 whiteout 标记，隐藏只读层的文件
  • 这种机制使得容器启动极快，且多个容器可以共享相同的只读镜像层
理解 CoW 对优化 Dockerfile 至关重要：频繁修改的层应放在 Dockerfile 后面，利用构建缓存加速。

RUN 指令优化

# 不推荐：多个 RUN 产生多层
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y vim
RUN rm -rf /var/lib/apt/lists/*

# 推荐：合并为一条 RUN，减少层数
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl vim && \
    rm -rf /var/lib/apt/lists/*
每条 RUN 指令都会创建一个新的镜像层。合并相关命令可以减少镜像层数和大小。使用 && 链接命令，\ 换行保持可读性。

CMD vs ENTRYPOINT

CMD

  • 提供容器启动的默认命令
  • 可以被 docker run 后面的命令完全覆盖
  • 一个 Dockerfile 中只有最后一条 CMD 生效
  • 推荐使用 exec 格式：CMD ["executable","param1"]
  • 三种写法：CMD ["exec","param"]（exec 格式）、CMD command param（shell 格式）、CMD ["param1","param2"]（配合 ENTRYPOINT）

ENTRYPOINT

  • 定义容器的主进程
  • 不会被 docker run 后面的命令覆盖（需 --entrypoint）
  • docker run 的参数会追加到 ENTRYPOINT 后面
  • 适合将容器作为可执行程序使用
  • 一个 Dockerfile 中只有最后一条 ENTRYPOINT 生效

CMD 与 ENTRYPOINT 组合使用

# 典型组合：ENTRYPOINT 定义主命令，CMD 提供默认参数
FROM nginx:latest
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]

# 运行时：docker run mynginx → nginx -g "daemon off;"
# 追加参数：docker run mynginx -c /etc/nginx/custom.conf → nginx -c /etc/nginx/custom.conf
Dockerfiledocker run imgdocker run img cmd
只有 CMD执行 CMDcmd 覆盖 CMD
只有 ENTRYPOINT执行 ENTRYPOINTcmd 追加到 ENTRYPOINT
两者都有ENTRYPOINT + CMDENTRYPOINT + cmd（cmd 替换 CMD）

容器网络模式

五种网络模式

模式说明使用场景
bridge（默认） 容器拥有独立 Network Namespace，通过 docker0 虚拟网桥与宿主机通信。容器有独立 IP，通过 NAT 访问外部 单机多容器通信（最常用）

存储驱动（Storage Driver）

Docker 使用存储驱动管理镜像层和容器可写层。overlay2 是推荐的存储驱动（Linux 4.0+ 内核）。

三种存储方式对比

类型说明生命周期使用场景
Volume Docker 管理的存储卷，存储在 /var/lib/docker/volumes/ 独立于容器，容器删除后保留 推荐，数据库数据、持久化存储

第二部分：场景化讲解

多阶段构建（Multi-stage Build）

为什么需要多阶段构建？

传统构建方式将编译环境和运行环境放在同一个镜像中，导致镜像体积巨大。多阶段构建允许在多个 FROM 指令间只复制需要的产物，最终镜像只包含运行时必要文件。

# === 多阶段构建示例（Java 应用） ===

# 阶段 1：构建（命名为 builder）
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline        # 缓存依赖层
COPY src ./src
RUN mvn package -DskipTests -B

# 阶段 2：运行（精简镜像）
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
# 从 builder 阶段复制产物
COPY --from=builder /app/target/app.jar ./app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
方式镜像大小包含内容
单阶段构建~800MB+JDK + Maven + 源码 + 编译产物
多阶段构建~200MB仅 JRE + JAR 包

前端多阶段构建示例

# 阶段 1：构建前端资源
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 阶段 2：Nginx 托管静态文件
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
多阶段构建是 Docker 最佳实践之一。构建阶段可以使用完整 SDK 镜像（如 Maven、Node），运行阶段只需精简的 Runtime 镜像（如 JRE-alpine、Nginx-alpine）。

Docker Compose

docker-compose.yml 语法

# docker-compose.yml 示例：Spring Boot + MySQL + Redis
version: '3.8'

services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      - SPRING_PROFILES_ACTIVE=prod
      - DB_HOST=mysql
      - REDIS_HOST=redis
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_started
    restart: unless-stopped
    networks:
      - app-net

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: mydb
    volumes:
      - mysql-data:/var/lib/mysql
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - app-net

  redis:
    image: redis:7-alpine
    command: redis-server --requirepass redis123
    volumes:
      - redis-data:/data
    networks:
      - app-net

volumes:
  mysql-data:
  redis-data:

networks:
  app-net:
    driver: bridge

容器编排：Swarm vs Kubernetes

Docker Swarm

  • Docker 原生编排工具
  • 部署简单，与 Docker CLI 完美集成
  • 适合小规模集群（数十节点）
  • 功能较简单，社区活跃度下降
  • 自动负载均衡、服务发现
  • 声明式服务定义（与 Compose 兼容）

Kubernetes

  • Google 开源，行业标准
  • 功能强大，生态丰富
  • 适合大规模集群（数千节点）
  • 学习曲线陡峭，运维复杂
  • 自动扩缩容、滚动更新、自愈
  • CNI / CSI / CRI 扩展机制

对比总结

维度Docker SwarmKubernetes
部署难度简单 docker swarm init复杂 kubeadm / 云托管
扩展性中小规模大规模生产级
自动扩缩容不支持HPA / VPA / Cluster Autoscaler
滚动更新基础支持精细控制（maxSurge / maxUnavailable）
网络Overlay 网络CNI 插件（Calico / Flannel / Cilium）

适用建议小团队快速上手生产环境首选
面试加分点：当前行业标准是 Kubernetes。Docker Swarm 已逐渐边缘化。了解 Swarm 的优缺点可以展示你对技术选型的判断力。

第三部分：模拟面试

Docker 容器和虚拟机有什么区别？为什么容器更快？
参考：虚拟机通过 Hypervisor 虚拟化硬件，每个 VM 运行独立的 Guest OS，启动需要分钟级，资源开销大。容器利用 Linux Namespace 实现进程隔离、Cgroups 限制资源，共享宿主机内核，启动只需毫秒~秒级，几乎无性能损耗。容器本质上是宿主机上被隔离的进程，而虚拟机是完整的操作系统。
追问：容器的安全隔离不如虚拟机怎么办？ 可以使用 gVisor（用户态内核）或 Kata Containers（轻量 VM）增强容器隔离，在安全性和性能间取得平衡。
Docker 镜像的分层原理是什么？什么是 Copy-on-Write？
参考：Docker 镜像由多个只读层叠加组成，每层对应 Dockerfile 中的一条指令。使用 UnionFS（如 overlay2）将多层合并为统一视图。容器启动时在顶层添加可写层。Copy-on-Write 是指读取文件时直接从只读层读，修改时先将文件复制到可写层再修改，删除时添加 whiteout 标记。这种机制使容器启动极快，多个容器可共享底层镜像。
CMD 和 ENTRYPOINT 有什么区别？什么时候用哪个？
参考：CMD 提供容器启动的默认命令和参数，可以被 docker run 后面的命令完全覆盖。ENTRYPOINT 定义容器的主进程，不会被覆盖，docker run 的参数会追加到 ENTRYPOINT 后面。典型用法是 ENTRYPOINT 定义主命令（如 java -jar），CMD 提供默认参数（如 app.jar），运行时可灵活替换参数。
追问：如何覆盖 ENTRYPOINT？ 使用 docker run --entrypoint /bin/bash image。
Docker 的 bridge 网络是怎么工作的？
参考：bridge 是默认网络模式。Docker 在宿主机创建 docker0 虚拟网桥（172.17.0.1），每个容器通过 veth pair 连接到网桥，获得独立 IP。容器间通过网桥直接通信。容器访问外部通过 iptables SNAT，外部访问容器通过 -p 端口映射（DNAT）。生产建议使用自定义 bridge 网络（docker network create），支持 DNS 自动解析容器名。
Volume、Bind Mount、tmpfs 三种存储方式有什么区别？
参考：Volume 由 Docker 管理，存储在 /var/lib/docker/volumes/，独立于容器生命周期，适合持久化数据。Bind Mount 将宿主机目录直接挂载到容器，依赖宿主机路径，适合开发环境。tmpfs 存储在内存中，容器停止后消失，适合敏感数据和临时缓存。生产环境推荐 Volume，开发环境推荐 Bind Mount。
什么是多阶段构建？为什么要用它？
参考：多阶段构建允许在一个 Dockerfile 中使用多个 FROM 指令，每个阶段可以使用不同的基础镜像。构建阶段使用完整 SDK 镜像（如 Maven + JDK），运行阶段只复制编译产物到精简的 Runtime 镜像（如 JRE-alpine）。好处：1）镜像体积大幅减小（从 800MB 到 200MB）；2）构建工具不进入最终镜像，减少攻击面；3）利用构建缓存加速 CI/CD。
如何优化 Docker 镜像的大小？
参考：1）使用小基础镜像（alpine / distroless / slim）；2）多阶段构建，只复制运行时必要文件；3）合并 RUN 指令减少层数，清理包管理器缓存；4）使用 .dockerignore 排除不必要文件；5）利用构建缓存，不常变的层放前面；6）使用 --no-install-recommends 避免安装推荐包；7）固定版本标签避免拉取过大 latest 镜像。
Docker Swarm 和 Kubernetes 该怎么选？
参考：看团队规模和业务复杂度。小团队（< 50 容器）快速上手选 Swarm，一条命令初始化集群，与 Docker CLI 完美集成。生产环境、大规模集群选 Kubernetes，支持自动扩缩容、精细的滚动更新、丰富的存储和网络插件。当前行业标准是 Kubernetes，Swarm 社区活跃度已下降。如果已有 K8s 经验，不建议回退到 Swarm。
