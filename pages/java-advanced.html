CAS 原理与 ABA 问题

// CAS（Compare And Swap）：无锁并发的核心
// 操作：比较内存值 V 与期望值 E，相等则更新为新值 N，否则不做操作
// Java 中通过 Unsafe 类的 compareAndSwapInt/compareAndSwapObject 实现
// 底层是 CPU 的原子指令（x86: CMPXCHG）

// AtomicInteger 使用示例
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet(); // CAS + 自旋，线程安全的 i++

// ABA 问题：
// 线程1：读取 V=A，准备 CAS(A, B)
// 线程2：读取 V=A，CAS(A, C) 成功，再 CAS(C, A) 成功
// 线程1：CAS(A, B) 成功，但值已经被改过

// 解决方案：AtomicStampedReference（带版本号）
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
int[] stampHolder = new int[1];
String val = ref.get(stampHolder); // 获取值和版本号
int stamp = stampHolder[0];
ref.compareAndSet("A", "B", stamp, stamp + 1); // 同时比较值和版本号

// JDK 8+ LongAdder：高并发计数器
// 思路：分散热点，内部维护 Cell[] 数组，不同线程写不同 Cell
LongAdder adder = new LongAdder();
adder.increment();
long total = adder.sum(); // 最终一致性

ThreadLocal 原理与内存泄漏

// ThreadLocal 原理：
// 每个 Thread 内部持有 ThreadLocalMap
// ThreadLocalMap 的 Entry 继承 WeakReference<ThreadLocal<?>>
// Key 是 ThreadLocal 对象的弱引用，Value 是实际存储的值

// 结构：
// Thread -> ThreadLocalMap -> Entry[] -> Entry(key=弱引用, value=强引用)

// 内存泄漏场景：
// 1. ThreadLocal 对象被 GC 回收（Key 变为 null）
// 2. 但 Value 仍被 Entry 强引用，无法回收
// 3. 如果线程是线程池中的核心线程，一直存活，Value 永远无法回收

// 解决方案：用完后必须调用 remove()
ThreadLocal<User> userContext = new ThreadLocal<>();
try {
    userContext.set(currentUser);
    // 业务逻辑
} finally {
    userContext.remove(); // 必须在 finally 中清理
}

// 使用场景：
// 1. 用户会话信息（Spring SecurityContextHolder）
// 2. 数据库连接（每个线程独立 Connection）
// 3. 日期格式化（SimpleDateFormat 非线程安全）
// 4. 链路追踪（traceId 传递）
ThreadLocal 内存泄漏是最常见的并发面试题之一。核心要点：Key 是弱引用，Value 是强引用，用完必须 remove()。线程池场景尤其危险，因为线程不会销毁。

volatile 原理

volatile 两大特性

保证可见性

  • 写 volatile 变量时，立刻刷新到主内存
  • 读 volatile 变量时，从主内存读取最新值
  • 底层通过内存屏障（Memory Barrier）实现
  • x86 下对应 lock 前缀指令

禁止指令重排

  • volatile 写之前的操作不会被重排到写之后
  • volatile 读之后的操作不会被重排到读之前
  • 通过 LoadLoad / LoadStore / StoreStore / StoreLoad 屏障实现
  • 典型应用：DCL 单例模式

DCL 双重检查锁单例

// 正确的 DCL 单例（必须加 volatile）
public class Singleton {
    // volatile 关键！防止指令重排导致获取到未初始化的对象
    private static volatile Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查（无锁，避免不必要的同步）
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二次检查（加锁后确认）
                    instance = new Singleton();  // 非原子操作
                }
            }
        }
        return instance;
    }
}

// new Singleton() 分为三步：
// 1. 分配内存空间
// 2. 初始化对象（执行构造方法）
// 3. 将引用指向内存地址
// 如果没有 volatile，步骤 2 和 3 可能重排，导致其他线程
// 读到非 null 但未初始化完成的对象
DCL 单例必须加 volatile！不加 volatile 时，由于指令重排，其他线程可能获取到一个半初始化的对象（引用非 null 但构造方法未执行完）。

// CountDownLatch：等待 N 个任务完成
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++) {
    executor.submit(() -> {
        try {
            // 执行任务
        } finally {
            latch.countDown(); // 计数减 1
        }
    });
}
latch.await(); // 阻塞直到计数为 0
// 可指定超时：latch.await(10, TimeUnit.SECONDS)

// CyclicBarrier：所有线程同时开始
CyclicBarrier barrier = new CyclicBarrier(3, () -> {
    System.out.println("所有线程就绪，开始执行！");
});
for (int i = 0; i < 3; i++) {
    executor.submit(() -> {
        barrier.await(); // 等待其他线程
        // 所有线程同时到达这里
    });
}

// Semaphore：限制并发数
Semaphore semaphore = new Semaphore(10); // 最多 10 个并发
for (int i = 0; i < 100; i++) {
    executor.submit(() -> {
        semaphore.acquire(); // 获取许可
        try {
            // 执行任务
        } finally {
            semaphore.release(); // 归还许可
        }
    });
}

execute vs submit

execute(Runnable)

  • 提交 Runnable 任务
  • 无返回值
  • 异常直接抛出（UncaughtExceptionHandler）
  • 底层直接调用 run()

submit(Runnable/Callable)

  • 提交 Runnable 或 Callable
  • 返回 Future 对象
  • 异常封装在 Future 中，调用 get() 时抛出
  • 底层包装为 FutureTask
// 常用线程池工厂方法（不推荐生产使用）
Executors.newFixedThreadPool(n);      // 固定线程数，LinkedBlockingQueue（无界！）
Executors.newSingleThreadExecutor();  // 单线程，LinkedBlockingQueue
Executors.newCachedThreadPool();      // 缓存线程池，SynchronousQueue，max=MAX_VALUE
Executors.newScheduledThreadPool(n);  // 定时线程池

// 生产推荐手动创建 ThreadPoolExecutor
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),        // 有界队列
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy() // 调用者执行
);
阿里开发规范禁止使用 Executors 创建线程池。newFixedThreadPool 和 newSingleThreadExecutor 使用无界 LinkedBlockingQueue，可能导致 OOM。newCachedThreadPool 最大线程数为 Integer.MAX_VALUE，可能创建大量线程。

CompletableFuture

CompletableFuture 核心 API

// 创建
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    return queryFromDB(); // 异步执行
}, executor);

// 链式处理（同步）
CompletableFuture<Integer> f1 = future
    .thenApply(s -> s.length())        // 转换结果（有返回值）
    .thenAccept(len -> print(len))     // 消费结果（无返回值）
    .thenRun(() -> log("done"));       // 执行动作（无参数）

// 链式处理（异步）
future
    .thenApplyAsync(s -> process(s), executor)  // 异步转换
    .thenAcceptAsync(s -> save(s), executor);   // 异步消费

// 组合（thenCompose = flatMap，展平嵌套）
CompletableFuture<String> f2 = future.thenCompose(s ->
    CompletableFuture.supplyAsync(() -> queryAnother(s))
);

// 合并两个结果（thenCombine = zip）
CompletableFuture<String> nameFuture = getNameAsync();
CompletableFuture<Integer> ageFuture = getAgeAsync();
CompletableFuture<String> combined = nameFuture.thenCombine(ageFuture,
    (name, age) -> name + " is " + age + " years old"
);

// 等待所有完成
CompletableFuture.allOf(f1, f2, f3).join();

// 任意一个完成
CompletableFuture.anyOf(f1, f2, f3).join();

// 异常处理
future.exceptionally(ex -> "默认值")  // 异常时返回默认值
    .handle((result, ex) -> {          // 统一处理结果和异常
        if (ex != null) return "error";
        return result;
    });

并发容器

并发容器一览

容器底层结构线程安全方式适用场景
ConcurrentHashMap数组+链表+红黑树CAS + synchronized高并发 Map

CopyOnWriteArrayList 原理

// 写时复制：写操作时复制整个数组，修改新数组，然后替换引用
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1); // 复制
        newElements[len] = e;
        setArray(newElements); // 替换引用（volatile）
        return true;
    } finally {
        lock.unlock();
    }
}

// 读操作无锁，读的是快照（旧数组引用）
// 适用场景：读多写少（如事件监听器列表、配置白名单）
// 缺点：1）写操作开销大（数组拷贝）；2）读到的是旧数据（弱一致性）

注解与 SPI

自定义注解 + 反射实现简单框架

// 自定义注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface RateLimit {
    int value() default 100;  // 限流阈值
    String key() default "";  // 限流 key
}

// 注解处理器（AOP 切面）
@Aspect
@Component
public class RateLimitAspect {
    @Around("@annotation(rateLimit)")
    public Object around(ProceedingJoinPoint pjp, RateLimit rateLimit) throws Throwable {
        String key = rateLimit.key();
        int limit = rateLimit.value();
        // 限流逻辑（令牌桶/滑动窗口）
        if (!tryAcquire(key, limit)) {
            throw new RateLimitException("请求过于频繁");
        }
        return pjp.proceed();
    }
}

// 元注解说明：
// @Retention：SOURCE（编译丢弃）/ CLASS（类文件保留）/ RUNTIME（运行时保留）
// @Target：TYPE / METHOD / FIELD / PARAMETER / CONSTRUCTOR 等
// @Inherited：子类继承父类注解
// @Repeatable：可重复注解（JDK 8+）

SPI 机制（ServiceLoader）

// Java SPI（Service Provider Interface）
// 1. 定义接口
public interface Logger {
    void log(String message);
}

// 2. 实现类
public class FileLogger implements Logger {
    public void log(String message) { /* 写文件 */ }
}

// 3. 配置文件 META-INF/services/com.example.Logger
// 内容：com.example.FileLogger

// 4. 使用 ServiceLoader 加载
ServiceLoader<Logger> loaders = ServiceLoader.load(Logger.class);
for (Logger logger : loaders) {
    logger.log("hello");
}

// Java SPI 特点：
// 1. 基于配置文件（META-INF/services/全限定接口名）
// 2. 遍历所有实现类（全量加载，懒初始化）
// 3. 线程不安全（Iterator 非线程安全）
// 4. 无法按需获取特定实现

// Dubbo SPI 改进：
// 1. 配置文件改为 key=value 形式（META-INF/dubbo/全限定接口名）
// 2. 支持按名获取：ExtensionLoader.getExtensionLoader(T.class).getExtension("name")
// 3. 支持 AOP（Wrapper 自动装饰）、IoC（setter 注入）
// 4. 支持 @Adaptive 自适应扩展（根据 URL 参数动态选择实现）
面试加分点：Java SPI 的典型应用是 JDBC DriverManager（加载数据库驱动）、SLF4J（加载日志实现）。Dubbo SPI 是 Dubbo 框架可扩展性的核心。

// 如：任务 80% 时间在等待 IO → N * (1 + 80/20) = N * 5
int ioIntensiveThreads = cpuCores * 2;

// 雪花算法（Snowflake）ID 结构（64 bit）
// 0 | 41 位时间戳 | 10 位机器 ID | 12 位序列号
// 符号位   毫秒级        1024 节点     每毫秒 4096 个 ID

// 简化实现
public class SnowflakeIdGenerator {
    private final long startTimestamp = 1609459200000L; // 2021-01-01
    private final long workerIdBits = 10L;
    private final long sequenceBits = 12L;
    private final long maxWorkerId = ~(-1L << workerIdBits); // 1023
    private final long sequenceMask = ~(-1L << sequenceBits); // 4095

    private long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) timestamp = waitNextMillis(lastTimestamp);
        } else {
            sequence = 0L;
        }
        lastTimestamp = timestamp;
        return ((timestamp - startTimestamp) << (workerIdBits + sequenceBits))
             | (workerId << sequenceBits)
             | sequence;
    }
}

异步编排

电商订单查询场景

// 查询订单详情：需要聚合用户信息、商品信息、物流信息
// 串行：3 次 RPC 总耗时 = 100 + 150 + 80 = 330ms
// 并行：3 次 RPC 总耗时 = max(100, 150, 80) = 150ms

public OrderDetailVO getOrderDetail(String orderId) {
    // 并行发起三个异步请求
    CompletableFuture<UserVO> userFuture = CompletableFuture.supplyAsync(
        () -> userService.getUser(orderId), executor);

    CompletableFuture<List<ProductVO>> productFuture = CompletableFuture.supplyAsync(
        () -> productService.getProducts(orderId), executor);

    CompletableFuture<LogisticsVO> logisticsFuture = CompletableFuture.supplyAsync(
        () -> logisticsService.getLogistics(orderId), executor);

    // 等待所有完成，组装结果
    CompletableFuture.allOf(userFuture, productFuture, logisticsFuture).join();

    OrderDetailVO vo = new OrderDetailVO();
    vo.setUser(userFuture.join());
    vo.setProducts(productFuture.join());
    vo.setLogistics(logisticsFuture.join());
    return vo;
}

// 异常处理：某个服务失败不影响其他服务
CompletableFuture<UserVO> userFuture = CompletableFuture.supplyAsync(
    () -> userService.getUser(orderId), executor)
    .exceptionally(ex -> {
        log.warn("查询用户信息失败", ex);
        return UserVO.empty(); // 返回默认值
    });

第三部分：模拟面试

synchronized 锁升级的过程是怎样的？为什么需要锁升级？
参考：synchronized 锁升级过程为：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。
1）偏向锁：对象头 Mark Word 记录首次获取锁的线程 ID，下次同一线程进入时无需 CAS，直接判断线程 ID 即可。适合单线程反复获取锁的场景。
2）轻量级锁：当第二个线程竞争时，偏向锁撤销，升级为轻量级锁。线程在栈帧中创建 Lock Record，通过 CAS 尝试将 Mark Word 指向 Lock Record。适合锁持有时间短、竞争不激烈的场景。
3）重量级锁：CAS 自旋超过阈值（默认 10 次，JDK 6+ 自适应自旋），升级为重量级锁。通过 OS 的 Mutex Lock 实现，未获取锁的线程阻塞挂起。
为什么需要锁升级：不同场景下锁竞争程度不同，锁升级机制让 JVM 根据竞争强度自动选择最优的锁实现，在无竞争时几乎零开销，高竞争时保证正确性。
volatile 能保证原子性吗？为什么 DCL 单例要加 volatile？
参考：volatile 不能保证原子性。volatile 保证可见性和禁止指令重排，但 i++ 这种复合操作（读-改-写）不是原子的。要保证原子性需要 synchronized、Lock 或 AtomicInteger。
DCL 单例加 volatile 的原因：instance = new Singleton() 不是原子操作，分为三步：1）分配内存；2）初始化对象；3）引用指向内存。JVM 可能将 2 和 3 重排，导致其他线程在第一次 null 检查时读到非 null 但未初始化完成的对象。volatile 通过内存屏障禁止这种重排。
追问：除了 DCL，还有什么方式实现单例？ 静态内部类（Holder 模式，类加载保证线程安全）、枚举单例（JVM 保证唯一，防反射和序列化攻击）。
线程池的核心参数有哪些？如何合理配置？
参考：7 大参数：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（非核心线程空闲存活时间）、unit（时间单位）、workQueue（工作队列）、threadFactory（线程工厂）、handler（拒绝策略）。
配置原则：1）CPU 密集型任务：线程数 = N + 1（N 为 CPU 核心数）；2）IO 密集型任务：线程数 = N * 2 或 N * (1 + W/C)；3）队列用有界队列（ArrayBlockingQueue），防 OOM；4）拒绝策略根据业务选择（CallerRunsPolicy 保证不丢任务）；5）自定义 ThreadFactory 设置线程名（方便排查）。
追问：为什么阿里规范禁止使用 Executors？ newFixedThreadPool 使用无界 LinkedBlockingQueue，任务无限堆积可能 OOM；newCachedThreadPool 最大线程数 Integer.MAX_VALUE，可能创建大量线程导致 OOM。
参考：AQS（AbstractQueuedSynchronizer）是 JUC 并发工具的基础框架。核心是一个 volatile int state（表示锁状态）和一个 CLH 双向队列（存放等待获取锁的线程）。
ReentrantLock 的实现：lock() 时尝试 CAS 修改 state（0→1），成功则获取锁并记录持有线程；失败则将当前线程封装为 Node 加入 CLH 队列，通过 LockSupport.park() 阻塞。unlock() 时将 state 减 1（可重入），为 0 时释放锁并唤醒队列中的下一个线程。
公平锁和非公平锁的区别：非公平锁在 lock() 时直接尝试 CAS（可能插队），公平锁先检查队列中是否有等待线程（hasQueuedPredecessors），有则排队。
CountDownLatch 和 CyclicBarrier 有什么区别？各自适用什么场景？
参考：CountDownLatch 是一次性计数器，countDown() 递减到 0 时唤醒所有 await() 的线程，不可复用。适合主线程等多个子任务完成的场景（如并行查询多个数据源后汇总）。
CyclicBarrier 是可复用的屏障，所有线程到达屏障点后同时继续，自动重置。适合多个线程互相等待、同时开始的场景（如多线程分段计算后合并）。
核心区别：1）CountDownLatch 计数递减到 0，CyclicBarrier 计数递增到 N；2）CountDownLatch 不可复用，CyclicBarrier 可复用；3）CountDownLatch 一个线程 countDown 多次，CyclicBarrier 每个线程 await 一次；4）CyclicBarrier 支持 barrierAction（最后一个到达的线程执行）。
CompletableFuture 的 thenApply 和 thenCompose 有什么区别？
参考：thenApply 类似 Stream 的 map，将结果 T 转换为 U，返回 CompletableFuture<U>。如果转换函数返回 CompletableFuture，结果会变成嵌套的 CompletableFuture<CompletableFuture<U>>。
thenCompose 类似 Stream 的 flatMap，用于展平嵌套。如果函数返回 CompletableFuture<U>，thenCompose 会自动展平为 CompletableFuture<U>，避免嵌套。
一句话总结：thenApply 用于同步转换，thenCompose 用于异步链式调用（当转换本身也是异步操作时）。
追问：CompletableFuture 的异常怎么处理？ exceptionally(ex -> default) 兜底；handle((result, ex) -> ...) 统一处理；whenComplete((result, ex) -> ...) 类似 handle 但不改变结果。
ThreadLocal 的原理是什么？为什么会导致内存泄漏？
参考：ThreadLocal 的实现依赖于 Thread 类中的 ThreadLocalMap。每个 Thread 持有一个 ThreadLocalMap，以 ThreadLocal 对象为 Key（弱引用），用户设置的值为 Value（强引用）。get() 时通过当前线程的 ThreadLocalMap 以 this（ThreadLocal 对象）为 Key 查找 Value。
内存泄漏原因：ThreadLocal 对象被 GC 回收后，Key 变为 null（弱引用），但 Value 仍被 Entry 强引用，无法被 GC。如果线程是线程池中的核心线程长期存活，这些 Value 就永远不会被回收。
解决方案：1）用完后必须在 finally 中调用 remove()；2）ThreadLocalMap 在 get/set 时会清理 Key 为 null 的 Entry（启发式清理），但不能完全依赖。
追问：InheritableThreadLocal 有什么问题？ 线程池中线程复用，父线程设置的值不会传递到新任务（因为线程已经创建了）。
参考：Java SPI（ServiceLoader）通过 META-INF/services/ 下的配置文件加载接口的所有实现类，全量加载，无法按名获取，遍历所有实现。典型应用：JDBC 驱动加载。
Dubbo SPI 改进：1）配置文件改为 key=value 形式（META-INF/dubbo/），支持按名获取；2）支持 AOP（自动 Wrapper 装饰器链）；3）支持 IoC（setter 依赖注入）；4）@Adaptive 自适应扩展（根据 URL 参数动态选择实现）；5）支持自动激活扩展 @Activate（如 Filter 链）。
追问：Dubbo 的 @Adaptive 怎么工作？ 标注了 @Adaptive 的方法在运行时根据 URL 参数（如 protocol=dubbo）动态选择对应的 SPI 实现类，生成代理类实现动态路由。
参考：CAS（Compare And Swap）是一种无锁并发原语，操作包含三个值：内存值 V、期望值 A、新值 B。当 V == A 时，将 V 更新为 B，否则不做操作。整个操作是 CPU 级别的原子指令（x86 的 CMPXCHG）。
ABA 问题：值从 A 变为 B 再变回 A，CAS 检测不到变化。解决：AtomicStampedReference 加版本号（stamp），每次修改版本号递增；AtomicMarkableReference 加布尔标记。
LongAdder 为什么快：AtomicLong 所有线程竞争同一个 value（热点集中），LongAdder 将 value 分散到 Cell[] 数组中，不同线程写不同 Cell（类似分段锁思想），sum() 时汇总。高并发下 LongAdder 的吞吐量远高于 AtomicLong。
