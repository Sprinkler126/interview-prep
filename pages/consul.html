核心角色

角色职责部署要求
Server存储数据、Raft 一致性、响应查询3 或 5 个（奇数）
Client无状态代理，转发请求到 Server每台应用机器一个
Agent每个节点上运行的守护进程所有节点
  • Client Agent 不存储数据，只负责健康检查和转发请求
  • Client 将 RPC 请求转发给 Server，本地缓存服务列表减少网络开销
  • Server 之间通过 Raft 协议保证数据一致性
  • Agent 运行在每个节点上，以 Client 或 Server 模式运行

健康检查

健康检查类型

类型说明适用场景
HTTP发送 HTTP GET，返回 2xx 为健康Web 应用（最常用）
TCP尝试 TCP 连接，成功则健康数据库、Redis 等
Script执行自定义脚本，退出码 0 为健康复杂检查逻辑
gRPC调用 gRPC 健康检查接口gRPC 服务
TTL服务主动上报心跳，超时则不健康简单应用、脚本
 
// 健康检查配置
// HTTP 检查
{
  "check": {
    "http": "http://localhost:8080/health",
    "interval": "10s",
    "timeout": "3s",
    "deregister_critical_service_after": "30m"  // 不健康 30 分钟后注销
  }
}

// TTL 检查（服务主动上报）
{
  "check": {
    "ttl": "15s"
  }
}
// 服务端定期更新 TTL
PUT /v1/agent/check/pass/service:my-service
Consul 的健康检查比 Eureka 更丰富。Eureka 只有客户端心跳，Consul 支持服务端主动探测（HTTP/TCP/gRPC）和客户端心跳（TTL）两种模式。

KV 存储操作

// 写入

// 当 ModifyIndex > 5 时立即返回，最多等 30 秒

Gossip 协议

Consul 的 Gossip 协议

  • Consul 使用两个 Gossip Pool：LAN Pool（数据中心内）和 WAN Pool（跨数据中心）
  • 底层使用 Serf 库实现 Gossip 协议，基于 SWIM（Scalable Weakly-consistent Infection-style Process Group Membership）协议
  • LAN Pool：同一数据中心的所有 Agent 参加，用于节点发现、故障检测、事件广播
  • WAN Pool：所有 Server 节点参加，用于跨数据中心的 Server 发现和故障检测
// Gossip 协议工作原理：
// 1. 每个节点维护一个成员列表
// 2. 随机选择一个节点发送 Ping
// 3. 如果收到 Ack → 节点正常
// 4. 如果未收到 Ack → 间接 Ping（请求其他节点帮忙 Ping）
// 5. 如果间接 Ping 也失败 → 标记为可疑（Suspect）
// 6. 超时后标记为故障（Failed）

// 优势：
// - 去中心化，无单点故障
// - 新节点加入只需知道集群中任意一个节点
// - 最终一致性，消息传播速度快（O(logN)）
// - 天然支持故障检测

第二部分：场景化讲解

多数据中心

多数据中心架构

  • 每个数据中心有独立的 Consul Server 集群（3~5 个 Server）
  • 同一数据中心内的所有 Agent 通过 LAN Gossip 通信
  • 不同数据中心的 Server 通过 WAN Gossip 通信
  • 跨数据中心查询：本地 Server 收到请求后，通过 WAN Gossip 转发到目标数据中心的 Server
// 跨数据中心服务发现
// 查询所有数据中心
GET /v1/catalog/datacenters
// ["dc1", "dc2"]

// 查询 dc2 中的 user-service
GET /v1/health/service/user-service?dc=dc2&passing=true

// DNS 方式
dig @127.0.0.1 -p 8600 user-service.service.dc2.consul

// 只查询本地数据中心（默认）
dig @127.0.0.1 -p 8600 user-service.service.consul
多数据中心是 Consul 的核心竞争力。Nacos 和 Eureka 都不原生支持多数据中心，需要额外配置或改造。

Consul Connect

Consul Connect（Service Mesh）

  • Service Mesh 功能：自动为服务间通信建立 mTLS（双向 TLS）加密
  • Sidecar Proxy：每个服务旁部署一个 Envoy 代理，透明处理加密和授权
  • Intentions：定义服务间通信的授权规则（允许/拒绝）
  • Native Proxy：应用可直接使用 Consul 的 Connect API，无需 Sidecar
// 服务注册时启用 Connect
{
  "service": {
    "name": "user-service",
    "port": 8080,
    "connect": {
      "sidecar_service": {}   // 启用 Sidecar 代理
    }
  }
}

// Intention（服务间授权规则）
// 允许 order-service 访问 user-service
{
  "SourceName": "order-service",
  "DestinationName": "user-service",
  "Action": "allow"
}

// 通过 API 管理 Intention
PUT /v1/connect/intentions
{
  "SourceName": "*",
  "DestinationName": "user-service",
  "Action": "deny"       // 默认拒绝所有
}
Consul Connect 是 HashiCorp 的 Service Mesh 解决方案，与 Istio 不同的是，它与 Consul 深度集成，无需额外安装控制面。

第三部分：模拟面试

请介绍 Consul 的架构，Server 和 Client Agent 分别是什么角色？
参考：Consul 架构中有两种角色：Server 和 Client。Server 是有状态节点，存储所有数据（服务注册信息、KV 数据、ACL 等），通过 Raft 协议保证一致性，通常部署 3 或 5 个。Client 是无状态代理，部署在每台应用机器上，负责本地健康检查和将请求转发给 Server。Client 不存储数据，只维护本地缓存。所有 Agent（无论 Server 还是 Client）通过 LAN Gossip 协议通信，实现节点发现和故障检测。这种架构的优势是 Client Agent 就近部署，减少网络延迟，同时 Server 数量可控。
Consul 的服务发现有哪两种方式？各有什么优缺点？
参考：Consul 支持 HTTP API 和 DNS 两种服务发现方式。HTTP API：通过 /v1/health/service/{name} 查询服务实例列表，返回详细信息（地址、端口、健康状态、元数据），支持过滤和阻塞查询，适合程序化调用。DNS 方式：通过标准 DNS 查询 {name}.service.consul，返回 IP 地址列表，支持 SRV 记录获取端口，适合任何支持 DNS 的客户端（如数据库连接池）。优点：DNS 方式无需 SDK，通用性好；HTTP API 信息丰富，支持高级过滤。缺点：DNS 方式信息有限，不支持标签过滤；HTTP API 需要集成 SDK。
Consul 的 Gossip 协议是什么？LAN Pool 和 WAN Pool 有什么区别？
参考：Consul 使用 Serf 库实现 Gossip 协议，基于 SWIM 协议。工作原理：节点随机选择其他节点发送 Ping，收到 Ack 则正常，未收到则请求其他节点间接 Ping，间接 Ping 也失败则标记故障。两个 Gossip Pool：LAN Pool 是同一数据中心内所有 Agent 参加的池，用于节点发现、故障检测和事件广播；WAN Pool 是所有数据中心的 Server 参加的池，用于跨数据中心的 Server 发现和故障检测。Gossip 协议的优势是去中心化、天然支持故障检测、新节点加入只需知道一个已有节点。
Consul 的多数据中心支持是怎么实现的？
参考：Consul 原生支持多数据中心。每个数据中心有独立的 Server 集群和 LAN Gossip Pool。不同数据中心的 Server 通过 WAN Gossip Pool 连接。跨数据中心查询流程：客户端请求本地 Server，如果请求指定其他数据中心（dc=dc2），本地 Server 通过 WAN Gossip 转发到目标数据中心的 Server，目标 Server 处理后返回结果。每个数据中心的数据是独立的（服务注册、KV 存储），跨数据中心只做查询转发。DNS 支持 {service}.service.{dc}.consul 格式查询特定数据中心的服务。
Consul 的健康检查有哪些类型？比 Eureka 有什么优势？
参考：Consul 支持五种健康检查：1）HTTP — 发送 GET 请求，返回 2xx 为健康；2）TCP — 尝试 TCP 连接，成功则健康；3）Script — 执行自定义脚本，退出码 0 为健康；4）gRPC — 调用 gRPC 健康检查接口；5）TTL — 服务主动上报心跳，超时则不健康。比 Eureka 的优势：Eureka 只有客户端心跳模式，Consul 额外支持服务端主动探测（HTTP/TCP/gRPC），可以在服务假死（进程在但无法处理请求）时准确发现不健康实例。Consul 还支持 deregister_critical_service_after，不健康实例在一定时间后自动注销。
Consul Connect 是什么？与 Istio 有什么区别？
参考：Consul Connect 是 Consul 的 Service Mesh 功能，提供服务间 mTLS 加密和授权。核心组件：1）Sidecar Proxy — 每个服务旁部署 Envoy 代理，透明处理加密和授权；2）Intentions — 定义服务间通信的 ACL 规则（允许/拒绝）；3）CA — 内置证书颁发机构，自动管理 TLS 证书。与 Istio 的区别：Consul Connect 与 Consul 深度集成，无需额外安装控制面（Istio 需要 Pilot/Citadel/Galley）；Consul 支持多种注册中心（Kubernetes/Nomad/EC2），Istio 主要面向 Kubernetes；Consul 更轻量，Istio 功能更全面（流量管理、可观测性）。
Consul 的 KV 存储可以用来做什么？CAS 操作是什么？
参考：Consul 的 KV 存储是内置的分布式 KV 数据库，用途：1）配置管理 — 存储应用配置，通过阻塞查询（Long Polling）实现配置变更通知；2）分布式锁 — 结合 Session 实现（acquire/release）；3）Leader 选举 — 利用 CAS + Session；4）服务标记 — 存储服务的动态标记信息。CAS（Check-And-Set）是乐观锁操作：PUT 时指定 ModifyIndex，只有当前 ModifyIndex 匹配时才更新。阻塞查询（?index=N&wait=30s）在数据变更时立即返回，是实现配置实时推送的基础。
