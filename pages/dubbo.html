第一部分：技术原理

整体架构

Dubbo 架构总览
Provider
服务提供者
Consumer
服务消费者
↓ 注册/订阅 ↓
Registry
注册中心（Zookeeper / Nacos）
↓ 通知变更 ↓
Monitor
监控中心
Container
服务运行容器

核心角色

角色职责说明
Provider服务提供者暴露服务，向 Registry 注册自身地址
Consumer服务消费者从 Registry 订阅服务地址列表，发起远程调用
Registry注册中心管理服务地址，支持 Zookeeper、Nacos、Redis 等
Monitor监控中心统计调用次数、调用时间等监控数据
Container服务运行容器负责启动、加载、运行 Provider

调用关系说明

  • Provider 启动时向 Registry 注册服务地址
  • Consumer 启动时从 Registry 订阅所需服务的地址列表
  • Registry 返回地址列表给 Consumer，并通过长连接推送变更通知
  • Consumer 根据负载均衡算法选择一个 Provider 发起调用
  • Consumer 和 Provider 定时向 Monitor 上报调用统计数据
  • Provider、Consumer 之间的调用为直连，不经过 Registry
面试关键点：Registry 只负责地址注册与发现，不参与实际的 RPC 调用过程。Consumer 与 Provider 之间是直接通信的。

Invoker 核心模型

Dubbo 中所有的服务调用都抽象为 Invoker 接口：

public interface Invoker<T> {
    Class<T> getInterface();     // 服务接口
    Result invoke(Invocation invocation) throws RpcException; // 调用
    URL getUrl();                 // 服务地址
    boolean isAvailable();        // 是否可用
}

// Consumer 端有三种 Invoker：
// 1. MockInvoker - 本地 mock 实现
// 2. ClusterInvoker - 集群包装（带容错）
// 3. RemoteInvoker - 远程调用（实际网络通信）

特点：

协议连接方式序列化适用场景

负载均衡策略

四种内置负载均衡策略

策略算法特点
Random加权随机默认策略，按权重设置随机概率，调用量越大分布越均匀
RoundRobin加权轮询按公约后的权重轮循调用，存在慢请求堆积问题
LeastActive最少活跃数优先调用活跃调用数最少的 Provider，慢机器收到更少请求
ConsistentHash一致性哈希相同参数的请求总是发到同一 Provider，适合有状态服务
 
// 配置负载均衡策略
// 方法级 > 接口级 > 全局
@DubboReference(loadbalance = "roundrobin")
private UserService userService;

// 服务端配置
@DubboService(weight = 100, loadbalance = "leastactive")
public class UserServiceImpl implements UserService { }

// 全局配置（application.yml）
dubbo:
  provider:
    loadbalance: roundrobin

LeastActive 详解

最少活跃数算法的核心思想：处理请求越快的 Provider，其活跃计数下降越快，因此能获得更多新请求。

// LeastActive 原理
1. Consumer 端维护每个 Provider 的活跃计数 active
2. 调用前 active++，调用后 active--
3. 选择 active 最小的 Provider 发起调用
4. 若有多个 Provider 活跃数相同，按权重随机选择
5. 效果：处理慢的机器自动收到更少的请求
LeastActive 是 Dubbo 特有的策略，天然具备自适应能力——慢节点自动减少流量，无需额外配置。

集群容错

集群容错策略

策略行为适用场景
Failover失败自动切换（默认），重试其他 Provider读操作，幂等性写操作
Failfast快速失败，立即报错非幂等写操作（如新增订单）
Failsafe安全失败，忽略异常日志记录、审计等不重要的操作
Failback失败自动恢复，后台定时重试消息通知等最终一致性场景
Forking并行调用多个 Provider，一个成功即返回对实时性要求极高的读操作
 
// 配置集群容错策略
@DubboReference(cluster = "failfast")
private OrderService orderService;

// 配置重试次数（仅 Failover 有效）
@DubboReference(retries = 2)  // 默认重试 2 次，共调用 3 次
private UserService userService;

集群容错流程

Failover 容错流程
调用 Invoker A
→
异常/超时
→
Cluster 层捕获
→
重试 Invoker B
→
成功返回
  • Failover：失败后从 Directory 中选择下一个 Invoker 重试，默认重试 2 次
  • Failfast：只调用一次，失败立即抛出异常
  • Failback：失败后返回成功结果，后台记录失败请求，定时重试（默认 5 秒后重试，最多重试 3 次）
  • Forking：同时并行调用 forks 个 Provider（默认 2 个），任一成功即返回

第二部分：场景化讲解

服务治理

超时配置

// 超时优先级：方法级 > 接口级 > 全局 Consumer > 全局 Provider
// Provider 端
@DubboService(timeout = 3000)
public class UserServiceImpl implements UserService { }

// Consumer 端（优先级更高）
@DubboReference(timeout = 5000)
private UserService userService;

// 方法级配置
@DubboReference(methods = {
    @Method(name = "getUser", timeout = 2000)
})
private UserService userService;
超时配置遵循"Consumer 优先"原则。Provider 设置的超时是默认值，Consumer 可以覆盖。面试时要强调配置优先级。

降级（Mock）

// 方式一：配置 return null/empty（简单降级）
@DubboReference(mock = "return null")
private UserService userService;

// 方式二：指定 Mock 类（复杂降级）
@DubboReference(mock = "com.example.UserServiceMock")
private UserService userService;

// Mock 类实现
public class UserServiceMock implements UserService {
    @Override
    public User getUser(Long id) {
        // 返回降级数据
        return new User(id, "默认用户", "服务暂时不可用");
    }
}

// 触发条件：调用抛出 RpcException 时执行 Mock 逻辑

限流

  • ExecuteLimitFilter：服务端限制并发执行数，超过阈值拒绝新请求
  • ActiveLimitFilter：客户端限制并发调用数，超过阈值等待或拒绝
  • TpsLimitFilter：基于 TPS 限流，滑动窗口统计
// 服务端并发限流（最多 10 个并发）
@DubboService(executes = 10)

// 客户端并发限流（最多 5 个并发）
@DubboReference(actives = 5)

// TPS 限流
@DubboService(tps = 100, tpsInterval = 60000) // 每分钟最多 100 次

灰度发布（流量染色）

  • 通过 tag 机制实现流量染色，请求携带 tag 标签
  • Provider 端通过 @DubboService(tag = "gray") 标记灰度节点
  • Consumer 端通过 RpcContext.getContext().setAttachment("dubbo.tag", "gray") 路由到灰度节点
  • 未匹配 tag 的请求不会路由到灰度节点（隔离性好）

Dubbo 3.x 新特性

Triple 协议

  • 基于 HTTP/2，兼容 gRPC 协议，天然支持跨语言
  • 支持 Unary、Server Streaming、Client Streaming、Bidirectional Streaming
  • 同时支持 Protobuf 序列化和 Java 接口直接调用（无需 IDL）
  • 自带 TLS 加密和请求级别超时
  • 可穿透 HTTP 代理（如 Nginx），对 Service Mesh 友好
// Triple 协议配置
dubbo:
  protocol:
    name: tri
    port: 50051
    serialization: protobuf

// 流式调用示例
public interface GreeterService {
    // Unary
    HelloReply sayHello(HelloRequest request);
    // Server Streaming
    StreamObserver<HelloRequest> sayHello(StreamObserver<HelloReply> responseObserver);
}

应用级服务发现

接口级服务发现（2.x）

  • 每个接口在注册中心占一条记录
  • 注册中心数据量 = 接口数 x 实例数
  • 大规模场景下注册中心压力大
  • 10 万接口 x 100 实例 = 1000 万条记录

应用级服务发现（3.x）

  • 每个应用（实例）在注册中心占一条记录
  • 注册中心数据量 = 实例数
  • 大幅降低注册中心压力
  • 10 万实例 = 10 万条记录
应用级服务发现是 Dubbo 3.x 的重大架构改进，将注册中心数据量降低数个数量级。接口映射关系通过元数据中心（MetadataService）获取。

第三部分：模拟面试

请描述 Dubbo 的整体架构，各角色之间的交互流程是什么？
参考：Dubbo 架构包含五个核心角色：Provider（服务提供者）、Consumer（服务消费者）、Registry（注册中心）、Monitor（监控中心）和 Container（运行容器）。交互流程：1）Provider 启动时向 Registry 注册服务地址；2）Consumer 启动时从 Registry 订阅服务列表，Registry 返回地址并推送后续变更；3）Consumer 根据负载均衡策略选择一个 Provider 直接发起 RPC 调用；4）Provider 和 Consumer 定时向 Monitor 上报调用统计。关键点：Registry 只负责地址管理，不参与实际 RPC 调用，Consumer 与 Provider 之间是直连通信。
Dubbo 的负载均衡策略有哪些？LeastActive 策略的原理是什么？
参考：Dubbo 提供四种负载均衡策略：1）Random（加权随机，默认策略）；2）RoundRobin（加权轮询）；3）LeastActive（最少活跃数）；4）ConsistentHash（一致性哈希）。LeastActive 的原理是：Consumer 端维护每个 Provider 的活跃调用计数，调用前 active++，调用后 active--，选择活跃数最小的 Provider 发起调用。这天然实现了自适应——处理速度快的 Provider 活跃计数下降快，自动获得更多新请求；慢节点自动减少流量。如果多个 Provider 活跃数相同，则按权重随机选择。
Dubbo 的集群容错策略有哪些？分别适用什么场景？
参考：五种容错策略：1）Failover（失败重试，默认，重试其他节点，适合读操作和幂等写）；2）Failfast（快速失败，立即报错，适合非幂等写操作如新增订单）；3）Failsafe（安全失败，忽略异常，适合日志记录等不关键操作）；4）Failback（失败恢复，后台定时重试，适合消息通知等最终一致性场景）；5）Forking（并行调用多个节点，一个成功即返回，适合对实时性要求极高的读操作）。配置优先级：方法级 > 接口级 > 全局。
Dubbo 的超时配置优先级是怎样的？超时是在 Consumer 还是 Provider 生效？
参考：超时配置优先级从高到低：Consumer 方法级 > Consumer 接口级 > Consumer 全局 > Provider 方法级 > Provider 接口级 > Provider 全局。原则是"Consumer 优先"——Consumer 端的配置优先级高于 Provider 端。超时是双向生效的：Consumer 端在调用超时后不再等待返回；Provider 端在执行超时后中断执行并返回异常。建议统一在 Provider 端设置合理的默认超时，Consumer 端按需覆盖。
Dubbo 3.x 的 Triple 协议相比 Dubbo 协议有什么优势？
参考：Triple 协议基于 HTTP/2，相比传统 Dubbo 协议的优势：1）天然支持跨语言，兼容 gRPC 协议；2）支持流式调用（四种模式）；3）可穿透 HTTP 代理和负载均衡器（如 Nginx），对 Service Mesh 友好；4）自带 TLS 加密和请求级别超时；5）同时支持 Protobuf 序列化和 Java 接口直接调用（无需 IDL）。Triple 是 Dubbo 3.x 的默认协议，是实现应用级服务发现的关键基础。
Dubbo 3.x 的应用级服务发现相比接口级有什么改进？
参考：接口级服务发现中，每个接口在注册中心占一条记录，若有 N 个接口 M 个实例则有 N*M 条记录，大规模场景下注册中心压力巨大。应用级服务发现将粒度从接口降低到应用实例级别，每个实例只注册一条记录，数据量降低数个数量级。接口与应用的映射关系通过元数据中心（MetadataService）获取，元数据以 KV 形式存储。代价是首次调用需要额外查询元数据获取接口信息，可以通过本地缓存优化。
Dubbo 中如何实现服务降级？Mock 机制是怎么工作的？
参考：Dubbo 通过 Mock 机制实现服务降级。两种方式：1）简单降级 mock = "return null" 或 mock = "return empty"，调用失败时返回空值；2）自定义 Mock 类 mock = "com.example.UserServiceMock"，实现与服务接口相同的 Mock 类，在调用抛出 RpcException 时执行 Mock 逻辑返回降级数据。Mock 只在 RPC 调用异常时触发（如网络超时、服务不可用），业务异常不会触发 Mock。配合 check = false 可以实现启动时不检查依赖服务。
Dubbo 的 Filter 链机制是什么？有哪些常用的内置 Filter？
参考：Dubbo 的 Filter 是一种 AOP 机制，在 Invoker 调用前后插入横切逻辑，形成调用链。Consumer 端和 Provider 端各有独立的 Filter 链。常用内置 Filter：1）ConsumerContextFilter — 传递调用上下文；2）ActiveLimitFilter — 客户端并发限流；3）ExecuteLimitFilter — 服务端并发限流；4）TimeoutFilter — 超时控制；5）ExceptionFilter — 异常处理（将非 RpcException 包装为 RuntimeException）；6）TokenFilter — Token 验证防止绕过注册中心直连。Filter 的执行顺序通过 @Activate 注解的 order 属性控制。
