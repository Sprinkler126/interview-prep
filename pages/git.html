🔬第一部分：技术原理

1.1 Git 的对象模型

Git 是内容寻址的快照数据库

Git 在每次提交时记录项目的快照。对象内容经哈希得到对象 ID；提交对象通过父提交连成不可变的有向无环图（DAG）。分支只是一个指向提交的可移动引用，因此创建分支几乎没有成本。

对象保存内容面试要点
blob一个文件的原始内容不含文件名；相同内容只存一份

ref分支、tag 等名称到 commit ID 的指针分支不是提交副本，而是一个引用

Pull Request 检查清单

  • 标题说明为什么改；描述包含方案、验证方式和风险点。
  • 只包含当前目标的改动；无关格式化和依赖升级单独提交。
  • CI 至少覆盖构建、静态检查与关键测试；失败时先修复再请求审查。
  • 合并前同步目标分支；合并后删除功能分支，保持仓库整洁。

2.2 冲突与误操作恢复

冲突解决的正确顺序

  1. 理解双方修改的业务意图，不能机械选择 “ours/theirs”。
  2. 编辑冲突标记之间的内容，保留正确实现，再运行相关测试。
  3. git add <file> 标记已解决；merge 使用 git commit，rebase 使用 git rebase --continue。
  4. 方案不对时，使用 git merge --abort 或 git rebase --abort 回到开始前。
# reflog 记录 HEAD 的移动历史，可找回刚丢失的提交
git reflog
git switch -c recover-work <commit-id>

# 已推送的错误提交，创建反向提交而非改写共享历史
git revert <commit-id>
高频踩坑：不要用 git push --force 覆盖共享分支；个人分支确需强推时优先使用 --force-with-lease，它会在远端已被他人更新时拒绝覆盖。

2.3 发布、版本与可追溯性

需求做法价值
标记正式发布git tag -a v1.4.0 -m "release v1.4.0"用不可变版本定位对应源码
定位引入问题的提交git bisect start二分提交历史，快速缩小回归范围
紧急回滚git revert + 重新发布保留完整审计轨迹，适合生产分支
追踪一行代码git blame path/to/file辅助理解上下文，不等同于追责
版本建议：使用语义化版本时，MAJOR 表示不兼容变更，MINOR 表示向后兼容的新功能，PATCH 表示向后兼容的修复。Tag、构建产物和部署记录应相互关联。

🎤第三部分：模拟面试

Git 的分支为什么创建和切换很快？
参考答案：Git 的分支本质是一个指向 commit 的引用，不复制项目文件或完整历史。创建分支只是新建一个 ref，切换分支让 HEAD 指向另一个 ref 并更新工作区，因此成本很低。提交对象由父指针形成 DAG，多个分支共享同一段历史。
merge 和 rebase 有什么区别？为什么不能随意 rebase 已推送分支？
参考答案：merge 汇合两条历史，保留原始 commit ID；rebase 会把一系列提交基于新基底重新创建，因此 ID 会改变。若 rebase 了他人已拉取的共享提交，其他人的历史就会分叉。个人功能分支在发 PR 前可 rebase 保持线性；共享分支应 merge。
误执行 reset --hard 后如何恢复？已经推送的错误提交如何回滚？
参考答案：先用 git reflog 找到 reset 前 HEAD 指向的 commit，再用 git switch -c recover <commit> 建恢复分支。若错误已推送到共享分支，不应 force push 改历史，应使用 git revert <commit> 创建反向提交并走正常发布流程。
如何处理代码冲突？
参考答案：先同步目标分支，阅读冲突两边的意图，手工合成正确代码而不是盲目选一边。删除冲突标记后执行测试，确认后 git add；在 merge 中提交合并结果，在 rebase 中执行 git rebase --continue。不确定时用 --abort 回退。
