第一部分：技术原理

核心概念

Sentinel 核心概念

概念说明
Resource需要保护的资源，可以是方法、接口、代码块
Entry资源访问的入口，每次访问资源都需通过 Entry
Slot Chain处理链，多个 Slot 按顺序处理（责任链模式）
Node资源的实时统计节点（QPS、线程数、异常数等）
Context调用上下文，包含入口名、调用链信息

Slot Chain 处理链

Sentinel Slot Chain

ClusterBuilderSlot
集群统计

实时统计
→
FlowSlot

熔断判断
→
AuthoritySlot
授权检查
  • NodeSelectorSlot：构建资源的调用树结构，用于统计入口流量
  • ClusterBuilderSlot：构建资源的集群维度统计（ClusterNode）
  • StatisticSlot：核心统计 Slot，记录 QPS、线程数、响应时间等
  • FlowSlot：限流判断，根据 FlowRule 决定是否通过
  • DegradeSlot：熔断判断，根据 DegradeRule 决定是否熔断
  • AuthoritySlot：黑白名单授权检查
  • SystemSlot：系统维度保护（CPU、负载等）
Sentinel 的核心设计思想：所有保护功能都是 Slot Chain 中的一个 Slot，通过责任链模式串联，每个 Slot 职责单一，可插拔。

限流算法

四种限流算法

算法原理优点缺点
固定窗口 固定时间窗口内计数 实现简单 窗口边界突发流量问题
滑动窗口 将窗口细分为多个小格，滑动统计 解决边界问题，统计精确 内存占用稍高
漏桶 固定速率流出，多余的丢弃 流量平滑 无法应对突发流量
令牌桶 固定速率生成令牌，请求需获取令牌 允许一定突发 实现相对复杂
Sentinel 默认使用滑动窗口算法（LeapArray），将时间窗口划分为多个 bucket（默认 2 个，interval 为 1 秒），每个 bucket 统计该时间片内的请求数据。

流控规则配置

属性说明

// 流控模式
// 1. 直接：资源本身超过阈值就限流
// 2. 关联：关联资源超过阈值，限流当前资源
//    例：读 /write 超过阈值，限流 /read（保护写优先）
// 3. 链路：入口资源超过阈值，限流从该入口的调用
//    例：入口 A 和 B 都调用 resource，只限制从 A 的调用

// 流控效果
// 1. 快速失败（默认）：直接拒绝，抛出 BlockException
// 2. Warm Up：预热模式，阈值从 threshold/coldFactor 开始
//    经过预热时长逐步升至设定阈值（适合冷启动场景）
// 3. 排队等待：匀速排队，漏桶模式
//    超过阈值的请求排队等待，超时则拒绝

熔断降级

熔断策略

策略触发条件说明

熔断器状态机

熔断器状态转换
CLOSED
关闭（正常放行）
OPEN
打开（拒绝所有）
HALF-OPEN
半开（试探放行）
触发条件满足 → CLOSED → OPEN（熔断）
熔断时长结束 → OPEN → HALF-OPEN（试探）
试探成功 → HALF-OPEN → CLOSED（恢复）
试探失败 → HALF-OPEN → OPEN（继续熔断） 
// 熔断规则配置
DegradeRule rule = new DegradeRule("resource")
    .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType())
    .setCount(0.5)              // 慢调用比例阈值 50%
    .setSlowRatioThreshold(200) // 慢调用 RT 阈值 200ms
    .setTimeWindow(10)          // 熔断持续时间 10 秒
    .setMinRequestAmount(5)     // 最小请求数（防止样本不足）
    .setStatIntervalMs(10000);  // 统计窗口 10 秒

热点参数限流

热点参数限流

// 热点参数限流：针对特定参数值设置不同阈值
// 例如：商品 ID=1001 是热门商品，限流阈值 100 QPS
//       其他商品阈值 1000 QPS

@SentinelResource(value = "getProduct", blockHandler = "getBlock")
public Product getProduct(Long productId) {
    return productService.getById(productId);
}

// 配置热点规则
ParamFlowRule rule = new ParamFlowRule("getProduct")
    .setParamIdx(0)              // 参数索引（0 = 第一个参数）
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(1000);             // 默认阈值

// 特殊值配置
ParamFlowItem item = new ParamFlowItem()
    .setObject(String.valueOf(1001L))  // 商品 ID 1001
    .setClassType(long.class)
    .setCount(100);                    // 热门商品限流 100 QPS
rule.setParamFlowItemList(Collections.singletonList(item));
热点参数限流是 Sentinel 的特色功能，适合秒杀、热门商品等场景。底层使用 LRU 缓存 + 滑动窗口统计每个参数值的 QPS。

系统自适应保护

系统保护规则

指标说明阈值
系统负载 (load)系统 1 分钟平均负载当 load > 阈值且当前线程数 > QPS 时触发
CPU 使用率系统 CPU 使用率CPU > 阈值时触发
平均 RT所有入口资源的平均响应时间RT > 阈值时触发
入口 QPS所有入口资源的总 QPSQPS > 阈值时触发
并发线程数所有入口资源的并发线程数线程数 > 阈值时触发
 
// 系统保护规则
SystemRule rule = new SystemRule();
rule.setHighestSystemLoad(5.0);      // 系统负载 > 5 时触发
rule.setHighestCpuUsage(0.8);        // CPU > 80% 时触发
rule.setAvgRt(200);                  // 平均 RT > 200ms 时触发
rule.setMaxThread(200);              // 并发线程 > 200 时触发
rule.setQps(1000);                   // 入口 QPS > 1000 时触发
系统自适应保护是全局维度的防护，当系统整体负载过高时，自动降低所有入口的流量，防止系统过载崩溃。

Sentinel 与 Hystrix 对比

特性SentinelHystrix
隔离策略信号量（并发控制）信号量 + 线程池

Sentinel 是 Hystrix 的全面升级替代品。Hystrix 已于 2018 年进入维护模式，Netflix 官方推荐使用 Resilience4j，而 Spring Cloud 生态推荐 Sentinel。

Spring Cloud 集成

@SentinelResource 注解

// @SentinelResource 核心注解
@SentinelResource(
    value = "getOrder",                    // 资源名
    blockHandler = "getOrderBlock",        // 限流/熔断处理方法
    blockHandlerClass = OrderBlock.class,  // 处理方法所在类
    fallback = "getOrderFallback",         // 业务异常兜底方法
    fallbackClass = OrderFallback.class,   // 兜底方法所在类
    exceptionsToIgnore = {IllegalArgumentException.class} // 忽略的异常
)
public Order getOrder(Long orderId) {
    return orderService.getById(orderId);
}

// blockHandler：处理 BlockException（限流/熔断）
// 必须在原方法同签名基础上加 BlockException 参数
public class OrderBlock {
    public static Order getOrderBlock(Long orderId, BlockException ex) {
        return new Order(orderId, "限流降级");
    }
}

// fallback：处理业务异常
// 必须在原方法同签名基础上加 Throwable 参数
public class OrderFallback {
    public static Order getOrderFallback(Long orderId, Throwable t) {
        return new Order(orderId, "业务降级");
    }
}

// 优先级：blockHandler > fallback > 全局兜底

第三部分：模拟面试

Sentinel 的核心架构是什么？Slot Chain 是如何工作的？
参考：Sentinel 的核心是 Slot Chain（处理链），采用责任链模式。每次访问资源时，通过 SphU.entry() 创建 Entry，依次经过各个 Slot 处理：NodeSelectorSlot（构建调用树）→ ClusterBuilderSlot（集群统计）→ StatisticSlot（实时统计 QPS/RT/线程数）→ FlowSlot（限流判断）→ DegradeSlot（熔断判断）→ AuthoritySlot（授权检查）→ SystemSlot（系统保护）。每个 Slot 职责单一，可插拔扩展。StatisticSlot 是核心，负责统计实时指标供其他 Slot 使用。如果某个 Slot 判定拦截，会抛出 BlockException。
Sentinel 的流控模式有哪些？关联模式和链路模式有什么区别？
参考：Sentinel 有三种流控模式：1）直接模式 — 资源本身超过阈值就限流；2）关联模式 — 当关联资源超过阈值时限流当前资源，例如写接口 /write 超过阈值时限流读接口 /read，保护写优先；3）链路模式 — 从特定入口调用的资源被限流，例如入口 A 和 B 都调用 resource，只限制从 A 进入的调用，B 不受影响。区别：关联模式关注的是"别的资源"的流量，链路模式关注的是"特定入口"的流量。链路模式需要配合 @SentinelResource 的 entry 属性使用。
Sentinel 的熔断器状态机是怎样的？从 CLOSED 到 OPEN 的转换条件是什么？
参考：Sentinel 熔断器有三个状态：CLOSED（正常放行）、OPEN（拒绝所有请求）、HALF-OPEN（试探放行）。从 CLOSED 到 OPEN 的转换条件取决于熔断策略：1）慢调用比例 — 在统计窗口内，响应时间超过阈值的请求比例超过设定值；2）异常比例 — 异常请求占总请求的比例超过设定值；3）异常数 — 异常请求绝对数量超过设定值。触发熔断后进入 OPEN 状态，拒绝所有请求。经过熔断时长（timeWindow）后进入 HALF-OPEN，放行一个试探请求。试探成功回到 CLOSED，失败回到 OPEN。
Sentinel 的热点参数限流是什么原理？适用于什么场景？
参考：热点参数限流是 Sentinel 的特色功能，可以针对方法参数的特定值设置不同的限流阈值。例如商品详情接口，热门商品 ID=1001 设置 100 QPS，其他商品 1000 QPS。底层实现：使用 LRU 缓存存储每个参数值的统计窗口，每个参数值独立维护一个滑窗口计数器。适用场景：秒杀场景（特定商品限流）、热点新闻（特定文章 ID 限流）、用户维度限流（防止刷接口）。配置时需要指定参数索引和特殊值列表，不在特殊值列表中的参数使用默认阈值。
Sentinel 和 Hystrix 有什么区别？为什么推荐用 Sentinel？
参考：主要区别：1）Sentinel 有限流功能（QPS/线程数/热点），Hystrix 只有熔断；2）Sentinel 支持系统自适应保护（CPU/负载），Hystrix 没有；3）Sentinel 有 Dashboard 控制台可在线管理规则，Hystrix 需配合 Archaius；4）Sentinel 的 Slot Chain 架构更灵活可扩展；5）Hystrix 已于 2018 年停止维护，Sentinel 持续更新。推荐 Sentinel 的原因：功能更全面（限流+熔断+系统保护+热点+授权），生态更活跃，与 Spring Cloud Alibaba 深度集成。
@SentinelResource 中 blockHandler 和 fallback 有什么区别？优先级如何？
参考：blockHandler 处理 Sentinel 规则触发的 BlockException（限流、熔断、系统保护等），fallback 处理业务异常（Java Exception）。优先级：blockHandler > fallback > 全局兜底。执行顺序：如果 Sentinel 规则触发拦截，优先走 blockHandler；如果是业务异常，走 fallback；如果都没配置，走全局 fallback。blockHandler 方法必须在原方法参数基础上加 BlockException 参数；fallback 方法可以加 Throwable 参数。blockHandlerClass/fallbackClass 可以将处理方法抽取到独立类中，避免与业务代码耦合。
Sentinel 的滑动窗口算法是怎么实现的？为什么不用固定窗口？
参考：Sentinel 使用 LeapArray 实现滑动窗口：将时间窗口划分为多个小 bucket（默认 2 个，每个 500ms），每个 bucket 独立统计计数。统计时根据当前时间定位到对应的 bucket，如果 bucket 已过期则重置并复用。通过跨多个 bucket 累加实现"滑动"效果。不用固定窗口的原因：固定窗口在窗口边界会出现"双倍突发"问题——例如限流 100 QPS，在第一个窗口末尾涌入 100 个请求，第二个窗口开头又涌入 100 个请求，实际上 1 秒内有 200 个请求，超过了限流阈值。滑动窗口通过细分时间片解决了这个问题。
