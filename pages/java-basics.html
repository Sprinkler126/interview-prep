fail-fast 与 fail-safe 机制

fail-fast（快速失败）

非线程安全

  • ArrayList / HashMap / HashSet 等
  • 迭代时检测到结构性修改（modCount 变化）立即抛出 ConcurrentModificationException
  • 内部维护 modCount 计数器
  • 适用于单线程场景

fail-safe（安全失败）

线程安全

  • CopyOnWriteArrayList / ConcurrentHashMap 等
  • 迭代时基于原集合的快照，不会抛出异常
  • CopyOnWrite：写时复制整个数组
  • ConcurrentHashMap：弱一致性迭代器

ArrayList 扩容机制

// 默认初始容量
private static final int DEFAULT_CAPACITY = 10;

// 扩容核心逻辑
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1); // 1.5 倍
    if (newCapacity - minCapacity < 0)
        newCapacity = minCapacity;
    elementData = Arrays.copyOf(elementData, newCapacity);
}

// 关键要点：
// 1. 默认初始容量 10（懒初始化，首次 add 时创建）
// 2. 每次扩容为原来的 1.5 倍（oldCapacity + oldCapacity/2）
// 3. 扩容通过 Arrays.copyOf() 实现数组拷贝（System.arraycopy）
// 4. 指定初始容量可减少扩容次数，提升性能
面试加分点：大容量 ArrayList 预设初始容量可避免多次扩容和数组拷贝。如确定存放 1000 个元素，直接 new ArrayList<>(1000)。

LinkedList 底层结构

// LinkedList 同时实现了 List 和 Deque 接口
public class LinkedList<E> extends AbstractSequentialList<E>
    implements List<E>, Deque<E>, Cloneable, java.io.Serializable {

    transient int size = 0;
    transient Node<E> first; // 头节点
    transient Node<E> last;  // 尾节点

    // 内部节点类：双向链表
    private static class Node<E> {
        E item;
        Node<E> next;
        Node<E> prev;
        Node(Node<E> prev, E element, Node<E> next) {
            this.item = element;
            this.next = next;
            this.prev = prev;
        }
    }
}

// 关键要点：
// 1. 双向链表，持有 first 和 last 引用
// 2. 实现 Deque 接口，可作为双端队列使用
// 3. add(index, element) 会先判断 index 位置再决定从头或尾遍历
// 4. 不支持高效随机访问，get(index) 需遍历到 index 位置

// 核心参数
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4; // 16
static final float DEFAULT_LOAD_FACTOR = 0.75f;
static final int TREEIFY_THRESHOLD = 8;   // 链表转红黑树阈值
static final int UNTREEIFY_THRESHOLD = 6; // 红黑树退化为链表阈值
static final int MIN_TREEIFY_CAPACITY = 64; // 树化最小数组容量

// hash 计算：高 16 位异或低 16 位（扰动函数）
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// put 流程：
// 1. 计算 key 的 hash 值
// 2. 如果 table 为空或长度为 0，执行 resize() 初始化
// 3. 根据 (n-1) & hash 定位桶位置
// 4. 桶为空：直接放入新 Node
// 5. 桶不为空：
//    a. 首节点 key 相同（equals）：覆盖 value
//    b. 首节点是 TreeNode：调用 putTreeVal 红黑树插入
//    c. 链表遍历：尾插法插入，链表长度>=8 且数组>=64 则树化
// 6. 超过 threshold（capacity * loadFactor）则 resize 扩容

HashMap 扩容机制

// resize 核心逻辑
final Node<K,V>[] resize() {
    Node<K,V>[] oldTab = table;
    int oldCap = (oldTab == null) ? 0 : oldTab.length;
    int oldThr = threshold;
    int newCap, newThr = 0;

    if (oldCap > 0) {
        newCap = oldCap << 1; // 容量翻倍
        newThr = threshold << 1; // 阈值翻倍
    }
    // ... 创建新数组，重新 hash 分配
    // JDK 1.8 优化：通过 hash & oldCap 判断元素在新数组的位置
    // 结果为 0：位置不变（原位置）
    // 结果非 0：位置 = 原位置 + oldCap
}
JDK 1.8 扩容优化：不需要重新计算 hash，只需判断新增的那一位 bit 是 0 还是 1。0 则位置不变，1 则位置 = 原位置 + 旧容量。这避免了 JDK 1.7 中扩容时的 rehash 开销。

HashMap 线程不安全问题

JDK 1.7 死循环问题：扩容时采用头插法，并发扩容可能导致链表成环（A→B→A），后续 get 操作死循环。JDK 1.8 改用尾插法解决了此问题。

JDK 1.8 数据丢失：并发 put 时可能出现数据覆盖（两个线程同时写入同一个桶位的空位置），size 不准确（非原子操作）。

解决方案：使用 Collections.synchronizedMap()、ConcurrentHashMap 或 Collections.unmodifiableMap()。

ConcurrentHashMap：JDK 1.7 vs 1.8

JDK 1.7：分段锁（Segment）

Segment + ReentrantLock

  • 数据结构：Segment[] + HashEntry[]
  • 默认 16 个 Segment（concurrencyLevel）
  • 每个 Segment 维护一个 HashEntry 数组
  • 锁粒度：Segment 级别（不同 Segment 可并发写）
  • 并发度 = Segment 数量（默认 16）
  • 不支持 ConcurrentHashMap 扩容时并发

JDK 1.8：CAS + synchronized

Node 数组 + 链表/红黑树

  • 数据结构：Node[] + 链表/红黑树（同 HashMap）
  • 无 Segment，直接对桶头节点加 synchronized
  • 锁粒度：桶级别（Node 级别，更细粒度）
  • 空桶使用 CAS 插入（无锁竞争）
  • 非空桶使用 synchronized 锁头节点
  • 支持并发扩容（多线程协作 transfer）

equals() 与 hashCode() 契约

// 核心契约（Contract）：
// 1. 如果 a.equals(b) == true，则 a.hashCode() == b.hashCode()
// 2. 如果 a.hashCode() == b.hashCode()，a.equals(b) 不一定为 true
// 3. 重写 equals 必须重写 hashCode

// HashMap 中的判断逻辑：
// 先比较 hashCode 定位桶，再比较 equals 确认是否同一个 Key
if (e.hash == hash &&
    (e.key == key || (key != null && key.equals(e.key)))) {
    // 找到相同的 key
}

// 典型错误：只重写 equals 不重写 hashCode
// 导致 equals 相等的两个对象被分配到不同的桶，HashMap 中出现"重复" Key

NIO Buffer 核心操作

// Buffer 使用流程：写入 → flip() → 读取 → clear()/compact()
ByteBuffer buffer = ByteBuffer.allocate(1024);

// 写入数据
channel.read(buffer);  // 或 buffer.put(data)

// 切换为读模式
buffer.flip();  // position=0, limit=写入位置

// 读取数据
while (buffer.hasRemaining()) {
    byte b = buffer.get();
}

// 清空缓冲区
buffer.clear();     // position=0, limit=capacity（完全重置）
buffer.compact();   // 保留未读数据，移到头部

// 核心属性：
// position：当前读/写位置
// limit：读模式下=可读数据量，写模式下=capacity
// capacity：缓冲区总容量
// mark：标记位置，可通过 reset() 回到标记处

传统 IO 与 NIO 对比

传统 IO（Stream）

  • 面向流（Stream）：单向，输入流/输出流
  • 阻塞 IO：read/write 阻塞等待
  • 缓冲区由底层实现，不直接操作
  • 适合少量连接、大量数据传输

NIO（Channel + Buffer）

  • 面向缓冲区（Buffer）：双向，可读可写
  • 非阻塞 IO：Selector 多路复用
  • 直接操作 Buffer，控制读写位置
  • 适合大量连接、少量数据传输

泛型

泛型类型擦除

// Java 泛型是编译期特性，运行时类型信息被擦除
// 编译前：
List<String> list = new ArrayList<>();
list.add("hello");
String s = list.get(0);

// 编译后（类型擦除后）：
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0); // 编译器自动插入强转

// 类型擦除规则：
// - T → Object（无界类型参数）
// - T extends Comparable → Comparable（有界类型参数）
// - 运行时无法获取泛型实际类型参数
类型擦除导致的限制：1）不能 new T()、new T[]；2）不能 instanceof 泛型类型；3）不能创建泛型数组 new List<String>[10]；4）静态成员不能引用类的类型参数。

// ? extends T（上界通配符）：只能读，不能写
// 可以接受 T 或 T 的子类
public void read(List<? extends Number> list) {
    Number n = list.get(0);  // OK：读取为 Number
    // list.add(1);          // 编译错误：无法写入
}

// ? super T（下界通配符）：可以写，读取受限
// 可以接受 T 或 T 的父类
public void write(List<? super Integer> list) {
    list.add(1);             // OK：写入 Integer
    Object o = list.get(0); // 只能读为 Object
}

// 经典用法：Collections.copy
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    // src 是 Producer（extends），dest 是 Consumer（super）
}

反射机制

获取 Class 对象的三种方式

// 方式 1：类名.class（编译时确定）
Class<String> clazz1 = String.class;

// 方式 2：对象.getClass()（运行时获取）
String str = "hello";
Class<?> clazz2 = str.getClass();

// 方式 3：Class.forName()（最灵活，常用于框架）
Class<?> clazz3 = Class.forName("java.lang.String");

// 三种方式获取的 Class 对象是同一个
System.out.println(clazz1 == clazz2); // true
System.out.println(clazz2 == clazz3); // true

反射核心 API

Class<?> clazz = Class.forName("com.example.User");

// 获取构造方法
Constructor<?> constructor = clazz.getDeclaredConstructor(String.class, int.class);
constructor.setAccessible(true); // 暴力反射，可访问 private 构造器
Object user = constructor.newInstance("张三", 25);

// 获取字段
Field nameField = clazz.getDeclaredField("name");
nameField.setAccessible(true);
String name = (String) nameField.get(user);    // 读取字段值
nameField.set(user, "李四");                     // 设置字段值

// 获取方法
Method method = clazz.getDeclaredMethod("getName");
method.setAccessible(true);
String result = (String) method.invoke(user);  // 调用方法

// 获取所有方法/字段
Method[] methods = clazz.getDeclaredMethods();
Field[] fields = clazz.getDeclaredFields();

反射性能开销与优化

操作耗时（相对值）说明
直接方法调用1x编译时绑定，JIT 可内联优化
缓存 Method 对象 + invoke3~5x避免重复查找 Method
每次 getMethod + invoke10~20x每次都查找 Method 对象
setAccessible(true)可减少 ~20%跳过安全检查
优化策略：1）缓存 Constructor/Method/Field 对象；2）调用 setAccessible(true) 跳过访问检查；3）高频场景考虑使用 MethodHandle（JDK 7+）或字节码生成（ASM/CGLIB）。

Stream API

String 不可变性与对比

String 不可变性

  • final char[] value（JDK 9+ 改为 byte[]）
  • final class，不可被继承
  • 字符串常量池复用
  • 线程安全（不可变天然安全）
  • hashCode 缓存（hash 字段）

String / StringBuilder / StringBuffer

  • String：不可变，每次修改创建新对象
  • StringBuilder：可变，非线程安全，性能最优
  • StringBuffer：可变，线程安全（方法加 synchronized）
  • 单线程拼接优先 StringBuilder
  • 多线程拼接使用 StringBuffer

// 自定义注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Table {
    String value(); // 表名
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Column {
    String value(); // 列名
}

// 实体类
@Table("t_user")
public class User {
    @Column("user_name")
    private String name;
    @Column("user_age")
    private int age;
}

// 利用反射自动生成 SQL
public static String generateInsertSql(Class<?> clazz) {
    Table table = clazz.getAnnotation(Table.class);
    StringBuilder sql = new StringBuilder("INSERT INTO " + table.value() + " (");
    StringBuilder values = new StringBuilder("VALUES (");

    Field[] fields = clazz.getDeclaredFields();
    for (int i = 0; i < fields.length; i++) {
        Column column = fields[i].getAnnotation(Column.class);
        if (column != null) {
            if (i > 0) { sql.append(", "); values.append(", "); }
            sql.append(column.value());
            values.append("?");
        }
    }
    sql.append(") ").append(values).append(")");
    return sql.toString();
}
// 生成：INSERT INTO t_user (user_name, user_age) VALUES (?, ?)

反射与依赖注入模拟

// 简易 IoC 容器
public class SimpleContainer {
    private Map<Class<?>, Object> beans = new HashMap<>();

    public <T> T getBean(Class<T> clazz) throws Exception {
        // 1. 检查缓存
        if (beans.containsKey(clazz)) return clazz.cast(beans.get(clazz));

        // 2. 创建实例
        Constructor<T> constructor = clazz.getDeclaredConstructor();
        constructor.setAccessible(true);
        T instance = constructor.newInstance();

        // 3. 依赖注入（字段注入）
        for (Field field : clazz.getDeclaredFields()) {
            Inject inject = field.getAnnotation(Inject.class);
            if (inject != null) {
                field.setAccessible(true);
                Object dependency = getBean(field.getType()); // 递归注入
                field.set(instance, dependency);
            }
        }

        // 4. 缓存并返回
        beans.put(clazz, instance);
        return instance;
    }
}

第三部分：模拟面试

HashMap 的底层数据结构是什么？JDK 1.8 做了哪些优化？
参考：JDK 1.8 中 HashMap 底层是数组 + 链表 + 红黑树。数组默认容量 16，负载因子 0.75。通过 key 的 hashCode 经过扰动函数（高 16 位异或低 16 位）计算 hash，再与 (n-1) 与运算定位桶位。哈希冲突时使用链表存储，当链表长度 >= 8 且数组长度 >= 64 时，链表转为红黑树（O(n) → O(log n)）。当红黑树节点 <= 6 时退化为链表。
JDK 1.8 优化：1）数据结构从数组+链表改为数组+链表+红黑树；2）插入方式从头插法改为尾插法，解决扩容并发死循环问题；3）扩容时通过 hash & oldCap 判断新位置，避免 rehash；4）插入时先插后判断是否扩容（1.7 先判断再插入）。
HashMap 为什么线程不安全？ConcurrentHashMap 如何解决？
参考：HashMap 线程不安全体现在：1）JDK 1.7 并发扩容头插法导致链表成环，get 死循环；2）JDK 1.8 并发 put 可能数据覆盖（两个线程同时写入空桶位）；3）size 非原子操作，并发下不准确。
ConcurrentHashMap 解决方案（JDK 1.8）：1）空桶使用 CAS 插入（无锁）；2）非空桶使用 synchronized 锁头节点（比 1.7 的 Segment 锁粒度更细）；3）size 使用 CounterCell 数组分散竞争（类似 LongAdder）；4）支持多线程协作扩容（transfer）。
追问：为什么不用 Collections.synchronizedMap？ synchronizedMap 对所有操作加同一把锁（synchronized(mutex)），并发度低。ConcurrentHashMap 锁粒度到桶级别，不同桶可并发读写，吞吐量高很多。
ArrayList 和 LinkedList 怎么选？实际开发中 ArrayList 为什么用得更多？
参考：ArrayList 底层数组，O(1) 随机访问，尾部 O(1) 增删（均摊），中间增删 O(n)（数组拷贝）。LinkedList 底层双向链表，O(n) 随机访问，头尾 O(1) 增删，但内存不连续导致缓存命中率低。
实际开发中 ArrayList 用得更多：1）大多数场景是随机访问或尾部增删，ArrayList 更优；2）CPU 缓存友好，连续内存局部性好；3）内存占用少（无额外指针开销）；4）即使中间插入，O(n) 的数组拷贝利用 System.arraycopy（native 方法），实际性能不一定比 LinkedList 差。LinkedList 只在频繁头部插入删除（如实现 Deque）时才有优势。
Java 泛型的类型擦除会带来什么问题？如何在运行时获取泛型类型？
参考：类型擦除导致：1）不能 new T()（编译器不知道 T 的具体类型）；2）不能 instanceof 泛型类型；3）不能创建泛型数组；4）泛型类型的静态变量共享（所有实例共用同一份）。
运行时获取泛型的方式：1）通过反射获取父类的 ParameterizedType：((ParameterizedType) getClass().getGenericSuperclass()).getActualTypeArguments()[0]（如 Guava 的 TypeToken）；2）通过匿名子类保留泛型信息；3）Spring 的 ResolvableType 工具类。
追问：为什么 Java 选择类型擦除而非真泛型？ 为了向后兼容 JDK 1.5 之前的代码，擦除后泛型代码和非泛型代码可互操作。
BIO、NIO、AIO 的区别？什么场景用 NIO？
参考：BIO 是同步阻塞，一个连接一个线程，read/write 阻塞等待。NIO 是同步非阻塞，通过 Selector 多路复用，一个线程管理多个 Channel，Channel 非阻塞读写 Buffer。AIO 是异步非阻塞，OS 完成 IO 后回调通知应用。
NIO 适用场景：大量连接（万级）、每个连接数据量少（如聊天、推送）。典型应用是 Netty 框架（基于 NIO），以及 Nginx、Redis 的 IO 多路复用模型。BIO 适合连接数少、每个连接数据量大的场景（如文件传输）。
追问：Netty 为什么用 NIO 而不用 AIO？ Linux 下 AIO 基于 epoll 模拟实现，性能提升不明显且编程模型复杂。NIO + 多线程 Reactor 模型已经足够高效。
Lambda 表达式的本质是什么？函数式接口有什么要求？
参考：Lambda 表达式本质是函数式接口的匿名实现类的简写。编译后通过 invokedynamic 字节码指令在运行时动态生成实现类（首次调用时通过 LambdaMetafactory 生成，后续调用复用）。相比匿名内部类，Lambda 不会生成额外的 .class 文件。
函数式接口要求：1）有且只有一个抽象方法（SAM：Single Abstract Method）；2）可以有多个 default 方法和 static 方法；3）可以用 @FunctionalInterface 注解标记（编译期检查）。
追问：Lambda 中访问外部局部变量有什么限制？ 局部变量必须是 effectively final（事实上的 final），即初始化后不再修改。这是因为 Lambda 捕获的是变量的副本（值传递），如果变量可变会导致语义混乱。成员变量无此限制（因为通过 this 引用访问）。
try-with-resources 的原理是什么？多个资源关闭顺序是怎样的？
参考：try-with-resources 是 JDK 7 引入的语法糖，自动关闭实现了 AutoCloseable 接口的资源。编译器会在 finally 块中自动生成 close() 调用。如果 try 块和 close() 都抛出异常，close 的异常会被 suppressed（可通过 getSuppressed() 获取）。
多个资源按声明的逆序关闭。即先声明的后关闭，后声明的先关闭。例如 try (A a = ...; B b = ...) 先关闭 B 再关闭 A，因为 B 可能依赖 A。
追问：close() 抛异常怎么办？ close 异常会被添加到 suppressed exceptions 数组中，不会覆盖主异常。可以通过 e.getSuppressed() 获取被压制的异常列表。
Stream 的中间操作和终端操作有什么区别？parallelStream 有什么注意事项？
参考：中间操作（filter/map/sorted 等）是惰性的，返回新的 Stream，不触发实际计算。终端操作（collect/forEach/reduce 等）触发整个流水线执行，执行后 Stream 不可复用。
parallelStream 注意事项：1）底层使用 ForkJoinPool.commonPool()，共享线程池可能影响其他并行任务；2）不适合 IO 密集型操作（线程会阻塞）；3）数据量小时并行开销大于收益（线程调度、拆分合并开销）；4）forEach 顺序不确定，如需有序用 forEachOrdered；5）有状态操作（如 sorted/distinct）在并行流中需要额外同步开销。
追问：什么时候不该用 parallelStream？ 数据量小（< 10000）、操作涉及 IO/锁/共享可变状态、需要保证顺序时。
反射的性能开销来自哪里？Spring 大量使用反射为什么性能还行？
参考：反射性能开销来自：1）方法查找（getMethod/getDeclaredMethod 遍历方法数组）；2）安全检查（每次 invoke 检查访问权限）；3）参数装箱（基本类型自动包装为对象）；4）JIT 无法内联优化（方法调用目标不确定）。
Spring 优化策略：1）启动时缓存所有反射元数据（AnnotatedElementMetadata、BeanDefinition），运行时直接查缓存；2）大量使用 CGLIB 字节码生成（FastClass），避免反射调用；3）AOP 使用动态代理（JDK Proxy 或 CGLIB），将反射调用转为直接调用；4）Spring 6 / Spring Boot 3 引入 AOT 编译，运行时代替编译期生成代码。
