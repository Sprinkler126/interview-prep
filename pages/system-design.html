Step 1：需求澄清

  • 功能需求：明确系统的核心功能和边界，先做 MVP 再扩展
  • 非功能需求：可用性（几个 9）、一致性（强一致/最终一致）、延迟（P99 响应时间）、吞吐量（QPS/TPS）
  • 约束条件：用户规模、数据量级、读写比、地域分布
  • 技巧：先问清楚再动手设计，展示你的沟通能力和系统思维

Step 3-5：概要设计、详细设计与扩展

  • 概要设计：定义 API 接口、设计数据模型（ER 图）、画出系统架构图（客户端→网关→服务→存储）
  • 详细设计：深入核心组件，如缓存策略、数据库分片方案、消息队列使用等
  • 扩展优化：识别单点瓶颈，讨论水平扩展、多级缓存、异步化、数据分片等方案
  • Trade-off：始终讨论方案的取舍，展示工程判断力

读优化策略

  • 多级缓存：浏览器缓存 → CDN → 本地缓存(Caffeine) → 分布式缓存(Redis) → 数据库
  • 读写分离：主库写、从库读，通过 binlog 同步
  • 搜索引擎：将复杂查询下沉到 ES，减轻数据库压力
  • 预计算：热门数据提前计算好，直接查结果

写优化策略

  • 异步写入：写请求先进消息队列，消费者异步处理
  • 批量写入：攒批后批量 insert/update，减少 DB 交互
  • 分库分表：数据水平拆分，分散写压力
  • 写合并：将多次小写合并为一次大写（如计数器合并）

CAP/BASE 理论在实际系统中的应用

CAP 定理

三个特性

  • C（Consistency）一致性：所有节点同一时刻看到相同数据
  • A（Availability）可用性：每个请求都能在合理时间内得到响应
  • P（Partition Tolerance）分区容错：网络分区时系统仍能运行

三种组合

  • CP 系统：放弃可用性，保证一致。如 ZooKeeper、HBase、etcd
  • AP 系统：放弃一致性，保证可用。如 Eureka、Cassandra、DynamoDB
  • CA 系统：不存在分区时的理论情况。如传统单机 RDBMS
分布式系统中网络分区是不可避免的，所以 P 是必选项。实际选择是在 C 和 A 之间权衡。

BASE 理论

  • BA（Basically Available）基本可用：系统出现故障时，允许损失部分功能（如响应时间变长、降级返回非精确数据）
  • S（Soft State）软状态：允许系统存在中间状态，不影响整体可用性
  • E（Eventually Consistent）最终一致性：经过一段时间后，所有节点数据达到一致

BASE 是 CAP 中 AP 的延伸，是大多数互联网系统的设计哲学：牺牲强一致性，换取高可用和高性能。

短码生成策略

哈希方案（MD5/SHA-256）

  • 对长 URL 做哈希，取前 N 位 Base62 编码
  • 冲突时追加随机字符重试
  • 优点：相同 URL 生成相同短码（可去重）
  • 缺点：需处理冲突，哈希计算有开销

自增 ID + Base62

  • 用分布式 ID 生成器获取唯一自增 ID
  • 将 ID 转为 Base62 编码（a-z, A-Z, 0-9）
  • 优点：无冲突，性能好
  • 缺点：相同 URL 每次生成不同短码
// Base62 编码示例
// 字符集：0-9a-zA-Z（共62个字符）
// ID=1000000 → Base62(1000000) → "4c92"
// 7位 Base62 可表示 62^7 ≈ 3.5万亿种组合

String charset = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
public String encode(long id) {
    StringBuilder sb = new StringBuilder();
    while (id > 0) {
        sb.append(charset.charAt((int)(id % 62)));
        id /= 62;
    }
    return sb.reverse().toString();
}

秒杀核心流程

  1. 前端防刷：按钮置灰、验证码、请求签名，防止脚本刷单
  2. Nginx 层限流：限制单 IP 请求频率，静态资源走 CDN
  3. Redis 预扣库存：将库存提前加载到 Redis，用 DECR 原子操作预扣减，库存不足直接返回
  4. 令牌桶限流：控制进入后端的请求速率，超出直接拒绝
  5. 异步下单：预扣成功后发送消息到 MQ，消费者异步创建订单、扣减数据库库存
  6. 数据库兜底：使用乐观锁 UPDATE SET stock=stock-1 WHERE id=? AND stock>0 保证最终一致性
秒杀系统的本质是将高并发读写转化为可控的异步处理。核心思想：前端做拦截，缓存做预扣，MQ 做削峰，数据库做兜底。

Feed 流系统设计

三种 Feed 流模式

推模式（Push / Fan-out）

  • 发布者发帖时，将内容推送到所有粉丝的收件箱
  • 读取时直接查自己的收件箱，读取速度快
  • 缺点：大 V 发帖写扩散严重（百万粉丝 = 百万次写入）
  • 适合：普通用户、粉丝量少的场景

拉模式（Pull / Fan-out on Read）

  • 发布者发帖时只写自己的发件箱
  • 读取时拉取所有关注者的发件箱并聚合排序
  • 缺点：读取慢，需实时聚合大量数据
  • 适合：粉丝量大但关注者少的场景

推拉结合模式（推荐方案）

根据用户粉丝量动态选择策略：

用户类型粉丝量策略
普通用户粉丝 < 5000推模式：发帖时推送到粉丝收件箱
大 V粉丝 ≥ 5000拉模式：读取时实时拉取大 V 的内容

读取流程：收件箱（推模式内容）+ 关注的大 V 最新内容（拉模式）→ 合并排序 → 展示

微博、Twitter 等主流社交媒体都采用推拉结合模式。关键是找到粉丝量的阈值，平衡读写压力。

Feed 流存储设计

  • 发件箱（Outbox）：用户发布的所有内容，按时间倒序存储。可用 Redis Sorted Set（score=时间戳）
  • 收件箱（Inbox）：用户关注的人的内容聚合，推模式下预计算好。Redis List 或 Sorted Set
  • 内容表：帖子/微博正文、图片等，存在 MySQL 或 MongoDB
  • 社交关系：关注/粉丝关系图，可用 Redis Set 或图数据库（Neo4j）

关键设计点

  • 文件分片（Chunk）：大文件切分为固定大小的块（如 64MB），分散存储在不同节点
  • 多副本策略：每个 Chunk 默认 3 副本，分布在不同机架，保证容错
  • 一致性哈希：通过一致性哈希决定 Chunk 存储位置，节点增减时只迁移少量数据
  • 元数据管理：Master 存储文件名→Chunk 列表的映射，单 Master 或多 Master（Raft 选主）
  • 数据校验：每个 Chunk 有 Checksum，读取时校验数据完整性
  • 副本一致性：写入时采用链式复制或并行复制，保证副本数据一致

第三部分：模拟面试

请设计一个短链系统，如何生成短码？如何处理高并发跳转？
参考：短码生成有两种主流方案：1）哈希方案：对长 URL 做 MD5/SHA-256，取前 N 位 Base62 编码，冲突时追加重试；2）自增 ID + Base62：通过分布式 ID 生成器获取唯一 ID，转为 Base62 编码，无冲突且性能好。高并发跳转：使用 Redis 缓存短码→长 URL 映射，命中缓存直接 302 重定向；缓存未命中查 MySQL 并回写缓存。Redis 使用集群模式保证高可用。推荐 302 重定向而非 301，便于统计点击量。
如何设计一个秒杀系统？如何保证不超卖？
参考：秒杀系统的核心是削峰+异步。1）前端拦截：验证码、按钮置灰防重复提交；2）Nginx 限流：限制单 IP 频率；3）Redis 预扣库存：用 DECR 原子操作扣减，库存不足直接返回；4）MQ 异步下单：扣减成功后发消息，消费者异步创建订单；5）DB 兜底：乐观锁 UPDATE SET stock=stock-1 WHERE stock>0。防超卖的关键是 Redis 原子操作+数据库乐观锁双重保障。一人一单可通过 Redis Set 记录已购买用户。
Feed 流系统中推模式和拉模式有什么区别？大 V 问题如何解决？
参考：推模式：发帖时将内容推送到所有粉丝收件箱，读取快但写扩散严重（大 V 百万粉丝 = 百万次写入）。拉模式：发帖只写自己发件箱，读取时实时聚合关注者内容，写入快但读取慢。大 V 问题解决方案：推拉结合模式。普通用户（粉丝少）用推模式，大 V（粉丝多，如 > 5000）用拉模式。读取时合并收件箱（推模式数据）和关注的大 V 最新内容（拉模式数据），按时间排序展示。Twitter 和微博都采用这种方案。
什么是 CAP 定理？实际系统中如何选择？
参考：CAP 定理指出分布式系统中一致性（C）、可用性（A）、分区容错（P）三者最多同时满足两个。由于网络分区不可避免，P 是必选项，实际是在 C 和 A 之间选择。CP 系统（如 ZooKeeper、etcd）保证强一致性但可能在分区时不可用；AP 系统（如 Eureka、Cassandra）保证可用性但数据可能短暂不一致。实际中多数互联网系统选择 AP + 最终一致性（BASE 理论），金融系统则倾向 CP。Nacos 的创新在于同时支持 AP（临时实例用 Distro）和 CP（持久化实例用 Raft）。
如何设计一个分布式文件存储系统？
参考：参考 GFS/HDFS 架构：1）文件分片：大文件切为固定大小 Chunk（如 64MB），分散存储；2）多副本：每个 Chunk 3 副本，分布在不同机架保证容错；3）元数据管理：Master 节点维护文件→Chunk 映射，可使用 Raft 保证高可用；4）一致性哈希：决定 Chunk 分布位置，节点增减只迁移少量数据；5）数据校验：Checksum 保证完整性；6）写入流程：客户端先查 Master 获取 Chunk 位置，直接写入 Chunk Server，采用链式复制保证副本一致。
如何进行容量估算？请估算一个日活 1 亿的短链系统的存储和 QPS。
参考：假设每个用户每天创建 0.1 个短链，访问 10 次。QPS 估算：1亿 × 10 / 86400 ≈ 11,500 QPS（读），峰值约 35,000 QPS。写 QPS：1亿 × 0.1 / 86400 ≈ 115 QPS。存储估算：每天新增 1000 万短链，每条记录约 500 字节（短码+长URL+时间戳），每天约 5GB，一年约 1.8TB。带宽：35,000 QPS × 500 字节 ≈ 17.5MB/s ≈ 140Mbps。这些数量级决定了我们需要 Redis 集群做缓存、MySQL 分库分表做持久化。
什么是限流？常见限流算法有哪些？令牌桶和漏桶有什么区别？
参考：限流是控制请求速率以保护系统的手段。常见算法：1）固定窗口：简单但有临界突发问题；2）滑动窗口：解决临界问题，精度更高；3）漏桶：以恒定速率处理请求，平滑流量但不允许突发；4）令牌桶：以恒定速率生成令牌，请求需消耗令牌，允许一定程度的突发。核心区别：漏桶的输出速率恒定（流量整形），令牌桶允许桶内积累的令牌被一次性消费（允许突发）。实际中令牌桶更常用（如 Guava RateLimiter、Sentinel）。
熔断和降级有什么区别？在微服务架构中如何使用？
参考：熔断：当下游服务错误率超过阈值时，自动切断请求（快速失败），经过冷却时间后进入半开状态试探恢复。类似于电路的保险丝。降级：在系统压力过大时，主动关闭非核心功能或返回兜底数据，保证核心链路可用。区别：熔断是被动触发（下游故障），降级是主动执行（预设策略）。在微服务中：Sentinel/Hystrix 实现熔断，根据慢调用比例/异常比例触发；降级则通过配置中心控制功能开关，如商品详情页降级时隐藏推荐模块。
