Service Mesh 核心价值

  • 基础设施下沉：将服务通信（负载均衡、熔断、重试、mTLS）从业务代码下沉到基础设施层
  • 语言无关：业务代码无需关心通信细节，适用于任何编程语言
  • 零侵入：通过 Sidecar 模式透明拦截流量，业务代码无需修改
  • 统一治理：通过控制平面统一管理所有服务的通信策略

设计动机：Sidecar 是怎么"偷偷"拦截流量的？

设计起点：Service Mesh 的卖点是"零侵入"——业务代码不改，通信治理全部由 Sidecar 接管。要做到这点，必须让进出 Pod 的流量不知不觉地走 Envoy，而不是直连目标。Istio 用 iptables 规则 + init 容器实现透明拦截。

Sidecar 注入与流量拦截全过程

iptables 拦截规则的关键点

  • OUTBOUND 重定向：业务发出的流量 → REDIRECT 到 Envoy 15001（出站监听）
  • INBOUND 重定向：进入 Pod 的流量 → REDIRECT 到 Envoy 15006（入站监听）
  • 排除 Envoy 自身：用 ISTIO_REDIRECT 链 + uid 1337（Envoy 运行用户）排除，否则 Envoy 出去的流量又会被自己拦截 → 死循环
  • 排除控制平面：访问 Istiod、kube-apiserver 的流量不拦截
易错点：iptables 拦截增加一跳，所有流量都过 Envoy，带来约 1-2ms 延迟和额外 CPU。这是 Sidecar 模式的固有代价，也是 Proxyless Mesh（gRPC 直连 xDS）想解决的痛点。

Ambient Mesh — 无 Sidecar 的新模式 (Istio 1.18+)

设计起点：Sidecar 每个 Pod 一个 Envoy，资源开销大、延迟有损耗。Ambient 模式把 Sidecar 拆成两层：ztunnel（每个 Node 一个 L4 代理，做 mTLS）+ Envoy Waypoint（按 Namespace 部署的 L7 代理，按需启用）。

维度Sidecar 模式Ambient 模式
L4 (mTLS)每个 Pod 的 EnvoyNode 级 ztunnel（共享）
L7 (路由/熔断)每个 Pod 的 EnvoyNamespace 级 Waypoint（按需）
资源开销高（每 Pod 一个）低（共享）
延迟+1-2msL4 更低
成熟度生产成熟1.22+ GA，逐步成熟
面试要点：Sidecar 拦截靠 iptables + init 容器，是当前主流。Ambient Mesh 是未来方向——把 L4/L7 拆分，降低资源开销。能讲清这个演进体现对 Service Mesh 的深度理解。

基于 Header 的路由适合内部测试：测试人员在请求头中添加 x-canary-user: true，流量直接导向 v2，其他用户不受影响。

熔断与重试

熔断（Outlier Detection）

  • Istio 的熔断基于 Envoy 的异常检测（Outlier Detection）
  • 当后端实例连续返回 5xx 错误超过阈值时，自动将其从负载均衡池中驱逐
  • 驱逐时间结束后自动恢复探测
  • 可配置最大驱逐比例，避免全部实例被驱逐

重试策略

http:
  - route:
      - destination:
          host: myapp-service
    retries:
      attempts: 3              # 最多重试 3 次
      perTryTimeout: 2s        # 每次超时 2 秒
      retryOn: "5xx,reset,connect-failure,retriable-4xx"
      retryRemoteLocalities: true

Envoy 原理

核心概念

概念说明
Listener监听端口，接收连接。Envoy 至少有一个 Listener（如 15006 端口拦截入站流量）
Route路由规则，根据条件（Header、Path）将请求转发到不同 Cluster
Cluster后端服务集群，包含一组 Endpoint（IP:Port）
Endpoint后端服务实例的具体地址

xDS 协议

  • xDS 是 Envoy 与控制平面（Istiod）之间的配置下发协议
  • LDS：Listener Discovery Service，下发监听器配置
  • RDS：Route Discovery Service，下发路由规则
  • CDS：Cluster Discovery Service，下发集群配置
  • EDS：Endpoint Discovery Service，下发端点列表
  • Istiod 通过 xDS 将配置实时推送给所有 Envoy Sidecar

Sidecar 模式 vs Proxyless Mesh

Sidecar 模式（传统）

  • 每个 Pod 注入 Envoy Sidecar
  • 流量透明拦截（iptables）
  • 语言无关，零侵入
  • 每个 Pod 多一个容器，资源开销增加

Proxyless Mesh（无代理）

  • 应用直接与控制平面通信
  • 通过 SDK 集成 xDS 协议
  • 无 Sidecar，延迟更低
  • 需要应用代码修改（有侵入）

第三部分：模拟面试

什么是 Service Mesh？Istio 的架构是怎样的？
参考：Service Mesh 是一种基础设施层，将服务通信（负载均衡、熔断、重试、mTLS）从业务代码下沉到 Sidecar 代理。Istio 架构分为控制平面和数据平面。控制平面是 Istiod（包含 Pilot 流量管理、Citadel 证书管理、Galley 配置验证）。数据平面是 Envoy Sidecar，注入到每个 Pod 中，拦截所有进出流量。Istiod 通过 xDS 协议将配置下发给所有 Envoy。
Istio 如何实现金丝雀发布？
参考：Istio 通过 VirtualService 和 DestinationRule 实现金丝雀。VirtualService 定义路由规则：1）基于权重：v1 90% + v2 10%，逐步调整比例；2）基于 Header：内部测试人员在请求头加 x-canary-user: true 访问 v2，其他用户访问 v1。DestinationRule 定义服务版本子集（subset）。配合 Ingress Gateway 处理外部流量。优势：无需修改部署配置，纯流量控制。
Istio 的熔断是怎么实现的？
参考：Istio 的熔断基于 Envoy 的 Outlier Detection（异常检测）。在 DestinationRule 中配置：当后端实例连续返回 5xx 错误超过阈值（consecutive5xxErrors: 5），自动将其从负载均衡池中驱逐（eject）。驱逐时间结束后（baseEjectionTime: 30s），Envoy 自动恢复探测。可配置最大驱逐比例（maxEjectionPercent: 50），避免全部实例被驱逐。还可配置连接池限制（maxConnections）。
Istio 的 mTLS 是如何工作的？PERMISSIVE 和 STRICT 模式有什么区别？
参考：mTLS（双向 TLS）要求客户端和服务端都出示证书，实现双向认证和加密通信。Istiod 自动为每个服务签发 SPIFFE 格式的证书，自动轮换。PERMISSIVE 模式同时接受 mTLS 和明文流量，适合从非网格迁移到网格的过渡期。STRICT 模式只接受 mTLS 流量，生产环境推荐。Envoy Sidecar 自动处理 mTLS 握手，应用代码无需关心。
VirtualService 和 DestinationRule 分别是什么？有什么区别？
参考：VirtualService 定义路由规则：根据条件（Header、Path、权重）将请求路由到不同版本的服务。DestinationRule 定义流量策略：连接池大小、熔断规则、负载均衡算法，以及服务版本子集（subset）。关系：VirtualService 管"路由到哪"，DestinationRule 管"到达后怎么处理"。两者配合使用：VirtualService 引用 DestinationRule 中定义的 subset。
什么是 Envoy 的 xDS 协议？
参考：xDS 是 Envoy 与控制平面之间的配置发现协议。包括：LDS（Listener，监听器配置）、RDS（Route，路由规则）、CDS（Cluster，集群配置）、EDS（Endpoint，端点列表）、SDS（Secret，证书）。Istiod 通过 xDS 协议将配置实时推送给所有 Envoy Sidecar，实现配置的动态更新，无需重启服务。Envoy 支持增量 xDS，只推送变更部分。
Istio 和 Linkerd 该怎么选？
参考：Istio 功能最丰富（流量管理、安全、可观测），但资源占用较高、学习曲线陡峭。Linkerd 更轻量（Rust 编写的 Linkerd2-proxy），资源占用低、部署简单，但功能相对较少。选择建议：需要复杂流量管理（金丝雀、熔断、多集群）选 Istio；追求简单轻量、快速上手选 Linkerd。两者都是 CNCF 毕业项目，生产可用。

面试与笔试实战：流量治理中的预算与身份

先用大白话讲机制，再说明故障边界；以下为自编练习，点击答案可展开解析。

机制与易错边界

控制面发规则，数据面处理请求

大白话：Istiod 像交通规则管理处，把路由和安全配置下发；真正转发请求的是代理。Sidecar 与 ambient 是不同数据面部署方式。

边界与易错：不要把旧的 Sidecar 描述当成全部 Istio；ambient 的 L4 与 L7 能力边界不同，具体功能应看部署模式与版本。控制面短暂不可用不必然让所有已有连接立刻中断。

重试要花时间和流量预算

大白话：代理发现可重试失败后再发一次，像重拨电话；每一次尝试都消耗下游容量与总时间。

边界与易错：只对允许重复的操作重试，设置总超时与单次尝试预算；应用和代理同时重试会乘法放大，超时后远端业务仍可能完成。

mTLS 识别工作负载，授权决定能做什么

大白话：双向证书校验帮助双方确认工作负载身份并加密传输；AuthorizationPolicy 再决定该身份可访问哪些路径或方法。

边界与易错：加密通道不自动等于拥有业务权限；还需用户身份和业务授权。追踪上下文也通常仍需应用跨调用传播。

面试追问

控制面挂了，数据面会立即全部停吗？

已有代理通常可以继续使用已下发配置处理流量，但新配置、证书更新、新工作负载接入等会受到影响。回答要区分已建立的数据面能力与持续控制面依赖，并说明持续故障时间的影响。

有代理了为什么链路还断？

代理能观察网络调用，但不知道应用收到请求后发出的某个请求是否属于同一条业务链。检查应用是否透传 trace 上下文、异步线程是否丢失上下文，以及采样和上报配置。
