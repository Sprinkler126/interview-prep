1.1 MVCC 实现

PostgreSQL MVCC 机制

PostgreSQL 的 MVCC 与 MySQL InnoDB 有本质不同：PG 不使用 Undo Log，而是在每个元组 (Tuple) 上直接记录版本信息。

元组隐藏字段

字段含义
xmin插入该元组的事务 ID（创建版本号）
xmax删除/更新该元组的事务 ID（删除版本号），0 表示未删除
ctid元组的物理位置（page, offset），类似行指针
cmin/cmax命令序号，用于同一事务内的命令区分

UPDATE 操作流程

原始 Tuple xmin=100 xmax=0
UPDATE →
原 Tuple xmax=200
标记删除
+
新 Tuple xmin=200 xmax=0
新版本插入

PG 的 UPDATE 实际上是 DELETE + INSERT，旧版本保留在原数据页中。这会导致表膨胀 (Table Bloat)，需要 VACUUM 回收。

VACUUM 机制

  • VACUUM：标记死元组空间为可复用，不回收磁盘空间，不阻塞读写
  • VACUUM FULL：物理重写表，回收磁盘空间，但会锁表
  • Autovacuum：后台自动执行，由 autovacuum_vacuum_threshold 和 autovacuum_vacuum_scale_factor 控制触发条件
  • 死元组：xmax 不为 0 且对所有活跃事务不可见的元组
如果 VACUUM 不及时，dead tuple 堆积导致表膨胀，查询需要扫描更多页面，性能下降。这是 PG 运维的重要关注点。

事务快照 (Snapshot)

-- 查看当前快照
SELECT txid_current_snapshot();

-- 返回格式: xmin:xmax:xip_list
-- xmin: 最小活跃事务 ID
-- xmax: 下一个将分配的事务 ID
-- xip_list: 当前活跃事务 ID 列表
  • 可见性判断：元组 xmin < snapshot.xmin 且不在 xip_list 中 → 可见
  • 元组 xmax = 0 或 xmax 是将来事务 → 未删除，可见

1.2 事务隔离级别

PostgreSQL 事务隔离级别
隔离级别脏读不可重复读幻读实现方式
Read Committed（默认）防止可能可能每条 SQL 获取新快照
Repeatable Read防止防止防止*事务开始时获取快照，全程使用
Serializable防止防止防止SSI (Serializable Snapshot Isolation)

PG 的特殊之处

  • Read Committed：每条 SQL 看到的是该 SQL 开始时的快照，不是事务开始时。同一事务中两次 SELECT 可能看到不同结果
  • Repeatable Read：PG 的 RR 真正防止了幻读（不像 MySQL InnoDB RR 仍有幻读）。遇到冲突会报 could not serialize access due to concurrent update
  • Serializable：使用 SSI 算法，基于快照隔离加序列化冲突检测，不加锁，性能比传统 S2PL 好得多
  • 无读锁：PG 所有隔离级别下 SELECT 都不加锁，依靠 MVCC 快照读

1.3 索引类型

PostgreSQL 索引类型
索引类型适用场景特点
B-tree等值、范围、排序、LIKE 'abc%'默认索引，最通用，支持 NULL
GIN全文搜索、JSONB、数组、HStore倒排索引，适合多值列，@>/? 等操作符
GiST地理空间、范围类型、全文搜索通用搜索树，支持 <@/@>/&& 等操作符
BRIN物理有序的大表（时间序列、自增ID）Block Range Index，极小索引，记录每组页面的 min/max
Hash仅等值查询比 B-tree 小，WAL 支持从 PG 10 开始

GIN 索引详解

-- JSONB 字段创建 GIN 索引
CREATE INDEX idx_data ON my_table USING GIN (data);

-- 支持的操作符
-- @>  包含
-- ?   键存在
-- ?|  任一键存在
-- ?&  所有键存在
-- @?  JSONPath 匹配
-- @@  JSONPath 匹配
  • GIN (Generalized Inverted Index)：内部是 B-tree of keys → Posting List/Tree
  • 支持 gin_trgm_ops 操作符实现模糊搜索 LIKE '%keyword%'
  • fastupdate：延迟批量写入提高写入性能

BRIN 索引

-- 适合时间序列数据
CREATE INDEX idx_created ON logs USING BRIN (created_at)
  WITH (pages_per_range = 32);
  • 每个索引条目记录一组连续页面（默认 128 页）的 min/max 值
  • 索引大小仅为 B-tree 的 1/100 ~ 1/1000
  • 适合数据与物理存储顺序一致的场景（如时间序列）

1.4 JSONB 类型及操作

JSON vs JSONB
特性JSONJSONB
存储格式原始文本二进制（分解的 key-value）
写入速度快（原样存储）稍慢（需解析）
查询速度慢（每次解析）快（预解析）
索引支持不支持 GIN支持 GIN 索引
保留格式保留空格、键顺序不保留，去重键

JSONB 操作符

-- 数据示例
-- { "name": "张三", "age": 28, "tags": ["Java", "Redis"] }

-- 获取值
data->'name'       -- 返回 JSON: "张三"
data->>'name'      -- 返回文本: 张三
data#>'{address,city}'  -- 嵌套路径取 JSON
data#>>'{address,city}' -- 嵌套路径取文本

-- 包含/存在
data @> '{"name": "张3"}'  -- 包含
data ? 'name'               -- 键存在
data ?| '["name","email"]'  -- 任一键存在
data ?& '["name","age"]'    -- 所有键存在

-- 修改
data || '{"email": "z@x.com"}'  -- 合并
data - 'age'                      -- 删除键
data #- '{address,city}'          -- 按路径删除

1.5 窗口函数

窗口函数语法

函数名() OVER (
  [PARTITION BY 分区列]
  [ORDER BY 排序列 [ASC|DESC]]
  [ROWS|RANGE 帧定义]
)
常用窗口函数
函数作用示例
ROW_NUMBER()行号，无并列ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC)
RANK()排名，有并列会跳号1, 2, 2, 4（跳过 3）
DENSE_RANK()排名，有并列不跳号1, 2, 2, 3（不跳过）
LAG(col, n)前 n 行的值LAG(salary, 1) OVER (ORDER BY id)
LEAD(col, n)后 n 行的值LEAD(salary, 1) OVER (ORDER BY id)
SUM() OVER累计/滑动求和SUM(amount) OVER (ORDER BY date ROWS UNBOUNDED PRECEDING)
AVG() OVER滑动平均AVG(price) OVER (ORDER BY date ROWS 6 PRECEDING) — 7日均值
NTILE(n)分成 n 等份NTILE(4) OVER (ORDER BY score) — 四分位
FIRST_VALUE / LAST_VALUE窗口内首尾值FIRST_VALUE(salary) OVER (PARTITION BY dept ORDER BY id)

窗口帧 (Frame) 定义

-- ROWS: 按物理行
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW   -- 当前行及前2行
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW  -- 从头到当前行
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING  -- 当前行到末尾

-- RANGE: 按值范围
RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW

1.6 CTE (Common Table Expression)

普通 CTE

WITH active_users AS (
  SELECT id, name, email
  FROM users
  WHERE status = 'active'
)
SELECT u.name, COUNT(o.id)
FROM active_users u
JOIN orders o ON o.user_id = u.id
GROUP BY u.name;
  • 提高可读性，将复杂查询拆分为逻辑步骤
  • PG 12+ 普通 CTE 可被内联优化（非 MATERIALIZED）

递归 CTE

WITH RECURSIVE tree AS (
  -- 基础查询（锚点）
  SELECT id, name, parent_id, 1 AS depth
  FROM categories
  WHERE parent_id IS NULL

  UNION ALL

  -- 递归查询
  SELECT c.id, c.name, c.parent_id, t.depth + 1
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree ORDER BY depth;
  • 递归遍历树形/层级结构
  • 自动检测循环（防止无限递归）
  • 常用于组织架构、商品分类、评论回复

2.1 扩展机制

PostgreSQL 的可扩展性

PG 的扩展系统是其最大特色之一，通过 CREATE EXTENSION 安装功能模块，无需重新编译。

常用扩展
扩展功能使用场景
pg_stat_statementsSQL 执行统计（调用次数、耗时、行数）慢查询分析、SQL 优化
PostGIS地理空间数据类型和函数LBS、地图应用、地理围栏
pg_trgm三元组模糊匹配LIKE '%keyword%' 高效搜索
pgvector向量相似度搜索AI 向量检索、RAG、推荐系统
TimescaleDB时序数据库扩展IoT、监控、日志数据
pg_partman自动分区管理大表按时间自动分区
uuid-osspUUID 生成函数分布式 ID 生成

pg_stat_statements 使用

-- 安装扩展
CREATE EXTENSION pg_stat_statements;

-- 查看最慢的 SQL
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 重置统计
SELECT pg_stat_statements_reset();

pg_trgm 模糊搜索

-- 安装扩展
CREATE EXTENSION pg_trgm;

-- 创建 GIN 索引
CREATE INDEX idx_name_trgm ON users USING GIN (name gin_trgm_ops);

-- 现在 LIKE '%keyword%' 可以走索引！
SELECT * FROM users WHERE name LIKE '%张三%';

pg_trgm 将文本拆分为三元组（trigram），建立 GIN 索引，使中间匹配也能走索引。

2.2 物化视图

物化视图 vs 普通视图

特性普通视图物化视图
存储不存储数据，每次查询重新计算存储查询结果到磁盘
查询性能与底层查询一致直接读取结果，极快
数据实时性实时需手动 REFRESH 更新
适用场景简化查询复杂聚合报表、BI 查询
 
-- 创建物化视图
CREATE MATERIALIZED VIEW mv_sales_summary AS
SELECT
  date_trunc('month', order_date) AS month,
  product_id,
  SUM(amount) AS total_amount,
  COUNT(*) AS order_count
FROM orders
GROUP BY 1, 2;

-- 创建索引（物化视图支持索引！）
CREATE INDEX idx_mv_month ON mv_sales_summary (month);

-- 刷新数据
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_sales_summary;
  • CONCURRENTLY：刷新时不锁定视图，允许查询（需要唯一索引）
  • 可通过定时任务（pg_cron）自动刷新

2.3 PL/pgSQL 存储过程

PL/pgSQL 示例

-- 存储过程：转账
CREATE OR REPLACE PROCEDURE transfer(
  p_from INT, p_to INT, p_amount NUMERIC
)
LANGUAGE plpgsql
AS $$
BEGIN
  -- 检查余额
  IF (SELECT balance FROM accounts WHERE id = p_from) < p_amount THEN
    RAISE EXCEPTION '余额不足';
  END IF;

  UPDATE accounts SET balance = balance - p_amount WHERE id = p_from;
  UPDATE accounts SET balance = balance + p_amount WHERE id = p_to;

  -- 记录日志
  INSERT INTO transfer_log(from_id, to_id, amount, created_at)
  VALUES (p_from, p_to, p_amount, NOW());

  COMMIT;
END;
$$;

PL/pgSQL 特性

  • 变量声明：DECLARE v_name TEXT;
  • 条件控制：IF ... THEN ... ELSIF ... ELSE ... END IF;
  • 循环：LOOP / WHILE / FOR i IN 1..10 LOOP
  • 游标：DECLARE cur CURSOR FOR SELECT ...;
  • 异常处理：EXCEPTION WHEN ... THEN ...
  • 动态 SQL：EXECUTE 'SELECT ...' USING var;
  • 返回结果：RETURN QUERY SELECT ...

2.5 流复制 vs 逻辑复制 + 分区表

设计动机：为什么 PG 有两种复制？

设计起点：PG 的物理复制（流复制）传数据页的字节流，逻辑复制传逻辑变更（INSERT/UPDATE/DELETE）。两者解决不同问题——流复制做高可用灾备（主备完全一致），逻辑复制做异构数据同步（可跨版本、跨库表、选择性同步）。

流复制 vs 逻辑复制
维度流复制 (Streaming Replication)逻辑复制 (Logical Replication)
复制内容WAL 字节流（物理数据页变更）逻辑变更（行级 INSERT/UPDATE/DELETE）
副本可写❌ 只读（Hot Standby）✅ 可写（可独立修改）
跨版本❌ 主备必须同版本✅ 可跨大版本（升级利器）
跨平台/架构❌ 必须同架构✅ 可跨平台
选择性同步❌ 全库复制✅ 可按表/行过滤（Publication）
一致性强一致（物理字节相同）最终一致（逻辑变更重放）
典型场景高可用灾备、读副本版本升级、跨库同步、数据分发
对应 MySQLbinlog row 模式主从binlog statement 模式 / Canal

逻辑复制核心概念

  • Publication（发布）：源库定义"发布哪些表的变更"
  • Subscription（订阅）：目标库订阅 Publication，建立复制槽
  • Replication Slot（复制槽）：保证源库 WAL 不会被覆盖（订阅方未消费前保留）
  • 限制：不复制 DDL（表结构变更需手动同步）；大对象、序列需特殊处理
易错点：逻辑复制不复制 DDL——源库 ALTER TABLE 后，目标库需手动执行相同 DDL，否则订阅中断。这是逻辑复制运维的主要痛点。

声明式分区表 (PG 10+)

设计起点：PG 9.x 分区要靠"继承表 + 触发器"手动实现，运维复杂。10+ 引入声明式分区，PARTITION BY 一句搞定，优化器自动裁剪分区。

-- 按范围分区（时间序列最常用）
CREATE TABLE logs (
  id BIGSERIAL,
  created_at TIMESTAMP,
  level TEXT,
  msg TEXT
) PARTITION BY RANGE (created_at);

-- 按月分区
CREATE TABLE logs_2026_01 PARTITION OF logs
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE logs_2026_02 PARTITION OF logs
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- 默认分区（兜底未匹配的数据）
CREATE TABLE logs_default PARTITION OF logs DEFAULT;

-- 按列表分区（按地区）
-- PARTITION BY LIST (region)
-- 按哈希分区（均匀打散）
-- PARTITION BY HASH (user_id)
  • 分区裁剪：查询 WHERE created_at > '2026-02-01' 只扫 2 月分区，自动跳过其他
  • 自动分区：用 pg_partman 扩展自动创建未来分区、归档老分区
  • 分区索引：在父表建索引会自动在所有子分区建
  • 优势 vs MySQL：PG 分区是原生的，MySQL 分区限制多（如外键、唯一索引必须包含分区键）
面试要点：PG 分区 + BRIN 索引是时序大数据的黄金组合——分区裁剪减少扫描范围，BRIN 极小索引记录每块 min/max，TB 级时间序列查询毫秒级。这是 PG 在时序/IoT 场景的优势。

🎤第三部分：模拟面试

PostgreSQL 的 MVCC 和 MySQL InnoDB 有什么区别？
参考：PG 在元组上记录 xmin/xmax，UPDATE = DELETE + INSERT（新版本），旧版本留在原表需 VACUUM 清理。InnoDB 原地修改数据页，旧版本写入 Undo Log 通过版本链实现 MVCC。PG 无 Undo Log 但有表膨胀问题；InnoDB 无膨胀但 Undo Log 管理复杂。
追问：PG SELECT 完全无锁，InnoDB 一致性读需构造 ReadView 并沿 Undo 版本链回溯。
PostgreSQL 的窗口函数有哪些？和聚合函数有什么区别？
参考：ROW_NUMBER/RANK/DENSE_RANK（排名）、LAG/LEAD（前后行）、SUM/AVG OVER（滑动聚合）、NTILE（分桶）。区别：聚合函数将多行合并为一行，窗口函数保留每一行并附加计算结果。
PostgreSQL 有哪些索引类型？GIN 索引适合什么场景？
参考：B-tree（默认，通用）、GIN（倒排，适合 JSONB/全文搜索/数组）、GiST（通用搜索树，地理空间/范围类型）、BRIN（块范围索引，时间序列大数据表极小索引）、Hash（仅等值查询）。GIN 索引适合多值列的包含查询（@>/? 操作符）。
什么是 VACUUM？为什么 PostgreSQL 需要它？
参考：PG 的 UPDATE 是 DELETE + INSERT，旧元组成为 dead tuple 占用空间。VACUUM 标记死元组空间可复用，VACUUM FULL 物理收缩表。Autovacuum 后台自动执行。不及时 VACUUM 会导致表膨胀、查询变慢。
追问：VACUUM 不阻塞读写，VACUUM FULL 会锁表。
CTE 递归查询怎么写？有什么应用场景？
参考：WITH RECURSIVE 语法，锚点查询 UNION ALL 递归查询。应用：组织架构树遍历、商品分类层级、路径查找。PG 自动检测循环防止无限递归。
PostgreSQL 的 JSONB 类型有什么优势？怎么索引？
参考：JSONB 二进制存储，支持 GIN 索引，查询性能优于 JSON。操作符：-> 取 JSON、->> 取文本、@> 包含、? 键存在。GIN 索引支持 @>/? 等操作符。
追问：JSONB 适合 Schema 灵活的场景，但大量 JSONB 查询建议迁移到关系列。
PostgreSQL 的物化视图有什么用？怎么保持数据最新？
参考：物化视图存储查询结果，适合复杂聚合报表（BI 查询快）。需手动 REFRESH MATERIALIZED VIEW 更新，CONCURRENTLY 选项不锁表。可通过 pg_cron 定时刷新。
PostgreSQL 和 MySQL 怎么选？
参考：PG 适合：① 需要高级 SQL 功能（窗口函数/CTE/JSONB）；② GIS/向量搜索等扩展需求；③ 复杂数据分析。MySQL 适合：① 互联网 OLTP 场景；② 生态工具链成熟；③ 运维经验丰富。两者差距在缩小，很多场景都能胜任。
