🔬第一部分：技术原理

0. 版本演进 — 从消息队列到流平台

Kafka 版本演进与技术方向
0.8 (2013) — 基础消息队列 · 依赖 ZooKeeper · Producer/Consumer API
0.10 (2016) — 引入 Kafka Streams · 从 MQ 升级为流处理平台 · 0.10.1 引入消息时间戳
1.0 / 2.0 (2017-2018) — Streams API 生产就绪 · 2.0 引入事务和 Exactly-Once · Kafka Connect 改进
2.4 / 2.5 (2020) — Incremental Cooperative Rebalance · MirrorMaker 2 · Static Membership
3.0 / 3.3 (2021-2022) — KRaft 公测→生产就绪 · 去 ZooKeeper · ZooKeeper-less 架构
3.5+ / 4.0 (2023-2024) — KRaft 唯一模式 · ZK 完全移除 · Share Group（预览）· 性能持续优化

技术演进思想

  • 消息队列 → 流平台：0.10 引入 Streams，Kafka 不再只是"消息管道"，而是"流数据基础设施"
  • 依赖外部 → 自治：ZooKeeper 是外部依赖，KRaft 用 Raft 协议让 Kafka 自己管理元数据，启动更快、扩展性更好
  • At-Least-Once → Exactly-Once：2.0 引入事务，实现端到端精确一次语义
  • Stop-the-World → 增量式：Rebalance 从全局暂停演进到增量式，减少对消费的影响

ZooKeeper vs KRaft

ZooKeeper 模式（传统）

  • 外部 ZK 集群管理元数据（Broker 注册、Topic 配置、Leader 选举）
  • Controller 从 ZK 读取/写入元数据
  • 启动慢：需要先连 ZK，再加载元数据
  • 扩展瓶颈：ZK 不支持太多 Partition（<20 万）

KRaft 模式（3.3+ 生产就绪）

  • Controller 节点组成 Raft 集群，自己管理元数据
  • 元数据存在内部 Topic __cluster_metadata
  • 启动快：无需外部依赖
  • 扩展性好：支持百万级 Partition
  • 4.0 起 ZK 模式完全移除

1.2 核心概念

Topic → Partition → Segment 层次结构
Topic — 逻辑消息流（如 order-events），一个 Topic 可有多个 Partition
Partition — 物理分片（P0/P1/P2），有序、不可变、追加写入
Segment — 分区内的文件切片（默认 1GB 或 7 天滚动）
Index + Log + TimeIndex — .index 稀疏索引 + .log 消息文件 + .timeindex 时间索引

关键术语

  • Offset：消息在 Partition 内的唯一递增 ID，从 0 开始，消费者按 offset 消费
  • Replica：每个 Partition 有多个副本（1 Leader + N Follower），分布在不同 Broker
  • Consumer Group：一组消费者共同消费一个 Topic，Partition 分配给组内唯一消费者
  • Rebalance：消费者加入/离开/订阅变化时重新分配 Partition 的过程
  • __consumer_offsets：内置 Topic（50 个 Partition），存储消费者组的消费位移
  • Coordinator：每个 Consumer Group 对应一个 Broker 作为 Coordinator，管理 Rebalance

Segment 文件结构详解

每个 Partition 由多个 Segment 组成，每个 Segment 包含三个文件：

  • .log：实际消息数据，追加写入
  • .index：稀疏索引（每 4KB 一个条目），记录 offset → 文件物理偏移量的映射
  • .timeindex：时间索引，记录 timestamp → offset 的映射，用于按时间查找

查找流程：① 二分查找 .index 定位 offset 所在的 .log 文件位置；② 从该位置开始顺序扫描 .log 找到目标消息。稀疏索引保证了 O(1) 的近似定位 + 小范围顺序扫描。

Log Compaction（日志压缩）

开启 cleanup.policy=compact 后，Kafka 会保留每个 key 的最新值，删除旧版本。效果类似数据库的 changelog：

key1:v1
key2:v1
key1:v2
key2:v2
→ compact →
key1:v2
key2:v2

用途：变更数据捕获（CDC）、数据库镜像、Kafka Streams 的 Changelog Topic。

1.4 副本机制：ISR 与高水位

ISR (In-Sync Replicas) 机制
Leader
LEO=7 HW=5
Follower 1
LEO=6 HW=5
Follower 2
LEO=5 HW=5
Follower 3
LEO=2（落后太多，踢出 ISR）

关键概念

  • LEO (Log End Offset)：每个副本最后一条消息的 offset+1
  • HW (High Watermark)：ISR 中所有副本 LEO 的最小值，消费者只能读到 HW 之前的消息
  • ISR：与 Leader 保持同步的副本集合。Follower 落后超过 replica.lag.time.max.ms（默认 30s）被踢出

Leader Epoch（2.4+）— 解决数据丢失和截断

问题：旧版本中，Follower 重新加入 ISR 时可能截断自己已有的数据（HW 不够精确）。

解决：引入 Leader Epoch 计数器。每次 Leader 变更 epoch+1，Follower 用 epoch 向 Leader 请求正确的截断点，避免不必要的数据丢失。

这是一个典型的"用元数据替代启发式"的改进思路——旧版本靠 HW 推断，新版本直接记录精确的 Leader 变更历史。

ACK 机制

acks行为可靠性性能
0发送即忘，不等确认可能丢消息最高
1Leader 写入即确认Leader 宕机可能丢较高
all ⭐ISR 全部确认最高较低

生产推荐：acks=all + min.insync.replicas=2，保证至少 2 个副本确认。

幂等 Producer 与事务

幂等（enable.idempotence=true，2.0+ 默认开启）：Broker 通过 PID + SequenceNumber 去重，保证单 Partition 内消息不重复。Producer 重启分配新 PID，所以幂等只在单次会话内有效。

事务（2.0+）：跨 Partition 原子写入。流程：initTransactions → beginTransaction → send × N → commitTransaction。Transaction Coordinator 在 __transaction_state 中记录状态。

幂等解决"单 Partition 内不重复"，事务解决"跨 Partition 原子性"。两者结合实现端到端 Exactly-Once。

1.6 Consumer 机制

Pull 模式

Kafka 采用 Pull：消费者主动拉取。优势：消费者掌控速率，不会被压垮。劣势：无消息时空轮询（通过 long poll fetch.max.wait.ms 缓解）。

Rebalance 策略演进

策略版本特点
Range早期按 Topic Partition 范围分配，可能不均
RoundRobin早期所有 Topic 的 Partition 轮询，更均匀
Sticky0.11+尽量保持上次分配，减少迁移
CooperativeSticky ⭐2.4+增量式 Rebalance，不暂停全部消费

旧版 Eager Rebalance 是 Stop-the-World：先释放所有 Partition → 重新分配 → 重新消费。Cooperative（2.4+）只迁移需要变更的 Partition，其余继续消费。

Static Group Membership（2.3+）

设置 group.instance.id，Consumer 重启后保持相同的成员 ID，不会触发 Rebalance（在 session.timeout.ms 内）。适合容器化部署频繁重启的场景。

关键配置

参数默认值说明
max.poll.records500每次 poll 最大消息数，降低可减少处理时间
max.poll.interval.ms300000两次 poll 最大间隔，超时则被认为死亡并 Rebalance

2.7 多数据中心

MirrorMaker 2（2.4+）

基于 Kafka Connect 框架重写，替代旧版 MirrorMaker。功能：Topic 自动发现和同步、Offset 映射、ACL 同步、配额同步。支持 Active-Active 双活和 Active-Passive 灾备。

旧版 MirrorMaker 是简单的 Consumer + Producer，无 Offset 映射、无自动发现。MM2 是 Connect 架构，更可靠更易运维。

🎤第三部分：模拟面试

Kafka 为什么吞吐量这么高？
① 顺序写磁盘（追加写比随机写快 1000 倍）；② Zero-Copy（sendfile 系统调用，数据不经过用户态）；③ Page Cache（利用 OS 页缓存，进程重启不丢）；④ 批量发送 + 压缩（batch.size + linger.ms 攒批，Snappy/LZ4 压缩减少网络）。
Kafka 如何保证消息不丢失？
三个环节——① Producer：acks=all + 幂等 + 重试；② Broker：min.insync.replicas=2 + 多副本 ISR + unclean.leader.election.enable=false；③ Consumer：手动提交 offset，处理完再确认。
Kafka 如何保证消息顺序？
Partition 内有序，跨 Partition 无序。保证顺序：① 同一业务 key 发到同一 Partition（指定 key）；② 单 Partition 单消费者。注意：Producer 重试可能乱序，幂等 Producer（2.0+）允许 max.in.flight.requests.per.connection=5 且不乱序。
Consumer Rebalance 是什么？怎么优化？
消费者变化时重新分配 Partition。旧版 Stop-the-World。优化：① CooperativeSticky（2.4+）增量式；② Static Membership（2.3+）减少重启触发；③ 合理设置 session.timeout.ms。
ISR 机制是什么？
与 Leader 保持同步的副本集合。acks=all 需要 ISR 全部确认。Follower 落后超过 replica.lag.time.max.ms 被踢出。Leader 宕机从 ISR 选举新 Leader。如果 ISR 为空且 unclean.leader.election.enable=true，可能选数据不完整的 Follower（会丢数据，生产建议 false）。
Kafka 和 RabbitMQ 的区别？
Kafka 是"日志型"——追加写磁盘、消费后不删除、高吞吐（百万级/s）、Pull 模式、适合大数据/日志。RabbitMQ 是"传统型"——消费后删除、灵活路由（4 种 Exchange）、低延迟（μs 级）、Push 模式、适合业务消息。大数据选 Kafka，业务消息选 RabbitMQ。
Kafka 如何实现 Exactly-Once？
Producer 端：幂等（PID + SequenceNumber 去重）+ 事务（跨 Partition 原子写入）。Consumer 端：手动提交 + 业务幂等（唯一 ID 去重）。Kafka Streams：processing.guarantee=exactly_once_v2 自动处理。
Kafka 消息积压怎么处理？
紧急：增加消费者（需 ≤ Partition 数）、跳过非关键消息。根本：优化消费逻辑（批量、异步）、增加 Partition。预防：监控 consumer lag。
Zero-Copy 原理？
传统：磁盘→内核→用户态→内核 socket→网卡（4 次拷贝）。Zero-Copy：磁盘→内核→网卡（2 次拷贝），sendfile() 系统调用，数据不经过用户态，减少 CPU 拷贝和上下文切换。
Log Compaction 是什么？
cleanup.policy=compact 时，保留每个 key 的最新值，删除旧版本。用于 CDC、数据库镜像、Streams Changelog Topic。注意：不保证删除所有重复 key，只在 Segment 滚动时压缩。
Leader Epoch 解决什么问题？
旧版本 Follower 重新加入 ISR 时可能截断已有数据（HW 不精确）。Leader Epoch（2.4+）记录每次 Leader 变更的 epoch，Follower 用 epoch 向 Leader 请求正确的截断点，避免不必要数据丢失。思想："用元数据替代启发式"。
Kafka Connect 的架构？
基于 Kafka Connect 框架：Source Connector（数据源→Kafka）、Sink Connector（Kafka→目标）、Converter（格式转换 JSON/Avro）、SMT（消息级转换）。Connector 定义配置，Task 执行实际搬运。Debezium 是最常用的 Source Connector（MySQL CDC）。
Kafka Streams 和 Flink 怎么选？
Kafka Streams：嵌入应用、无需集群、适合简单 ETL/聚合。Flink：独立集群、丰富的 Window/State/CEP、适合复杂实时计算。简单聚合用 Streams，复杂场景（风控、CEP、多流 Join）用 Flink。
Partition 数量怎么选？
① 消费者并行度（Partition ≥ 消费者数）；② 吞吐需求（更多 Partition = 更高并行度，但也有上限）；③ 端到端延迟（Partition 越多，Rebalance 越慢）；④ Leader 选举时间。经验值：单 Topic 不超过 200 个 Partition。
KRaft 和 ZooKeeper 的区别？
ZK 是外部依赖，管理元数据，启动慢，扩展瓶颈（<20万 Partition）。KRaft（3.3+）用 Raft 协议让 Kafka 自己管理元数据，启动快，支持百万级 Partition。4.0 起 ZK 模式完全移除。技术方向：去外部依赖，提升自治能力。
