ZooKeeper vs KRaft

Kafka 传统模式依赖 ZooKeeper 管理元数据（Broker 注册、Topic 配置、Leader 选举）。KRaft 模式（3.3+ 生产就绪）用 Raft 共识协议取代 ZK，Controller 节点管理元数据，启动更快、扩展性更好。

1.2 核心概念

Topic → Partition → Segment 层次结构
Topic — 逻辑消息流（如 order-events）
Partition — 物理分片（P0 / P1 / P2），有序、不可变
Segment — 分区内文件切片（默认 1GB 或 7 天滚动）
Index + Log — .index 稀疏索引 + .log 消息文件

关键术语

  • Offset：消息在 Partition 内的唯一递增 ID，消费者按 offset 消费
  • Replica：每个 Partition 有多个副本（Leader + Follower），分布在不同 Broker
  • Consumer Group：一组消费者共同消费一个 Topic，每个 Partition 只分配给组内一个消费者
  • Rebalance：消费者加入/离开组时，重新分配 Partition 的过程
  • __consumer_offsets：内置 Topic，存储消费者组的消费位移

1.3 存储机制 — 为什么这么快

Kafka 高性能四板斧
① 顺序写磁盘
追加写入 append-only
比随机写快 1000 倍
600MB/s vs 100KB/s
② Zero-Copy
sendfile() 系统调用
磁盘→内核缓冲→网卡
跳过用户态，减少 2 次拷贝
③ Page Cache
利用 OS 页缓存
热数据在内存中

④ 批量 + 压缩
batch.size 攒批发送
linger.ms 等待更多消息
Snappy/Gzip/LZ4 压缩

Zero-Copy 详解

传统：磁盘→内核→用户态→内核→网卡（4次拷贝）
Kafka：磁盘→内核→网卡（2次拷贝，sendfile）

数据不经过应用程序，直接从文件描述符传到 socket，减少 CPU 拷贝和上下文切换。

1.4 副本机制：ISR 与高水位

ISR (In-Sync Replicas) 机制
Leader
LEO=7 HW=5
Follower 1
LEO=6 HW=5
Follower 2
LEO=5 HW=5
Follower 3
LEO=2（落后太多，踢出 ISR）

关键概念

  • LEO (Log End Offset)：每个副本最后一条消息的 offset+1
  • HW (High Watermark)：ISR 中所有副本 LEO 的最小值，消费者只能消费到 HW 之前的消息
  • ISR：与 Leader 保持同步的副本集合。Follower 落后超过 replica.lag.time.max.ms（默认 30s）会被踢出
  • acks=all 时：Producer 发送的消息需要 ISR 中所有副本确认才返回成功
Leader 选举：Leader 宕机后从 ISR 中选择新 Leader。如果 ISR 为空（unclean.leader.election.enable=true），可能选一个数据不完整的 Follower 当 Leader，会丢数据。生产环境建议设为 false。

ACK 机制与可靠性保证

acks行为可靠性性能
0发送即忘，不等确认可能丢消息最高
1Leader 写入即确认Leader 宕机可能丢较高

分区策略

  • 指定 key：hash(key) % partitionNum，同 key 的消息进同一 Partition（保证顺序）
  • 无 key：Sticky 分区（2.4+），一个批次内的消息发到同一 Partition，减少小消息开销
  • 自定义 Partitioner：实现 Partitioner 接口，按业务逻辑路由
幂等 Producer（enable.idempotence=true）：Broker 端通过 PID + SequenceNumber 去重，保证单 Partition 内消息不重复。Producer 重启会分配新 PID，所以幂等只在单次会话内有效。

1.6 Consumer 机制

Push vs Pull

Kafka 采用 Pull 模式：消费者主动拉取消息。优势：消费者掌控消费速率，不会被压垮；劣势：Broker 无消息时消费者空轮询（通过 long poll 缓解）。

Offset 管理

  • 自动提交（enable.auto.commit=true）：定时提交，简单但可能丢消息或重复消费
  • 手动提交：消费完业务逻辑后调用 commitSync() / commitAsync()，生产推荐
  • Offset 存储在 __consumer_offsets 内置 Topic 中（50 个 Partition）
Rebalance 策略对比
策略特点适用场景
Range按 Topic 的 Partition 范围分配简单场景，可能不均
RoundRobin所有 Topic 的 Partition 轮询分配多 Topic 均匀分配
Sticky尽量保持上次分配结果减少 Rebalance 迁移
CooperativeSticky增量式 Rebalance，不暂停全部消费生产推荐，减少停顿
Rebalance 问题：Rebalance 期间整个 Consumer Group 停止消费（Stop-the-World）。优化：① 用 CooperativeSticky 增量式；② 合理设置 session.timeout.ms 和 heartbeat.interval.ms；③ 避免频繁重启消费者。

🎤第三部分：模拟面试

Kafka 为什么吞吐量这么高？
① 顺序写磁盘（追加写入比随机写快 1000 倍）；② Zero-Copy（sendfile 系统调用，数据不经过用户态）；③ Page Cache（利用 OS 页缓存，进程重启不丢）；④ 批量发送 + 压缩（batch.size + linger.ms 攒批，Snappy/LZ4 压缩减少网络）。
Kafka 如何保证消息不丢失？
三个环节——① Producer：acks=all + 幂等 Producer + 重试；② Broker：min.insync.replicas=2 + 多副本 ISR + unclean.leader.election.enable=false；③ Consumer：手动提交 Offset，处理完再确认。
Kafka 如何保证消息顺序？
Partition 内有序，跨 Partition 无序。要保证顺序：① 同一业务 key 的消息发到同一 Partition（指定 key）；② 单 Partition 单消费者。注意：Producer 重试可能导致乱序，max.in.flight.requests.per.connection=1 或开启幂等（5.0+ 允许 <5 且不乱序）。
Consumer Rebalance 是什么？有什么问题？怎么优化？
消费者加入/离开组时重新分配 Partition。问题：Rebalance 期间整个组停止消费（Stop-the-World），可能持续几十秒。优化：① 用 CooperativeSticky 增量式 Rebalance；② 合理设置 session.timeout.ms；③ 避免频繁重启；④ 静态成员（group.instance.id）减少不必要的 Rebalance。
ISR 机制是什么？
ISR（In-Sync Replicas）是与 Leader 保持同步的副本集合。acks=all 时需要 ISR 全部确认。Follower 落后超过 replica.lag.time.max.ms 会被踢出。优势：不需要所有副本确认，只要"跟得上"的确认，兼顾可靠性和性能。Leader 宕机从 ISR 选举新 Leader。
Kafka 和 RabbitMQ 的区别？
Kafka 是"日志型"——追加写磁盘、消费后不删除、高吞吐（百万级/s）、Pull 模式、适合大数据/日志。RabbitMQ 是"传统型"——消费后删除、灵活路由（4 种 Exchange）、低延迟（μs 级）、Push 模式、适合业务消息。简单说：大数据选 Kafka，业务消息选 RabbitMQ。
Kafka 如何实现 Exactly-Once？
Producer 端：幂等（PID + SequenceNumber 去重）+ 事务（跨 Partition 原子写入）。Consumer 端：手动提交 + 业务幂等（唯一 ID 去重）。Kafka Streams：processing.guarantee=exactly_once_v2 自动处理。端到端 Exactly-Once 需要 Source 和 Sink 都支持事务。
Kafka 消息积压怎么处理？
紧急：增加消费者实例（需 ≤ Partition 数）、临时跳过非关键消息。根本：优化消费逻辑（批量处理、异步写入、减少 DB 调用）、增加 Partition 数。预防：监控 consumer lag，设置告警。
Zero-Copy 原理？
传统方式：磁盘→内核缓冲→用户态→内核 socket 缓冲→网卡（4 次拷贝）。Zero-Copy：磁盘→内核缓冲→网卡（2 次拷贝），使用 sendfile() 系统调用，数据不经过用户态，减少 CPU 拷贝和上下文切换。
__consumer_offsets 是什么？
Kafka 内置 Topic（50 个 Partition），存储消费者组的消费位移。消费者提交 Offset 时写入该 Topic（key=groupId+topic+partition，value=offset）。Coordinator 根据 groupId 的 hash 选择 Partition。旧版本依赖 ZK 存储 Offset，新版本全部用 __consumer_offsets。
KRaft 模式是什么？
Kafka 3.3+ 用 Raft 共识协议取代 ZooKeeper。Controller 节点组成 Raft 集群管理元数据。优势：① 启动更快（不需要加载 ZK 数据）；② 扩展性更好（支持更多 Partition）；③ 运维更简单（少一个组件）。生产环境 3.3+ 推荐使用 KRaft。
Partition 数量怎么选？
考虑因素：① 消费者并行度（Partition 数 ≥ 消费者数）；② 吞吐需求（更多 Partition = 更高并行度，但也有上限）；③ 端到端延迟（Partition 越多，Rebalance 越慢）；④ Leader 选举时间（Partition 越多，选举越慢）。经验值：单 Topic 不超过 200 个 Partition，按需扩展。
