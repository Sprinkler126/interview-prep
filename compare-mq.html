消息队列解决的三大问题

🔗 解耦

生产者和消费者不需要知道彼此的存在，通过 MQ 中转。新增消费者无需改生产者代码。

⚡ 异步

非核心链路异步处理。下单后同步调库存+积分+短信太慢，改为发消息异步处理，响应时间从 500ms → 50ms。

📈 削峰

秒杀场景瞬时流量 10 万 QPS，数据库只能扛 5000。MQ 先承接流量，消费者按能力匀速消费，保护下游。

面试话术：Kafka 是"日志型"消息系统，数据追加写入磁盘，消费后不删除，适合高吞吐、大数据量、需要回溯的场景。RabbitMQ 是"传统型"消息代理，消息消费后删除，路由灵活（4种 Exchange），适合业务消息、需要精确路由、低延迟的场景。简单说：大数据选 Kafka，业务消息选 RabbitMQ。

📨 消息队列

做什么：数据的搬运工，负责可靠传输

不做什么：不做复杂计算、窗口聚合、状态管理

关键词：解耦、削峰、异步、广播

🌊 流处理引擎

做什么：数据的加工厂，负责实时计算

不做什么：不做消息持久化和可靠投递

关键词：窗口、聚合、CEP、状态、ETL

面试要点：Kafka 既是消息队列也是流平台（Kafka Streams），但在大数据场景通常只用它做传输层，计算交给 Flink。不要把"消息队列"和"流处理"混为一谈——前者解决"数据怎么传"，后者解决"数据怎么算"。

🎯场景选型指南

📨 选 Kafka
• 高吞吐日志收集（万级 → 百万级/s）
• 大数据管道（Hadoop/Spark/Flink 数据源）
• 需要消息回溯（按 offset 重新消费）
• CDC 数据同步（Debezium + Kafka Connect）
• 典型：日志平台、数据仓库、实时数仓
🚀 选 RocketMQ
• 金融级消息（事务消息、可靠投递）
• 延迟消息（订单超时、定时推送）
• 消息过滤（Tag/SQL 表达式）
• 国内大厂技术栈（阿里系）
• 典型：电商交易、金融支付、物流
🐰 选 RabbitMQ
• 复杂路由规则（Topic/Direct/Fanout）
• 低延迟业务消息（μs 级）
• 企业级 AMQP 合规需求
• 小团队，运维简单优先
• 典型：企业应用、微服务通信、任务队列
📡 选 Pulsar
• 云原生环境，需要存算分离
• 多租户隔离需求
• 跨地域数据同步（Geo-Replication）
• 典型：云平台、SaaS 服务、多数据中心
🌊 选 Flink
• 实时计算（延迟 < 1秒）
• 复杂事件处理（CEP 规则引擎）
• 状态管理（大状态 + Exactly-Once）
• CDC 实时入湖
• 典型：实时风控、实时大屏、实时 ETL
⚡ 选 Spark
• 大规模离线批处理
• 机器学习训练（MLlib）
• 图计算（GraphX）
• 已有 Spark 生态，统一技术栈
• 典型：离线数仓、数据挖掘、模型训练

🎤面试高频对比题

Kafka、RabbitMQ、RocketMQ 怎么选？
参考答案：看场景——大数据/日志/高吞吐选 Kafka（百万级/s，磁盘堆积无压力）；业务消息/低延迟/复杂路由选 RabbitMQ（4 种 Exchange，μs 级延迟）；金融级/延迟消息/事务消息选 RocketMQ（阿里双十一验证，18 级延迟消息）。三者不互斥，大型系统可能同时用 Kafka 做数据管道 + RabbitMQ 做业务消息。
Kafka 为什么吞吐量比 RabbitMQ 高？
参考答案：四个原因——① 顺序写磁盘：Kafka 追加写入，比随机写快 1000 倍；② 批量发送：Producer 攒一批消息一起发，减少网络开销；③ Zero-Copy：sendfile 系统调用，数据直接从磁盘到网卡，不经过用户态；④ Pull 模式：消费者按需拉取，Broker 不需要维护推送状态。RabbitMQ 是单条投递 + 内存操作，延迟低但吞吐量上不去。
Flink 和 Spark Streaming 最本质的区别是什么？
参考答案：计算模型不同。Flink 是真正的流处理，数据逐条到达逐条处理，延迟 ms 级。Spark Streaming 是微批处理，把流数据切成小批次（如 1 秒一批），本质上还是批处理，延迟秒级。这个本质区别导致：Flink 天然支持 Event Time 和 Watermark 处理乱序数据，有完善的 State 管理和 Checkpoint 机制。Spark Structured Streaming 虽然也在改进，但在低延迟和状态管理上仍不如 Flink。
消息队列如何保证消息不丢失？
参考答案：三个环节都要保证——
① 生产者：Kafka 用 acks=all + 幂等 Producer；RabbitMQ 用 Publisher Confirm；RocketMQ 用同步发送 + 重试。
② Broker：Kafka 多副本 ISR + min.insync.replicas=2；RabbitMQ 消息持久化（durable + deliveryMode=2）；RocketMQ 同步刷盘 + 主从同步。
③ 消费者：手动提交 Offset/ACK，处理完再确认。不要用自动提交，否则消息处理失败就丢了。
什么是消息积压？怎么处理？
参考答案：消费者处理速度跟不上生产速度，导致消息在队列中堆积。
紧急处理：① 增加消费者数量（加机器）；② 增加分区数（Kafka）或队列数（RabbitMQ）；③ 消费者跳过非关键消息。
根本解决：① 优化消费逻辑（减少 DB 查询、批量处理）；② 消费者并行消费（多线程）；③ 架构优化（读写分离、异步处理）。
预防：监控消费延迟（Kafka lag），设置告警阈值。
Kafka 的 ISR 机制是什么？
参考答案：ISR（In-Sync Replicas）是与 Leader 保持同步的副本集合。Producer 发送消息时，需要 ISR 中所有副本确认才算写入成功（acks=all 时）。如果 Follower 同步太慢（落后超过 replica.lag.time.max.ms），会被踢出 ISR。ISR 机制的优势：不需要所有副本都确认，只需要"跟得上"的副本确认，兼顾了可靠性和性能。如果 Leader 宕机，从 ISR 中选举新 Leader，不会丢数据。
Flink 的 Checkpoint 和 Spark 的 Checkpoint 有什么区别？
参考答案：Flink 的 Checkpoint 基于 Chandy-Lamport 分布式快照算法，通过 Barrier 对齐实现全局一致性快照，支持 Exactly-Once 语义，且对正常处理的影响很小（异步增量快照）。Spark 的 Checkpoint 是血缘截断，将 RDD 持久化到 HDFS，主要用于容错和切断过长的血缘链。两者目的不同：Flink Checkpoint 是为了故障恢复时保证状态一致性，Spark Checkpoint 更多是为了优化计算和容错。
Pulsar 的存算分离架构有什么优势？
参考答案：Pulsar 把 Broker（计算层）和 BookKeeper（存储层）分离。优势：① 扩容无需迁移数据：加 Broker 直接用，数据在 BookKeeper 上不动；② 独立扩展：计算瓶颈加 Broker，存储瓶颈加 Bookie；③ 故障恢复快：Broker 无状态，挂了直接启动新的，不需要恢复数据。对比 Kafka：Kafka 的 Broker 既计算又存储，扩 Broker 需要 Rebalance 迁移 Partition，耗时且影响性能。
